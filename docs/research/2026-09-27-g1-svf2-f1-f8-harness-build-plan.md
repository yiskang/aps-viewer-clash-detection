## 4. Mandatory corrections from the diagnostic-harness review

### 4.1 Fail-closed format classifier (fixes Finding 1)

Replace the diagnostic script's ambiguous `if (otgTrue || svf2True)` with an explicit state machine evaluated **once, immediately after the load-done wait, before any F1–F8 check runs**:

```
readFormat(model):
  otg  = typeof model.isOTG  === 'function' ? model.isOTG()  : UNAVAILABLE
  svf2 = typeof model.isSVF2 === 'function' ? model.isSVF2() : UNAVAILABLE

  if otg === true  and svf2 === true  → CONFIRMED_SVF2
  if otg === false and svf2 === false → CONFIRMED_NON_SVF2
  if otg !== svf2 and both are boolean → CONTRADICTORY          // otg/svf2 disagree — never silently pick one
  if exactly one of {otg, svf2} is UNAVAILABLE and the other is boolean →
        INDETERMINATE_PARTIAL(available_signal, available_value)
  if both are UNAVAILABLE → INDETERMINATE_UNAVAILABLE
```

This is deliberately **not** an OR (either flag true is enough) or a bare AND (both must be true, with no room for one API being absent) — it distinguishes five outcomes instead of collapsing them into H1/H2/H4, and never treats a single available signal as sufficient to declare SVF2 confirmed when the design's own vocabulary (`isOTG` **and** `isSVF2`) implies both are meant to be checked. Only `CONFIRMED_SVF2` authorizes proceeding to F1–F8 as "verified under SVF2." `CONTRADICTORY` and both `INDETERMINATE_*` states stop the run and are reported as harness/environment findings (per the G1 authorization's "no production fixes during G1" §), never guessed closed. `CONFIRMED_NON_SVF2` reproduces the original G1 BLOCKED disposition (D3-consistent) and also stops before F1–F8.

### 4.2 Preserve `Document.load` failure detail (fixes Finding 2)

The load-failure branch retains the full structured rejection object, not just a stringified message:

```js
Autodesk.Viewing.Document.load(
  'urn:' + urn,
  (doc) => resolve(doc),
  (code, message, errors) => reject({ code, message, errors: errors ?? null }),
);
```

and the harness records `{ code, message, errors }` — passed through the bounded serializer below — into `loadError` (plus, separately, the model/document context: URN, initializer options, viewer version) rather than `String(err.message || err)`. Same discipline applies to `loadDocumentNode`'s rejection path, which the diagnostic script never even attempted to capture structurally.

**Bounded, JSON-safe, secret-redacting error serializer (new — fixes this round's own internal-review High #7):** "verbatim" never means "whatever `JSON.stringify` happens to accept" — Viewer/network error objects can carry circular references, typed arrays, non-JSON values, large response bodies, or a signed derivative URL with embedded credentials, any of which could throw during the atomic evidence write (§8) or leak a credential into a durable, committed `docs/research/evidence/` artifact. Every error object retained anywhere in this harness's evidence (`loadError`, `errorLedger` entries, `cleanupFailures`, control/check `reason` fields) is passed through one shared `describeError(e)` helper (already named in §4.3's cleanup snippet; this is its full, normative contract) that:
- allowlists scalar fields only (`name`, `message`, `code`, `reason`, `stack` truncated to a fixed byte cap) plus a bounded, depth-capped walk of a typed error's own known structured fields (`errors`, `details`, `limit`, `requested`) — never an unbounded generic object walk;
- caps recursion depth and total serialized size per error (informational fields beyond the cap are replaced with a `truncated: true` marker, never silently dropped without a trace);
- detects and breaks circular references (a `WeakSet`-tracked visited-node guard) rather than letting `JSON.stringify` throw;
- normalizes typed arrays/`Error` instances/`DOMException`-shaped objects to plain, serializable structures;
- **redacts** any string value matching a bearer-token/`Authorization`-header/cookie shape, and strips known-sensitive query parameters (e.g. a signed derivative URL's own signature/token parameters) from any retained URL, replacing each redacted span with a fixed placeholder and recording that a redaction occurred (a `redactions: [...]` list, never silently invisible).

"Verbatim" therefore means **the sanitized, structured representation this serializer produces**, plus its own truncation/redaction ledger — never the raw, unbounded object graph.

**Disposition of this rejection (answers this remediation's own Q4 — §6.3's overall-verdict precedence, branch 1 vs. branch 2):** a `Document.load`/`loadDocumentNode` rejection via this **own structured error callback** (as opposed to a bare timeout, §6.4, or a harness-side setup failure) is, by itself, a classifier-level "never confirmed" outcome — `classifier = INDETERMINATE_UNAVAILABLE` with `loadOutcome:'failed'` and the full `loadError` retained — which routes to §6.3's branch 2, `BLOCKED`, **not** branch 1's `FAIL`. It escalates to branch 1 (`FAIL`, fatal) only if the rejection's own `code`/`message` independently identifies one of §6.6's fatal categories (for example, the rejection says the Viewer script itself never initialized, or names a required-resource failure) — in which case that fatal condition, not the mere fact of a load rejection, is what triggers `fatalErrorObserved`. A model-specific, non-fatal load rejection (e.g. the URN being momentarily unavailable) stays `BLOCKED`: it says nothing about whether the *harness itself* is broken.

### 4.3 Failure-safe cleanup (fixes Finding 3)

Cleanup is modeled directly on T3's own pattern (`clashtest-viewer-adapter.acceptance.mjs`'s `H_CLEANUP`, already reviewed and accepted): a `resources` record whose fields start `null` and are set only once real, and an ordered list of independently-guarded steps, each wrapped so **one step's failure never prevents a later step from running**:

```js
const failures = [];
async function step(name, guard, fn) {
  try { if (!guard()) return; await fn(); }
  catch (e) { failures.push({ step: name, error: describeError(e) }); }
}
// steps run unconditionally in order, regardless of prior step outcome:
await step('removeF3Listeners', () => resources.f3Listener, () => viewer.removeEventListener(evName, resources.f3Listener));
await step('closePage',    () => resources.page,    () => resources.page.close());
await step('closeContext', () => resources.context, () => resources.context.close());
await step('closeBrowser', () => resources.browser, () => resources.browser.close());
```
`browser`/`context`/`page` are created and assigned into `resources` immediately as each is obtained (not held only in local `const`s created before a `try`, which was Finding 3's exact defect) so a mid-setup throw still leaves whatever was created reachable for cleanup. Primary check failures (`result.checks`, `result.disposition`) are computed and written to the report **before** cleanup runs and are never overwritten or suppressed by a cleanup failure; `result.cleanupFailures` is a separate array, always present (possibly empty), exactly mirroring T3's `primary-error / cleanupFailures` separation that the independent review's codex-review pass praised in T3 and found missing here.

| Step | Timeout constant | On timeout |
|---|---|---|
| Initializer ready | `INIT_TIMEOUT_MS = 30_000` | **corrected (fixes C3's `HARNESS_ERROR` inconsistency):** sets `fatalErrorObserved = true` with reason `initializer-never-ready` (a required-resource-style setup failure, per §6.6) and proceeds directly to Phase 11 cleanup; `computeOverall()`'s branch 1 (§6.3) then yields `FAIL` — no separate `HARNESS_ERROR` value exists anywhere in the schema |
| `Document.load` + `loadDocumentNode` (initial) | `LOAD_TIMEOUT_MS = 180_000` (matches T3's own constant) — enforced **in-page** as an absolute `performance.now()` deadline stored on each load's own browser-owned record (§6.4a "Browser-owned load record"), checked by the in-page timer and by every in-page callback; Node keeps only a `LOAD_TIMEOUT_MS + LOAD_BACKSTOP_MARGIN_MS` (`= 15_000`) backstop for an unresponsive page | classifier = `INDETERMINATE_UNAVAILABLE` with `loadOutcome:'timed-out'`, set from the in-page decision returned by `START_LOAD` (never re-derived later); **not** itself `fatalErrorObserved` (a load timeout is a classifier-level "never confirmed," §6.3 branch 2 → `BLOCKED`, unless the underlying cause is independently also a §6.6 fatal category, e.g. the Viewer script itself never loaded — in which case branch 1 already caught it); proceed to cleanup, where the load record is sealed, drained by value, and — if still unsettled — abandoned at page teardown (§4.3 steps 1, 20a; §6.4b) |
| `awaitObjectTree` settling, as observed by F3 (and by F6's reload probe, step 7) | `READINESS_TIMEOUT_MS = 60_000` (informational — the Adapter's own `resolveRoots` call in Phase 4 has its own internal wait; this is the F3/F6 *observation* deadline, not a change to Adapter behavior) | F3 (or F6) verdict = `FAIL` with reason `readiness-never-settled`, per F3's own text ("record ... whether the existing readiness gate is sufficient" — a hang IS a sufficiency answer, recorded not silently dropped) |
| Each single-shot read-only Fi (F1/F2/F5) | `CHECK_TIMEOUT_MS = 30_000` per check | that Fi = `FAIL` with reason `check-timed-out`; independent checks continue per §6.2 |
| F4/F7/F8 full-census work (fixes H6; F4 moved here — fixes I2) | `CENSUS_TIMEOUT_MS = 120_000` per check — larger than `CHECK_TIMEOUT_MS` because these three checks each perform a deterministic full census over the population (F4: every distinct geometry id; F7/F8: every root/fragment relationship), not a bounded sample, and no existing performance contract sets a stricter deadline for exhaustive geometry-buffer adaptation. **Actually interruptible (fixes H1's concrete gap):** each census is chunked per §6.4a's in-page absolute-deadline-check-and-macrotask-yield discipline (`CENSUS_YIELD_BATCH_SIZE`), so this timeout can genuinely stop the loop rather than merely being observed after a synchronous pass already ran to completion | that check = `NOT_EVIDENCED` (not `FAIL`) with reason `census-incomplete`, plus the exact processed/total counts actually reached — a census timeout on a large-but-otherwise-healthy fixture is incomplete evidence, not itself proof of a collision-layer regression (fixes I2's exact concern). The census's own token transitions `timed-out`, feeding the pre-phase drain gate (§6.4a) before the next phase begins |
| Unload settling (`X_GONE` poll) | `UNLOAD_TIMEOUT_MS = 30_000` | F6 = `FAIL` with reason `unload-never-observed`; do not attempt reload |
| Reload settling (`Y_APPEARED` poll) | `RELOAD_TIMEOUT_MS = 180_000` | F6 = `FAIL` with reason `reload-never-observed` |

On any timeout, whatever partial evidence a check produced up to that point is retained in its `evidence` field (never discarded), the check's own verdict reflects the timeout explicitly (never silently reported as the same shape as a clean PASS/FAIL), and the harness always proceeds to Phase 11 rather than aborting the process — matching §4.3's "cleanup must continue after another cleanup action fails" discipline extended to the primary-evidence phases as well.

### 6.4a Per-operation tokens, cancellation/drain, and late-completion quarantine (fixes H4; corrected — fixes I1 from the targeted re-review; corrected again — fixes H1 from the bounded re-review)

The independent Work review found that a timed-out check's own promise is left running: `resolveRoots` calls, Viewer load callbacks, and F6's own unload/reload waits are not cancelled just because the harness moved on, so a late completion can still write into `result` or mutate the shared `world`/`registry`/`model` state during a *later* phase. The **bounded re-review's "H1"** found this still holds even after per-operation tokens (below) were introduced: a token only quarantines *result publication*, never the underlying work itself, and — for a single synchronous in-page loop (F4/F7/F8's own census) — a timer cannot interrupt a loop that never yields, no matter how the token is checked.

**Per-operation tokens (fixes I1):** one per distinct asynchronous operation the harness starts, each with an explicit state machine `active → (completed | timed-out | disposed)`, plus exactly one post-teardown transition reserved for Viewer-load tokens, `timed-out → abandoned` (§4.3 step 20a; defined in "Browser-owned load record," below). `abandoned` is terminal, because its owning page realm is confirmed destroyed and no continuation can ever run again. It is **not** a clean terminal state. Every existing call site that tests for `completed`/`disposed` deliberately keeps treating it as unresolved: §4.3's token-row guard, the pre-phase drain gate below, and the `late-completion-after-timeout` control's "confirmed `disposed`" requirement. It can only arise after §4.3 step 18, so no pre-Phase-11 call site can ever observe it. A load token still `active` when Phase 11 begins is first moved `active → timed-out{reason:'cleanup-preempted'}` (§4.3 step 1a), so no load token can be left in a state step 20a cannot finalize. A **distinct, independently-tracked token** is minted for each of: the initial `Document.load` call, the initial `loadDocumentNode` call, each read-only Fi's own primary operation (F1's `resolveRoots`, F2's tree walk, F4's per-geometry census, F5's limit check, F7's per-dbId census, F8's per-relationship census), the unload wait, the reload's `Document.load` call, the reload's `loadDocumentNode` call, and (new, fixes C1) each mandatory control's own operation. No two operations ever share a token. Every continuation of a token's operation — a `.then()`, an event-listener callback, a `waitForFunction` resolution — checks `if (token.state !== 'active') return;` as its **first statement**, before touching `result`, `viewer`, `world`, or `registry` — where "`token`" is always the object **in the same realm as the continuation**. Node-side continuations (a Playwright promise resolution) check the Node-side token. **In-page** continuations (a Viewer `Document.load`/`loadDocumentNode` callback) check only the browser-owned load record `window.__g1.loads[tokenId]` (below), because a Node-side token is unreachable from page code: an in-page function "may reference only its argument and page globals" (`test/acceptance/clashtest-viewer-adapter.acceptance.mjs:176`). A continuation that fails this check is silently dropped **from primary evidence** but is separately counted, per-token, in a diagnostic-only `result.staleContinuationsDropped` list (`{tokenId, operation, phase}`, visible, never hidden, but never itself a FAIL reason on its own). On that specific operation's own timeout, its token (and only its token) transitions `active → timed-out`; no other token is affected, regardless of what else happens to be in flight. **The two-stage `Document.load`/`loadDocumentNode` lifecycle gets two tokens, explicitly linked**: `loadDocumentNode`'s token is only minted once `Document.load`'s own token reaches `completed`; if `Document.load`'s token times out first, `loadDocumentNode`'s token is never minted at all.

**Three-way cancellation classification (new — fixes H1):** every asynchronous operation the harness starts is classified, at design time, into exactly one of:

- **A. Cancellable** — the underlying API offers a real cancel/abort primitive. Playwright's own `page.waitForFunction`/`page.waitForEvent` (used by F3's/F6's readiness probes, the unload/reload settling polls) accept an `AbortSignal` or reject-on-timeout; on timeout the harness calls `abort()` and, where the API provides one, awaits the cancellation's own acknowledgement (Playwright's rejected promise settling) before the token transitions to `disposed`. These are cancelled outright, never merely poisoned.
- **B. Non-cancellable, but drainable** — the underlying Viewer API has no cancel primitive (`Document.load`/`loadDocumentNode`'s callback-based API has no `abort()`), but the harness's *own* code around it can be made to stop touching shared state deterministically. On timeout: (1) mark the token `timed-out` (blocks result publication, as before); (2) rely on late-arrival handling that was attached **at call time** so a late completion cannot leave stray state. For Viewer loads this is the in-page load record's own callbacks (below). It is never installed afterward from Node, which cannot reach page code; (3) **before the harness enters any later phase that shares mutable resources with this operation** (the next `Xc` control, or F6 — per §6.1's phase table), require this token to have reached a terminal state (`completed` or `disposed`) — i.e., explicitly await it (for a Viewer-load token, by the value-only `drainLoadToken` poll defined below; bounded by a `DRAIN_TIMEOUT_MS = 15_000` grace period on top of the operation's own timeout), not merely leave the late-arrival handler installed and move on. F1/F2/F4/F5/F7/F8's own primary operations, and every mandatory control's operation, are Category B: their per-item loops (below) make them drainable even though the underlying Viewer read calls themselves have no abort.
- **C. External, cannot safely be drained** — an operation whose completion the harness cannot observe or bound at all (none exists in this design today, since every operation above is either Category A or B; this classification is retained for completeness and for rejecting any future addition that doesn't fit A/B). If a future operation is Category C: the check/phase depending on it is classified `FAIL` or `BLOCKED` (never left ambiguous), the harness stops reading the contaminated resource/session immediately, cleanup (§4.3) still runs to completion, and the harness never proceeds to a later phase carrying evidence that assumes that resource is clean.

**Per-item deadline checks and yields inside census loops (corrected — fixes H1's concrete "single synchronous loop cannot be interrupted" gap; corrected again — fixes this round's own targeted internal review, "a microtask yield cannot release timer/task-queue callbacks"):** the prior text relied on an externally-flipped token being observed by an `await Promise.resolve()` yield — but `Promise.resolve()` only yields to the *microtask* queue, and a loop that repeatedly awaits an already-resolved promise can starve the *macrotask*/timer queue indefinitely, so the very timer meant to flip the token might never get a turn to run. It also left unclear which JS realm (Node or the page) owns the token, when the census itself executes entirely inside one `page.evaluate` call — a Node-side `setTimeout` cannot reach into that realm to mutate an in-page value without an explicit message.

The corrected design removes the cross-realm dependency entirely: F4's per-geometry census, F7's per-dbId census, and F8's per-relationship census each capture their own **absolute, monotonic in-page deadline** at operation start — `const deadline = performance.now() + CENSUS_TIMEOUT_MS;`, computed and checked **entirely inside the same `page.evaluate` closure**, never requiring a Node-side timer to reach across realms. The loop is chunked (never a single unbroken synchronous pass): after every `CENSUS_YIELD_BATCH_SIZE = 200` items, it (a) checks `if (performance.now() >= deadline) return { timedOut: true, processed, total };` — a direct, synchronous comparison, never dependent on a timer callback having already fired — and (b) yields with a genuine macrotask break, `await new Promise(resolve => setTimeout(resolve, 0))` (not `Promise.resolve()`), so the page's own event loop, rendering, and any other pending task-queue work actually get a turn between batches. The in-page function's own return value (`{timedOut, processed, total}` vs. the normal success shape) is what the outer Node-side Playwright call reads to set that operation's own per-operation token to `timed-out` with the exact processed/total counts (§6.4's `NOT_EVIDENCED` disposition) — the token's Node-side bookkeeping is a **report of what the in-page loop already decided**, never the mechanism that stops the loop. Playwright's own outer call additionally keeps its generic `CENSUS_TIMEOUT_MS`-plus-margin wall-clock bound as a backstop only, for the pathological case where the in-page code itself hangs before ever reaching a deadline check (e.g. inside a single `await getRenderProxy(...)` call that never settles) — that backstop is a Category-B "non-cancellable, drain via the one-shot late-arrival handler" case, not the primary interruption path. **Required (fixes this round's own internal-review Medium #8):** an offline, browser-free test must prove a loop respecting this exact deadline-check-and-yield pattern actually terminates early when its deadline is set below its own total work, independent of any live Viewer/SVF2 run.

**Pre-phase drain gate (new — fixes H1's "before starting a patching control or F6" requirement):** immediately before every `Xc` control phase (3c/4c/5c/7c/8c, §6.1) and before F6 (Phase 10) begins, the harness enumerates every token still in `timed-out` state whose operation could still read or mutate the shared `world`/`registry`/`modelBefore`. For each: Category A tokens are already cancelled (nothing to wait for); Category B tokens are awaited up to `DRAIN_TIMEOUT_MS`. If any token cannot be confirmed `completed`/`disposed` within that grace period, the gate does **not** proceed optimistically — the dependent phase(s) are marked `BLOCKED{reason:'undrained-timeout:<tokenId>'}` (Fi checks) or `NOT_EXECUTABLE{reason:'undrained-timeout:<tokenId>'}` (controls, §6.3a), and the harness proceeds directly to Phase 11 cleanup rather than continuing concurrently with unresolved background work.

**Browser-owned load record and realm-split late-arrival handling (replaces the prior "Document-load vs. loadDocumentNode late-arrival handling" paragraph — fixes the fresh bounded re-review's "H1"):** the prior paragraph correctly distinguished a late `Document` from a late `Model`, but it never said which realm runs the handler or how that handler learns the operation timed out. §6.4b then guarded both handlers with `page.isClosed()`. That is a Node-side Playwright method (`node_modules/playwright-core/types/types.d.ts:3707`, `isClosed(): boolean` on `Page`) and does not exist inside a Viewer callback. The corrected design assigns every resource and action to exactly one realm and never passes a live object across:

| Realm | Owns | Never does |
|---|---|---|
| **Playwright/Node** | `browser`/`context`/`page`; the Node-side per-operation tokens; outer backstop timers; `closeIntent` (§6.6); `result`, evidence, `cleanupFailures`; the atomic write (§8) | touch a `Document`, `Model`, `viewer`, or in-page record as a live object — it only sends JSON-safe arguments into, and reads JSON-safe return values out of, `page.evaluate`/`page.waitForFunction` |
| **Browser/Viewer** | the Viewer instance; `Document.load`/`loadDocumentNode` calls and all their callbacks; the in-page `LOAD_TIMEOUT_MS` deadline; the load records; `window.__g1.closing`; every `viewer.unloadModel()` of a late or unclaimed model | read any Node-side value (a token, `closeIntent`, `page`) — it learns Node's intent only from an argument or a page global Node wrote via an earlier `page.evaluate` |

Value passing only is this repository's existing convention. T3 keeps every live object in `window.__t3` and returns plain results (`clashtest-viewer-adapter.acceptance.mjs:181-185,519-524,839`). The diagnostic keeps `window.__viewer`/`window.__diag` in-page (`g1-svf2-initializer-diagnostic.mjs:72-79,124`). It is also Playwright 1.62.1's own contract (`package.json:48`; `node_modules/playwright/package.json:3`): `page.evaluate` waits for a returned promise, and a non-serializable return value resolves to `undefined` (`node_modules/playwright-core/types/types.d.ts:92-100`). So a live `Model`/`Document` cannot cross the boundary even by accident.

*The record.* One in-page namespace, created by the harness page's own inline script before any load:

```
window.__g1 = { closing: false, nextGen: 1, loads: {}, docs: {}, models: {} };
window.__g1.loads[tokenId] = {
  tokenId, api,          // api: 'Document.load' | 'loadDocumentNode'
  gen,                   // window.__g1.nextGen++ at mint; returned to Node, which stores it beside its token
  deadline,              // performance.now() + LOAD_TIMEOUT_MS — absolute, in-page, monotonic
  status,                // 'active' | 'completed' | 'timed-out' | 'sealed' | 'late-discarded'
                         //   | 'late-unloading' | 'late-unloaded'
  outcome: null,         // JSON-safe {kind:'success'|'rejected', error} — via an in-page errOf helper mirroring
                         //   T3's t3.errOf (clashtest-viewer-adapter.acceptance.mjs:182-185); re-serialized
                         //   Node-side through describeError (§4.2) before retention
  transitions: [],       // JSON-safe [{from, to, cause, at: performance.now()}]
  handlerErrors: [],     // JSON-safe; an in-page entry point never throws (below)
  // in-page only, never returned to Node:
  timer, preLoadModels,  // loadDocumentNode only: new Set(viewer.getAllModels()) at call time —
                         //   T3's own reloadBefore pattern, clashtest-viewer-adapter.acceptance.mjs:816
  lateModels: [],
};
```

A record is **ownership-clean** if and only if its status is one of: `completed` (and claimed by Node, below), `late-discarded`, or `late-unloaded`; or its status is `sealed` and `api === 'Document.load'`. "Ownership-clean" means safe to release: the record can no longer leave, or still own, Viewer state. It is not proof that the native call ever settled. A missing record, or one whose generation does not match, is never ownership-clean; either can happen if `window.__g1` is re-created by an unexpected navigation.

*Serialization invariant.* At most one load record is ever `active`, `timed-out` or `late-unloading` at a time. The initial pair is strictly sequential (two-stage linkage, above). F6's reload pair is minted only after the initial pair completed and `modelBefore` was unloaded. Any model the sweep below finds therefore belongs unambiguously to the one unsettled `loadDocumentNode` record.

*Starting a load (in-page, one `page.evaluate` per token).* Node mints its token, then calls `page.evaluate(START_LOAD, {tokenId, api, urn | docTokenId, LOAD_TIMEOUT_MS})`. `START_LOAD` does five things:
1. Creates the record.
2. Arms an in-page `setTimeout(onDeadline, LOAD_TIMEOUT_MS)`. This timer only wakes the operation; the callbacks enforce the deadline themselves, below.
3. Issues the Viewer call inside `try/catch` with every callback attached synchronously at call time: `Document.load(urn, onSuccess, onError)`, or `Promise.resolve().then(() => viewer.loadDocumentNode(doc, node, opts)).then(onSuccess, onError).catch(recordHandlerError)`. Here `doc` is read in-page from `window.__g1.docs[docTokenId]`. `loadDocumentNode` is typed `Promise<Model>` (`node_modules/@types/forge-viewer/index.d.ts:1207-1211` — 7.99.1 typings, not the pinned 7.124.2, hence the defensive wrapping). Production already assimilates its return value through a promise (`wwwroot/viewer.js:49`).
4. Routes a synchronous throw from either call to `onError`.
5. Returns a promise that resolves, JSON-safe, with `{tokenId, gen, status, outcome}` on whichever decision is made first.

Attaching `onError` at call time, plus the terminal `.catch`, is load-bearing: a late or synchronous rejection can never surface as an in-page `unhandledrejection` (§6.6, always fatal).

*One decision, in one realm, by absolute deadline.* Every in-page entry point begins `const g = window.__g1, r = g && g.loads[tokenId]; if (!r || r.gen !== gen) return;` and then:
- `onDeadline`: `if (r.status === 'active') { r.status = 'timed-out'; settle(); }`.
- `onSuccess(x)` / `onError(e)`: **first** `if (r.status === 'active' && performance.now() >= r.deadline) { r.status = 'timed-out'; settle(); }`. This closes the window where a callback is dispatched after the deadline but before the timer task runs. Then:
  - if still `active` and `g.closing === false`: `r.status = 'completed'`, `clearTimeout(r.timer)`, record `outcome`, store `x` in-page only (`g.docs[tokenId]` for a `Document`, `g.models[tokenId]` for a `Model`), `settle()`;
  - otherwise: the **late-arrival disposition** (below). Never `completed`, never stored, never passed onward.

Page JavaScript is single-threaded and the deadline is absolute. So a load is `completed` only if its callback ran before the deadline and before sealing, and once `status` leaves `active` no code path ever writes `completed`. The timeout decision and the late-arrival decision are made by the same realm against the same record, so Node and page can never disagree about whether a load timed out. Node's token is a **report of the in-page decision**, exactly as for the census above. The `START_LOAD` return `completed` becomes Node token `completed`, and Node records that tokenId as claimed. `timed-out` becomes Node token `timed-out` plus §6.4's `loadOutcome:'timed-out'`. Every in-page entry point wraps its body in `try/catch`, appends to `r.handlerErrors`, and never rethrows or calls `console.error`, so a late arrival can never itself produce a `pageerror`/`console.error` fatal (§6.6). A genuine Viewer-emitted error during a late unload is still captured and is still fatal, as it should be.

*Late-arrival disposition (in-page).*
- Late `Document` success, late `Document.load` error, or late `loadDocumentNode` rejection: `r.status = 'late-discarded'`. The `Document` or error is dropped, with no reference retained. A late `Document` is never passed to `loadDocumentNode`: a `Document` owns no Viewer model, so there is nothing to unload.
- Late `Model`: `r.lateModels.push(model); r.status = 'late-unloading';` then `viewer.unloadModel(model)` inside its own `try/catch`. `unloadModel` is typed `void` (`index.d.ts:1206`), so synchronous removal from `getAllModels()` is **not** assumed. The record moves `late-unloading → late-unloaded` only once `r.lateModels.every(m => !viewer.getAllModels().includes(m))` is observed true. That check runs immediately after the unload and again inside Node's drain predicate, below. It is T3's own unload-then-poll-gone pattern (`X_GONE`, `clashtest-viewer-adapter.acceptance.mjs:611-612,843-845`).

*Sealing (in-page, Phase 11 step 1a).* Node first moves any still-`active` load token to `timed-out{reason:'cleanup-preempted'}`. It then calls `page.evaluate(SEAL_LOADS, {claimed: [tokenIds Node recorded as completed]})`. That call:
1. Sets `window.__g1.closing = true`.
2. Moves every record whose status is `active` or `timed-out` to `sealed`.
3. Treats any record that is `completed` in-page but absent from `claimed` as late: its stored `Document` is discarded (→ `late-discarded`), or its stored `Model` goes through the late-`Model` disposition. This covers a completion Node never received, for example because the `START_LOAD` evaluate rejected.
4. For the (at most one, per the serialization invariant) sealed `loadDocumentNode` record, sweeps `viewer.getAllModels()` for models that are absent from its `preLoadModels` and not held by a claimed record. Each such model is moved into `lateModels` and unloaded, each in its own `try/catch`, and the record becomes `late-unloading`. This covers the case where the Viewer adds a model but its promise has not settled.
5. Returns one JSON snapshot per record.

A sealed `Document.load` record is ownership-clean: the only path by which a `Document` can reach `loadDocumentNode` or any Viewer state is `onSuccess` while `active`, and sealing has permanently closed that path. A sealed `loadDocumentNode` record is **not** ownership-clean, because a late `Model` may still arrive until the realm is destroyed. If one does, the late disposition unloads it.

*`window.__g1.closing` vs. `closeIntent` (§6.6): two deliberately separate flags.* `closing` is in-page, written once at step 1a, and read only by in-page load callbacks. `closeIntent` is Node-side, set immediately before each of steps 18–20, and read only by Node's `'close'`/`'crash'` listeners. They cannot be one flag. §6.6 requires `closeIntent` to be set "immediately before ... and never before" each close call, so setting it at step 1 would misclassify a genuine crash during steps 2–17 as intentional teardown. The seal, by contrast, must happen before the drain. Invariant: `closing` is set strictly before `closeIntent` is first set. Neither flag ever influences the other realm's decision, and `closing` never affects fatality classification. §6.6 is unchanged.

*Drain (Node, value only — `drainLoadToken`).* For each Node load token still `timed-out`, Node calls `await page.waitForFunction(IS_OWNERSHIP_CLEAN, {tokenId, gen}, {timeout: DRAIN_TIMEOUT_MS})`. The `timeout` option is used exactly as at `g1-svf2-initializer-diagnostic.mjs:124` and `clashtest-viewer-adapter.acceptance.mjs:845`. The predicate also performs the `late-unloading → late-unloaded` gone-check. Node then makes one `page.evaluate(READ_LOAD_RECORD, {tokenId})` call, which returns `{present, gen, status, transitions, handlerErrors, lateModelsStillPresent}`: counts and booleans only, never a model. Node moves `timed-out → disposed` **only** when that snapshot is present, generation-matched, and ownership-clean.

An elapsed drain window is **never** treated as a terminal signal. Treating elapse itself as disposal would record a disposal Node never observed, which is exactly the defect this fix removes. Such a token stays `timed-out` for step 20a. Every Node→page call in step 1 is bounded by a `Promise.race` against `DRAIN_TIMEOUT_MS`. The losing `page.evaluate` promise gets a no-op `.catch`, so its eventual rejection at page close cannot become a Node-side unhandled rejection. Concurrent drains share step 1's `FINAL_DRAIN_TIMEOUT_MS = 20_000` cap.

The same `drainLoadToken` is the Category-B await the pre-phase drain gate (above) uses for a load token. In the current phase order that gate can never meet a timed-out **initial**-load token: a load timeout leaves the classifier `INDETERMINATE_UNAVAILABLE`, which stops the run before Phase 3 (§6.2) and routes directly to Phase 11. It is specified so a future phase reordering cannot bypass it.

*Abandonment (Node, after teardown — §4.3 step 20a).* Page closure is the explicit abandonment boundary, not a hoped-for in-page guard. After steps 18–20, a Viewer-load token still `timed-out` moves `timed-out → abandoned` if and only if Node confirms the owning realm destroyed: `page.isClosed() === true` (Node-side only), or step 19/20 succeeded. Once the realm is gone no in-page callback can run, so `abandoned` is final. If destruction cannot be confirmed (all three closes failed), the token stays `timed-out`, and the existing `page`/`context`/`browser` rows (§4.3) record the live handle and set `cleanupUnresolvedOwnership`.

*Terminal-state machine — the four cases.* These apply to the initial load. F6's reload tokens use the identical record and differ only in escalation (§4.3).

| Case | Transition (in-page record; Node token) | Owning realm of each action | Cleanup action | Evidence record | Abandon page/context/session? |
|---|---|---|---|---|---|
| **A. Timeout before `Document.load` settles** | In-page: the deadline wins, `active → timed-out`. Node, from the `START_LOAD` return: `active → timed-out`. Step 1a: record `timed-out → sealed`, which is ownership-clean for `Document.load`. Step 1b snapshot: Node `timed-out → disposed`. `loadDocumentNode`'s token is never minted (two-stage linkage). | Deadline and seal: browser. Token transitions and drain poll: Node. | Sealing only; no model can exist. | `classifier:'INDETERMINATE_UNAVAILABLE'`, `loadOutcome:'timed-out'`; the `START_LOAD` snapshot is retained as load evidence. No `cleanupFailures` entry for this token. | Normal phases stop immediately (§6.2 classifier stop → Phase 11). Page/context/browser are closed by the ordinary steps 18–20. |

*Why a timed-out or late load can never become `PASS` or contaminate F1–F8.*
1. **No revival.** The only write of `completed` requires `status === 'active'`, a current time before the absolute deadline, and `closing === false`, all checked in the same realm that makes the timeout decision. A record that timed out can never become `completed`. Node's classifier input (`loadOutcome:'timed-out'`) is fixed from the `START_LOAD` return and never recomputed (§6.4b: "unchanged").
2. **No downstream execution.** `classifier ≠ CONFIRMED_SVF2` stops the run before Phase 3 (§6.2). Phase 2.5 never builds `world`/`registry`/`binding`, no Fi and no control runs, every `checks.F*` is prepopulated `BLOCKED`, and every control is prepopulated `NOT_EXECUTABLE` (§6.3a's "Classifier stop" paragraph, fixes M3). There is no later phase to contaminate. `computeOverall()` resolves at branch 1 or branch 2 (§6.3), and branch 5 (`PASS`) is unreachable twice over: through the classifier, and through every Fi being `BLOCKED`.
3. **No model leaks into evidence.** A late `Document` never reaches `loadDocumentNode`. A late or unclaimed `Model` is never claimed, never registered, and is either unloaded in-page or destroyed with the realm before the atomic result write (§8, after Phase 11).
4. **Cleanup integrity comes from observables only.** An initial-load token that is not `disposed` is recorded in `cleanupFailures` (§4.3) but never sets `cleanupUnresolvedOwnership`. The only resource it could own is an in-page Viewer model, whose realm's destruction step 20a confirms with a Node-observable fact. If that destruction cannot be confirmed, the `page`/`context`/`browser` rows escalate instead. The unobservable callback is never the basis of any verdict.
5. **F6 reload loads.** The same record applies. F6 is the last primary phase, and its own verdict on a reload timeout is already `FAIL{reload-never-observed}` (§6.4). Its reload load tokens keep §4.3's F6 escalation.

**Sensitivity control, redesigned (fixes H4's original request; corrected — fixes the bounded re-review's "C1" contradiction and "H1"):** the prior design artificially delayed F1's own real `resolveRoots` call and asserted the control "confirms F1 is correctly marked `FAIL`" — but that makes F1's own real verdict `FAIL` in every run where this mandatory control executes, making overall `PASS` unreachable even for a perfectly healthy fixture. The mandatory control `late-completion-after-timeout` (§6.3/§6.3a/§6.5), is corrected to use **its own control-local synthetic operation**, entirely decoupled from F1's real operation:

1. Before starting, the control snapshots F1's **already-recorded** `checks.F1` object (whatever it actually is for this run — `PASS` in a healthy run, or any other verdict) as `f1Snapshot` — a deep, read-only copy.
2. The control mints its own token for a harness-only synthetic operation (a controllable async gate that does nothing but resolve a value after a release signal — no production call, no real Viewer read) and artificially holds it open past `CHECK_TIMEOUT_MS`.
3. At the deadline, the harness's normal timeout machinery marks this token `timed-out` exactly as it would for any other operation (proving the general mechanism, not a special case).
4. The control then releases the held synthetic operation and confirms its late resolution is dropped — counted in `staleContinuationsDropped` under this control's own token id — and never written into `checks.F1`, `checks.*`, or any other result field.
5. The control re-reads `checks.F1` and asserts it is **byte-for-byte (deep-equal) identical to `f1Snapshot`** — proving the quarantine left F1's real, already-recorded verdict untouched, whatever that verdict was.
6. The control also confirms the pre-phase drain gate (above) would have correctly blocked progression had this token still been `timed-out` at gate time — by checking that the gate observed this token and required it to reach `disposed` before the control itself is allowed to report `DETECTED_RESTORED` — proving both halves H1 requires: (1) stale completion cannot publish, and (2) the underlying async work is cancelled, drained, or the session is abandoned safely, never silently ignored.

Outcome mapping into §6.3a's five-state model: `DETECTED_RESTORED` iff steps 4–6 all hold; `NOT_DETECTED` if the late resolution *did* leak into any result field; `RESTORE_FAILED` if `f1Snapshot` comparison fails (F1's real record was disturbed) or the token cannot be confirmed `disposed`; `TIMED_OUT` if steps 4–6 themselves do not complete inside the control's own bounded deadline; `NOT_EXECUTABLE` per §6.3a's definition.

**Does page closure safely terminate an unresolved load? (corrected — fixes the fresh bounded re-review's "H1")** Yes, but only as an explicit, Node-observed abandonment boundary, never as an in-page guard. The prior text had both late-arrival handlers call `page.isClosed()`. That is a Node-side Playwright method (`node_modules/playwright-core/types/types.d.ts:3707`) and is unreachable from a Viewer callback running in the page (`clashtest-viewer-adapter.acceptance.mjs:176`); that guard is removed, and no in-page code references `page` at all. The in-page callbacks consult only their own browser-owned record `window.__g1.loads[tokenId]` and the in-page `window.__g1.closing` flag (§6.4a). The order is fixed:
1. Step 1a seals the records in-page.
2. Step 1b drains them by value, moving a Node token to `disposed` only on an ownership-clean snapshot.
3. Steps 18–20 close page, context and browser, with `closeIntent` set immediately before each (§6.6).
4. Step 20a, Node-only, moves every load token still `timed-out` to `abandoned` if and only if Node confirms the realm destroyed (`page.isClosed() === true` Node-side, or step 19/20 succeeded).

A callback can no longer run after that point, so nothing is left to orphan. Before that point, every in-page entry point is `try/catch`-contained and every Viewer promise has a call-time rejection handler, so a late arrival is never an unhandled rejection, never a `pageerror`, and never a `fatalErrorObserved` trigger of its own. The final token and cleanup result after teardown is computed only from Node-held values: the last JSON snapshot, the close-step outcomes, and `page.isClosed()`.

### 6.2 Failure propagation rule

- **Independent checks continue** even if an earlier independent check fails: F1 failing does not stop F2, F7 from running (they don't depend on F1's *result*, only on the model being loaded).
- **Dependent checks are marked `BLOCKED: <reason>`, never silently skipped**, when their prerequisite failed: if F1 fails, F4 and F8 (which need F1's root/owner data) are recorded as `BLOCKED: F1 did not produce a usable root set` rather than attempted against known-bad input or omitted without a record.
- **F6 always attempts to run** (it needs a "before" snapshot, which exists as long as *any* of F1/F2/F4/F5/F7/F8 produced usable read-only evidence) but its own verdict notes which pre-reload baseline checks it could and could not compare against.
- **A classifier outcome other than `CONFIRMED_SVF2` stops before Phase 3 entirely** (§4.1) — this is the one true "stop immediately" case, because every Fi's evidence is meaningless without a confirmed SVF2 load. **Fixes M3:** on this stop, the harness still **prepopulates every one of `result.checks.F1`…`F8`** as `{ verdict: 'BLOCKED', reason: 'classifier:<state>' }` and every one of the nine `result.controls.*` records as a §6.3a `ControlResult` in that section's single five-value `state` enum — `{ state: 'NOT_EXECUTABLE', executed: false, detected: null, restored: null, restorationRequired: <that control's own fixed value, per §6.3a's per-control classification table>, reason: 'classifier:<state>' }` (corrected — fixes the fresh bounded independent re-review's own "M3": the prior `{ status: 'not-run', ... }` shape was a second, undocumented control schema outside §6.3a's exhaustive enum; the overall verdict is still `BLOCKED` via §6.3 branch 2, which is evaluated before branch 3 — see §6.3a, "Classifier stop") before writing the report — the classifier state itself (`CONFIRMED_NON_SVF2`/`CONTRADICTORY`/`INDETERMINATE_PARTIAL`/`INDETERMINATE_UNAVAILABLE`, plus the raw `runtime.isOTG`/`runtime.isSVF2` values) is retained in full. The report can never contain a missing/absent F1–F8 object merely because the classifier stopped early — the G1 authorization's evidence requirements ("each of F1–F8 marked verified/failed/not-evidenced") apply even to a `BLOCKED` overall run.

### 6.3 Overall G1 gate verdict (corrected — fixes C3, and now C1/H7/M3 from the independent Work review)

**Exhaustive per-check verdict enum** (replaces the first draft's ambiguous `PASS|FAIL|BLOCKED` plus prose-only "not evidenced"):

- `PASS` — the check's success criteria were fully exercised and met.
- `FAIL` — a genuine contract violation was observed (a real defect, per the check's own failure criteria).
- `BLOCKED` — the check could not run because a dependency (an earlier Fi, or the classifier) did not produce usable input; always carries a `reason` naming the blocking dependency.
- `NOT_EVIDENCED` — the check ran but the fixture/environment never exercised the condition the check exists to observe. **Never conflated with `PASS`** — `NOT_EVIDENCED` records "we could not tell," `PASS` records "we told and it held." **Mandatory-control manifest (corrected — fixes the bounded re-review's own "C1"):** the prior round's three-outcome model let a control that detected its own injected defect but then failed to restore the model to a valid state land in `PARTIAL` (not `FAIL`), and let a control that never ran at all (`NOT_EXECUTABLE`) also land in `PARTIAL` instead of `FAIL` — both contradict the requested contract "any mandatory control that does not both detect and restore must force `FAIL`." §6.3a below replaces the three-outcome model with an exhaustive five-state local result per control. **The gate binds bytes, not routes.** A redirect is not itself ambiguity: a fully reconstructed chain whose final decoded bytes match is `VERIFIED`, and a chain to different bytes is `MISMATCH`. Service-worker/cache provenance likewise never overrides the digest. A match proves the executed bytes whichever layer served them, and no provenance rescues a mismatch. The context is still created fresh with `serviceWorkers: 'block'` (§8), and `finalUrl`, each hop's status, and `fromServiceWorker` are retained for review, not gated on separately.

**Why `BLOCKED`, not `PARTIAL`, once no failure has already been observed (corrected — fixes the remediation-2 re-review's own "High 1"):** `PARTIAL` (branch 6) means the run was validly scoped to the certified runtime and only some checks went unexercised or had resolved cleanup failures. That is partial credit toward G1, which would overclaim when the runtime itself is unidentified. `NOT_EVIDENCED` is not available because it is Fi-scoped and not a value of the overall enum. An unestablished executable identity, once branch 3 has already confirmed no Fi/control failure exists, leaves the run in the same epistemic position as an unconfirmed classifier: no further Fi/control outcome can be attributed to Viewer 7.124.2. It is therefore its own arm, **branch 4**, evaluated immediately after branch 3's failure check — deliberately **not** merged into the classifier's branch 2, since (unlike the classifier) unresolved identity does not itself stop the run and must never be checked ahead of a real failure (see "Precedence, corrected" above). No phase in §6.1/§6.2 changes. Every Fi/control record is its real, fully retained result.

**Ordering requirement:** `integrityResult` is finalized after Phase 11's page close and before `computeOverall()` reads it, mirroring §6.6's own ordering requirement. No new timeout constant is needed: a still-pending `response.body()` settles (rejects) when its page closes in Phase 11, and it is then classified `CAPTURE_UNAVAILABLE`. It is never silently omitted.

**Precedence, corrected (fixes this targeted re-review's own "C3"; corrected again — fixes the remediation-2 re-review's own "High 1"):** the prior round's `if classifier != CONFIRMED_SVF2 → BLOCKED` branch was checked **first**, ahead of `fatalErrorObserved` — so a required-resource failure (e.g. the Viewer script itself failing to load, per §6.6's fatal categories) that also prevented the classifier from ever confirming SVF2 would be reported as the weaker `BLOCKED` instead of `FAIL`, contradicting §6.6's own rule that such failures are always fatal. ### 6.3a Mandatory-control verdict model — exhaustive states, exclusive of Fi's own enum (new — fixes the bounded re-review's "C1")

```

  detected: boolean | null,   // did the guarded check's own detection fire? null if never reached
  restored: boolean | null,   // did the control's post-control oracle pass? — the RESTORATION oracle when
                               // restorationRequired is true (shared state re-read and verified back at its
                               // pre-perturbation baseline), the NON-INTERFERENCE oracle when it is false
                               // (synthetic state proven isolated from every shared resource/result field
                               // AND terminal); null if not reached
  restorationRequired: boolean, // fixed per control at design time (classification table below), never
                               // computed at run time: true for the shared-state perturbations, false
                               // for the harness-local synthetic ones. false never means "nothing is
                               // checked" — restored === true (via the non-interference oracle) is still
```

### 6.6 Console/page/runtime error ledger (fixes H7)

Per the governing adjudication (§5b item 3), G1 fails on a broken runtime even if every Fi and every control otherwise looks clean — a module-load failure, unhandled exception, WebGL/context loss, or required-resource failure must never coexist with an overall `PASS`. This ledger's `fatalErrorObserved` computation (§6.3) runs **before** the aggregate verdict, over events collected continuously from Phase 0 through Phase 11:

**Always fatal (force `fatalErrorObserved = true`):**
- any `pageerror` event (an uncaught in-page exception);
- any `unhandledrejection` inside the page;
- failure of a **required** resource load — the Viewer script/style URLs, the `GET /api/auth/token` response, or any of the in-page `import()` calls the harness itself issues for repository modules (`/clashtest/viewer/index.js`, `/clashtest/index.js`, `/collision/index.js`, `/collision/viewer/ViewerModelAdapter.js`, `/collision/viewer/ViewerGeometryAdapter.js`, `/clashtest/planning/scopeDigest.js`, `/collision/constants.js`);
- browser/context/page crash or unexpected close (Playwright's own `'crash'`/`'close'` events firing while `closeIntent !== 'cleanup'` — **corrected, fixes this round's own internal-review High #6:** the prior wording referenced a nonexistent "Phase-12 close" (this plan's own phase table ends at Phase 11, §6.1, which performs the intentional close itself, steps 18–20 of §4.3's ledger); a single boolean-like `closeIntent` field, set to `'cleanup'` **immediately before** each of `page.close()`/`context.close()`/`browser.close()` is called and never before, is the actual lifecycle signal these listeners check — a `'crash'`/`'close'` event observed while `closeIntent` is still its initial, unset value is always fatal; one observed after `closeIntent === 'cleanup'` was set for that exact resource is the harness's own expected teardown, recorded but never fatal; a duplicate/repeated close event for an already-closed resource is recorded informationally and is likewise never fatal);
- WebGL context loss (`webglcontextlost` on the canvas, if observable) — recorded as fatal because it invalidates every subsequent Viewer read for the remainder of the run;
- any `console.error` **not** matched by the exact allow-list below.

**Never fatal (diagnostic only, retained but excluded from `fatalErrorObserved`):** `console.warn`, `console.info`, `console.log`.

**Allow-list discipline:** this plan defines **no allow-listed `console.error` fingerprint at plan time** — the prior diagnostic-harness run (`docs/research/2026-09-27-g1-svf2-diagnostic-harness-result.md`) recorded zero console/page errors under this same isolated pattern, so no known-benign noise has actually been observed yet to justify one. If the eventual implementation run surfaces a specific, reproducible, benign `console.error` (for example, a SwiftShader software-rendering notice, if one is ever observed — none was in the diagnostic run), it may be added to the allow-list **only** as an exact string/regex fingerprint tied to its phase, source, and the exact Viewer version, with a one-line justification recorded alongside it in the harness source and the eventual research report — never a broad substring or "contains" rule. Every allow-listed message is still retained verbatim in the raw evidence; only its fatality is suppressed.

**Ordering requirement:** fatality classification runs to completion (every collected event classified) before `computeOverall()` (§6.3) reads `fatalErrorObserved` — the aggregate verdict never races the error ledger.

### 7.5 F5 — existing limits under SVF2 (corrected — fixes H3 from the independent Work review; corrected again — fixes this round's own internal-review High #4/#5)

- **Purpose:** compare the observed SVF2 population against already-accepted resource limits — never invent new ones.
- **Adjudicated F5 rule (fixes H3 — reverses the prior draft's `NOT_EVIDENCED`-by-default disposition):** the owner's adjudication (§5b item 1) is explicit — G1 F5 must prove the real SVF2 fixture is **completely enumerated**, its observed counts recorded, **no silent truncation occurred**, and every applicable existing bound is respected. The governing F5 text (§3) never requires the fixture to organically exceed a limit, and the independent Work review found the prior draft's conditional `NOT_EVIDENCED` disposition made a valid `PASS` **unreachable** for the accepted (modest) Room Locator fixture — a defect, not a correct caution. This is now fixed: F5's own primary verdict for the unperturbed real fixture can and normally will be `PASS`.
- **Corrected organic-breach verdict (fixes this round's own internal-review High #5):** the prior round mapped a correctly-thrown `CapacityExceededError` to F5 `PASS` — but that conflates "enforcement fired correctly" with F5's own actual purpose, "the real fixture is within existing limits." An organically-over-limit fixture is, by definition, **not** within its existing limits, so labeling that outcome `PASS` directly contradicts F5's own stated purpose even though enforcement worked. This is corrected below: an organic breach is F5 `FAIL` (`withinLimits: false`), with `enforcementObserved: true` recorded **separately** as a positive, non-gating fact. The **mandatory `capacity-breach` control** (§6.5, unchanged) remains the sole independent proof that enforcement itself still works — F5's own primary verdict never again needs to (or is allowed to) stand in for that control's job.
- **Evidence source/API:** counts from F2/F4 (`fragListCount`, `rootsLength`, per-root `fragmentCount`, per-dbId fragment counts, per-node child-fanout counts from F2's tree walk), **F4's own `maxActiveTriangleCount`/`oversizedGeometryCount`** (§7.4, new — fixes High #4), the collision engine's existing limit constants (`/collision/constants.js`: `maxCollisionInstancesPerEpoch = 20_000`, `maxFragmentsPerDbId = 5_000`, `maxChildrenPerNode = 10_000`, `maxSyncTriangleCount = 12_000`), and the `CapacityExceededError`/`EnumerationBoundExceededError` classes those limits raise; **and, directly, F1's own outcome** — see the corrected dependency below (fixes I5).
- **Two independent limit dimensions (new — fixes High #4):** F5 now tracks **two, separately-named** existing-limit checks, since they are enforced at different points in the pipeline and a breach of one says nothing about the other:
  1. **Population-level** (`maxCollisionInstancesPerEpoch`/`maxFragmentsPerDbId`/`maxChildrenPerNode`) — enforced by `resolveRoots`/`scanPopulation` **before** any tree traversal (`ViewerElementEnumerator.js:118-128`, `populationScan.js:10-15`); a breach here throws `CapacityExceededError` out of F1 itself, per the corrected dependency below.
  2. **Per-geometry sync-build ceiling** (`maxSyncTriangleCount`) — enforced by `compactAndWeld` (`activeRangeCompaction.js:140-146`) per geometry id, independent of the population-level check; a breach here never throws, it returns F4's own `geometry-too-large-for-sync-build` marker (§7.4, corrected), copied into F5 as `oversizedGeometryCount`/`maxActiveTriangleCount`.
- **Corrected dependency (fixes I5):** the prior draft made F5 strictly dependent on F2 *and* F4 succeeding — but `resolveWhole`'s own documented order (verified by source read, `clashtest/viewer/ViewerElementEnumerator.js:118-128`: "(2) bounded population/count validation FIRST (the O(1) `getCount()` gate, then <= `maxCollisionInstancesPerEpoch` records) BEFORE any tree traversal") means a genuinely over-limit fixture makes `resolveRoots` itself throw `CapacityExceededError` **before** any tree walk happens — so F1 (which calls `resolveRoots`) would itself be `FAIL`/`BLOCKED` in exactly this scenario, cascading to F2/F4 `BLOCKED` under the old dependency rule, and leaving F5 with no path to a defined verdict for the one condition it exists to measure. **F5 is corrected to consume F1's own outcome directly**, not only F2/F4's:
  - If F1 (and therefore F2/F4) succeeded normally: F5 uses F2/F4's counts, **and F4's `maxActiveTriangleCount`/`oversizedGeometryCount`**, as below.
  - If F1 itself failed with a **typed** `CapacityExceededError`/`EnumerationBoundExceededError` (i.e., the enforcement path correctly fired before traversal): F5 reads that typed error directly and is `FAIL` (corrected, above) with `withinLimits: false`, `organicBreach: { limit, requested }` (the specific limit and requested count the error names), and `enforcementObserved: true` — while F1/F2/F4 remain `FAIL`/`BLOCKED` for their own, separate reasons (F5's own verdict is never silently inferred from F1's failure without inspecting the error's actual type).

  6. *Oracle arithmetic.* This is F7's own transform and min/max, done in JS float64. For one 4-term affine row its forward error is at most about `4·2^-53·S_a` (below), which is negligible (under `2^-29` of `T_pass`).

  **What this implies.** Input quantization (float32 vertices, stored matrix elements) is **common-mode**: both sides read the same stored values. The discrepancy sources are therefore (i) the Viewer's own opaque arithmetic and internal float32 storage, plus the final Float32Array write, which are roundoff; and (ii) **non-roundoff semantic differences**. Two such differences are legitimate and one is a defect:
  - *Legitimate:* the Viewer may bound transformed local-bbox corners rather than vertices, which gives a looser box for rotated fragments.
  - *Legitimate:* the Viewer may bound fragments the oracle skips.
  - *Defect:* on a model with non-identity placement, the classic-SVF prior predicts `getNodeBox` omits placement while the oracle includes it. This is exactly the world-space-correctness question F7 exists to answer.

  A **two-sided equality test is therefore structurally wrong** whatever the tolerance: the two legitimate differences only ever make `getNodeBox`'s box *larger* than the vertex-tight reference. F7 instead tests a **bracket**. The vertex-tight reference must be contained, and that side gates FAIL. The conservative corner envelope bounds the other side, and that side is a calibration gate only.

  **Per-dbId, per-axis operand scale `S_a` (handles cancellation).** For each dbId and axis `a ∈ {x,y,z}`:
  - Let `G = model.getGlobalOffset()` and `P = model.getPlacementTransform()` (identity if `null`). Both are the public accessors this repository's live acceptance evidence already reads: `test/acceptance/clash-finder.acceptance.mjs:268,620,841`.
  - For each non-skipped fragment `f`, with copied world matrix `e` (`Float64Array(16)`, column-major) and all-vertex local AABB `[lo, hi]` (step 3b below), let `L_k = max(|lo_k|, |hi_k|)` and compute
    `S_a(f) = |e[a]|·L_x + |e[a+4]|·L_y + |e[a+8]|·L_z + |e[a+12]| + |G_a| + |P.elements[a+12]|`
  - If `P`'s 3×3 block is not the identity, each `|e[a+4k]|` term is replaced by `Σ_j |P.elements[a+4j]|·|F[j+4k]|`, where `F = P^-1·e` is computed in float64. This bounds products that cancelled during the placement composition, not just the composed result.
  - Then `S_a = max( max_f S_a(f), |refMin_a|, |refMax_a|, |nodeMin_a|, |nodeMax_a|, 2^-126 )`.

  The sum-of-absolute-terms form is the standard forward-error scale of an inner product: it bounds rounding in `Mx + t` even when a small world coordinate comes out of large, cancelling terms. The `|G_a|` and `|P_translation|` terms record the separate translation magnitudes the review asked for, because an offset subtraction or placement composition performed separately inside the opaque pipeline can cancel against the fragment translation before the final matrix is stored. Including the compared values themselves covers the final Float32 write. The `2^-126` floor (the smallest normal float32) keeps relative bounds valid in the subnormal range, where absolute error per operation is at most `2^-149`, which is far below `16u·2^-126`. The prior round's `max(1, ·)` floor is dropped: "one native unit" has no numerical basis when native units vary (ft, mm, m).

  **Thresholds, with `u = 2^-24`** (float32 unit roundoff for round-to-nearest; `2^-23` is machine epsilon `= 2u`):
  - `T_pass(a) = 16·u·S_a = 2^-20·S_a`. This is a **declared, provisional PASS allowance**, counted for the modelled chain: one 4-term affine inner product (`γ_4 ≈ 4u`), up to two separately rounded compositions or offset operations whose operand magnitudes `S_a` now includes (`≈ 4u` each), and up to two float32 stores (fragment box and node box, `≈ 1u` each). That sums to `≈ 14u`, rounded up to 16. It is **not** claimed as a proven end-to-end bound for the opaque Viewer pipeline.
  - `T_gross(a) = 2^-10·S_a`. This is the **correctness-FAIL boundary**, 64× above an allowance of even `1024` float32 rounding events (`2^-14·S_a`, ≥ 60× the counted chain). With every recorded operand magnitude inside `S_a`, a roundoff-only discrepancy of this size would need either thousands of rounding events or cancellation among operands about `2^10` times larger than any magnitude the Viewer exposes. **Residual risk, stated rather than hidden:** a Viewer bounds source that is not derived from the same live geometry (e.g., a precomputed box from a different geometry revision) could exceed `T_gross`. F7 then legitimately reports that `getNodeBox` does not bound the rendered geometry, and that is itself a world-space-correctness finding.
  - The open band `(T_pass, T_gross]` is a **calibration gate**. A containment violation there is recorded with its full residual, in units of `u·S_a`, and makes that dbId `near-tolerance`: never PASS, never FAIL. The allowance and the gate stay as written until a bounded live run establishes the real residual envelope. **Calibration may never tune `T_pass` or `T_gross` against the same run's observations** (unchanged anti-tuning discipline, §5b M1).

  **Per-dbId classification, in this precedence order** (componentwise: each of the 6 components is tested independently against its own axis's thresholds):
  1. `disagrees`: some containment residual exceeds `T_gross(a)`. The residuals are `r_min(a) = nodeMin_a − refMin_a` and `r_max(a) = refMax_a − nodeMax_a`; a positive value means the reference pokes out of `getNodeBox`'s box. When `P` is non-identity, a diagnostic `placementOmissionExplains` is also recorded (whether `nodeBox` brackets the reference recomputed with `P^-1·e` within `T_pass`), naming the classic-SVF-predicted cause. It is a diagnostic only, never a separate verdict.
  2. `near-tolerance`: the maximum containment residual is in `(T_pass, T_gross]`.
  3. `envelope-incomplete`: containment holds within `T_pass`, but at least one of this dbId's fragments has no computable envelope (skip reasons `unsupported`, `non-float-positions`, or `non-affine-world-matrix`, step 2). Containment alone would let an arbitrarily oversized box through, so this cannot PASS.
  4. `exceeds-envelope`: containment holds within `T_pass`, but some excess `e_min(a) = envMin_a − nodeMin_a` or `e_max(a) = nodeMax_a − envMax_a` exceeds `T_pass(a)`. The Viewer box is larger than the mathematical corner envelope; that could be undocumented legitimate padding, so it is calibration and not FAIL.
  5. `agrees`: `tightRef ⊆ nodeBox ⊆ envelope`, all 6 components within `T_pass`.
  6. `viewerApiNull` and `no-reference-geometry` are unchanged (step 7).

  **Why legitimate roundoff passes.** Both sides consume identical stored inputs, so only the Viewer's arithmetic and storage rounding separate them. Those are bounded by `T_pass` for the modelled chain, with every recorded operand magnitude, including cancelling translations, inside `S_a`. The oracle's float64 contribution is negligible. The Viewer's legitimate conservatism (corner boxes, extra fragments) only enlarges its box, so it never trips containment and is bounded by the envelope.

  **Why materially wrong bounds fail, or at least never PASS.**
  - Any box that fails to contain the rendered geometry by more than `2^-10·S_a` fails: a missing or extra placement translation, a unit-scale mixup (`0.3048`, `25.4`, `1000`: O(1) relative), an axis swap, or a union missing a fragment.
  - Any smaller containment defect lands in `near-tolerance`.
  - Any oversized box lands in `exceeds-envelope`, or in `envelope-incomplete` when coverage is partial.
  - PASS needs the two-sided bracket within `2^-20·S_a`.

  **Scope of a PASS, stated deliberately.** PASS means "`getNodeBox`'s box is a correct conservative world-space bracket of the rendered geometry for this fixture". It does not mean "the Viewer computed exactly the vertex-tight box". A wrong box that happens to fall strictly between `tightRef` and a loose envelope (unused vertices, thin rotated geometry) is not distinguished, and this limitation is recorded rather than closed.
