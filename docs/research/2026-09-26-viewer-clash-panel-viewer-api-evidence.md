## 1. Scope and method

Ten claims (C1–C10) about Viewer APIs that the Viewer Clash Panel's `ViewerBridge` would need. Method, per the `aps-viewer-api-evidence-investigation` conventions:

- **Target version:** exact `7.124.2` (repo pin: `wwwroot/index.html:46`; viewer built as `Autodesk.Viewing.GuiViewer3D`, `wwwroot/viewer.js:33`). No conflicting entry point found.
- **Bundle evidence:** the downloaded `viewer3D.js`, read by symbol. Citations are `viewer3D.js:<line>` on the decoded bytes. Line numbers are a secondary locator; the symbol and the described behaviour are the durable anchors.
- **Docs evidence:** Autodesk Reference Guide v7 pages (`aps.autodesk.com/en/docs/viewer/v7/reference/...`) fetched 2026-09-26 through the `r.jina.ai` render proxy (retrieval mechanic only). These describe the current v7 release, not specifically 7.124.2, so they establish "public contract exists", not pinned-build behaviour. Argument order and semantics below come from the bundle.
- **Typings:** `node_modules/@types/forge-viewer` 7.99.1 (older than runtime; corroboration only, never evidence of public status).
- **Classification vocabulary:** `public` (Reference Guide entry) / `internal` (affirmative private evidence) / `undocumented` (exists, no official entry, no internal label). Evidence labels: `official-doc`, `source-observed` (bundle), `inferred`. Where docs and bundle disagree, the bundle governs the pinned build and the disagreement is stated.
- **Not done:** no Viewer was run, no fetched code was executed, no probe was created. Every behavioural verdict is therefore `source-observed`, not `runtime-observed`. Items that need a live run are listed in section 4.
- **Formal knowledge consulted:** `viewer-api-stability` (Private-namespace precedent) and `viewer-bundled-three` (fork API surface must be feature-detected). Both are `status: active`.

### 2.1 C1 and C2 detail (theming)

- **Signature.** `Viewer3D.prototype.setThemingColor = function (dbId, color, model, recursive)` (`:30860`): `model = model || this.model; model.setThemingColor(dbId, color, recursive); this.impl.invalidate(true)`. The wrapper forwards `recursive` to the Model method; the Model method's own order is `(dbId, color, recursive)` (`:152780`), so the wrapper and the delegate orders were read independently and differ as expected. The Reference Guide lists `(dbId, color, model, recursive)`, agreeing with the bundle.
- **Colour type.** Docs: `Autodesk.Viewing.Math.Vector4` `(r, g, b, intensity)` in `[0,1]`. Bundle: `Autodesk.Viewing.Math.Vector4` re-exports the fork's `THREE.Vector4` (`:86679`), and the bundle assigns the same fork to the page global (`av.getGlobal().THREE = LMV.THREE`, `:91992`), with `THREE.REVISION` `'71'` (`:198164`). Consumers read only `.x .y .z .w` (`:123187`, `:127517`, `:131879`), and `FragmentList.setThemingColor` calls `.equals` on the previously stored colour (`:136798`). The shader is `mix(rgb, themingColor.rgb, themingColor.a)` (`:407`). Use `new Autodesk.Viewing.Math.Vector4(r,g,b,a)` (or `window.THREE.Vector4`); a stock ES-module three `Vector4` (this repo imports one through the import map, `wwwroot/index.html:49`) is duck-compatible by reading the code but was not verified.
- **`model` honoured in an aggregate scene.** Yes: state lives per model (`FragmentList.db2ThemingColor`, or `InstanceCollection3D.db2ThemingColor` at `:141336` when the Scene API flag selects it, `:151975`-`:151998`). Nothing in the wrapper looks at other models.
- **`recursive`.** No default; `undefined` is falsy, so descendants are not themed. `recursive=true` enumerates the node itself plus all descendants (`ObjectTree.enumNodeChildren(..., recursive=true)` calls the callback on the node first, `:148835`); if the object tree is not yet available the code silently falls through to the non-recursive path (`:152785`-`:152793`).
- **Isolated nodes.** Nothing excludes themed-and-isolated nodes. In the shader path hidden fragments are collapsed (`gl_Position.w = 0`, `:417`), so theming shows exactly on nodes that are visible; a node in the highlight/selection state (`vizflag & 2`) is drawn with the selection colour instead of its theming colour (`:417`). This is static shader reading; it is not runtime-observed.
- **Model not loaded / gone.** `RenderModel.initialize` allocates the fragment store at model creation (`:151952`-`:151998`); `FragmentList` records pre-load theming by dbId and applies it later (`:136780` comment, `themingOrGhostingNeedsUpdateByDbId`). After `model.dtor()` the store is set to null (`:152123`), and the call falls through to the leaflet branch, which logs "Theming colors are not supported by this model type." (`:152800`); whether it throws after `sceneTraversal.dtor()` was not established. Treat theming a possibly-unloaded model as unsafe and guard on the live model list.
- **C2.** `Viewer3D.clearThemingColors(model)` (`:30876`) is `model = model || this.model; model.clearThemingColors()`; `FragmentList.clearThemingColors` (`:136827`) resets only that fragment list's map and notifies its own callbacks. A multi-model clear must iterate models. Per-node un-theme: `db2ThemingColor[dbId] = color || undefined` (`:136800`), and the bundle JSDoc says "Set to undefined for 'no theming'"; the Reference Guide page for the Viewer3D wrapper does not state this.

### 2.2 C3 detail (aggregate isolation)

- `Viewer3D.setAggregateIsolation(isolation)` -> `visibilityManager.aggregateIsolate(isolation)` (`:28875`, `:95003`). Logic: an empty or falsy array runs `setAllVisibility(true)` on every model; otherwise, for each loaded model, an entry with `model === thatModel` calls `model.visibilityManager.isolate(ids)` (`ids = item.ids || item.selection`), and a model with no entry is fully hidden (`setAllVisibility(false)`, default `hideLoadedModels = true`). Entries whose `model` is not in the loaded list are ignored. A single aggregate event is fired at the end.
- `{model, ids: []}`: an empty array is truthy, `isolate([])` finds no root, and `isolateMultiple([])` calls `setAllVisibility(true)` (`:105189`-`:105220`), so that model becomes fully visible (matches the repo's reliance). Falsy `ids` (`null`/`undefined`) also resets that model.
- `Viewer3D.isolate(ids, model)` (`:28620`) goes through the same manager with `hideLoadedModels: false` (`:94985`), touching only the given model; it also fires the aggregate event.
- Descendants: `isolateMultiple` calls `setVisibilityOnNode(node, true, ..., setRecursive = true, trackIsolation = true)`, whose enumeration is documented in-source as "inclusive of the root" (`:105275`-`:105300`). Isolating a dbId therefore shows the node and all its descendants. If the model has no object tree yet the code assumes `fragId = dbId` (`:105320`), which is wrong for real models; do not isolate before the tree exists.
- Getter: `getAggregateIsolatedNodes()` (`:94921`) returns `{model, ids}` only for models whose tracked isolated set is non-empty. The tracked set holds the requested ids, and "all hidden" is tracked as the root id in the hidden set (`updateNodeVisibilityTracking`, `:105358`), so a fully hidden model does not appear in the getter's result.
- **Repo wording risk.** `wwwroot/extensions/ClashFinderExtension.js:388`-`:392` says every model/dbId not present in the array "becomes visible again". Per the bundle, for a non-empty array a model absent from the array is hidden entirely, and dbIds of a listed model not in `ids` are hidden. Only `[]` (or falsy `ids` for a model) makes things visible. The comment is misleading; the repo's behaviour (which already relies on "hide other models") is consistent with the bundle.

### 2.3 C4, C5 detail (framing and selection)

- **`fitToView`.** `Viewer3D.fitToView(objectIds, model, immediate)` (`:29941`): if `objectIds[0].model` is truthy the array is treated as an aggregate selection and used as is; otherwise it is wrapped as `[{model: model || this.model, selection: objectIds}]`. `Viewer3DImpl.fitToView` (`:36544`) then calls `get3DBounds` (`:36703`), which reads `aggregateSelection[i].selection` and, per dbId, unions `fragList.getWorldBounds(fragId)` over `objectTree.enumNodeFragments(dbId, cb, true)` (descendants included), with a fallback to `dbId2fragId` or `dbId` as fragId when the tree is missing. World bounds include each model's placement matrix. If every `selection` is empty it fits the visible scene bounds. It ends in `navigation.fitBounds(immediate, bounds)` with `reorient` and `force` unset, fires `AGGREGATE_FIT_TO_VIEW_EVENT` (plus `FIT_TO_VIEW_EVENT` for a single model), returns nothing, and does nothing if the bounds are empty.
- **`fitBounds(immediate, bounds, reorient, force)`** (`:95801`): returns `{position, target}`; returns the unchanged camera if `!isActionEnabled('gotoview') && !force` or the bounds are empty; `immediate` true sets the view instantly, false animates. `viewer.navigation` is created at `:26254`. Documented public on `Navigation`.
- **Public union alternatives.** `ObjectTree.getNodeBox(dbId, Float32Array(6))` is documented, but whether its box is in world space (placement applied) was not established, so it should not be used for cross-model framing without a live check. `Model.getBoundingBox()` is documented but whole-model.
- **Selection shapes.** Getter `:100641` returns `{model, selection}` per model with a non-empty selection. Setter `:100769` reads `ids` else `selection`, skips unregistered models, calls `model.selector.setSelection(ids, selectionType)`, does not touch unlisted models, fires once unless `fireEvent=false`. `Viewer3D.select` -> `MultiModelSelector.setSelection` (`:100742`): empty/null clears every model's selection; otherwise all other models' selections are cleared. Single-model legacy `SELECTION_CHANGED_EVENT` is fired in addition when exactly one model is loaded. `_select` remaps each id via `findNodeForSelection` under the current selection mode and skips locked or unselectable nodes.
- `ISOLATE_EVENT`/`HIDE_EVENT` listeners deselect nodes that became invisible (`:100494`-`:100502`); in a multi-model scene `ISOLATE_EVENT` is only fired for a single loaded model (`:95187`-`:95200`), so do not assume a selection survives or is dropped by an isolation change; select after isolating.

### 2.4 C6, C7 detail (events)

- **C6.** `aggregateIsolate` and `aggregateRestore` call `#fireAggregateIsolationChangedEvent` (`:95187`) after all models are updated; it builds the payload from `getAggregateIsolatedNodes()` and calls `viewerImpl.api.dispatchEvent({type, isolation})`. `EventDispatcher.dispatchEvent` (`:13300`) invokes listeners in a plain loop on the caller's stack with no try/catch, so it is synchronous and a throwing listener propagates into the caller. `VisibilityManager.setVisibility` (state restore, `:105632`) emits the same event type with an entry per model, including an empty `ids` array. Foreign emitters include the viewer's model browser (`:80977`, `:80993`), `viewer.isolate`, `showAll` (`:28927`) and any other extension; the event carries no origin. Model removal changes the tracked state (`MultiModelVisibilityManager.removeModel`, `:94897`, calls `setAllVisibility(true)`) without firing the event.
- **C7.** `Viewer3DImpl.unloadModel` (`:34052`): dispatches BEFORE_MODEL_UNLOAD_EVENT first (model still registered, `getAggregateIsolation()` still includes it), then `removeModel` (`:34133`: renderScene, selector, visibilityManager, layers, `this.model` reassigned, then MODEL_REMOVED_EVENT), then `dtor`, then MODEL_UNLOADED_EVENT (model already disposed, per its docs). If the model is unknown, BEFORE fires and the function returns without further events. `hideModel` (`:31003`) calls `impl.removeModel` directly, so the model leaves the scene with MODEL_REMOVED_EVENT only; `showModel` re-adds it. `addModel` (`:33782`) fires MODEL_ADDED_EVENT at its end, after selector/visibility registration; the model's object tree and geometry may still be loading.

### 2.5 C8, C9, C10 detail (names, units, UI)

- **Names.** The viewer's own model-name helper (`:76355`) resolves: `loadOptions.modelNameOverride` (documented load option, `:27080`), else `model.getDocumentNode().getModelName()` (first child of the manifest root), else the placeholder `'Model'`. `BubbleNode#name()` is public but returns the node's own name (viewable/view name), not necessarily the file name. Element names: `ObjectTree.getNodeName(dbId, includeCount)` reads the in-memory name table (`InstanceTreeAccess.name`, `:141857`); the tree is available synchronously when `model.isObjectTreeCreated()` / `model.getObjectTree()` (no callbacks) returns it, otherwise `getObjectTree(onSuccess, onError)` or `getObjectTreeAsync()` (documented) or OBJECT_TREE_CREATED_EVENT. `getBulkProperties2` and `getProperties2` (documented) are the property-database alternatives and are asynchronous.
- **Units.** `getUnitString()` order: `overriddenUnits` > `scalingUnit` (set only if `applyScaling` changed the scale) > `overrideDistanceUnit` > metadata `distance unit`; null if unknown. `getUnitScale()` is metres per unit (docs: unity if unknown). The load-option code states that a scaling factor "converts model file units to viewer world units" and that these accessors then report the corrected values (`:44627`-`:44660`, comment `:44620`). The renderer's unit scale is taken from the first model only and used for screen-space effects (`:33797`, `:174012`); geometry is not rescaled. This repo's loader passes no `applyScaling` (`wwwroot/viewer.js:47`-`:54`; no `applyScaling` in repo code), so each model is expected to stay in its native unit; the repo's collision code already divides by `model.getUnitScale()` (`collision/CollisionWorld.js:37`-`:47`).
- **Panel.** `new Autodesk.Viewing.UI.DockingPanel(parentContainer, id, title, options)` appends `container` to the parent, calls `this.initialize()` (overridable; default creates title bar, close button, optional footer) and then `setVisible(false)` (`:72455`-`:72500`). `setVisible(show)` toggles `container.style.display` and invokes every registered visibility callback with the boolean (`:72568`-`:72618`); the default close button calls `setVisible(false)` (`:72786`). `addVisibilityListener(cb)` only appends (`:72559`); no `removeVisibilityListener` exists in the bundle. `uninitialize()` (`:72534`) removes tracked DOM listeners, empties the callback array, removes `container` from the parent and nulls `container`. Toolbar: `Extension.prototype.onToolbarCreated(toolbar)` (`:14541`) is called by `GuiViewer3D` right after an extension loads if the toolbar exists (`:74050`-`:74060`) and otherwise when the toolbar is created (`:74206`); the official guide creates `new Autodesk.Viewing.UI.Button(id)`, sets `onClick`/`setToolTip`/`addClass`, wraps it in `new Autodesk.Viewing.UI.ControlGroup(id)`, calls `toolbar.addControl(group)` and removes it with `this.viewer.toolbar.removeControl(group)` in `unload()`. `ControlGroup.addControl` returns false if the id already exists (`:84375`-`:84390`). `GuiViewer3D.addPanel/removePanel` (`:75225`) only track a panel for resize; they are not in the Reference Guide.

## 3. Consequences for the Panel design

Format scope: the Panel v1 target is SVF2; the verdicts below are **not established for SVF2** (see section 4, "Model format"). Ordered by importance.

**Safe to rely on (public, docs and bundle agree, pinned build read)**

1. Aggregate isolation through `Viewer3D.setAggregateIsolation` / `getAggregateIsolation`, with `[]` as clear-all and entries `{model, ids}`. Design the Panel's isolation as a full-scene declaration (a listed model shows only `ids`, an unlisted model is hidden). The Panel must own one reconcile function that composes its intent with the existing Clash Finder / Room Locator isolation, since every call replaces the whole state.
2. `AGGREGATE_ISOLATION_CHANGED_EVENT`, `BEFORE_MODEL_UNLOAD_EVENT`, `MODEL_ADDED_EVENT`, `MODEL_REMOVED_EVENT` exist with `model` payloads. Do a per-model cleanup on BEFORE_MODEL_UNLOAD **and** treat MODEL_REMOVED as "model left the scene" (hide or unload), because `hideModel` skips BEFORE_UNLOAD.
3. Self-vs-foreign isolation changes: use a synchronous re-entrancy flag set around the Panel's own `setAggregateIsolation` call, reset in `finally`. The event has no origin field, fires on no-op calls, is emitted by other actors, and is not emitted when a model is removed.
4. `Viewer3D.setThemingColor(dbId, color, model, recursive)` and `Viewer3D.clearThemingColors(model)` with an `Autodesk.Viewing.Math.Vector4`, always passing an explicit live `model`. Panel-owned theming should be tracked per `(model, dbId)` and removed individually via `setThemingColor(dbId, undefined, model)` rather than `clearThemingColors(model)`, which would also erase theming set by others on that model.
5. Model names via `getDocumentNode()?.name()` with the viewer's own fallback chain (`modelNameOverride` -> `getModelName()` -> placeholder); element names via `model.getObjectTree()?.getNodeName(dbId)` after `isObjectTreeCreated()`; use `getObjectTree` (not the deprecated `getInstanceTree`).
6. Toolbar button via `onToolbarCreated(toolbar)` + `ControlGroup` + `Button`, removed in `unload()` (official guide pattern). Requires `GuiViewer3D`, which this repo uses.

**Needs a live check before the design depends on it**

7. Framing two elements across two models: `fitToView([{model, selection}, ...], immediate)` is source-verified but undocumented and its result (world bounds with placement, hidden fragments included?) is not runtime-observed. Fallback: compute a `Box3` from data the Panel already has and call the documented `navigation.fitBounds(false, box, false, true)`.
8. Unit compatibility across models (C9): read `getUnitScale()` for both models in a live session; if they differ, the Panel must not present a single-unit distance derived from world coordinates.
9. Visual behaviour of theming on isolated nodes and its interaction with the selection colour (the bundle's shader lets the selection colour win); also that a stock-three `Vector4` works if the design prefers not to use the viewer's.
10. `getNodeName` for a dbId not in the tree, and theming after unload (throw vs warn).
11. `DockingPanel` subclass lifecycle in 7.124.2: subclass fields assigned after `super` are not visible inside the overridden `initialize()` because the constructor invokes it.

**Must be avoided**

12. `fitToView` aggregate entries with `ids` (throws; use `selection`), and any reliance on `select(ids, model)` to preserve other models' selection or on `setAggregateSelection` to clear unlisted ones.
13. `Model#setThemingColor` / `Model#clearThemingColors`, `viewer.impl.*`, `visibilityManager.*`, and `Autodesk.Viewing.Private.*` (undocumented or internal). The public `Viewer3D` wrappers cover the design's needs.
14. Calling `viewer.clearThemingColors()` without a model in a multi-model scene expecting a global clear; calling theming, isolate or selection on a model that may have been unloaded.
15. `DockingPanel` methods are undocumented: if used (no public alternative exists for show/hide/observe), wrap them in one adapter, subclass only via `initialize` as in the official example, register exactly one visibility listener, never call `setVisible` after `uninitialize()`, and treat `removeVisibilityListener` as non-existent (the listener dies with `uninitialize()`).
16. Trusting `getAggregateIsolation()` as a complete save/restore of visibility: it omits models with no isolation and cannot express hidden nodes (`getAggregateHiddenNodes` is a separate documented call).
