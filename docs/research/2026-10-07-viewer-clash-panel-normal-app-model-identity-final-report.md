## 11. Addendum — bounded SVF2 root-cause investigation of the three remaining Clash Finder failures (owner-authorized; read-only)
Scope: establish root cause only; no repo edits, no re-baselining, no legacy fallback, no collision changes. Evidence scripts/data live in the session scratchpad (not committed). Live probes ran on Viewer 7.124.2, Audubon fixtures, SVF2 default; SVF comparisons used a throwaway route override of `viewerOptions.js` in probe pages only.

**Cause 1 — containment pair struct 5750→253 absent under SVF2: the SVF pair is a false positive; SVF2 "no pair" is geometrically correct.** Geometry is identical between formats (world-space Hausdorff ≤ 7e-6 ft; after welding both give flange 1646 v / 2892 tri, roof 68 v / 104 tri; both meshes OPEN in BOTH formats — the earlier "different non-manifold SVF2 mesh" claim is refuted). SVF2 normalizes each mesh to a [-0.5,0.5]³ unit cube and moves scale/rotation into the fragment matrix (SVF matrices are translation-only). `ContainmentQuery.classifyPoint` casts fixed ray directions in the target's LOCAL frame; against an OPEN roof, even-odd parity is undefined (the library tags it `unverified-parity-operand`). SVF local rays all point up (1 crossing → "inside", all 1646 vertices); SVF2's skewed local frame maps them down/horizontal (0 hits → "outside"). World truth: the flange (z 12.084–13.076) sits below the roof (z 12.736–14.378), nearest vertex distance 0.1216 ft, no surface intersection — SVF witness z=12.103 is outside the roof. Diagnostic names (`unverified-open-component` vs `non-manifold-component`) follow the parity outcome, not mesh topology. Fix options: (a) accept SVF2 result and re-baseline the expectation (owner decision; not done); (b) make containment frame-invariant (world/canonical isotropic rays/tolerances) = **collision query-semantics change**; (c) bake matrices into SVF2 geometry at the adapter = breaks Core/Adapter geometry-sharing contract and only moves the false positive. Latent: weld/`surfaceEpsilon`/`mergeDistance` tolerances are in local units → different world tolerances under SVF2 unit-cube frames (up to ≈0.067 ft here; unaffected in this case).

**Cause 2 — 2 × `fragment-not-loaded`: a false-positive diagnostic for geometry-less 2D-symbol fragments, not a load/timing problem.** Arch frags 4600/4601 belong to "Sink-Mop-2D [1603808]" (SVF2 dbId 2082) and "[1309898]" (1154); each element also has a real 3D mesh (frags 904/905, loaded in both formats). SVF: degenerate zero-length LINE geometry (geomId 2055/2056, isLines, 2 vertices, bbox 0×0×0, loaded). SVF2/OTG: the Viewer's OTG translation dropped the zero-length line → geomId 0 (`INVALID_GEOM_ID`), `OtgLoader.tryToActivateFragment` calls `stopLoadingFragment` → flags 0x45 (VISIBLE|HIDE|NOTLOADED), a deliberate final loader decision (unchanged after 30 s / `isLoadDone`). Emitted at `collision/viewer/ViewerModelAdapter.js:244-246` (`fragList.isNotLoaded`) and `clashtest/viewer/populationScan.js:19`; policy "never silently skipped" is binding in `docs/superpowers/specs/m2-extractAllFragments-viewer-evidence.md`, evidenced for SVF non-OTG only. A product-level load wait cannot help. Fix options: (1a) adapter checks `getGeometryId(fragId)===0` first and skips silently (matches SVF); (1b) emit a distinct informational reason (e.g. `fragment-null-geometry`) not counted as "diagnosed"; (2) suite-level tolerance = re-baselining; (3) accept 2 permanent diagnostics on SVF2. **1a/1b change the Adapter's binding diagnostic policy / ClashDiagnostic reason set (protected contract) and require updating the evidence spec for OTG.**

**Cause 3 — Soft clearance 0 pairs (`clearance-anisotropic-scale-unsupported`): real non-uniform scale in SVF2 fragment matrices by construction.** Raised by `collision/query/ClearanceTransform.js:25-71` `validateUniformScale` (tol 1e-4 relative; `collision/constants.js:103`) on the raw `fragList.getWorldMatrix` output (`CollisionWorld.js:2380-2402`); a deliberate design rule (M3 clearance design §3/§5/§9, `collision/README.md:930`). Measured: SVF — every fragment passes (worst dev 8.6e-8); SVF2 — 541/543 Struct and 5432/5435 Arch fragments fail (worst dev 1.97; columns orthogonal, no shear), e.g. dbId 6615/6618 scale (9.708, 0.583, 0.583), 5750 (0.331, 14.79, 0.993), Arch 5428 (124.9, 27.2, 7.56). Cause: SVF2's unit-cube meshes carry the element dimensions in the fragment matrix (SVF2 shares meshes: 416 vs 487 Struct, 1176 vs 2643 Arch); placement/globalOffset/unitScale are identical, so it is not an offset/placement/quantization artifact. Tolerance loosening is not viable (≈4 orders of magnitude). Fix options: (B) bake per-axis scale into per-fragment scaled meshes for clearance (keeps clearance semantics; **changes mesh-identity/extraction-record contracts, digest, memory/cache budgets, placement refresh in `collision/`**); (C) anisotropic clearance in core with conservative pruning (**rewrites M3 semantics**); (D) no change — Soft on legacy SVF only / uniform-scale fixtures.

**Protected-contract verdict (all three): none can be fixed without owner authorization.** Cause 1 → collision query semantics (b) or re-baseline (a); Cause 2 → Adapter diagnostic policy; Cause 3 → collision mesh-identity/clearance contract. No G2/C6/C8 artifact is implicated. No repo file was changed by this investigation. Gates unchanged from §10. **Status: package still not checkpoint-ready; awaiting owner decision per cause.**
