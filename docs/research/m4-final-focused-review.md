## Verdict

BLOCKED

There are **no Critical findings**. The verdict is BLOCKED under the brief's own disposition rule because of **H-1**, which materially prevents *deterministic* implementation planning: the spec gives two mutually exclusive definitions of the one arm S7′'s verdict-deciding comparison rests on, and the plan cannot choose between them without inventing a design decision.

## Summary

**Two of this round's three edits land cleanly.** §7.3 condition 3's residual is now the **longest contiguous** uncovered main-only interval per task, with a correct and well-argued justification (a worker `await` genuinely ends the task, so summing the pieces would overstate post-boundary blocking and could force a spurious no-boundary D). And §19.2's adoption-prerequisites bullet now carries **T-a alongside T-b1/T-b2/T-c**, with condition 3 restating explicitly that it is a *permissive no-boundary exclusion screen* whose pass proves nothing about the boundary a B verdict names. Those two changes close the previous round's two High findings exactly as intended; no surviving section over-reads the screen or omits T-a from the deferral.

**The third edit — naming §7.4.2's operand — does not.** The prior round's Critical was that the effect rule had no operand, so B/C reachability turned on an unstated choice. An operand is now named: **each arm's *maximum* CDP main-thread task duration inside its stage-scoped mark window**. That correctly rejects elapsed time (which would make B/C unreachable by construction, as §7.4.2 itself argues). But it substitutes a **peak-task** statistic for what clause (a)'s own stated purpose describes — "the boundary demonstrably takes main-thread **time away** rather than merely relocating it," a *sum* concept — and it explicitly forbids the sum (X-2's numerator) as an operand. Three defects follow, and they compound:

- **H-1** — §7.4.2 justifies the peak operand by asserting the synchronous arm "runs uninterrupted on the main thread." §17 requires that same arm to run "exactly as the library does today," and the landed library yields cooperatively *inside* both verticals S7′ can select. The two statements cannot both be built. Under §17's reading, the peak operand cannot detect the improvement in the failure mode §6.2 names as the important one, and that is the only failure mode verdict C admits.
- **H-2** — the worker arm's operand and clause 4(b)'s `Hᵢ` are defined as *any* main-thread task inside a window that deliberately contains the `await`. Viewer rendering, the rAF cadence recorder and the 100 ms input probe all run there, and they run there *because* the boundary freed the main thread. The metric therefore charges the boundary's own benefit against it.
- **H-3** — the known M-1 scope gap has been promoted by this round's edit. Clause (a) is now pass/fail, and clause (b)'s `Rᵢ` is *undefined* at a non-failing R1/R2 tuple because condition 3 defines that residual only "in the failing query window."

Independently of the operand cluster, **H-4** records that §17's mechanical vertical-selection rule maps every narrow-phase dominance outcome to the Hard-Clash-precheck vertical without the substage caveat its geometry-side counterpart carries.

On the R1/R2 scrutiny item specifically: this is **no longer only M-1's Medium scope gap**. Promoting clause (a) from a report to a pass/fail claim made the unstated scope verdict-bearing and exposed a genuine blank (`Rᵢ` at a non-failing tuple) and a degenerate case (a warm geometry-preparation comparison, which §8.2 fixes as zero-work). It is now High. It is *not* Critical: the literal universal reading is mechanically executable, and the practical "overhead swamps the gain at R1/R2" worry is weaker than it sounds, because R1/R2 are small only in *source-instance* count — §3.1 shows R2 already touches 1,461 distinct geometries and 1,913 candidate pairs, so the stage workload there is within the same order as the largest verdict-bearing case.

## Findings

### Critical

### High

**H-1 — §7.4.2's named operand is a *peak* task statistic, and its stated justification contradicts §17's definition of the synchronous arm. The contradiction is unresolvable from the text, and the reading §17 mandates makes B and C unreachable in the failure mode the spec's own evidence predicts. (§7.4.2, §7.3 condition 4(a), §17's window note, §7.5.5, §2.1, §3.1, §6.2)**

*The contradiction.* §7.4.2: "For the **synchronous arm** the same method yields that arm's own bracket's main-thread task duration — **in practice its whole bracket, since it runs uninterrupted on the main thread**." §17, of the same arm: "one arm executes the named stage **synchronously on the main thread, exactly as the library does today**." The library does not run either stage uninterrupted. §2.1 fixes cooperative yielding at `frameBudgetMs = 8`, and the landed source puts the checkpoints *inside* both verticals S7′ can select:

- geometry preparation — `GeometryRegistry` checkpoints before each build phase, per geometry (`collision/geometry/GeometryRegistry.js:196-207`), across §3.1's **1,461** distinct geometries;
- narrow phase — per-pair checkpoints (`collision/CollisionWorld.js:1713`, `:1806`), a composed-stage checkpoint (`:423`), and a between-term checkpoint inside the precheck itself (`collision/query/VolumeOverlapQuery.js:145-150`), across §3.1's **1,913–1,978** candidate pairs.

A yield is a `setTimeout(0)` macrotask hop (`collision/scheduler.js:80`), which ends the current renderer task; the continuation is a new task. So the synchronous arm's stage-scoped bracket is tens to hundreds of short tasks whose maximum is bounded near `frameBudgetMs` — §3.1's largest observed checkpoint-bracketed span is 12.2 ms cold and 6.0 ms warm — not one task equal to the bracket. The spec asserts both and never says which semantics S7′'s synchronous arm must have. That choice determines whether condition 4(a) usually passes or usually returns INCONCLUSIVE, so an implementation plan cannot be written without inventing it. This is the specific reason the verdict is BLOCKED.

*Why the contradiction matters, and not just the wording.* Take the reading §17 mandates — the only one under which condition 4's evidence describes today's architecture at all. Then for repetition `i`:

- the synchronous arm's operand ≈ the largest single checkpoint-bounded unit, ~6–12 ms on §3.1's evidence and hard-bounded near 8 ms by construction;
- the worker arm's operand = `Hᵢ`, the largest task among snapshot / extra copy, transfer and serialization, and response receipt and deserialization — for a one-way population of 1,461 geometries' buffers plus serialized BVHs, plausibly *larger* than 12 ms unless the spike yields inside its own snapshot.

§7.4.2's rule then requires the median difference to exceed the noisier arm's IQR **and** a consistent direction in 4 of 5 pairs. With both arms pinned near the same 8 ms granularity, and the worker arm carrying extra work on that side of the boundary, the rule returns INCONCLUSIVE — or an outright regression — for a boundary that genuinely removes ~316 ms (cold geometry preparation) or ~450–518 ms (warm narrow phase) of **total** main-thread work. §7.5.5 converts INCONCLUSIVE into mandatory D.

*Why this bears on verdict reachability.* B condition 1 admits a baseline that fails **T-a, T-b1, T-b2, or T-c**. §3.1's carried-forward evidence — largest bracketed span 12.2 ms cold, 6.0 ms warm, "zero over `frameBudgetMs`" for the distance primitive — makes a T-a failure unlikely and a T-b1/T-b2/T-c-only failure the expected shape. §6.2 says as much in its own words: "a query can consume hundreds of conforming 8 ms tasks, pass the span gate, and still starve Viewer rendering — precisely what the M3-era '6.1 ms vs 8 ms' framing cannot see." In exactly that shape a peak-task operand has no headroom to improve. Verdict **C** is worse off: C *requires* the failure to be in the **warm narrow phase**, which §3.1 shows is composed entirely of sub-8 ms units. This does not make B/C unreachable in every conceivable workload — a genuine >50 ms task would give the operand headroom — which is why this is High and not Critical. But on the evidence the spec itself carries forward, it biases the experiment toward D for reasons that are artifacts of the metric rather than findings about the architecture.

*Why the fix is small.* Clause 4(b) is legitimately peak-based: `Rᵢ + Hᵢ ≤ 50 ms` is charged against T-a, itself a peak threshold, and that construction is sound. It is only clause 4(a) — the "does the boundary help at all" test — whose stated purpose names a sum. The quantity is already being collected: main-thread task time **summed** across the same stage-scoped bracket. It is immune to the elapsed-operand objection §7.4.2 correctly raises, because worker-side execution and the main thread's `await` occupy no main-thread task and contribute zero to it.

*Smallest correction, preserving the current M4 direction:*
1. In §17's window note, state that the synchronous arm executes the stage **through the library's ordinary cooperative checkpoint path**, so both arms reflect today's task topology; delete §7.4.2's "in practice its whole bracket, since it runs uninterrupted on the main thread."
2. In §7.4.2, change the S7′ operand **for clause 4(a) only** from each arm's *maximum* to each arm's **total (summed) boundary-attributable main-thread task time** inside its stage-scoped mark window — see H-2 for why "boundary-attributable" rather than "all tasks in the window" — keeping elapsed (X-3) report-only and leaving clause 4(b), `Hᵢ` and condition 3's screen peak-based. Stop calling the peak statistic "occupancy."
3. Propagate to §7.3 condition 4(a), §17's S7′ Result column, and the two §23 paragraphs ("Decision thresholds", "Required spikes") that repeat "maximum CDP main-thread task duration" verbatim.

**H-2 — the worker arm's operand and clause 4(b)'s `Hᵢ` count *any* main-thread task inside a window that deliberately contains the `await`, so ambient Viewer/rAF/input work — the work the boundary exists to enable — is charged to the boundary as cost. (§7.3 condition 4(b), §7.4.2, §17's window note, §6.1.7, §6.2)**

§17 fixes the worker arm's bracket so that "the snapshot, the transfer, the worker-side execution, the await, and the receipt of the return value are all **inside** the bracket." §7.3 condition 4(b) then defines `Hᵢ` as "the largest CDP main-thread task duration inside the **worker arm's** mark window," and immediately asserts it is "the main-thread cost the boundary *adds*: the input snapshot and any extra copy, the transfer and its serialization, and the response's receipt and deserialization … Worker-side execution and the main thread's `await` occupy no main-thread task, so by construction they contribute nothing."

That "by construction" holds only if the main thread is idle across the `await`, and it is not. §6.1.7 has every observer running for the duration of each measured query, and §6.2 dispatches a trusted `mousemove` "one every 100 ms for the query's duration"; the page also has a loaded federated model whose Viewer rAF loop and renderer keep producing main-thread tasks. Across a worker-arm `await` of a few hundred milliseconds, the window will contain Viewer render tasks, rAF cadence-recorder callbacks and input-handler tasks — none of which the boundary adds. The synchronous arm, being main-thread-saturated, largely crowds those same tasks out. So the contamination is **asymmetric and perverse**: the more successfully the boundary frees the main thread, the more ambient work lands in the worker arm's window, inflating both its 4(a) operand and `Hᵢ`, pushing 4(a) toward INCONCLUSIVE and 4(b) toward `Rᵢ + Hᵢ > 50 ms`. Either forces D on a boundary that worked.

This compounds H-1 rather than duplicating it: fixing the operand's *statistic* without fixing its *attribution* leaves a sum contaminated by the same ambient tasks.

*Smallest correction:* have S7′'s worker arm emit sub-marks around the boundary-owned main-thread chunks — snapshot/extra copy, serialization plus `postMessage`, response receipt plus deserialization — and define both the worker arm's 4(a) operand and `Hᵢ` over **only the CDP tasks overlapping those sub-marks**, explicitly excluding ambient tasks that run while the main thread is otherwise free. Harness-side marks only; no addition to §16.4.

**H-3 — condition 4's clauses (a) and (b) are now pass/fail, but the tuple set they range over is unstated, and clause (b)'s `Rᵢ` is undefined at a non-failing tuple. (§7.3 conditions 3, 4 and 5; §17's S7′ bound; §7.5.5; §8.2)**

Condition 4's lead-in binds S7′ evidence to "**every failing `(case, broadPhase, state)` tuple plus R1 and R2**." Before this round clause (a) was a report; it is now a pass/fail claim, which makes the scope question verdict-bearing. Three concrete gaps:

1. **`Rᵢ` has no definition at a passing R1/R2.** Clause (b) is "`Rᵢ + Hᵢ ≤ 50 ms` for all five repetitions," with `Rᵢ` = "condition 3's main-only-attributed residual maximum at that repetition." Condition 3 defines that residual only for "**the failing query window**." If R1/R2 pass the baseline there is no failing window, so `Rᵢ` is undefined at a tuple the same sentence requires clause (b) to hold at. An implementer must invent one — most plausibly the same computation over R1/R2's own baseline window — and the invented choice can decide the verdict: a *passing* tuple with a 45 ms residual and a 10 ms `Hᵢ` fails clause (b) and, under §7.3's "Requires **all** of," forces D, even though nothing was wrong at that tuple and a real boundary need not be applied there at all.
2. **"plus R1 and R2" carries no state or broad-phase qualifier**, where every other evaluation in §7.2, §7.3 and §17 is per `(case, broadPhase, state)`. If it means every state and the selected vertical is geometry preparation, the *warm* comparison is degenerate — §8.2 fixes WB-1a/WB-1b as "cold-only … the geometry cache already amortizes them to zero warm," so both arms measure a stage that does no work, the effect rule cannot separate them, and §7.5.5 forces D. §6.1.8/§16.2's `NOT EXERCISED` guard is the obvious escape, but the spec never says whether `NOT EXERCISED` at a required condition-4 tuple is a pass, a fail, or an INCONCLUSIVE.
3. **Condition 3 and condition 5 carry the same latent scope question, and the two enumerations of S7′'s evidence set already disagree.** Condition 3 says "the failing query window" (singular) where several failing tuples are possible — resolvable from "Requires all of," but unstated. Condition 5 separately requires S7′ *overhead* to be **measured** at R1/R2, which is redundant if condition 4 already requires a *pass* there; that redundancy is itself evidence that clause (a)'s intended scope is the failing tuples, with R1/R2 present for condition 5's small-query reporting. And §17's bound and §23 both add "plus the largest verdict-bearing workload" to the S7′ set, which condition 4's lead-in omits entirely.

*Smallest correction:* state in condition 4 that clauses (a) and (b) are **pass/fail at the failing `(case, broadPhase, state)` tuples only**; move R1, R2 and the largest verdict-bearing workload wholly under condition 5 as report-only overhead coverage; add that only the states which actually exercise the selected vertical are run (cold for the geometry-preparation vertical; the applicable states for the narrow-phase one); and add one clause to condition 3 saying the screen must pass at **every** failing tuple.

**H-4 — §17's vertical-selection rule maps every narrow-phase dominance outcome to the Hard-Clash-precheck vertical, without the substage caveat its geometry-side counterpart carries. (§17's variant note, §7.3 condition 2, §12.4, §13, §23 open question 6)**

§17 opens the selection rule correctly — "the vertical selected is the one whose stages carry the failing cost" — then instantiates it as: "**Narrow-phase stages dominate** (precheck, exact queries, distance query — WB-2/WB-4): the **warm Hard-Clash-precheck vertical**." All three substages collapse to one arm. On the geometry side §17 is scrupulous about exactly this hazard: "This arm models WB-1b, and on its own proves only WB-1b. A B verdict naming **WB-1a** … additionally requires the worker-side `bvh-construction` sub-stage timed and reported as its own figure." The narrow-phase side has no equivalent sentence, and §7.3 condition 2 reinforces the collapse ("the precheck vertical for a narrow-phase boundary").

The spec itself refuses to assume precheck dominance: §12.4 makes the precheck-vs-geometry-resolution split "the most important stage to understand" and says "**Then, and only then**, evaluate whether a worker boundary should target this stage"; §13 re-measures whether the distance primitive is a worker candidate at all; §23's open question 6 calls the split "the largest single determinant of whether a worker is the right remedy." If M4 measures exact-query or distance-query dominance and still runs the precheck vertical, condition 4's clause (a) is evaluated on a stage that is not where the failing cost is, and a B or C verdict naming WB-2/WB-4 would rest on evidence about a different substage — invalid evidence under §17's own "reporting a geometry-preparation result as evidence for a narrow-phase boundary, or the reverse, is forbidden" principle, which the spec applies across verticals but not within the narrow-phase one.

*Smallest correction:* mirror the WB-1a/WB-1b sentence on the narrow-phase branch — the precheck vertical is selected only when the precheck substage carries the failing cost, and it on its own proves only a precheck-scoped boundary; if a different narrow-phase substage dominates, either a bounded stage-scoped vertical for that substage is run under the same bound, or condition 4 is unmet and the verdict is D for want of matching evidence.

### Medium

**M-1 — §15.3's above-budget exception requires a demonstration the spec elsewhere says M4 structurally cannot make. (§15.3 vs. §7.3 conditions 3, 4 and 6; §17; §19.2)**

§15.3: "a proposal exceeding `1.0 × base` may only be recommended if it **moves a *failing* target metric to *passing*** under §7.4.2's effect rule, a binary precommitted condition." Two problems. §7.4.2's rule does not compute threshold crossing at all — it is a paired median/IQR/sign test on a stage-scoped operand, and after this round it is explicitly bound to the S7′ comparison ("No other comparison is governed by this rule unless some other condition invokes it on a quantity that condition names explicitly"). And "moves a failing target metric to passing" is exactly what §7.3 conditions 3 and 4, §17 and §19.2 now say M4 **cannot** establish for any target metric, T-a included, because it would require the integrated worker path §17 forbids.

Impact is bounded, which is why this is Medium: §7.3 condition 6 independently requires the budget to be *met*, so a proposal above 1.0× fails B regardless and the exception is unreachable rather than dangerous. But it is a live contradiction with the round-4/5 deferral framing and will mislead anyone reading §15 on its own. *Smallest correction:* delete the exception clause, or restate it as "a proposal whose steady-state `delta` exceeds `1.0 × base` fails §7.3 condition 6; there is no exception, because the demonstration that would justify one is an adoption prerequisite (§19.2), not an M4 finding."

**M-2 — two of §6.3's thirteen stages have no attribution mechanism in §16.4's closed list, and §7.5.6 does not say whether that counts as an incomplete partition. (§6.3, §16.4, §16.2, §7.5.6)**

§6.3 marks "Result aggregation, dbId grouping, provenance mapping" and "Lifecycle validation and result publication" as **main-only**, "Instrumented today? No", "Must be attributed" — and §16.2 makes the partition a first-class report section. §16.4's closed list reaches neither: item 2 is narrow-phase interior labels, item 3 is the extraction bracket, item 4 is read-only memory accessors, and item 5's event recorder has a fixed four-value `kind` enum (`clearance-distance-query` | `hard-clash-precheck` | `narrow-phase-pair` | `geometry-resolve`) with a pair-identity payload. Item 6 is "Nothing else."

This is **not** a blocker, for two reasons, which is why it is Medium. No verdict-bearing computation depends on it — condition 3's screen needs only the *transferable* stages covered, and all of those do have hooks. And the permitted toolset (§6.2's CDP/Playwright access) can in principle attribute these two rows from the trace's own JS call-frame profile, harness-side, with no new library hook — so no genuine instrumentation blocker exists and none should be proposed. But the spec never names that mechanism, and §7.5.6 makes "§6.3's partition is incomplete" a **mandatory-D** condition while its "in particular" list enumerates only the three gaps §16.4 items 2 and 3 do close, leaving it unclear whether these two unattributed rows force D on their own. *Smallest correction:* one sentence in §6.3 or §16.4 naming how those two rows are attributed (CDP call-frame profile, or a single lumped "main-only remainder" row computed by subtraction), plus one clause in §7.5.6 confirming its trigger is the three enumerated gaps, not the whole thirteen-row table.
