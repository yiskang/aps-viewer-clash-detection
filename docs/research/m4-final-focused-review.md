## Findings

### Critical

**C-1 — §7.4.2's effect rule has no operand, and the S7′ comparison it gates decides B/C reachability. (§7.4.2, §7.3 condition 4, §7.5.5, §17)**

§7.4.2 specifies the statistic ("the difference of the two arms' **medians** exceeds the **interquartile range of the noisier arm** across its five repetition values" and "the improvement's **direction** is consistent in at least 4 of the 5 paired repetitions") but never states **which measured quantity** supplies those five per-repetition values. §17 records that S7′'s arms are "measured on X-1/X-2/X-3 and on §15's metrics" — a main-thread task timeline plus rAF cadence plus input latency (X-1), a duty cycle (X-2), and elapsed makespan (X-3) — so at least three candidate scalars exist for every comparison, and the spec never chooses.

This is verdict-controlling in both directions:

- **If the operand is elapsed stage cost (X-3),** which is what §17's Result column most directly supports — "The named boundary's own stage-level **cost** — transfer, serialization, and **worker execution** included — against the synchronous stage, under §7.4.2's effect rule" (worker execution can only be "included" in an *elapsed* measure, since by condition 4(b)'s own reasoning it occupies no main-thread task) — then the worker arm executes the same work as the synchronous arm *plus* the snapshot, the transfer and its serialization, the await, and the receipt. It will systematically fail to show an improvement. Under §7.4.2 that is INCONCLUSIVE, and under §7.5.5 INCONCLUSIVE "forces D rather than permitting B or C". Since S7′ only runs when the baseline has already failed the target — i.e. in exactly the situation where B or C is the live question — **B and C become unreachable by construction**, which is precisely what §1.2 exists to prevent and what the prior review's C1 finding already had to fix once.
- **If the operand is X-1's maximum main-thread task within the stage window (or X-2's duty cycle),** the rule is meaningful and B/C are reachable — an offloaded stage genuinely removes main-thread occupancy even when elapsed time grows. This is the reading condition 4(b)'s own `Hᵢ` construction implies, but condition 4(b) is an explicit hard-maximum threshold rule that does **not** route through §7.4.2 at all.
- **If the reference is vestigial** — a third defensible reading, since condition 4's clause (a) merely "establish[es] the worker arm's own real-world cost" (a report, not an improvement claim) and clause (b) has its own self-contained formula — then no S7′ comparison is governed by the effect rule, §7.5.5 never fires for S7′, and B's condition set contains **no requirement that the named boundary measurably helps anything**. Where the baseline failure is T-b1 or T-c only, `Rᵢ + Hᵢ ≤ 50 ms` is satisfied trivially and B would rest on no demonstrated benefit at all.

An implementation plan cannot avoid the choice: the S7′ harness must emit the CONCLUSIVE/INCONCLUSIVE determination that §7.5.5 consumes, and the three readings above give opposite verdicts on the same numbers. This is the one place in the document where the spec's own standard — "Read mechanically", "so two harnesses cannot disagree" — is not met on a verdict-bearing rule.

*Smallest correction (preserves the current direction, no scope change):* in §7.4.2, name the operand explicitly — for the S7′ paired comparison, each repetition's **maximum CDP main-thread task duration inside that arm's stage-scoped mark window** (lower is better), i.e. the same per-repetition scalar condition 4(b) already calls `Hᵢ` for the worker arm; and state that X-2 and X-3 are reported for that comparison but do not gate it unless a condition invokes the effect rule on them by name. One sentence in §7.4.2 plus a matching clause in §17's Result column closes it. (This also makes §7.5.5's trigger determinate: the only effect-rule-governed comparison the verdict depends on is that one.)

### High

**H-1 — condition 3's screen sums *all* uncovered intervals in a task, so a screen failure does not actually prove "no boundary can close the gap". (§7.3 condition 3, §1.1's *no-boundary* D)**

The residual is defined as: "For each CDP main-thread task interval inside the marked window, subtract the portions of that task covered by stages classified **transferable** …; the remainder is that task's main-only-attributed residual", maximised over tasks and repetitions and compared against 50 ms. The remainder of one task is treated as one number. But a real boundary replaces the removed stage with a worker `await`, which ends the current task — so main-only work lying on *both sides* of a transferable stage inside one task would, post-boundary, occupy **two shorter tasks**, each potentially under T-a's 50 ms even when the concatenated residual exceeds it. Condition 3 nevertheless states the absolute claim that "a screen that still fails under it is a genuinely conservative finding that **no** §8.2 boundary … can close the gap. That is exactly what licenses the *no-boundary* **D**", and §1.1 reports that D as a decisive architectural finding rather than a missing prerequisite.

The permissive-classification argument establishes conservatism only along the *classification* axis (which stages count as removable). Along the *topology* axis the screen runs the other way, and the spec's own text in the same paragraph concedes the mechanism — "moving work also changes task boundaries, message handling, yield placement, and frame opportunities" — but uses that concession solely to disclaim T-b1/T-b2/T-c while still asserting strict conservatism for T-a.

I checked how reachable the counterexample is against landed source, because that bounds the severity. `createFrameBudgetAccumulator` (`collision/scheduler.js:68-79`) yields only once `frameBudgetMs = 8` has elapsed, and checkpoints sit between phases and between narrow-phase pairs (`collision/geometry/GeometryRegistry.js:202-210`, `collision/CollisionWorld.js:1712-1713`), so a main-thread task is bounded by roughly 8 ms of accumulated work plus one non-preemptible atomic unit's overrun. That makes the layout narrow but not absent — e.g. a ~7 ms main-only prefix, a short transferable stage, and a 45 ms main-only atomic suffix within one budget window yields a 52 ms concatenated residual (screen fails, forced no-boundary D) where the post-split tasks are 7 ms and 45 ms (both pass T-a). The frequency is unknown and unknowable before the gate runs; the validity of the inference rule is what matters, since it is the sole licence for a decisive negative verdict.

*Smallest correction:* define the residual as the **longest contiguous uncovered interval** remaining in each task rather than the sum of all uncovered intervals — a one-clause change to condition 3's computation that keeps it fully mechanical and still conservative on the classification axis. If that is rejected, weaken condition 3's conclusion to "no boundary can close the gap **for any task whose residual is a single contiguous main-only interval**", and classify the other case as blocked/inconclusive rather than as the decisive no-boundary D.

**H-2 — the screen is permissive with respect to the *named* boundary, and §19.2 omits T-a, so full-query T-a sufficiency for the adopted boundary is never established by anyone. (§7.3 conditions 3 and 4, §19.2)**

Condition 3's pre-registered rule deliberately credits "any stage §6.3 marks as movable under *any* §8.2 variant" — so `compactAndWeld` and warm per-pair geometry resolution are both subtracted regardless of which boundary is later named. That is correct and well-argued *for the exclusion direction* (a failure excludes every variant). But `Rᵢ` therefore is not the main-thread residual the **named** boundary leaves: if B names WB-1a (BVH construction only, §8.2's ~43 ms cold), the screen has already credited the removal of the ~176 ms weld and of warm geometry resolution, neither of which WB-1a moves. Consequently `Rᵢ + Hᵢ ≤ 50 ms` (condition 4(b)) does **not** bound the post-boundary maximum main-thread task for the boundary B actually names.

Nothing downstream recovers this. §19.2's end-to-end bullet enumerates "**full-query T-b1 / T-b2 / T-c sufficiency for the adopted boundary**" and conspicuously omits **T-a**, explaining the omission with "§7.3 condition 3's screen is T-a-only by construction" — which reads as *M4 settled T-a*, when what M4 settled is T-a for the union of all variants, not for the one adopted. A B verdict can therefore be issued, and the boundary later adopted, with no gate anywhere establishing that the adopted boundary meets T-a on a complete query.

*Smallest correction:* (i) add **T-a** to §19.2's end-to-end responsiveness bullet, so it reads "full-query T-a / T-b1 / T-b2 / T-c sufficiency for the adopted boundary, measured end to end on the real (non-stub) integrated worker path"; and (ii) add one sentence to condition 3 stating that the screen is a *permissive no-boundary exclusion screen* and is not a claim of named-boundary T-a sufficiency. (Optionally, and more strongly: have the gate additionally report a **named-boundary residual** computed from only the stages that boundary moves — that costs no new instrumentation, since it is the same subtraction over a smaller stage set, and it would let B assert the stronger §1.2 claim directly.)

### Medium

**M-1 — condition 3's screen and condition 4(b) do not state over *which* tuples they must hold. (§7.3 conditions 3 and 4, §1.1)**

Condition 3 speaks of "the failing query window" in the singular, and §1.1's no-boundary cause likewise says "the main-only remainder alone already fails it". Condition 1, however, permits the baseline to fail "at one or more verdict-bearing R-cases … in **any** measured state", so multiple failing `(case, broadPhase, state)` tuples are the expected case. Whether the screen must pass at *every* failing tuple or at *at least one* is never stated, and the two readings give opposite verdicts (one bad window forcing a decisive no-boundary D, versus B remaining available on the strength of a single clean window). The parallel with condition 4's explicit "at **every** failing `(case, broadPhase, state)` tuple" implies the universal reading, but it is an inference, and the spec's stated bar is that two harnesses cannot disagree.

The same gap has a second face: condition 4 requires S7′ evidence "at every failing tuple **plus R1 and R2**", and clause (b) is computed from `Rᵢ`, "condition 3's main-only-attributed residual maximum at that repetition". Where R1 or R2 are *not* failing tuples, condition 3's screen was never computed for them, so `Rᵢ` has no defined value there and it is unclear whether clause (b) is a pass/fail gate at those tuples at all or whether R1/R2 supply only clause (a)'s small-query overhead figure (which is what condition 5 uses them for).

*Smallest correction:* state in condition 3 that the screen is evaluated per failing tuple and must pass at **every** failing tuple; and in condition 4 that clause (b) is evaluated at every failing tuple, while R1 and R2 supply clause (a)'s overhead evidence only.

**M-2 — §15.3's above-budget exception requires a demonstration the spec elsewhere says M4 cannot make. (§15.3 vs. §7.3 condition 3, §17, §19.2)**

§15.3 replaces "proportionate gain" with a binary rule: "a proposal exceeding `1.0 × base` may only be recommended if it **moves a *failing* target metric to *passing*** under §7.4.2's effect rule, a binary precommitted condition." After this round's S7′ demotion, M4 explicitly cannot produce that demonstration: condition 3 states that "T-b1, T-b2, and T-c sufficiency for the hypothetical post-boundary configuration is … not established by M4 at all", §17 repeats it, and §19.2 makes it an adoption prerequisite. For T-a the nearest available evidence is conditions 3+4's screen arithmetic, which is not an effect-rule comparison and (per H-2) is not a named-boundary bound either. The clause is therefore unsatisfiable as written within M4, so any design above `1.0 × base` fails condition 6 automatically and silently. It does not make B unreachable — a design at or below `1.0 × base` still satisfies condition 6, and §7.5.7 forces D on the unconfirmed multipliers in any case — but it is a residual contradiction left by the demotion, in a section this round's edits did not sweep.

*Smallest correction:* either scope §15.3's exception to the adoption milestone's integrated-path evidence (§19.2), or restate it against exactly the M4-obtainable evidence — conditions 3 and 4's T-a screen after H-2's correction — rather than against "a failing target metric".
