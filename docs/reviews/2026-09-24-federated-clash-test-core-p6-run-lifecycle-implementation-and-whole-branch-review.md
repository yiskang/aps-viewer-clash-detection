## Whole-branch review

After all 8 tasks were individually complete, one final review pass covered the whole phase's diff (`50bfcb5..1eb5af8`, 322 KB, 14 commits) — cross-task consistency, integration correctness only visible with everything present, a holistic re-check of the two governance-level exceptions (H1, the `pairsOverflowLength` fix), and triage of every item the individual task reviews had deferred.

**Findings: 2 Critical, 2 Important, 6 Minor.**

### Critical — C1: sealed provenance missing required schema columns

`provenanceOf` (`clashtest/run/Run.js`) projected only `{modelKey, modelVersion, bindingGeneration, placementGeneration}` per model into `provenance.models[]`. P5's real `ProvenanceModel` schema also requires `scopeKinds`, `elementCount`, and `scopeDigests`. Consequence, reproduced directly: **every normally-sealed Result Set failed P5's own `validateResultSet`**, and `getFreshness()` threw a `TypeError` on it. This was flagged by Task P6.4's own implementer at the time ("Flagging so P6.6/P6.7/P6.8 close it (R21-2)") and then genuinely lost — no later task or ledger entry picked it up, and `test/clashtest/run/lifecycle.test.mjs` was silently filtering these exact issue codes out of its own assertions as "separately tracked." Task P6.7's own freshness tests only ever exercised a hand-built fixture, never an actual engine-sealed set, so the two tasks' pieces were never tested together — precisely how this survived 8 individual task reviews.

**Fixed**: `provenanceOf` now projects the full row from `run.plan.models` (which already carries `scopeKinds`/`scopeDigests` from P3's planner). `elementCount` has no canonical source anywhere in the codebase or spec; it was defined as the count of fragment-owning elements in the planned scope (sum of `rootOwners[].ownerDbIds.length`) — independently confirmed harmless (no current consumer reads `elementCount`: not in any digest, not in freshness/claim/status derivation, not in the result-store identity index), but flagged as needing a one-line spec definition at §13.2 before any future consumer relies on it (recorded below as a spec-gate item, not a P6 defect). Independently re-verified: `validateResultSet` returns zero issues on a real, `realSealing`-produced engine-sealed set, and `getFreshness()` runs correctly end-to-end against real sealed data (including correctly detecting content drift via the sealed `scopeDigests`, not just placement-generation changes — confirmed with a live probe, stronger than what the committed test alone checks).

### Critical — C2: a non-evaluated outcome with an out-of-vocabulary `failure.code` produced a false clean claim

`factsFromOutcome` only turned `outcome.failure.code` into a settlement fact when it was a member of the closed §16.7 Table A vocabulary (`UNIT_FACTS`). P4's real, valid `UNIT_CAUSES` enum (§8.3) also includes `cancelled` and `run-failed`, neither of which is a Table-A fact. An outcome shaped `{outcome:'failed', scopeProof:'equal', failure:{code:'cancelled'}}` was structurally valid, yielded zero facts, was classified U9 (`evaluated`, `merges: true`), and was **silently merged as a clean result** — reproduced directly: `completed`/`coverage:'full'`/`integrity:'clean'`/`freshness:'current'`/`reasons:[]`, and `assessNoClashClaim` returned `allowed:true, unqualified:true` for a unit the executor itself had explicitly reported as failed. This is the same severity class this project treats as blocking (see the `pairsOverflowLength` finding under P6.8 above) — P4's real default `LocalUnitExecutor` never emits these codes, but §7.1 allows any §8.3 cause from a conforming host executor, so it is reachable in production, not just theoretical. Originally flagged as a Minor "forward-note" during Task P6.4's own review and never escalated once its true severity became clear.

**Fixed**: `factsFromOutcome` now has a fail-closed guard — `if (outcome.outcome !== 'evaluated' && facts.length === 0) facts.push('internal-error')`. Independently confirmed correctly scoped (the exact set `UNIT_CAUSES \ Table-A facts` is `{'cancelled','run-failed'}`; every other non-evaluated outcome already carries a legitimate fact, so the guard cannot fire on a genuine `failed`/`skipped`/`discarded` case, and `evaluated` outcomes are never touched). Regression test confirmed RED before / GREEN after; negative controls confirmed unaffected.

### Important — I1: `testIdOfInput` ambiguity across P6/P7

P6 consumes `run.spec.testIdOfInput` as a plain value; P7's own plan describes it as one of P7's "closures" (implying a function). Recorded as a new cross-file need, **C-P7-3**, in the P6 plan file's existing cross-file-needs table, in the same format as C-P7-1/C-P7-2 — P7 must pass this field as a plain value matching what P6 actually consumes.

### Important — I2: `result-unit-invalid` window in `applyUnitResult`

A unit's results were merged into the accumulator before the diagnostic aggregator / statistics accumulator ran; if either threw, the ledger record could be closed while its results were already merged, which `validateResultSet` would reject. **Fixed**: the ledger record and progress counters are now written immediately after the merge, before the diagnostic/statistics calls, closing the window for that specific ordering. A narrower residual (diagnostics/statistics can still hold a partial record after an internal throw between those two calls) is accepted and documented in code as an internal-fault-only residual — that set is always `failed` and never claimable.

### A new residual found while fixing the above (parked, not blocking)

While verifying the C1/C2 fix wave, a further defect was found and reproduced: **every R10 fallback seal that happens after a plan exists** (an ordinary post-plan sealing failure, not just the already-tested broken-plan edge case) **produces a Result Set that fails its own `validateResultSet`** with `coverage-model-mismatch` — `emptyLedgerRecord` unconditionally sets `planExists: true` with `rootOwners: []` once a plan exists, and the cross-field rule requiring `rootOwners` to be non-empty whenever `planExists` is true then fires. This is pre-existing (not introduced by this session's fix wave).

**Ruling: parked, does not block P6.** The runtime guarantee that actually matters today still holds — `done` still settles exactly once, never rejects, and returns a real, resident, `failed`/`unit:internal-error`/`partial` object that can never be claimed clean. What breaks is a *future* read-back guarantee: no runtime path calls `validateResultSet` on a stored set yet (that arrives with Task P7.6's read-through). **Hard deadline: this must be fixed before Task P7.6's read-through lands, or before any AC-11 round-trip acceptance test runs against an R10 set** — recorded here and in the handoff so it cannot be silently missed when P7 starts. Two candidate fixes are already sketched in the fix session's report (emit `planExists: false` for the fallback, after confirming other cross-field rules tolerate it; or carry the real ledger's `rootOwners` into the fallback) — left undecided, since resolving it needs the same cross-field-rule verification discipline this project applies to results-layer changes, and it is now a P7-adjacent carry-forward rather than a live P6 defect.

### Minor findings (Work-review triage list; none block P6)

- `elementCount`'s meaning is an implementer judgment call, harmless to every current consumer — needs a one-line spec §13.2 definition before anyone relies on it.
- A run that snapshots then fails planning now correctly seals `provenance.models: []` (previously produced schema-invalid partial rows) — a correct consequence of the C1 fix, with two harmless side effects: such a run's models no longer populate the result store's `modelKey`→`modelVersion` identity index, and `getFreshness` on such a set is now vacuously `current` rather than throwing (already true of pre-resolution sets; a `failed` set can't be claimed regardless).
- H1's live-binding scan is skipped on early-return validation-failure paths, losing a secondary `unit:model-evicted` reason on those specific units — status/freshness stay correct via the run-level scan; only affects reasons-completeness on an already-failing unit.
- A genuine, pre-existing spec self-contradiction between §7.1 and H7.2/AC-3 about raw-oversized-diagnostics-array handling — P6 fails closed either way; recorded as a spec-gate item, not a P6 defect.
- Raw-array vs. marker-form over-cap pairs produce different ledger record bytes for an equivalent coverage/integrity outcome — AC-3 compliant (identical verdict), just non-identical bytes; informational.
- A handful of stale/inaccurate code comments (including the exact comment that caused C1 to be believed already-owned-elsewhere when it wasn't) and small test-power gaps (an untested precedence interaction, a cosmetic typo, an assertion that overstated what it proved before being renamed) — full list in `.superpowers/sdd/p6-run-lifecycle/progress.md`, carried forward for the independent Work review.
