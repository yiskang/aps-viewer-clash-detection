## C1 — settlement precedence (flagged item 2): the owner decision

**This is flagged item 2, and it is a real contradiction, not a layering choice.** I reached that independently and `codex-advisor high` reached it independently as well, on the same evidence and with the same reading of Table A; it then found a further sub-case I had misjudged.

**What the frozen spec says.** §16.7 is headed *"Settlement precedence (**normative**)"*. Table A part A orders the facts of one attempt: **U1** `world-disposed` → **U2** `internal-error` → **U3** `result-cap` → **U4** `input-changed` → **U5** `scope-drift` → **U6** `model-evicted` → **U7** `scope-unverifiable` → **U8** the gap causes. Part B then derives run status: U1–U3 ⇒ `failed`, U4/U5 ⇒ `invalidated`, resolved **in that order**.

**What the shipped code does.** The post-check returns before the thrown error is classified, so **scope drift always wins**. Three distinct violations follow:

1. **U1–U4 masked by U5.** A `WorldDisposedError` thrown alongside post-check drift settles as `discarded:scope-drift` instead of `failed:world-disposed`, which changes the **externally observable run status from `failed` to `invalidated`**. Same for an unmapped error (U2) and for `ModelPlacementChangedError` with a moved generation (U4, confirmed reproduced by Codex: generations moved `0 → 1`, outcome still `discarded:scope-drift`).
2. **U7 beats every thrown cause.** Post-check `unverifiable` returns before classification too, so it also masks `ModelEvictedError` — but Table A ranks U6 **above** U7.
3. **U6 masks U5 in a multi-participant unit.** The pre-check lease gate returns before any digest runs. Codex reproduced: `mk-a`'s lease dead **and** `mk-b`'s scope changed ⇒ `skipped:model-evicted`, `scopeProof: 'not-checked'`, **zero** digest calls — where Table A wants the observable U5 drift to win. (My own initial reading, that this case was unreachable because a dead binding can only be `unverifiable`, is correct only for a **single**-participant unit; `checkScopeBracket` deliberately processes every scope and lets drift dominate.)

**Why the plan's rationale does not hold.** P4.8 line 1568 justifies drift-first as "the fail-closed direction … because drift invalidates the run (§16.3 item 3) while most thrown causes only gap it". Two problems. First, **§16.3 item 3 does not say that** — read directly, it defines what a `scope-drift` *outcome* does to run status and says nothing about precedence against a thrown failure. Second, the argument inverts for U1–U3: those make the run `failed`, which part B resolves **before** `invalidated`, so masking them with drift is fail-**open**, not fail-closed. The rationale is sound only for the U6–U8 band, where the shipped behaviour is in fact correct.

**Why the implementer's layering defence does not hold.** The defence was that Table A's multi-fact resolution is a P6/ledger concern because `UnitOutcome` has no `secondaryCauses` field. But Table A **part A is the unit outcome** — precisely what P4 produces — and the information P6 would need is **destroyed at the P4 boundary**: once `failure.code` says `scope-drift`, nothing in the closed schema records that a `WorldDisposedError` was thrown. P6 can recover U4 (from `generations.start/end`) and drift (from `scopeProof`), but it cannot reconstruct an arbitrary U2 error, nor the U6/U8 causes drift hides. That P6 owns cancel/dispose is irrelevant — those are part **B** facts, and they do not excuse discarding facts only P4 observed.

**Decisive corroboration from P6's own accepted plan.** While adjudicating this I read `p6-run-lifecycle.md`'s `factsFromOutcome` (~L2518). **P6 already implements a Table A resolver**, and it is written to read *two independent facts off one outcome*:

```js
const scopeFact = SCOPE_PROOF_FACT[outcome.scopeProof];          // drift / unverifiable / null
if (scopeFact !== null) facts.push(scopeFact);
if (outcome.failure !== null && UNIT_FACTS.has(outcome.failure.code)) facts.push(outcome.failure.code);
```

So the accepted division of labour is already exactly the right one — **P4 reports facts, P6 ranks them** — and `scopeProof` is precisely the channel by which drift is meant to reach that resolver *without* consuming `failure.code`. P4's early return collapses the two facts into one before P6 ever sees them, feeding a two-input resolver a single input. That reframes C1 usefully: it is **not** an ambiguity in the division of responsibility, it is P4 failing to supply the input its own accepted consumer is written against. It also means a schema change is probably **not** required for the two-fact case — `failure.code` carries the thrown cause, `scopeProof` carries the drift, and the validator already permits a non-`evaluated` outcome to carry `scopeProof: 'drift'` (only `evaluated` requires `'equal'`, and `finish` already returns empty `pairs`/`diagnostics` for every non-evaluated outcome, so the no-merge rule is untouched).

**Why it was still not fixed here.** Two reasons, both about authority rather than difficulty. First, the repair changes which `outcome`/`failure.code` P4 emits in a whole class of settlements — an externally observable contract — in direct contradiction of the accepted plan's explicit written instruction. Overriding accepted plan text is a milestone-owner call, not an internal-review one, and this repository's `CLAUDE.md` says to persist such a disagreement rather than resolve it unilaterally. Second, a residual genuinely may need a schema decision: when U5 drift legitimately beats a U8 capacity error, Table A still wants that capacity fact retained as a secondary cause, and with `failure.code` spent on `scope-drift` no field can carry it. That residual is small and separable, but it is the owner's to scope.

**Options for the owner (pick one):**

- **(B) Recommended — fact-preserving repair, no schema change.** Stop early-returning: emit the thrown cause in `failure.code` and the bracket answer in `scopeProof`, choose the `outcome` kind per Table A part A, and let P6's existing `factsFromOutcome` resolver rank them. Fixes all three violations and the `failed`-vs-`invalidated` bug, and matches what P6's accepted plan already expects. Record the U5-beats-U8 secondary-cause residual as a known, bounded gap.
- **(A) Full compliance.** (B) plus an owner-approved bounded `secondaryCauses`-style field on `UnitOutcome`, with the reconciliation register and P5/P6/P7 updated. Closes the residual. *Codex's own recommendation, made before it had the `factsFromOutcome` evidence.*
- **(C) Narrow the requirement.** Owner rules Table A part A's multi-fact resolution out of scope for P4 and amends the plan text — which currently cites §16.3 item 3 for something that clause does not say — to state that explicitly. Requires a conscious, recorded exception to a clause the frozen spec marks normative, and leaves P6's resolver under-fed.

Whichever is chosen, the plan's §16.3-item-3 citation at P4.8 line 1568 should be corrected, since it is load-bearing for a claim the cited text does not support. Table-driven tests over every U1–U8 collision (including moved-generation U4 and U6-vs-U7) should come with the fix.

## Disposition of the three flagged items

**1 — duplicate-then-reconciled `LIBRARY_STATISTICS_KEYS`.** *The specific fix is correct and complete; the pattern sweep it implied was not done, and found two more.* `UnitExecutor.js` now imports the frozen list from `diagnostics.js`, no second definition exists anywhere in the phase, and the module-level comment records why `diagnostics.js` is the owner despite the plan's summary table saying otherwise — the right call, since `diagnostics.js` is the module that actually validates a statistics object. But a systematic sweep of every top-level declaration across the three files found the identical producer/validator split twice more (**M3**): `CAPACITY_DETAIL(S)_KEYS` and `MAX_NESTED_STRING_CODE_UNITS`. Both are now fixed the same way. One further duplication (`isFiniteNumber`, verbatim in two files) is left alone deliberately — it is a generic one-line predicate with no invariant riding on it, and an import would add coupling for nothing. A fourth, `isPlainObject`, **differs** between the two files (`diagnostics.js` also accepts a null-prototype object); that asymmetry is defensible — lenient inbound from the untrusted library, strict outbound on the DTO — and is now the only undocumented divergence left, recorded as CF7.

**2 — post-check scope drift vs. a higher-precedence thrown failure.** *A real contradiction with a normative clause of the frozen spec, requiring owner escalation — not a correct layering decision.* The plan's literal instruction is what the implementer followed, but the authority it cites (§16.3 item 3) does not support it, the behaviour changes an externally observable run status from `failed` to `invalidated`, and the boundary is lossy so P6 cannot repair it. The implementer was right that `secondaryCauses` is a ledger-level field; they were wrong that this makes the *primary cause* a ledger-level decision. Full detail and three owner options in the section above. Two further precedence violations in the same region were found while adjudicating it.

**3 — mid-run re-binding / `bindingGeneration` vs `request.snapshot`.** *The implementer was wrong, and so was my own first reading: this is a genuine P4 defect (**H5**), now fixed.* My initial adjudication accepted the implementer's scope argument on the grounds that the information survives the boundary — `outcome.generations.start` carries the live generation and P6 holds `request.snapshot`, so P6 could detect a pre-call re-bind and discard the unit. `codex-advisor` overruled that, and the argument is decisive: **P6 rejecting the outcome afterwards cannot un-issue a `findClashes` call already made against the wrong `Model`.** §16.1's "the engine never re-binds mid-run" constrains the engine's *behaviour*, not merely the data it keeps, and no downstream filter can restore it. Codex reproduced the reload-before-execution case (`evaluated`, one library call, start generation `2` vs the request's `1`).

Nor is either P6-side remedy equivalent. A snapshot-backed `registry` facade would work operationally, but P4's accepted interface explicitly names P1's real live registry and `bindingFor`, and no facade obligation is documented anywhere. Post-hoc generation comparison prevents *merging* but still permits the prohibited call. The architecture as accepted therefore implies a **P4 pre-call guard**, using generations already present on `request.snapshot` — which is what was implemented, folded into the existing §7.4 lease gate exactly as Table A U6 groups the two facts.

Two things fell out of fixing it. First, the same flawed reasoning had also been extended to the **post-call** window, where the information genuinely was *not* preserved (`readGenerations` falls back to the stale binding, hiding the death completely) — that is finding **H2**. Second, the fixture was wrong: `makeRequest` defaulted to `bindingGeneration: 0` while P1's registry assigns `1` on first registration, so the request's run-start generations disagreed with the registry in every single test and nothing noticed, because nothing compared them. Correcting that (and the three explicit snapshot literals in `localExecutor.call.test.mjs`) was necessary evidence, not incidental churn; test F11's second case now pins fixture/registry agreement so it cannot silently drift again.

## Carry-forward (recorded, not fixed — not defects against P4 at its own abstraction level)

1. **CF1 — unbounded `dedupMap` in `createDiagnosticAggregator` (Codex rated High, perf).** `maxRetainedDiagnostics` bounds the **output**; every distinct diagnostic is retained until `snapshot()`. Across many units, memory is not tied to the configured retention limit. **Not fixed:** the shipped code implements the accepted plan exactly ("`snapshot()` sorts the dedup map … truncates to `maxRetainedDiagnostics`"), and a bounded heap would break §12.4's cross-unit de-duplication exactness, since you cannot de-duplicate against entries you evicted. Classify as a **verification/calibration gate**: it is a `RUN_OPTION_CEILINGS` question for the owner, and a sibling of the P3 review's own carried-forward P5 ceiling item.
2. **CF2 — `checkUnit` does not validate `sourceRanges`/`targets` elements or the `cell` enum (Codex rated High).** Real, but it is the **request** side: the producer is P6 building from P3's already-validated plan, not an untrusted executor, and the executor never reads either field (it uses `request.materialized.sourceDbIds`). Adding a closed schema for P3's `WorkUnit` internals here would duplicate P3's own validation — the exact duplicate-ownership pattern this plan family works hard to avoid. Worth an owner/P6 note if the request will really cross a worker boundary.
3. **CF3 — `projectPairs` is an unsliced synchronous loop up to `maxPairsPerOutcome` (Codex rated Medium, perf)** while diagnostics projection uses the deadline-aware slicer. Fixing it makes an **exported, plan-pinned** function async, which is an interface change. Defer to the owner.
4. **CF4 — P6 plan defect, `outcome.kind` does not exist (High if uncorrected).** `p6-run-lifecycle.md` L2524 computes `const phase = outcome.kind === 'skipped' ? 'pre' : …`. P4's `UnitOutcome` has no `kind`; the field is `outcome.outcome`. As written, `phase` can never be `'pre'`, so every pre-call skip would be filed under the wrong settlement phase. Found by `codex-advisor` and verified directly against the plan text. This is exactly the consumer-assumed-wrong-spelling class that P4's own conformance check exists to catch — it simply lives in the consumer's artifact, where P4's greps cannot reach. **Belongs to P6; recorded here because P4 is the producer whose DTO it mis-spells.**
5. **CF5 — P6 obligation, bare `placementGeneration` movement (High if omitted).** §16.3 item 1 and Table A U4 make a placement move at unit completion `discarded:input-changed` **unconditionally**; the shipped executor evaluates `placementGenerationChanged` only inside the thrown branch — which is exactly what the plan's own test table specifies, and is legitimate layering, since `generations.start`/`.end` are both on the outcome. But P6's `factsFromOutcome` derives `input-changed` from `run.placementChangedSince(request.unit)` and **never examines `outcome.generations`**, so the executor-observed move may not reach the resolver at all. P6 must: compare `start` vs `end` per participant; add `input-changed` on any difference; do so before any retry or merge decision; and separately compare unit start against the run snapshot.
6. **CF6 — P6 obligation, pre-call re-binding is now enforced in P4 but P6 should still not assume a live registry.** With **H5** fixed, a reloaded model is refused before the call. P6 should nonetheless be explicit about whether it hands `createLocalUnitExecutor` P1's live registry (the accepted interface) or a snapshot-backed facade, because the guard's correctness depends on `request.snapshot` genuinely carrying the run-start generations.

7. **Withdrawn — strict unknown-statistics rejection is NOT a defect.** I had flagged `projectStatistics` rejecting any key outside `LIBRARY_STATISTICS_KEYS` (which the executor turns into `failed:internal-error`, failing the whole run) as brittleness against a future library counter. `codex-advisor` corrected this against the frozen contract: unknown keys are expressly malformed and **AC-3 requires rejection**. ## Remediation (owner-authorized 2026-09-22, Option B)

The milestone owner selected **Option (B) — fact-preserving repair, no schema change**. `clashtest/execution/LocalUnitExecutor.js` is the only production file changed; `diagnostics.js`, `UnitExecutor.js`, `clashtest/{planning,identity,definition,util}` and the frozen spec are untouched.

**Post-check region (C1 violations 1 and 2).** The two `post.proof` early returns no longer run unconditionally. When the call threw, the error is classified first and the outcome reports **both** facts: `failure.code` is always the classified thrown cause and `scopeProof` is always the true bracket answer. Only the coarse outcome kind is chosen, by comparing §16.7 Table A part A ranks (a small private `TABLE_A_CAUSE_RANK` table plus a `scopeProofRank` entry point, with an explicit U8 default for any unlisted or future cause); a bracket answer that outranks the thrown cause yields `discarded`, otherwise the thrown cause keeps its own kind. When nothing was thrown the behaviour is byte-for-byte what it was.

**Pre-check region (C1 violation 3).** The lease/re-bind gate no longer returns before the bracket.
