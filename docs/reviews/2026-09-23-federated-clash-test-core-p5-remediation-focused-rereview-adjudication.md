### The design (summary)

A new step generator, `provePairExactCoverSteps`, would run last inside the existing `reconcileEvaluatedCoverageSteps`, under the same `coverage:'full' && derivedFull` gate as `coverage-root-uncovered` (never able to reject an honest `partial` set). It reuses the closed-form `|P|` formulas already established by P5-REM7 (ordered: `|A||B|−|C|`; unordered, computed via a symmetric-closure trick: `2αβ−c²−c` where `α=a′+c`, `β=b′+c`). Each evaluated leaf contributes a combinatorial rectangle `S_u × T_u` (its effective source/target root sets, correctly handling whole-model targets and cross-model root-ID namespacing via per-model ranking). The design proposed counting the exact number of distinct covered pairs via a sweep-line/coordinate-compression algorithm, with a cost guard (`R > N ⇒ fail closed`, two new codes `coverage-pair-uncovered`/`coverage-pair-proof-unbounded`) to bound worst-case cost.

### The design review found a blocking issue (R5) — independently confirmed real, but substantially narrower than first reported

The `codex-advisor high` design review accepted four revisions (R1–R4: apply the cost guard before unordered-mode doubling; compute it in BigInt; use a canonical `(model, class, dbId)` root ranking; add explicit memory bounds) and confirmed the core arithmetic, the whole-model/rootless-model/duplicate-row handling, and that no schema change is needed. It found one blocking issue (R5): the cost guard, as designed, can reject a **legitimate, fully-covering layout** — its counterexample was 6 roots per side split into odd/even subsets, covered by 4 leaves (all four odd/even combinations), which trips the guard even though it covers every required pair.

**Independent verification (a dedicated math-focused pass, not trusting the report's framing) found two things the original report did not distinguish:**

1. **Most of the R5 blow-up is an artifact of a fixable design choice, not a fundamental limit.** The report's guard variable (`R0`) is not the sweep algorithm's own event count (which is genuinely O(k log k) in the number of leaves and never blows up) — it's the number of GEOMETRIC rectangles needed to represent each leaf's combinatorial `S_u × T_u` set under one FIXED root ordering. A leaf's set only becomes a single geometric rectangle if its roots are contiguous under that ordering; the specific counterexample's odd/even split is exactly non-contiguous under the report's chosen `(model, class, dbId)` ranking. Independent verification confirmed: under a *data-driven* ranking (e.g. all "odd-class" roots first, then all "even-class" roots — a consecutive-ones-property ordering, computable in linear time via a standard PQ-tree/Booth–Lueker construction, within the same O(N) budget), the exact same counterexample becomes 4 genuinely-geometric rectangles and the standard sweep computes the correct count in O(4 log 4) — no blow-up, no false rejection. This ordering improvement was NOT part of the original design and should be folded into whichever path forward is chosen.
2. **A real, narrower hardness wall remains underneath that fix, independently confirmed sound.** For layouts that lack the consecutive-ones property under ANY root ordering (this can be tested, but the best-ordering search itself is NP-hard when the property fails), independent verification confirmed the task's Orthogonal-Vectors/SETH-hardness reduction is genuinely sound (not a conflation of "compute union size" with "decide arbitrary coverage," as was suspected going in — since `|P|` has a closed form, counting the covered pairs and comparing to `|P|` is equivalent to deciding coverage exactly, so the two problems are not actually different in difficulty here). Under SETH, no exact check can stay far below `|P|` in the absolute worst case for arbitrarily-fragmented, non-conforming layouts. This part of the R5 concern is real and not an artifact.
3. **The counterexample as literally stated is not even a legal layout under the ALREADY-frozen §6.4 rules** (independently confirmed by reading §6.4 directly): §6.4 requires cell-1 sources "packed in ascending dbId order, greedily" with ascending-order target cuts and bisecting splits — the stated odd/even example is cell-1-shaped and would violate that. However, an equivalent counterexample IS constructible inside §6.3's cell-3b "block-triangular substitute," whose only textual constraint is that "the coverage invariants and AC-2 still hold" — it does **not** require the substitute's blocks to be contiguous in dbId order, and independent verification confirmed no shipped check (schema, `unit-range-invalid`, `split-topology-invalid`, the REM5 ownership check, or the REM7 role checks) would reject such a fragmented-but-legal cell-3b layout, and a persisted unit record carries no `cell` field the reader could use to distinguish cell-1 (constrained) from cell-3b (open) even if it wanted to.

**The actual open question is: does the §6.3 cell-3b block-triangular substitute require its blocks to be a contiguous run of the sorted per-class root list, or may they be arbitrary subsets?** This is a much narrower reading question than "is pair-level exact cover achievable at all" — with a "yes, contiguous" reading (below, option e1), the design (plus the ordering fix from point 1 above) has **zero false positives on any legal set**, at a flat, cheap O(N) worst-case cost, and needs no ongoing budget/fallback contract.
