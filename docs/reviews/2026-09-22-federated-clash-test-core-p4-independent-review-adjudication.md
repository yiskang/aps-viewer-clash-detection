## H1 — confirmed, reframed, and one new sub-finding (H1.4)

**The core defect is real.** `classifyLibraryError` (`LocalUnitExecutor.js:145–199`) is given a freshly-rechecked `deadModelKeys` at the post-call classification site (line ~488, `unheldModelKeysOf(request, registry, world)` re-run specifically because a participant may die *during* the call), but consults it at exactly one place: `case 'ModelEvictedError':` (line 162). Both adjudicators independently reproduced the exact byte-for-byte outcome the Work review quotes — evict a participant inside a scripted `findClashes`, throw `CapacityExceededError`, and the death is invisible on every channel of the returned `UnitOutcome` (`failure.modelKeys` absent, `generations.end === generations.start` because `readGenerations` falls back to the stale binding). `p6-run-lifecycle.md`'s `factsFromOutcome` (~L2518-2522) reads only `outcome.scopeProof` and `outcome.failure.code`, confirmed independently by both passes to read nothing else, so the death cannot be reconstructed downstream from the unit outcome alone (Pass B notes P6 *does* have an independent boundary-scan channel — `collectBoundaryFacts`/`sealTimeFreshness` — so run-level `freshness`/`reasons` still see the death; the loss is confined to the unit's own ledger primary cause and `secondaryCauses`, which narrows but does not remove the defect against §16.7).

**Where the Work review overstates the remedy.** Both passes independently falsified, by direct probe against the shipped `validateUnitOutcome`, the review's claim that fixing this *requires* "a bounded canonical fact/secondary-cause field on `UnitOutcome`" (a schema change / freeze exception). `{code:'model-evicted', modelKeys:[...]}` together with an unrelated `scopeProof` value, and even `{code:'model-evicted', errorName:'CapacityExceededError', capacityKind, capacityDetails, modelKeys}`, both validate as `{ok:true, issues:[]}` today. A no-schema-change repair is possible in principle. However, Pass B's `codex-advisor high` consultation refuted the specific "rank-elevate `failure.code` to `model-evicted`" remedy Pass A initially favored, on the grounds that it destroys the U8 thrown cause entirely (trading one loss for another), that it reverses the owner-authorized Option-B contract ("`failure.code` always carries the classified thrown cause; P6 ranks") without new authorization, and that it still cannot carry a third simultaneous fact. The surviving no-schema option — teach `factsFromOutcome` itself to independently detect a death by comparing live bindings against the run snapshot (P6-side, not P4) — was endorsed by both passes as cleaner, but it is still a **coordinated change across the owner-authorized Option-B contract and a P6 interface that has not yet been implemented**, which this repository's `CLAUDE.md` treats as requiring the same authorization tier as C1 did, not a routine internal fix.

**A genuine spec tension neither pass could resolve on its own authority.** Pass B found that spec §16.3 item 1 says a binding death discovered *after the unit has finished* is `discarded:scope-unverifiable` ("the post-check cannot digest a dead binding") — i.e. the spec's own prose routes exactly this case to **U7**, while §16.7 Table A's ranking would put **U6** first if read as a pure priority list. This is the same species of intra-spec tension C1 resolved for a different pair of clauses, and it is the owner's to rule on, not an adjudicator's.

**H1.4 — a new, more severe sibling defect found while verifying H1 (Pass B).** `bindingsStillHeld(resolved, registry, world)` (line 449's argument) is evaluated **synchronously**, then `bracket(...)` is awaited. A participant whose lease dies *during* that await (inside the post-check's own `digestScope` calls) is therefore invisible to the post-check — the same TOCTOU shape as the pre-check race this session already fixed (the `unheldNow` re-check at line ~427), but **never applied to the post-check side**. Reproduced independently: with no thrown error at all, evicting a participant mid-bracket yields `outcome: evaluated`, `scopeProof: equal`, **with pairs merged from the now-dead model** (`mk-b dead at end: true`, `validateUnitOutcome: {ok:true, issues:[]}`). This is worse than fact-loss — it is a live violation of §16.1 "the engine never re-binds mid-run" / §16.3 item 1's fail-closed intent, in the same family as the already-fixed H5, and it passes the closed-schema validator silently. **This was not in the Work review; it surfaced only during adjudication.** Per `CLAUDE.md`, a new finding surfaced during adjudication of a different finding is recorded here, not silently fixed (no production code was touched) and not silently dropped.

## H2 — confirmed; reclassified from implementation defect to interface-reconciliation decision

Both passes independently measured all four cited spans (`projectPairs`, `deriveUnitTaints`, `createDiagnosticAggregator.addUnit`'s unsliced prologue, `createDiagnosticAggregator.snapshot()`) exceeding `frameBudgetMs` on legal cap-shaped input (13–124 ms across both passes' independent timings), and confirmed spec §17.3 requires deadline-aware slicing with no exception for these spans. The material correction both passes converge on: the shipped code is not a bug against the *accepted P4 plan* — the plan's own Phase interface summary (line 61, line 93's sync/async table) and cross-phase reconciliation row **N20** explicitly pin `addUnit` asynchronous and `snapshot()` **synchronous**, and `projectPairs` was never specified as sliced. The internal review already recorded exactly this tension for `projectPairs` as **CF3, deferred to the owner**; both adjudicators independently conclude the same deferral now applies to the other three spans too. Fixing H2 as the Work review's "minimum correction" describes means changing an **exported, cross-phase-consumed interface** (P5/P6 already plan against `snapshot()` being synchronous), which needs owner authorization to reconcile, not a routine code fix.

## H3 — confirmed on facts; disagreement persisted on blocking scope

Both passes independently measured the same shape of defect: `createDiagnosticAggregator`'s `dedupMap` retains every distinct diagnostic for the run's full duration (30.6 MiB / ~200,000 entries in Pass B's measurement, at a configured `maxRetainedDiagnostics` of only 10), with the cap applied only at `snapshot()` time. Both confirm §12.4's exactness requirement and §17.1's memory formula are cited accurately, and both independently conclude the internal review's prior "CF1: calibration question" disposition understated the defect, since no value of `maxRetainedDiagnostics` changes the map's unbounded growth.

**Disagreement:** Pass A calls this an owner-level decision that should be treated as blocking, matching the Work review. Pass B agrees the diagnosis is correct and the fix requires an owner-adjudicated bounded strategy, but argues it should **not** block *P4's own acceptance* — the unboundedness is a direct, unavoidable consequence of §12.4's exactness requirement crossed with an unbudgeted term in §17.1's own memory formula (a spec-internal gap, not a P4-introduced defect), and it is already covered by §17.1's own **R11-7 memory-ceiling calibration gate**, which already forbids freezing these defaults before AC-12 — i.e., the spec already has a named gate for exactly this class of item, of which this is one instance, and it need not additionally block phase acceptance the way a genuine implementation contradiction (H1, H1.4) does.

Per `CLAUDE.md`, this disagreement is persisted rather than resolved unilaterally: **the owner should decide whether H3 blocks P4 acceptance specifically, or is folded into the existing R11-7/G-CAL-class calibration gate as a non-blocking, explicitly-named carry-forward** (which would still need to close before any P6/P7 memory-bound claim, exactly as G-CAL already gates other provisional caps).

2. **H2:** **Deferred, recorded as a bounded carry-forward.** The existing CF3 disposition (already recorded for `projectPairs` alone, in the internal review) is extended to cover all four cited spans (`projectPairs`, `deriveUnitTaints`, `createDiagnosticAggregator.addUnit`'s unsliced prologue, `.snapshot()`). No interface change now; revisit sizing/slicing under the AC-12/G-CAL calibration gate. **No P4 code change.**
3. **H3:** **Non-blocking, folded into the existing §17.1 R11-7 memory-ceiling calibration gate.** Recorded as an explicitly-named item under that gate (the `dedupMap` working-set bound), which must close before any P6/P7 memory-bound claim. Does not block P4 acceptance. **No P4 code change.**

**H1.4 and the two Medium findings (M1, M2) required no owner design input and were fixed and verified in this same pass**, per the adjudication's own conclusion that they are ordinary bounded remediation:

- **H1.4 fixed** (`clashtest/execution/LocalUnitExecutor.js`): the post-check had the identical TOCTOU race the pre-check race fix (earlier this phase) never covered — `bindingsStillHeld(...)` is evaluated synchronously as `bracket(...)`'s argument, but the bracket itself is async and yields internally, so a participant dying *during* the post-check bracket was invisible to it. Fixed by re-checking `bindingsStillHeld` immediately after the bracket resolves; if a participant died during the bracket and the bracket nonetheless answered `equal`, the answer is downgraded to `unverifiable` (never left as a silent `equal` merge). A `drift`/`unverifiable` answer already found during the bracket is untouched. Regression test: `'a lease that dies DURING the post-check bracket settles unverifiable, never equal, and merges nothing (H1.4)'` in `localExecutor.scope.test.mjs` — confirmed to fail against the pre-fix code (reverted in place, re-run, restored) and pass after.
- **M1 fixed** (`clashtest/execution/UnitExecutor.js`): pair-scoped diagnostic operands (`fragments.first`/`.second`) were validated through the same `FRAGMENT_KEYS` as a singular fragment-scope operand, illegally accepting `role`. `checkFragment` now takes an explicit allowed-key set (`FRAGMENT_KEYS` for singular fragments, a new `PAIR_FRAGMENT_KEYS` without `role` for pair operands). Regression test added to the existing AC-3 rejection battery in `unitOutcome.validate.test.mjs`.
- **M2 fixed** (`clashtest/execution/LocalUnitExecutor.js`): `classifyLibraryError` read `error.name`/`.message`/capacity-detail properties and the projection catch read `err.name`/`.message` directly on untrusted thrown/returned values; a hostile getter on any of them escaped the executor's own promise as a raw rejection instead of settling `failed:internal-error`. Fixed with a new `safeGet(obj, key)` guarded reader (mirrors `UnitExecutor.js`'s existing `safeDetail`/`safeThrownMessage`, applied here on the producer side), used at every one of those read sites. Four regression tests added to `localExecutor.errors.test.mjs` (hostile `.name`/`.message`/capacity-detail/`.kind` getters) and one to `localExecutor.call.test.mjs` (a hostile getter surfaced deep inside a malformed library result, reaching the projection catch specifically) — all five confirmed to fail against the pre-fix code and pass after.
