## Area 2 — Phase 0 durable evidence (Task 9)

`main()`'s Phase 0 try/catch, originally covering only 3 of its real steps, now covers the entire Phase 0 sequence from `harnessIntegrity` computation through the dynamic `import('playwright')`, browser/context/page construction, all route/init-script registration, navigation, bootstrap-readiness, and module install. Any failure anywhere in that sequence now calls a new `handlePhase0Failure`, which runs best-effort, individually-timeout-bounded cleanup, finalizes whatever Viewer-script identity evidence was already captured, builds every `checks.F*`/`controls.*` field in the same fail-closed "not reached" shape the harness's own mid-sequence fatal path already uses, computes `overall` through the unchanged, already-reviewed `computeOverall` function (never a hand-set literal), and writes the result through the same atomic write-temp-then-rename mechanism the success path uses. The primary Phase 0 error is always rethrown unchanged; a secondary evidence-write failure is attached as a distinct property, never silently swallowed and never promoted over the primary failure. All error-ledger events (in both the new failure path and — closing an asymmetry a review round found — the pre-existing success path) are now redacted through the same machinery `describeError` already uses elsewhere in this file.

Three `codex-review` rounds progressively found and closed 3 Critical/High-class gaps (the try/catch not actually covering the steps it needed to; a hardcoded failure category; discarded ledger events) plus several smaller issues, leaving 2 Medium findings explicitly disclosed as pre-existing design decisions from earlier (already-accepted) stages, out of this task's own scope: an unconditionally-fatal classification of every `requestfailed` event regardless of whether the resource was essential, and a synchronous bootstrap error only being discovered after a full 30-second timeout rather than immediately. ## Area 3 — six mandatory controls wired through the browser realm (Tasks 10–13, corrected by Task 14)

### The problem this area solves

Six mandatory controls (`tree-unavailable`, `wrong-owner`, `hidden-fragment`, `capacity-breach`, `invalid-bounds`, `bounds-beyond-tolerance`) existed only as Node-side functions that assumed direct, synchronous Node access to live page-realm objects (`modelBefore.fragList.getDbIds = ...`, etc.) — structurally impossible for a real Playwright-driven run, since a live Viewer Model object exists only inside the browser page and cannot be referenced or mutated directly from Node. `buildRealPageDeps`'s real wiring passed `controls: {}` — safe (every control resolved `NOT_EXECUTABLE`, which correctly blocks `PASS`) but incomplete relative to the authorization's own stated goal: "so a future authorized live run can actually reach a valid PASS/FAIL verdict."

### The architecture (Task 10, validated by a `codex-advisor` consult before implementation)

Each control's mutate → detect → restore → verify sequence now runs entirely inside the browser page, via a new shared foundation:

- **A control lease** (`acquireControlLease`/`releaseControlLease`/`recordControlPatch`) — validates session/token/generation identity and mutual exclusion before any control mutates page state, and records exactly what was patched (as a property descriptor) so a fallback restoration path can recover it even if the control's own cleanup never runs.
- **Scratch-artifact isolation** (`createControlScratchSession`/`disposeControlScratchSession`) — for the controls that re-run F1's or F2's own detection logic (`wrong-owner`, `hidden-fragment`, `capacity-breach`, `invalid-bounds`, `bounds-beyond-tolerance`), a temporary session with fresh or selectively-copied artifacts prevents that re-run from corrupting the real, retained F1/F2/F4 results that F5/F7/F8/F6 depend on later in the same run.
- **A two-tier timeout** (`runBridgedControl`) — an inner, in-page timeout races the detection call so the in-page `finally` (restoration) completes before a `TIMED_OUT` result is even constructed, matching the original Node-side functions' own timeout semantics; a separate, longer, outer Node-side watchdog exists only to catch a genuinely hung or crashed page — something no in-page code can help with.
- **A session-taint short-circuit** (`sessionTainted`, in `runControlSafely`/`runHarness`) — if the outer watchdog ever fires (Task 10), or (after Task 14's own fix) a control's own result is `TIMED_OUT`/`RESTORE_FAILED`/executed-but-not-restored, the rest of the phase sequence short-circuits to the same fail-closed placeholder-fill path the harness already uses for a classifier stop, rather than continuing to run further checks/controls against a possibly-still-perturbed model.
- **A cleanup fallback** (`restoreAllControlPatches`, Phase 11) — if a control's own restoration path never ran to completion, this step recovers the recorded patch from its descriptor and verifies restoration via postcondition, closing a gap the original 8-stage implementation had explicitly left as future work.

### Porting the six controls (Tasks 11–12)

Each control's original Node-side implementation remains in the file, unmodified, as the behavioral specification (and, confirmed by the final review, as now-dead reference code no longer called by any real wiring — see "Disclosed, non-blocking items" below). Each was ported into a same-shaped in-page function following the pattern above; two shared in-page helpers (`raceWithInnerTimeout`, `checkSessionLiveness`) were extracted during Task 12 to eliminate duplication Task 11's own review had flagged, and Task 11's three original functions were retrofitted onto them (confirmed behavior-preserving — its own pre-existing test file required zero assertion changes).

### Final integration (Task 13)

All six controls were wired into `main()`'s real dependency object via a new `buildRealControls` factory. A new cross-control staged test drives all six through one real `runHarness` sequence and proves properties no single-control test could: no lease overlap between controls, no leaked scratch sessions, zero net drift in the real session's own retained F1/F2/F4 artifacts across the whole sequence, and (a mid-sequence-taint variant) that a watchdog timeout on one control genuinely aborts every control and check after it. Task 13's own review — the first review to look at all six controls' final, merged state together rather than in per-task subsets — caught and fixed a real bug in already-"approved" Task 11 code (an unguarded property read that could leak a lease and a scratch session under a specific failure shape) that neither Task 11's nor Task 12's own narrower-scoped reviews had re-examined. This is the concrete reason a dedicated final whole-pass review was warranted rather than trusting the accumulation of individually-clean per-task reviews.

### The dedicated final whole-pass review's own finding (Critical to this area's actual purpose)

The final reviewer downloaded and decoded the actual pinned Viewer 7.124.2 bundle (confirmed byte-identical to the harness's own `EXPECTED_VIEWER_SHA256` via SHA-256) and found that `model.fragList` and `model.tree` — bare properties three of the six controls (`wrong-owner`, `hidden-fragment`, `capacity-breach`) patched — **do not exist on the real Model class**. Fragments live in a private field exposed only through `getFragmentList()`; no model class defines a `.tree` property. On any real run, this meant all three controls would always resolve `NOT_EXECUTABLE`, and `computeOverall` could never reach `PASS`. Three prior reviews (Task 11, Task 12, and the controller's own pre-Task-13 investigation) had checked this repo's own *usage convention* by grep, confirming every real-Viewer-tested file consistently avoids the bare properties — a real and informative signal, but not the same check as verifying against the actual Viewer API surface, which the authorization's own "Hidden-fragment" section had explicitly required and which none of those three checks had actually performed.

This has been fixed (Task 14, verified by its own scoped re-review): `wrong-owner` and `capacity-breach` now resolve the fragment list via `model.getFragmentList()`; `hidden-fragment` resolves the tree via `model.getObjectTree()` with an `model.getInstanceTree()` fallback, mirroring `invalid-bounds`'s own already-correct pattern. Each function's own doc comment now records the deviation from the original Node-side functions' bare-property convention, per the authorization's own explicit requirement. The tests that had been masking this bug — fixtures whose `model.fragList` was a different, unpatched object from what `getFragmentList()` returned — were corrected to use one stable object read through the accessor, matching the real production contract (independently confirmed against `ViewerElementEnumerator.js`, `populationScan.js`, and `ViewerModelAdapter.js`).

The same final review also found, and Task 14 also fixed, a related gap: an in-page-only detection timeout or restore failure did not taint the session (only an outer Node-side watchdog timeout did), risking a stale, still-executing detection call touching the live model after a later control had already proceeded — traced by the reviewer to never produce a false `PASS` (every such path already reaches a `computeOverall`-FAIL branch), but a real risk to how trustworthy a live run's own FAIL evidence would be. `runControlSafely` now taints the session on a resolved `TIMED_OUT`/`RESTORE_FAILED`/not-restored outcome too, additive to the pre-existing outer-watchdog trigger.

## Disclosed, non-blocking items (open for owner awareness or a future authorized fix wave)

None of the items below can produce a false `PASS` — every one was independently traced through `computeOverall`'s unchanged precedence at the point it was found, and confirmed to still resolve to a fail-closed outcome.

1. **Generic control-exception doesn't taint the session** (new; found during the Task 14 fix wave's own `codex-review` pass and independently confirmed real by that fix wave's scoped re-review, which judged it the higher-priority of the two new items below). If a control's own restore `finally` block itself throws (for example, the shared liveness-check helper throwing), `fatalErrorObserved` is set — forcing the final verdict to `FAIL` — but `sessionTainted` is not, so a later phase step can still run while a lease may remain held or a patch remain unrestored, via this specific rejected-promise path rather than the resolved-`ControlResult` cases Task 14's own fix already covers.
2. **`bounds-beyond-tolerance`'s combined "perturbation not representable + restore also failed" case is mislabeled** as `NOT_EXECUTABLE{executed:false}` rather than a shape the new taint check can see — the same underlying gap as item 1, specific to this one control's own edge case.
3. **`runCleanup`'s page/context/browser close steps have no bounded timeout** (pre-existing, predates this whole bounded pass — commit `41eeade`), unlike Task 9's own bounded `closeAllBestEffort`, which only covers the Phase 0 failure path. A wedged `page.close()` during ordinary (non-Phase-0) cleanup could still hang indefinitely, which would in turn mean the result file is never written for that run.
4. **The six original Node-side `run*Control` functions (and `runSetupThroughClassification`) are confirmed dead code.** They remain in the file as the historical specification the in-page ports were built from, but are never called by the real wiring — the final review confirmed this and flagged that an earlier `codex-advisor` recommendation to delete them once parity was proven had been adopted in the working ledger but not carried into the actual implementation task briefs. Worth a deliberate decision (delete vs. keep as documented historical reference) rather than continued silent drift.
5. **A Phase 0 evidence-handler edge case**: `handlePhase0Failure` is called without its own `try` — an unexpected throw inside the handler itself (not inside whatever it's handling) could in principle replace the primary Phase 0 error it's meant to report. Assessed by the final reviewer as low-probability.
6. **A scratch session can be leaked (page memory only, no live browser resource)** if a control is abandoned mid-flight via the lease-lost-mid-flight path — the Phase 11 fallback (`restoreAllControlPatches`) covers lease and patch restoration but not this specific scratch-session key.
7. **Accessor-fidelity was resolved for the properties directly implicated (`fragList`/`tree`), but no broader audit of every live-object access pattern across all six controls against the real Viewer API was performed** beyond what H1 required — the final review's own check was targeted at the specific defect it found, not an exhaustive API-surface audit.
