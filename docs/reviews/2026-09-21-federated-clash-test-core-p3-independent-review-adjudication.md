## Corrections and additions to the review's evidence

1. **H1 citations.** AC-18(c) does **not** support H1 (its text is "`plan-too-large` **before any call**" — satisfied; the collision call happens later) and AC-16 is the resident-bound/identity criterion. §6.5.1's "incrementally, before allocation" governs the *counted record classes*, and a CellSpec is not one. The clauses that do support H1 are §6.5.1's `O(roots + owners + unit records)` plan-memory bound together with §17.3.
2. **H1 is broader than stated.** It is not cell-3a-only: `targetsOf` (`decompose.js:55-58`) is re-evaluated per source model inside the cell-1 and cell-2 loops (`:61-73`), an independent O(M²) path that needs **no class C** (1,024 models each with one `A'` and one `B'` root → 1,024 cells carrying 1,048,576 target entries, 272 ms, 317 MiB). The review's minimum correction, applied only to 3a, would miss it.
3. **H1 reachability.** Model count is bounded by `maxEntriesPerSelection` (`options.js:82`, `int(1, 10_000, 1_024)`, an engine limit); `maxPlanReferences` does not bite (M=4,000 uses 8,000 plan records). Default worst case: 1,024 models / 523,776 cells / ~212 MiB / ~300 ms, still ending in a correct `plan-too-large`. The 10,000-model OOM is real but ceiling-only.
4. **H2.** The P3 plan's "Left to implementers" item 2 (`p3-planner.md:2131`) states the plan requires `await checkpoint()` at least once per model and once per cell batch and that the per-slice item count is an implementer choice "until AC-12 measures a cap-sized plan"; the implementation meets that minimum. AC-12(a) itself is the gate and `spanRecorder` is not wired into planning. Against that, frozen §17.3 requires a clock check at least every 64 items; the item-2 text licenses granularity within a seam, not the absence of one. P2 (accepted) and P0 already provide the tools: `assertRootAntichainSliced`/`checkCrossRoleNestingSliced`/`hierarchyInternalCandidatesSliced` and `deepFreezeSliced` (`capture.js:293-301`); `planner.js:87-100` re-implements an unsliced deep freeze.
5. **Verification prose.** The clean-environment full runner is `1,720 / 1,719 pass / 0 fail / 1 todo` (the review's three `listen EPERM` failures are the known sandbox restriction and did not reproduce). One of three aggregate adjudication runs hit the pre-existing flaky `test/query/ContainmentModeQuery.test.mjs` "duct through beam" (passes 10/10 in isolation; `test/query` is untouched by this branch): it does not change any P3 finding but weakens the review's sentence "no product failure appeared outside those environment-bound tests" as a general claim. It is recorded, not adjudicated. The unquoted `node --test test/clashtest/**/*.test.mjs` is the same 594 tests in zsh; under bash without `globstar` it would skip four files.

## Remediation (owner-authorized 2026-09-21: "targeted P3 remediation of all confirmed findings: H1, H2, H3, H4, M1, and L1")

Applied and committed with owner authorization (`fix(clashtest): P3 review remediation …`, see `git log -1`); awaiting a focused independent re-review. Only the six adjudicated findings and their directly affected invariants; no P4 work, no Viewer-adapter work, no G-CAL closure, no frozen-spec change, no P0–P2 file changed, no unrestricted re-review. The owner resolved the adjudication's open question (H3) as: fix the P3 helper-level contradiction only.

**H1 (lazy decomposition; both quadratic paths).** `decompose.js` gains the `decomposeCellsLazy` generator (`decomposeCells` is `[...lazy]` for compatibility); the cell-1/cell-2 target list is built once per cell id and shared read-only (it no longer scales with the number of source models); cell 3a walks only models holding a C table. `sizing.js`: `sizeUnitSteps` generator drives `sizeUnits` (sync) and `sizeUnitsSliced`; `cells` may be any iterable and the generator is released when sizing stops at `limit + 1`. `createPlan` consumes the generator directly (never builds a CellSpec array). Evidence at 1,024 models: class-C → at most `limit + 1` cells pulled and exactly `limit + 1` records (was 523,776 cells); A'/B' → 1,024 retained target entries (was 1,048,576); end-to-end `plan-too-large/unit-record` in ~111 ms / 15 MiB peak (was 254 ms / 211 MiB) and ~91 ms / 24 MiB (was 279 ms / 320 MiB). Output is byte-identical to the previous eager implementation: a verbatim copy of it is kept as an oracle in `decompose.test.mjs` and matches over 250 random universes, ordered and unordered.

**H2 (checkpoint coverage).** New `clashtest/planning/steps.js` (`runSync`/`runSliced` for step generators, the P2 `normalize.js` precedent) so sync and sliced forms share one body; `buildRootTablesSliced` (tick per row and per owner), `sizeUnitsSliced`, `rootOwnerRowsOfSliced`; `createPlan` checkpoints every 64 items inside every size-dependent loop plus per model, per cell batch and per stage; the three `records.reduce` and two filter passes are fused into one sliced pass; the plan is assembled and deep-frozen with a sliced freeze that keeps D10 (`plan.ledger` un-frozen), truly read-only Maps and `structuredClone`d model entries. The ledger tail is now atomic and tight: `ledger.stagePlanned` validates and copies in slices and mutates nothing; `ledger.commitPlanned` is an O(1) swap (0.07–0.14 ms measured at 100k+20k roots, 40,000 units), guarded against structural ledger writes between stage and commit, and is the last statement after the last checkpoint, so a cancellation at any checkpoint leaves `toLedgerRecord()` deep-equal to the pristine ledger.

**H3 (P3 helper level only).** `scopeDigest.js`: population and subtree preprocessing is one generator per record class (`digestPopulation`/`digestSubtree`; new `encodePopulationRecordsSliced`); when a `slicer` is supplied the validate/project pass ticks per record and the sort is P0's `slicer.sortSliced`; the sync path is unchanged in effect. Stable sorts on both paths ⇒ byte-identical digests (checked over 40 randomized inputs with duplicate `fragId`s against a verbatim copy of the previous algorithm). A slicer without `sortSliced` now throws `TypeError`; `digestSubtree` now validates records like population `L` fragments (needed for identical error behaviour on both paths).

**H4.** `validateResolveRootsResult` (explicit scope): `unresolved` must be strictly ascending and unique (`unresolved-not-ascending`, reported once per list; rows already `not-a-dbid` are skipped). `rootResolution.js` additionally canonicalizes each row with `ascendingUnique` defensively (unreachable while the validator rejects duplicates, so no mutation can distinguish it; kept as a belt-and-braces guard). Tests: boundary, conformance helper (a duplicating enumerator is reported, not thrown), production path (`enumeration-failed / invalid-answer`), same missing id in both roles (one row per role), and a `createLedger(...).recordPlanning(...).toLedgerRecord()` round-trip against the strictly-ascending-unique rule P5 pins.

**M1.** `compareScopeExpectation` validates a whole observation (and, beyond the finding, a whole expectation) with the port's own `validateDigestScopeResult` rules before comparing: invalid → `unverifiable / malformed-observation` (expectation: `malformed-expectation`). `unverifiable` still absorbs `equal`, `drift` still dominates. Tests: `{count:'bad',digest:null}`, `{count:-1,digest:'nope'}`, `{kind:'population'}`, non-integer/NaN count, short/uppercase/unprefixed/non-string digests, whole/roots symmetry, and `checkScopeBracket` level.

**L1.** The `elapsed < 500` assertion is removed. The planner test now asserts `plan-too-large`/`unit-record` end to end and, at the sizing seam, `units + gaps === limit + 1` and `exceeded`; a 40-model class-C case proves both the refusal and that the same universe plans with room.
