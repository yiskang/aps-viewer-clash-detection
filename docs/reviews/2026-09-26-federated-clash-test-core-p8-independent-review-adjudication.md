## H1 — where the adjudication disagrees

**Reproduced (agreed):** a base containment result `(100,200)` compared against a next set whose only unit has source roots `[100,200]`, target roots `[100]` and no results yields `resolved: [100→200]`; swapped, `added: [100→200]`. The cited `compare.js:73` is accurate.

**Disagreement 1 — the review's premise is false.** The review (following this project's own internal convergence record, which said so) states that `validateResultSet` does not enforce source/target role disjointness. It does: `validateResultSet.js` ~L883-901 rejects a target root that is also a source root of the same model (`coverage-root-role-invalid`), and a whole-model target on a model with a source-role root. A mutated planner set with an overlapping leaf fails with `coverage-root-role-invalid` (+ `coverage-layout-noncontiguous`); with `definition: null` it fails `pre-resolution-shape-invalid`. **Correction of record:** the "validateResultSet does not enforce it" statement in the internal convergence record's deferred-minor list was inaccurate and is superseded by this document.

**Disagreement 2 — the shape is not planner-reachable.** The real planner (`createPlan` + `planSplit`) was run over five scenarios, including class-C roots present in both selections, both modes, planned and split to the bottom, default and small caps: **580 leaves, 0 same-model source/target overlaps, 0 whole-model targets on a model holding a source-side root.** The only route is a caller handing a **forged raw set** straight to a derivation; derivations deliberately capture but do not run full `validateResultSet` (spec §13.6, R12-3/R19-1). For every engine-produced or validator-accepted set P8's output is correct, so frozen §15.4 is not contradicted.

**Disagreement 3 — the proposed minimum correction would not close it.** Requiring the second root in the unit's target scope still yields false `resolved`/`added` for source `[100,200]` with target `[200]`, `[100,200]`, or whole-model `M` (the library drops target fragments also in the source set, so `100→200` is never evaluated), and the **unordered** (volume-overlap) path has the same result. A predicate that is right per pair: **first ∈ source ∧ second ∈ target ∧ ¬(same model ∧ second ∈ source)**, with ordered semantics requiring the direct orientation and unordered allowing either; source `[100]` against whole-model `M` legitimately proves `(100,200)`.

**Where the review is right:** existing ordered comparison tests use only disjoint single-root units, so nothing pins the forged-overlap behavior; and a caller-visible false clean, even from forged input, is the sensitive direction.

**Adjudicated classification:** Medium, defense-in-depth hardening inside the declared non-validating-derivation trust boundary (the same boundary under which the other forged-raw-set cases — both-`null` definitions, non-numeric evidence — were already left). Not a Critical/High; the gate does not fail because of H1.

Correction should return a **detached copy** that callers use instead of re-reading the caller's object.

## Second owner ruling — M2 depth/resource refinement (2026-09-26) and final remediation state

**Owner rulings:** (1) the former "deeper than 128 accepted, silently matches nothing" behavior is rejected; **depth 64 is approved** as the governing captured-data ceiling for filter operands (spec §5.3 / §13.6, R11-1 — the same data-format ceiling P0 `captureData` and `validateResultSet.js` use); depth ≤ 64 supported, depth > 64 an explicit `InvalidOptionsError`; no silent non-match fallback. (2) The P8 derivation context must **honor the engine's resolved `maxCapturedNodes`** rather than the default 16M; minimum `engine.js` change authorized. (3) **No new operand-specific budget** — the existing `maxCapturedNodes` contract only.

**Bounded evidence check (controller, before any further code change):**
1. *Why a shared sub-object blows up the comparison key:* operand capture kept sharing (a shared sub-object copied once, re-linked), but the comparison key came from P0 `canonicalJson`, which serialises a DAG as a **tree** — a ladder `a_k=[a_{k-1},a_{k-1}]` of N containers expands to 2^N leaves in time and string memory (pre-existing: the old `isJsonValue` also walked tree-wise). `canonicalJson` also throws beyond its own `MAX_CANONICAL_DEPTH=128`; the first pass caught that throw and turned it into the silent non-match.
2. *Worst case for a legal acyclic operand:* unbounded expanded size (~2^(N/2) for N shared containers) — it must be budgeted on **expanded** size.
3. *Governing budget that already exists:* depth ≤ 64 and the node ceiling "charged before the copy is allocated" (spec §5.3/§13.6/R11-1; P0 `captureData` `maxDepth`/`maxNodes`; §17.1 `maxCapturedNodes`, default 16,000,000). P0 `captureData` cannot be used as-is: its `visited` set reports **any** container reached twice as `cyclic`, which would falsely reject a legitimate shared acyclic operand such as `[ref, ref]`.
4. *Smallest implementation:* P8-local refinement of `captureJsonOperand` (`validate.js`) — no schema/spec/public-interface change.

**Implemented (uncommitted working tree on `72497d1`):**
- Explicit depth ceiling 64 (root container = depth 1): deeper ⇒ `InvalidOptionsError` `operand-too-deep`; the silent non-match path is removed.
- Expanded-tree node charging with memoised per-container sizes (saturating), **before** anything is expanded, against **one budget per filter call shared across all clauses** (`in` lists included): over budget ⇒ `InvalidOptionsError` `operand-too-large`. A small shared operand (`[r, r]`, diamond) is accepted and behaves exactly like its expanded copy; a 60-level shared DAG (2^60 expanded) is rejected instantly.
