# M4 Design Spec — Performance / Worker Decision Gate

Status: design/spec only. No implementation, no implementation plan, no worker. Source of truth is landed `main` after the M3 merge (`f941e07`), not older design text where the two differ.

This document defines **how M4 reaches a verdict**, not what the verdict is. M4's product question — *is the current synchronous collision architecture good enough under realistic federated workloads, or is some worker/off-main-thread execution justified?* — is an empirical question this spec deliberately does **not** answer. Its job is to fix the workload matrix, the measurement protocol, the thresholds, the verdict rules, the feasibility analysis, the correctness gates, and the bounded spikes, so that whichever verdict the measurements produce is defensible and reproducible.

M4 is designed as a **pre-registered decision experiment**: the workloads, the metrics, the target, the statistics, and the evidence→verdict mapping are all fixed *before* any measurement is taken, so the verdict is read off the evidence mechanically rather than argued for after the numbers are in.

Landed context reconciled for this spec: `collision/` (`CollisionWorld.js`, `constants.js`, `scheduler.js`, `errors.js`, `index.js`, `blas/`, `tlas/`, `geometry/`, `query/`, `viewer/`), `collision/README.md`, `CHANGELOG.md`, `docs/superpowers/specs/collision-library-roadmap.md`, the finalized M1/M2/M2.1/M3 design specs, `test/performance/run-gate.mjs` + `run-gate-m2.mjs` + `run-gate-m3.mjs` + `browser-probes.mjs` + `checkpoint-recorder.mjs` + `README.md`, `test/acceptance/clash-finder.acceptance.mjs`, `test/CollisionWorld.findClashes.clearance.test.mjs`, the archived gate result JSON under `test/performance/results/`, `wwwroot/index.html` / `server.js` / `scripts/sync-vendor.mjs`, and the pinned `three-mesh-bvh@0.9.14` / `three@0.185.1` source trees in both `node_modules/` and `wwwroot/vendor/`.

## 1. What M4 is, and what M4 is not

**M4 is:** benchmark → evidence → architecture decision. It produces (a) a measurement harness, (b) a set of bounded, disposable spikes, (c) a recorded evidence set, and (d) exactly one of four verdicts.

**M4 is not** (binding, from `collision-library-roadmap.md` §5 and this milestone's own prompt): Federated Clash Test definitions, Selection A / Selection B workflows, persistent clash result sets, Group By / filtering UI, the Viewer Clash Panel, result approval/status workflow, issue-management integration, or model-vs-model orchestration introduced as a side effect of worker research. M4 also does not add UI progress components, and does not define batch-result terminal semantics (reject vs. partial vs. discard) — those belong to the future Federated Clash Test & Results layer.

**M4 does not reopen M1–M3 architecture.** Nothing here changes a public contract named in roadmap §1. Where M4 needs something the library does not expose, it is *instrumentation*, in the same class as M1 Task 23's `setSpanRecorder` — additive, no-op when unused, and enumerated exhaustively in §16.4 so it cannot grow silently.

### 1.1 The four possible verdicts (Required Decision 4)

- **A — Stay synchronous.** No worker. The current architecture meets the declared responsiveness target at every declared realistic scenario.
- **B — Targeted worker boundary is sufficient.** A bounded, **named** execution stage moves off-main-thread while the main thread retains the surrounding query orchestration (§8.2's **B-class** boundaries). A worker-resident cache may exist solely to support that one bounded stage; cache residency alone does not make the design C.
- **C — A broader ownership boundary is required.** No applicable §8.2 **B-class** boundary can satisfy §7.3's conditions, but a named §8.2 **C-class** boundary — one moving a larger query-execution region, and the resident data/cache that region requires — can. C's own predicate requires B's insufficiency as a precondition (§7.3), so B and C are mechanically exclusive: a tuple never satisfies both, and B is never displaced by C where B alone already holds.
- **D — No decision yet / blocked.** Either a prerequisite for a sound decision is missing, or the evidence M4 is permitted to gather itself settles that no verdict of A, B, or C is reachable from it. **D is as much a designed, valid terminal outcome of this pre-registered experiment as A, B, or C are — never a sign that the gate malfunctioned or that the question went unanswered.** In particular, a run where the synchronous baseline fails on frame cadence or input latency while the single 50 ms-anchored, T-a-scoped evidence path M4 is permitted to gather has nothing to say (§7.5.9 below) is an **intentional** D, not a broken decision path: it means M4 cannot justify a worker architecture from the evidence it is permitted to collect, not that a worker architecture is proven useless — the open question is resolved by the next milestone's own end-to-end measurement (§19.2), which is exactly what a D of this kind names as its resolution. §7.5 makes D **mandatory**, not merely available, in **ten** enumerated circumstances. Three of those D outcomes are *findings* rather than missing external inputs, they arise by different mechanisms, and **they must never be conflated**:
  - **The *no-boundary* cause — a decisive negative about the architecture.** The baseline fails the target *and* §7.3 condition 3's screen shows the **main-only remainder alone** already fails it, so A is excluded by the failure and B and C are excluded by condition 3. That D is reported as a finding about the architecture, naming the main-only stages responsible, not as a missing external input; it is forced by §7.3's mapping rather than by §7.5's prerequisite list. It says: *no §8.2 boundary can close the gap.*
  - **The *no-full-query-evidence* cause — a decisive finding about the scope of M4's own evidence, and about nothing else** (§7.5.9). A verdict-bearing `(case, broadPhase, state)` tuple fails the target on **T-b1, T-b2, and/or T-c only**, with **T-a passing** at that tuple. M4's one mechanical, full-query-relevant evidence path — §7.3 condition 4(b)'s `Rᵢ(w,τ) + Hᵢ(w,τ) ≤ 50 ms` check — is tied to T-a's own 50 ms threshold and has **no defined application** where T-a does not fail, and S7′'s evidence is stage-scoped (§17) and structurally cannot supply end-to-end frame-cadence or input-latency sufficiency. M4 therefore cannot determine A vs. B vs. C for that failure shape with the evidence it is permitted to gather, and the tuple's contribution to the decision is **D**. **This is an evidence-scope limitation finding about M4's method — explicitly *not* a claim that no worker boundary would help.** Unlike the *no-boundary* cause it asserts nothing whatever about the architecture and names no stage as responsible. The question it leaves open is answered by the adoption milestone's end-to-end measurement on a real integrated worker path (§19.2), exactly as full correctness parity already is.
  - **The *no-settled-boundary* cause — a finding about the evidence gathered for specific named boundaries (or their absence), distinct from both above** (§7.5.10). A verdict-bearing tuple where T-a *is* among the failing metrics (so §7.5.9 does not apply) and condition 3's boundary-independent screen passes (so the *no-boundary* cause does not apply) can still leave no boundary of either class SUFFICIENT there — because no **B-class** §8.2 boundary is even applicable at that tuple (the exact-query-substage case — C-class boundaries remain separately eligible there, per §7.3's applicability rule, and may still settle the tuple), because an applicable boundary is UNEVALUABLE (no matching §17 vertical, or an unboundable derived-evidence package) rather than affirmatively INSUFFICIENT, or because every applicable boundary of both classes is INSUFFICIENT with nothing else settling the tuple. This D names the specific boundary(ies) left unsettled, or their absence, and what would resolve it — never conflated with the other two causes.

### 1.2 What a B or C verdict does and does not authorize

This distinction is load-bearing; getting it wrong makes B and C mechanically unreachable.

**B and C are *justification* verdicts, not proofs of parity.** They mean: *the synchronous baseline fails the declared responsiveness target at a declared realistic scenario, a named boundary is measurably capable of closing that gap with its own overhead included, and no structural blocker or budget violation stands in the way.* They authorize the **next** milestone to design and build that boundary.

They do **not** assert that a worker implementation is correct. Full correctness parity (§19.2) is a property only a real implementation can have, and §17 forbids M4 from building one. Parity therefore belongs to the **adoption prerequisites** of the implementation milestone, not to M4's own verdict conditions — which is why §7.3's B/C conditions rest on *stage-scoped* evidence from a bounded vertical spike rather than on end-to-end result equality.

Conversely, **A and D are binding on M4's own evidence alone.** A closes the question for now; D names precisely what must be obtained before it can be closed.

## 2. The landed architecture M4 measures

Restating only the facts M4's design depends on, verified against landed source (file:line where load-bearing).

### 2.1 Execution model

- `CollisionWorld` (`collision/CollisionWorld.js:534`) is entirely main-thread. `fromViewer` (`:626`) and `findClashes` (`:1184`) are the **only** async members; every lifecycle/identity method is synchronous and throws synchronously.
- Cooperative scheduling is the checkpoint port (`collision/scheduler.js:151`). `checkpoint({loadEpoch, modelIdHint, label})` returns `undefined` **synchronously** when `frameBudgetMs = 8` has not elapsed, and a Promise (one `setTimeout(0)` macrotask yield, `scheduler.js:80`) when it has. It re-validates lifecycle before, and again after, every real yield.
- **Checkpoints exist between phases, never inside one.** None inside `new MeshBVH(...)` (`blas/ThreeMeshBvhBackend.js:55`), inside `new CollisionInstanceBVH(records)`/`init()` (`tlas/TlasCache.js` has exactly one, before `buildPrimitives`, `:181`), or inside a single `bvhcast` / `closestPointToGeometry` traversal. This is why a single pair can overrun `frameBudgetMs` with no budget able to stop it (a documented M3 limitation).
- `setSpanRecorder(fn)` / `clearSpanRecorder()` / `reportSpan(label, ms)` (`scheduler.js:47-55`) are real **production** instrumentation, no-ops when unset. Their signature is **`(label: string, ms: number)` and nothing else** — §16.4 depends on this being true today.
- **`totalMs` is wall time, not CPU time** (`statistics.totalMs = this._now() - startedAt`, `CollisionWorld.js:1772`, bracketing the whole async operation with its cooperative yields included). §6.2 makes this load-bearing.

### 2.2 Identity and lifecycle

- `loadEpoch` is a global, monotonic, never-reused counter (`:540`), incremented only in `admitModel` (`:697`). A lease is `Object.freeze({model, epoch})`. `_modelLifecycle` is a `WeakMap<Model, …>` keyed by the object (`:538`), transitioning `live → evicted` permanently; `_liveEpochs: Set<epoch>` (`:550`) is the reverse-lookup companion the checkpoint port needs.
- `modelId` is diagnostic-only and never consulted by a correctness path (`:541-542`).
- `CollisionWorld` subscribes to **no** Viewer events. Its only Viewer call is `viewer.impl.getRenderProxy(model, fragId)` (`:2830`). Unload is observed by host extensions, which call `evictModel(event.model)` from `BEFORE_MODEL_UNLOAD_EVENT`.
- `invalidateModelPlacement(model)` **only marks cached placement stale** — it bumps `_placementRevisionByEpoch` and records `_placementInvalidatedAtRevision` (`:752-760`). It does not itself move anything; the re-read of `worldMatrix`/`worldBounds` is lazy, staged, and published atomically in `_refreshPlacementForEpoch` (`:2487`), and forces a TLAS rebuild. **Invalidating without an actual placement change cannot change a clash verdict** — §5.2.1 depends on this.
- **Mid-call placement-revision rejection is path-specific.** `createCompositeCheckpointPort(leases, tlasConsultedEpochs)` (`:1105`) arms revalidation for **exactly the TLAS-consulted epochs**; every `broadPhase:'linear'` call passes none, deliberately, because a linear call never consults `_placementByEpoch` or a cached TLAS and would gain nothing but spurious aborts (`:1095`).
- **Concurrent `findClashes` calls are an existing, handled scenario.** `_getTlasEntryForEpoch`'s supersession branch reasons explicitly about "a DIFFERENT concurrent call" (`:2591-2599`) and resolves it by retrying with fresh state, not by cancelling either call. §10 must not regress this.
- `_placementByEpoch` is **write-once per fragment and historically accumulating** within an epoch (`:2450`, `:2728-2737`).

### 2.3 Cancellation, as it actually exists today

- **No caller-facing cancellation.** `findClashes` accepts no signal, token, or deadline; `collision/index.js` exports none. `AbortController` appears zero times in `collision/`; `AbortSignal` appears once, in prose, at `tlas/TlasCache.js:171-176`, as the codebase's own admission of the gap.
- Two internal hand-rolled deferred-rejection signals (`GeometryRegistry.makeCancellationSignal`, `TlasCache.makeCancellationSignal`) stop *waiting*; they cannot preempt running synchronous work. Their trip conditions are eviction, disposal, or revision supersession — never a caller request.
- The nearest abort token is the **checkpoint port**: a poll-on-checkpoint validator throwing `WorldDisposedError` / `ModelEvictedError` / `ModelPlacementChangedError`.

### 2.4 The three data shapes at the narrow-phase boundary

| Shape | Where | Contents | Cloneable? |
|---|---|---|---|
| `CollisionInstance` | `:854`, cached in `_instanceCache` | `{fragmentId, geometryIdentity:{loadEpoch, geometryIndex}}` — **no geometry, no bvh, no matrix, no dbId** | **Yes**, fully |
| `PlacedInstance` | `makePlaced`, `:51` | `{instance, worldMatrix: Float64Array(16), worldBounds:{min:[3], max:[3]}, ownerDbId}` | **Yes** — `viewer/ViewerModelAdapter.js:28-37` already enforces "only numbers cross the Viewer/collision boundary" |
| narrow-phase `Instance` operand | `toInstance`, `:376` (shape at `:352-360`) | `{geometry: THREE.BufferGeometry, bvh: MeshBVH, localDiagonal, connectivity:{componentCount, componentOf: Int32Array, closedManifold: boolean[]}, closedManifold: boolean, aspectRatioExceeded, matrix: THREE.Matrix4}` | **No** — an object graph, not data |

The third is what every narrow-phase query consumes. Its *backing buffers* are all transferable; the objects wrapping them are not.

### 2.5 Geometry pipeline and where memory accumulates

- `_resolveGeometryView` (`:2809`) → `viewer.impl.getRenderProxy` (`:2830`) → `adaptViewerGeometry`, which returns **live references into the Viewer's own buffers, never copies**, and must be consumed in the same synchronous span with no intervening `await` until collision-owned copies exist (`geometry/createGeometryRegistry.js:28-33`). `compactAndWeld` (`geometry/activeRangeCompaction.js:125`) is that copy step, returning `{position: Float32Array, index: Uint32Array, triangleCount}`. **The Viewer's own buffers can never be transferred; only the collision-owned copies can.**
- `BlasCache` (`blas/BlasCache.js`) **caches nothing** — a 20-line stateless delegation, existing as an injection point for a future multi-backend milestone. The real cache is `GeometryRegistry._epochs: Map<loadEpoch, Map<geometryIndex, Entry>>` (`geometry/GeometryRegistry.js:55`), single-flight per entry, keyed per `(loadEpoch, geometryIndex)`.
- **Eviction is wholesale-per-epoch only.** No LRU, no size cap, no memory-pressure eviction, no TTL. Instance count is capped (`maxCollisionInstancesPerEpoch = 20_000`); **distinct-geometry record count is uncapped** — only each geometry's triangle count is bounded (`maxSyncTriangleCount = 12_000`).
- Each entry retains the welded typed arrays, a `THREE.BufferGeometry` **wrapping** them, the `MeshBVH` built over that geometry, and `connectivity.componentOf: Int32Array(triangleCount)`. **The `BufferGeometry` does not duplicate the welded `position`/`index` buffers**: `ThreeMeshBvhBackend.build` (`:38-40`) passes `weldedGeometry.position`/`.index` straight into `new THREE.Float32BufferAttribute(...)` / `new THREE.Uint32BufferAttribute(...)`, and because both are already typed arrays of the constructor's own element type, `BufferAttribute` stores the **same array reference** rather than copying it (confirmed against the pinned `three@0.185.1` source) — `geometry.attributes.position.array === weldedGeometry.position`, held alive by `geometry.boundsTree = bvh` (`:56`). What genuinely adds memory beyond the one welded copy `compactAndWeld` itself already produces (`geometry/activeRangeCompaction.js:125`) is: the `MeshBVH`'s own internal structures (`_roots`, `_indirectBuffer` — new arrays, not copies of `position`/`index`), the `connectivity.componentOf` array (likewise new), and the `BufferGeometry`/`BufferAttribute`/`MeshBVH` **wrapper objects** themselves (JS object overhead, not buffer duplication). §15.1's Metric M formula already itemizes these correctly — `position.byteLength + index.byteLength + Σᵢ bvh._roots[i].byteLength + indirectBuffer + connectivity...` — and was never computed from a "~2×" narrative multiplier, so this correction changes no figure Metric M produces, only the prose explaining what the main thread holds.
- **No byte-level memory accounting exists in `collision/`.** Zero occurrences of `byteLength`, `performance.memory`, or heap accounting. The only production accessor is `getEpochCollisionInstanceCount(epoch)` (`:770`). `run-gate-m2.mjs:285-310` reaches into private internals and says so.

### 2.6 Existing seams a worker backend would plug into

`BlasCache`'s documented injection point (`blas/BlasCache.js:6-8`); `fromViewer`'s `narrowPhase` / `indexOwnership` reserved options (`:627-640`); `createGeometryRegistry`'s three injectable builders (`geometry/createGeometryRegistry.js:16-22`); the "only numbers cross the boundary" discipline. There is **no** existing worker code: zero `Worker`, `postMessage`, `Transferable`, or `structuredClone` in `collision/`.

## 3. Baseline evidence — carried forward as hypotheses, not conclusions

All figures from an archived gate run on the real 3-discipline federated Audubon fixture (Architecture 5,435 + Structure 543 + Mechanical 1,496 = **7,474 fragments**), **one** source instance (Structure dbId `3076`), whole-model target scope across all three models. **M4 re-measures.**

### 3.1 M3 clearance gate (`test/performance/results/m3-gate-1788864064755.json`, `clearance = 0.05`)

| Quantity | TLAS cold | TLAS warm | Linear cold | Linear warm |
|---|---|---|---|---|
| `totalMs` (**wall time**, yields included) | 2250.6 | 526.7 | 2166.9 | 517.1 |
| `broadPhaseMs` | 4.2 | 1.4 | 2.0 | 1.7 |
| `narrowPhaseMs` | 2238.3 | 517.8 | 2157.7 | 508.2 |
| `clearanceQueryMs` | 58.4 | 55.9 | 57.5 | 57.5 |
| `clearanceQueryMs / totalMs` | 2.6% | 10.6% | 2.7% | 11.1% |

- **Broad phase is 0.19% of wall clock.** TLAS reduces clearance candidates 3.78× (1,978 vs. 7,473) bit-identically, with no measurable end-to-end difference — matching M2's 3.91× / no-wall-clock finding.
- **Narrow phase is ~98%, and the distance primitive is not what dominates it.** Of 1,978 candidates, 1,913 (96.7%) ran the `volumeOverlapQuery` precheck; only 129 (6.5%) reached a `closestPointToGeometry` call. 1,197 dbId pairs were Hard-Clash-excluded; 30 hits returned. **465 of 1,913 prechecks (24.3%) were `inconclusive`.** **The precheck's own duration was never measured** — it is inferred from the remainder around an awaited call (`CollisionWorld.js:2318`), and `classifyHardClashPrecheck` collapses every inconclusive cause into one generic diagnostic (`query/ClearanceHardClashPrecheck.js:29-30`).
- **Worst single `clearance-distance-query` span: 6.10 ms** over 516 samples (p50 0.20, p95 2.0, p99 4.7, zero over `frameBudgetMs`) — the "thin margin" figure the prompt cites.
- **The largest checkpoint-bracketed span is not that one:** 12.2 ms (`composed-narrow-phase-stage`, cold), 10.7 ms (`clearance-narrow-phase-pair`, cold); warm 3.1 ms and 6.0 ms. M3's criterion 6 examined only one label.
- Cold-only build cost from direct brackets: `weld` 1,461 builds / 176.4 ms / 2.8 ms max; `connectivity` 96.4 ms / 2.0 ms max; `bvh-construction` 43.1 ms / 0.7 ms max — **~316 ms** against a cold-minus-warm wall-time delta of **~1,724 ms**. **~1.4 s of the cold delta is unexplained by any existing timer.**
- `narrowPhaseBudgetHeadroom`: 1,978 of `maxClearanceNarrowPhasePairs = 20,000` — **9.89% consumed by one source instance.**

### 3.2 Two things the archived spans cannot be used for

Both documented at `test/performance/README.md:196-315`, and both bind M4's protocol:

1. **Span sums are not CPU time.** A `narrow-phase-pair` span can absorb a separate `GeometryRegistry` port's *yielded* wall-clock; nested and direct-bracket spans overlap the checkpoint-bracketed ones.
2. **A loop's last iteration may go unflushed**, so a genuine 24.8–49 ms violation can be invisible to both the manual bracketing and the longtask observer (which fires only above ~50 ms).

Accordingly M4 does **not** infer a yield tax by subtracting span sums from wall time and does not estimate yield counts; §6.2 measures main-thread task time from an external trace and §16.4 measures yields directly.

### 3.3 M2 Hard Clash gate (`m2-gate-1788758319999.json`), same fixture and source

TLAS cold 1,836.4 / warm 450.5 ms; linear cold 1,858.7 / warm 438.1 ms. `broadPhasePairs` 1,913 vs. 7,473 = 3.91×. Broad phase 0.22% / 0.10% of cold wall clock.

### 3.4 M1 gate, for the worst-span convention

Max labeled span **6.8 ms cold / 1.8 ms warm** against its declared **24.8 ms** ceiling — PASS with margin. §7.1 reuses that ceiling and §7.2 explains why it is a *scheduler-conformance* check, not a user-experience threshold.

### 3.5 The runtime the archived evidence came from is not representative

All three gates launch Chromium with `--no-sandbox --disable-dev-shm-usage --single-process --no-zygote` (`run-gate-m3.mjs:180`). `--single-process` collapses the normal browser/renderer separation. Fine for the historical continuity those gates were written for; **it cannot be the sole basis for a decision about worker execution.** §6.1.5 requires a representative multi-process configuration.

### 3.6 What this evidence does not establish

**Every measurement used exactly one source instance, and none measured Viewer responsiveness at all.**

## 4. Existing conventions and shipped ceilings M4 inherits

| Constant / line | Value | Origin | Status |
|---|---|---|---|
| `frameBudgetMs` | 8 ms | `constants.js:45` | Shipped |
| Worst-case-span ceiling | **24.8 ms** = 8 + 16.8 | M1 spec `:2283-2284`, `:4882-4885` — `frameBudgetMs` plus the *measured* worst non-preemptible atomic unit (a weld at ~19,800 triangles) | Shipped |
| `maxClearanceNarrowPhasePairs` | 20,000 | Upfront preflight on the assembled clearance candidate list (`CollisionWorld.js:2206`) | Provisional |
| `maxBroadPhaseInstancePairs` | 1,000,000 | `broadPhase:'linear'` only, **per target epoch group** (`:1545-1559`) | Provisional |

| `maxCollisionInstancesPerEpoch` | 20,000 | Per-epoch instance ceiling | Provisional |
| `maxSyncTriangleCount` | 12,000 | Per-geometry synchronous-build ceiling | Provisional |

Two are **workload ceilings M4 must respect and report as capability boundaries**:

- **Clearance's executable ceiling.** At the measured density of one dense source instance (1,978 narrow-phase candidates), `maxClearanceNarrowPhasePairs = 20,000` is exhausted at roughly **ten** similarly dense instances, throwing `CapacityExceededError('clearance-narrow-phase-budget')` before any narrow-phase work. Sparse elements produce far fewer candidates, so ten bounds *dense* sources only.
- **The linear oracle's executable ceiling.** `_exceedsBroadPhaseCeiling(sourceExtracted.size, effectiveTargetCount)` is evaluated **once per target epoch group** (`:1545-1559`), with `effectiveTargetCount` reduced by source self-exclusion for the source's own epoch only. On this fixture the binding group is **Architecture at 5,435 fragments**, giving `⌊1,000,000 / 5,435⌋ =` **183 source instances** (strict `>`, so 183 passes and 184 throws) — *not* a cap derived from the 7,474 federated total. This path throws a **plain `Error`**, not `CapacityExceededError`, which the harness must classify correctly.

**A capacity rejection is a measured capability boundary, never a pass.** The gate reports the limit, the observed value, and `CAPACITY_REJECTED`; it may additionally run a reduced set, but must report both and must never silently trim until a case passes.

**M4 retunes none of these constants.**

## 5. Adopted workload matrix (Required Decision 1)

The matrix separates **declared realistic scenarios** — what a verdict is *about* — from **synthetic scale and stress sweeps**, which characterise behaviour and find breaking points and may not on their own force a verdict.

### 5.1 Why source-instance count is a controlled variable, not "the" scaling axis

Cost is driven by at least: extracted **source-fragment** count (not requested `dbId` count); broad-phase candidates per source instance (spatial density × target population); unique geometries and triangle counts (cold cache work); the narrow-phase **outcome mix** (early proven overlap / full negative traversal / inconclusive precheck / distance query), which have very different costs; and cache reuse and output aggregation density.

So source-instance count is swept, but source sets are **stratified into low / typical / high candidate-density cohorts** (§5.4), and every run records: requested dbId count, **extracted source-instance count**, unique geometry count, total triangle count, broad-phase candidate count, narrow-phase candidate count, the four-way outcome mix, and result count. Picking high-count but spatially *sparse* sources is a named loophole (§7.6.1).

Selecting cohorts needs no new library capability: `findClashes` already accepts multiple source `dbIds` (`CollisionWorld.js:1301`). The roadmap forbids implementing selection workflows and model-vs-model orchestration, not benchmarking a fixed dbId list in one invocation.

### 5.2 Declared realistic scenarios (R-cases)

| # | Scenario | Source | Target | Mode | Why realistic |
|---|---|---|---|---|---|
| **R1** | Single-element Hard Clash | Structure dbId `3076` | all 3 models, whole-model | `volume-overlap` | Exactly what the shipped "Find Clashes" action does. Continuity anchor vs. M2. |
| **R2** | Single-element Soft Clash | Structure dbId `3076` | all 3 models, whole-model | `clearance` @ 0.05 | Exactly what the shipped "Find Soft Clashes" action does. Continuity anchor vs. M3. |
| **R3** | Typical-density multi-element Soft Clash | typical cohort, target ~10 **extracted instances** | all 3 models, whole-model | `clearance` @ 0.05 | The nearest thing to a realistic multi-select. **Verdict-bearing only if product-confirmed** (§5.5). |
| **R4** | Typical-density multi-element Hard Clash | the same dbId set as R3 | all 3 models, whole-model | `volume-overlap` | Isolates *mode* from *scale* at identical source and target. Same §5.5 condition. |
| **R5** | Single-model, non-federated | Structure dbId `3076` | Structure only, whole-model | `clearance` @ 0.05 | The non-federated anchor. Against R2 it measures the **combined** effect of restricting the target to Structure — target population, model count, target epoch-group count, and near-source candidate composition all change together, so the R2−R5 delta is **not** a target-population coefficient and does not isolate *federation* from *scale* (§5.7). Pair-normalized figures (`ms / broadPhasePairs`, `ms / narrowPhasePairs`) are reported as descriptive diagnostics only; they do not separate the components after the fact. |
| **R6** | Placement change + refresh | R3's source set | all 3 models, whole-model | `clearance` @ 0.05 | §5.2.1 — the lazy re-read and forced TLAS rebuild, the one path with revision semantics no other case exercises. Same §5.5 condition. |

#### 5.2.1 R6 must actually move a model

`invalidateModelPlacement` **only marks cached placement stale** (`CollisionWorld.js:752-760`); re-reading unchanged Viewer matrices cannot change a clash verdict, so an "invalidate, re-run, expect a different result" design is impossible as stated. R6's adopted sequence mirrors what `test/acceptance/clash-finder.acceptance.mjs` and `test/CollisionWorld.findClashes.clearance.test.mjs:370` already do — mutate placement *first*:

1. Run R3 warm; record the pair set `P₀`.
2. **Capture** the model's current placement transform verbatim — `model.getPlacementTransform()`, or the identity matrix where it returns none — as `T₀`, then apply a **real, reversible** placement transform via `viewer.impl.setPlacementTransform` — a translation chosen and recorded so it demonstrably changes the clearance verdict for at least one pair (e.g. on the order of the measured 0.0417-unit near-miss gap, so a known near-miss crosses the threshold in a known direction). **`T₀` is captured, not assumed to be identity**: the fixture's Architecture model may already carry a placement transform, and restoring identity instead of `T₀` would silently change the fixture between repetitions.

   **The transform is frozen once, before any measured run, by a deterministic calibration pass — it is never chosen adaptively per repetition.** A translation "chosen so it changes at least one verdict" that is re-derived each run is not reproducible: two implementers, or two runs, could pick different axes or magnitudes and produce different pair deltas, and R6's own assertion (`P₁ ≠ P₀` *in the specific pre-recorded way*) would have nothing fixed to compare against. The calibration pass is **unmeasured**, runs once, and fixes all of: the **axis and sign** (the world **+X** axis, positive direction); the **composition order** (`T_moved = Translation(d) × T₀`, pre-multiplied, so the translation is applied in world space regardless of `T₀`); the **magnitude** `d`, found by the smallest step of the sequence `d ∈ {0.02, 0.04, 0.06, 0.10, 0.20}` world units at which the R3 pair set first changes, taking the **first** value that produces a change so the perturbation stays minimal; and the resulting **expected pair delta** — the exact set of pairs entering and leaving — recorded verbatim. Those frozen values are then **reused unchanged across every arm, state, and repetition**, and a run whose observed delta differs from the recorded one is a failure, not a new calibration. If no `d` in the sequence changes the pair set, R6 is reported `NOT EXERCISED` with the sequence tried, rather than the sequence being extended ad hoc.

   **Transform comparison and stabilisation are also fixed**: two placement matrices are equal when every one of their 16 elements agrees within an absolute `1e-9`, and "render stabilisation" means **two consecutive `requestAnimationFrame` turns** observed after the `setPlacementTransform` call before the next query is issued.
3. Call `invalidateModelPlacement(architectureModel)`.
4. Re-run R3; record the pair set `P₁`.
5. **Restore `T₀`** via `setPlacementTransform`, **then call `invalidateModelPlacement(architectureModel)` a second time**, and only then re-confirm `P₀` is recovered. **Both halves are required, and both run in a `finally`.** The fixture's Architecture model is shared by every later case and repetition, so a `CapacityExceededError`, a comparator assertion, or any throw between steps 2 and 5 would otherwise exit with the model still displaced and silently contaminate every subsequent measurement. Restoration, the second invalidation, and a render-stabilisation turn therefore run in a `finally` around steps 2–4; the restored transform is **verified equal to `T₀` before any subsequent tuple begins**, and a restoration that cannot be verified **aborts the entire run** rather than allowing a moved fixture to be measured as if it were the declared one. `CollisionWorld` subscribes to no Viewer events (§2.2), so a `setPlacementTransform` it is not told about changes nothing it has cached: restoring the transform without a second invalidation leaves the moved placement — and, on the TLAS arm, the TLAS built from it — authoritative, and the re-confirm query would return `P₁` again and fail the gate while the library was behaving correctly. This mirrors what `test/acceptance/clash-finder.acceptance.mjs:1138-1155` already does: capture, move, invalidate, restore the **captured** transform, invalidate again.

**Measured:** the cost of the lazy staged refresh plus, on the TLAS arm, the forced TLAS rebuild (`tlasBuildMs`, `tlasBuilds`), on top of the ordinary warm cost. Step 1's two queries are R6's `cold` and `warm` samples; **step 4's re-run is R6's third measured query, the `refresh` state** (§6.1.4's declared exception, §7.2's evaluation unit), and it is verdict-bearing on its own. Step 5's restore-and-re-confirm query is correctness-only and unmeasured.

**Asserted (§19.1), with the rebuild clause stated per arm because the two arms genuinely differ.** `P₁ ≠ P₀` in the specific, pre-recorded way step 2 was designed to produce, **identically under both broad phases** — this part *is* arm-independent, and is the correctness point: both arms must observe the moved placement. A run where `P₁ == P₀` is a **failure**, not a pass — it would mean the refresh did not happen. `P₀` must be recovered after step 5's restore, under both arms. **The TLAS-rebuild count, however, is arm-specific and must not be asserted identically**: `statistics.tlasBuilds` is incremented only inside `_getTlasEntryForEpoch` (`CollisionWorld.js:2636`), which is reached only from `_runTlasBroadPhase` / `_runClearanceTlasBroadPhase` — both guarded by `effectiveBroadPhase === 'tlas'` (`:1691`, `:1781`). A `broadPhase:'linear'` call consults no TLAS and passes no armed epochs at all (`:1339`, and §2.2's path-specific rule), so its `tlasBuilds` is **0** by construction. Therefore: on the **`tlas` arm**, exactly one rebuild attributable to each invalidation (a `tlasBuilds` delta of 1 across step 4, and again across step 5's re-confirm), plus an observed fresh placement read; on the **`linear` arm**, `tlasBuilds` **must be 0** across every R6 query, and correctness rests on the freshly extracted matrices alone. Asserting a delta of 1 on the linear arm would force a conforming harness either to fail `FAILED_VALIDATION` on correct library behavior or to fabricate a rebuild.

### 5.3.1 S2T — construction, control, and what it does not establish

**Why it exists.** §5.1's own cost model names `spatial density × target population` as a driver, but no other case varies total target population: R2 vs. R5 is the only variation and is confounded (§5.2's R5 row), and S2 sweeps source count at one fixed federation. §14 asserts that linear cost scales as `sourceCount × targetCount` while TLAS traversal does not; S2 supplies `sourceCount` and S2T supplies `targetCount`.

**Construction — fixed here so two implementers build the same fixture.**

1. **The facade replaces the Architecture target `Model` identity; it never adds a fourth model.** `_modelLifecycle` is a `WeakMap` keyed by the `Model` object and `loadEpoch` is assigned per admitted model (§2.2), so admitting a facade *alongside* the real Architecture model would create a fourth target epoch group — the exact confound that makes R2 vs. R5 uninterpretable, and the one §4's per-target-epoch-group linear ceiling keys on. The invariant is: **one Architecture-equivalent `Model` object and one target epoch group per run**, at every level. The real Architecture model stays loaded in the Viewer and is the geometry source the facade delegates to.
2. **The facade is test-local and adds no library seam.** It lives in the harness, not in `collision/`, and requires **no** addition to §16.4's closed instrumentation list. It supplies the Viewer surface §8.5 names — instance-tree readiness and enumeration, `getFragmentList`, `getCount`, `isNotLoaded`, `getDbIds`, `getGeometryId`, `getWorldMatrix`, `getWorldBounds` — and **delegates `getUnitScale` to the real model**, because it controls the welding epsilon. A test-local `getRenderProxy` adapter maps (facade, real fragment id) back to the real Architecture model: `getRenderProxy` is never called for a bystander, but it **is** called for every real near-cohort candidate through the facade object, so the translation is required, not optional.
3. **Synthetic fragments are appended contiguously after the real Architecture range**, because whole-model extraction iterates a dense fragment range. **Synthetic geometry ids occupy a disjoint range above the real model's measured maximum** — representative-fragment selection is first-discovery-wins, so a geometry-id collision could make a real candidate resolve through a synthetic fragment, which is a silent correctness corruption rather than a measurement error.
4. **Bystander layout is deterministic, dispersed, nested, and recorded verbatim.** Every bystander AABB lies outside the source's query region at every level. Placing them all at one identical far AABB is forbidden — it is a degenerate BVH artifact, not a population. Each larger level retains the exact prefix of the smaller levels, so levels are nested rather than independently generated.
5. **The baseline level runs through the facade too**, with zero bystanders, so facade overhead is a constant across levels rather than a step between the baseline and the rest.
6. **One fresh `CollisionWorld` per `(runtime, case, level, broadPhase, repetition)`** (§6.1.4). **Population is never grown inside a live world** — that would bump the placement revision and force TLAS rebuilds, measuring revision churn instead of population scaling.

**Both broad phases are mandatory, and their responses are expected to differ. That divergence is the evidence, not a parity failure.** Under `broadPhase:'linear'` every non-self pair is counted before the AABB predicate is applied, so `broadPhasePairs` necessarily grows roughly linearly with total target population, distant bystanders included. Under `broadPhase:'tlas'` the traversal reaches only primitives whose own AABBs overlap the query box, so the **exact** candidate count stays flat while raw leaf expansion and build cost may still move (below). **This is exactly the `sourceCount × targetCount` contrast §14 predicts, and §6.4's comparator is already written for it**: the statistics it requires to be equal are `clearanceExactAabbSurvivors`, `narrowPhasePairs`, `clearanceOverlapPrechecksRun`, `clearanceHardClashExclusions`, `clearanceDistanceQueriesRun`, and `clearanceHits` — **`broadPhasePairs` is deliberately not among them**. A future reader must not "repair" the divergence, and must not weaken or skip the linear arm to obtain matching counts (§14).

**The mechanical level-to-level control rule.** S2T's result is interpretable **only if all of the following hold across all four population levels**, evaluated on existing observables with no new instrumentation:

- `clearanceExactAabbSurvivors` is **identical in count and identical as a pair set** — counts alone are insufficient, since one lost real near-pair plus one unintended bystander pair would leave the count unchanged;
- `narrowPhasePairs` is **identical in count**;
- the **four-way outcome mix** (early proven overlap / full negative traversal / inconclusive precheck / distance query, §5.1) is **identical count-for-count in every category**;
- the final **pair set, distances, and witnesses** are identical, by §6.4's field rules;
- **no synthetic bystander fragment id appears** in any survivor, candidate, result, or diagnostic record, at any level;
- **zero `getRenderProxy` calls and zero geometry-resolve events are attributed to synthetic fragment ids**, at any level.

These are exact equalities, not approximate ones: the source and near-source cohort are fixed and the bystanders are constructed disjoint from the query region, so any drift is a construction defect. **A violation invalidates the S2T characterization result for that run and nothing else** — it never changes the gate's A/B/C/D outcome, never sets `FAILED_VALIDATION`, and never fails the process (§16.2). The violated condition and the offending level are reported by name.

**What S2T measures.** What is expected to move: TLAS construction — the one-checkpoint, non-preemptible atomic unit (§2.1) — TLAS traversal, the linear scan, collision-side admission, `PlacedInstance` construction and placement recording, checkpoint and yield counts, and Metric M's placement, instance, and TLAS terms (§15). Reported alongside, as consequences rather than controls: TLAS structural quality (tree depth, partitioning, which real instances share leaves, raw leaf expansion, build duration), which distant bystanders can reshape even while the **exact** candidate set is unchanged — "flat" above always means exact candidates, never raw leaf expansion.

**Cost attribution is three-way, and must be reported as such.** *Facade-specific*: time inside the delegated or synthetic Viewer accessors. *Real library work over synthetic records*: extraction loops, checkpoints, record allocation and freezing, placement recording, instance admission, TLAS build and traversal, the linear scan, and Metric M — all genuine library cost. *Not representative*: real Viewer metadata-access behavior for synthetic fragments. Yields are time-driven, so facade accessor speed influences yield frequency; yield figures at S2T are reported as hybrid-workload behavior and never as real-Viewer extraction performance.

**Named non-conclusions — S2T must never be cited for these.** Far bystanders never become narrow-phase candidates, and geometry resolution is lazy and candidate-gated (§2.4, §2.5, §6.3), so a bystander never reaches `GeometryRegistry.getOrBuildGeometry`. **S2T therefore exercises no BLAS construction, no welding, no connectivity analysis, and no `GeometryRegistry` cache growth whatsoever**, under any choice of bystander geometry — whether one geometry repeated N times or N distinct ones, which is why that choice is left open. S2T is **not** evidence about unique-geometry scaling, cold-cache work, or the ~1.4 s unattributed cold extraction cost (§3.1). Nor does it establish real-federation-growth behavior: real growth interleaves geometry and adds candidates, which S2T deliberately does not (§5.7). Its top level builds the largest TLAS the shipped constants permit, and that build span is reported against §7.1's bands as the observed boundary **for the recorded layout only** — build cost depends on spatial distribution, so it bounds no other distribution.

**Capacity behavior.** `maxCollisionInstancesPerEpoch = 20,000` (§4) is the per-epoch admission ceiling, so the top level fills the Architecture epoch exactly to it and is expected to execute. Probing above the cap is expected to return `CAPACITY_REJECTED`, which is this case's **measured capability boundary** in §4's sense, reported with the limit and the observed value. **It does not activate §7.5.3**, whose condition is that *the workloads the decision turns on* could not be executed: no verdict depends on executing a synthetic population level, and S2T is characterization-only.

### 5.4 Cohort construction — the exact, deterministic algorithm

**Profiling pass** (cheap, unmeasured, touching **no** `collision/` narrow phase — the public API exposes no broad-phase-only operation, so this must not be built out of `findClashes`). For every Structure `dbId` owning at least one fragment, compute in-page using only Viewer APIs:

- `instances(dbId)` = the count of **first-discovered** fragment ids produced by walking `dbId`'s subtree the same way `extractFragments` does (`viewer/ViewerModelAdapter.js:100-153`): a depth-first stack walk starting at `dbId`, calling `InstanceTree.enumNodeFragments(node, cb, false)` at **every visited node** — not `dbId` alone — and `InstanceTree.enumNodeChildren` to descend, with first-discovery-wins deduplication matching `extractFragments`'s own rule. **A single non-recursive `enumNodeFragments(dbId, cb, false)` call at the root undercounts any `dbId` with descendant fragments** and computes density over a different population than `findClashes` actually extracts, which is exactly the population §5.1's cost model and every downstream cohort-size claim (~10/~50/~100/~183 **extracted instances**) is stated in terms of. This duplicates `extractFragments`'s walk shape rather than calling it, because the profiling pass must touch no `collision/` narrow phase and the public API exposes no broad-phase-only operation to reuse (this section's opening constraint); it is not itself subject to `maxFragmentsPerDbId` or `maxChildrenPerNode` rejection, since profiling characterises density and is never itself a `findClashes` call;
- `proximity(dbId)` = the number of `(sourceFragment, targetFragment)` pairs across all three models whose world AABBs, read from each model's own `fragList.getWorldBounds`, are within `0.05` world units of each other, by a plain nested scan **over the identical, correctly-walked fragment set `instances(dbId)` above produces** — never the flat, non-recursive set the earlier definition would have scanned;
- `density(dbId)` = `proximity(dbId) / instances(dbId)` — the **per-instance** figure, and the one cohorts are stratified on.

`proximity` is a **Viewer-side proxy** for candidate density — deliberately not the collision library's own candidate count, which would require running the very queries the cohorts configure. The report states it is a proxy and records `proximity`, `density`, and the measured `broadPhasePairs` per run, so its fidelity is visible.

**Why stratification is on `density`, not on raw `proximity`.** `proximity` is a raw pair *count* summed over all of a dbId's fragments, so it rises with instance count as well as with spatial density: a dbId owning many fragments ranks high on `proximity` merely by owning them. Ranking on it would stratify **work**, not density, and would fold source-instance count — the very variable S2 sweeps — back into the factor S2 stratifies by. `density` is the per-instance normalisation that separates the two. Raw `proximity` remains recorded because it is the quantity whose fidelity against the measured `broadPhasePairs` the report checks.

**Cohort selection** for a required cohort size `k` (in extracted instances):

1. Rank all dbIds by ascending `density`; ties broken by ascending `dbId`. Call the ranked list `L`, `n = |L|`.
2. For quantile `q ∈ {0.25 (low), 0.50 (typical), 0.90 (high)}`, take the **nearest-rank index** `i_q = min(n − 1, max(0, ⌈q·n⌉ − 1))` (0-based).
3. The **band** is the contiguous window of `L` centred on `i_q` of width `w = max(3k, 25)` entries, clipped to `L` and, when clipped at one end, extended at the other to preserve `w` where possible. If `n < w` the band is all of `L`, and this is recorded. **Because `w` grows with `k`, the band widens as S2's levels rise, and the three cohorts converge; at `n < w` they are drawn from an identical band and the density factor is gone.** This is not hypothetical at S2's top level: `k ≈ 183` gives `w = 549`, and Structure holds 543 fragments in total (§3), so `n ≤ 543 < w` and the band **is** all of `L` there. The achieved-separation rule below turns that into an explicit label rather than a silent degeneracy.
4. Walk the band in ascending `dbId` order, accumulating dbIds into the cohort's requested set. **The cumulative count against which `k` is checked is not the naive sum of each accumulated dbId's own `instances(dbId)`** — that would double-count any fragment reachable from more than one accumulated dbId's subtree. It is instead the size of **one shared, first-discovery-wins fragment set accumulated across every dbId walked so far in this band**, built by the identical rule `instances(dbId)` itself uses (§5.4's opening bullet) but applied once, cumulatively, across the whole accumulated set — mirroring `extractFragments`'s own whole-call dedup, whose `results` map is "unique across the WHOLE call" (`viewer/ViewerModelAdapter.js:62,73`) rather than per-requested-dbId. This keeps the achieved count in step 4 identical to what the eventual multi-dbId `findClashes` call on this cohort will actually extract, whether or not the walked dbIds' subtrees overlap. Continue walking until this shared count first reaches or exceeds `k`. Record requested dbIds and the achieved (deduplicated) instance count — never the sum of independent per-dbId counts.
5. **`3076` is forced into the high cohort**, so that S2's high-cohort arms strictly contain R1/R2's single-element source and the high-cohort count sweep is anchored on it. It replaces the band member whose `density` is closest to `3076`'s, ties broken by ascending `dbId`, and the replacement is recorded explicitly, together with `3076`'s own `density` and its rank in `L` — because under `density` ranking `3076` need not fall in the high band on its own, and a forced member far from the band's own density weakens the high cohort's definition. **This rule reaches S2's high-cohort arms and nothing else.** It does **not** make R3/R4/R6 contain R1/R2: those cases use the **typical** cohort (§5.2), so no R-case comparison is a containment, and R2→R3 and R1→R4 each move source count and cohort density together (§5.4's closing rule requires both to be reported so the two are not read as one effect).
6. If a band cannot reach `k` instances even after widening to all of `L`, the case is recorded `NOT EXERCISED` with the achieved count — never silently run at a smaller size.

**Achieved separation is reported, and asserted, per level — never assumed.** For every `k`, the harness records each cohort's selected dbId list and its achieved cohort-weighted density `Σproximity / Σinstances` (the weighted figure, not the mean of per-dbId `density` values, which would overweight single-fragment dbIds) — where, exactly as step 4 already requires, `Σinstances` is the size of the cohort's one shared, first-discovery-wins fragment set, never the naive per-dbId sum. A level is labelled **`DENSITY_UNSTRATIFIED`** whenever the achieved results show the stratification is gone — identical or near-identical selected sets across cohorts, equal achieved weighted density, or loss of the `low < typical < high` ordering. **The label is decided on achieved results, never on band overlap alone**, since overlapping bands can still yield separated selections. A `DENSITY_UNSTRATIFIED` level is reported as a **source-count-only** arm: its three nominal cohorts are not density contrasts, and no finding at that level may be attributed to density. §5.3's S2 row and §23's open question 8 both depend on this label being present.

Every parameter (`q`, `w`, ranking metric, tie rule, replacement rule, undersized behavior, and the `DENSITY_UNSTRATIFIED` criterion) is fixed here so two implementers produce identical cohorts from the same model, and the resulting dbId lists are recorded verbatim.

### 5.5 The realistic-workload validity condition

R3, R4, and R6 use a ~10-instance source. **Nothing in this repository establishes that a 10-element selection is a real workload** — the shipped extension gates its context-menu actions on exactly one aggregate selection with exactly one dbId (`collision/README.md`, "Reference sample: Clash Finder"). Therefore:

- If the ~10-instance workload is **product-confirmed**, R3/R4/R6 are verdict-bearing as written.
- If it is **not** confirmed, they are reclassified as synthetic sensitivity cases, and **if the decision turns on them, §7.5.4 forces D.** R1, R2, and R5 — which correspond exactly to what ships today — remain verdict-bearing unconditionally.

Recorded as open question 3 (§23) rather than assumed either way.

### 5.6 Protocol dimensions

Cold/warm applies to R1–R6, S2, and S2T (S4 is warm-only; **R6 additionally has the third `refresh` state** of §6.1.4/§7.2, and is the only case that does). `broadPhase ∈ {'tlas','linear'}` applies to every case executable under both. Both runtime configurations (§6.1.5) apply to R1–R6 and S4.

**S1, S2, and S3's dimensions, stated explicitly for the same reason S2T's are below: the general sentences above name R-cases (and, for runtime, S4) only, and leave S1–S3 unstated.** So that two conforming harnesses cannot legitimately execute a different matrix for the same case, each of S1, S2, and S3 runs under **both** runtime configurations (§6.1.5) — reported for both exactly as R1–R6 and S4 are, even though no S-case target-evaluates against §7.2 — under **both** broad-phase arms it can execute, in every state its own §5.3 row declares (S1 and S3: cold and warm; S2: cold and warm, at every source-count level, for every density cohort, under both modes), and **five counterbalanced repetitions per state** under §6.1.6's identical arm-order/case-order schedule — the same protocol R-cases and S2T already have, never a smaller or looser one chosen ad hoc per case. This is not a new requirement on S1–S3; it closes the one gap the general repetition and runtime sentences leave open for them.

**S2T's dimensions, stated explicitly because the sentences above do not reach it by default.** Both broad phases are **mandatory** (§5.3.1 — their divergent response is the evidence). Cold and warm both apply, at every population level. Five repetitions per state, under §6.1.6's counterbalancing, with the **population-level order counterbalanced alongside arm order and case order** — higher levels run longer, so a fixed level order would correlate the population factor with thermal and runtime drift. One fresh world per `(runtime, case, level, broadPhase, repetition)` (§6.1.4). **Only the representative multi-process runtime (§6.1.5b) is required**: the historical `--single-process` configuration exists to preserve continuity with M1–M3's archived numbers, and S2T has no archived counterpart to be continuous with, so running it would produce a second set of numbers comparable to nothing.

### 5.7 Target population — what is varied, and the declared limit on it

**Every verdict-bearing case runs at the real shipped federation.** R1–R6 all target the three-model, 7,474-fragment fixture (R5 excepted, at Structure-only), and that federation *is* the workload M4's verdict is about. Total target population is varied in exactly one place — **S2T** — and only synthetically, by appending spatially distant bystanders to one existing target epoch (§5.3.1).

**The limit this leaves, stated rather than papered over.** S2T grows population with geometry that never enters the query region. Real federation growth does not behave that way: it interleaves geometry, adds candidates, and adds whole disciplines with their own epoch groups. So S2T characterises **index, admission, TLAS, and memory scaling** with population, and **does not** license extrapolating M4's verdict to a materially larger or denser real federation. That extrapolation is outside M4's evidence scope, and the way to obtain it is to re-run the gate on a larger real fixture — not to reinterpret S2T. The R2 vs. R5 contrast is likewise not a substitute (§5.2's R5 row).

**This is deliberately *not* wired to §7.5, and the asymmetry with §5.5 is intentional.** §5.5's condition and S3 are mandatory-D-wired because a *verdict-bearing* case rests on an unconfirmed premise — whether a ~10-instance selection, or a whole-model source, is a real workload. Nothing analogous holds here: no verdict-bearing case depends on any assumption about target population, because every one of them runs at the shipped federation size. A missing population-scaling extrapolation is therefore an **external-validity limit on generalising the verdict**, not a missing prerequisite for reaching it, and wiring it to mandatory D would force D on every run for a question no verdict-bearing case asks. S2T adds no §7.5 condition and no verdict predicate.

## 6. Measurement protocol (Required Decision 2)

### 6.1 Run protocol

1. **Fixture load.** Architecture normally, then Structure and Mechanical as-additional via `#keep-current-models`; wait for `isLoadDone()` **and** `getData().instanceTree` on every model.
2. **Fixture identity re-confirmation**, live, in this run. Nothing taken on faith from a prior gate's header.
3. **Sacrificial unmeasured warm-up** — one throwaway `volume-overlap` and one throwaway `clearance` query, each in its own disposable world, disposed immediately, **with no recorder installed**. "Cold" means no BLAS/TLAS cached *in the measured world*, not a cold JavaScript engine.
4. **Fresh-world identity is `(runtime, case, broadPhase, repetition)`** — extended to `(runtime, case, level, broadPhase, repetition)` for **S2T**, whose population level is part of its fixture (§5.3.1, §5.6); no other case has a level dimension. Exactly one `CollisionWorld` is constructed per such tuple. Its **first** measured query is that tuple's *cold* sample; its **immediately following second** query, on the same world with no intervening world, is the *warm* sample. The world is disposed before the next tuple's world is constructed. No world is reused across cases, arms, repetitions, or runtimes.

   **Two measured queries per world, with exactly one declared exception: R6.** §5.2.1's sequence needs a third query in the *same* world — the cold sample is R6's setup query, the warm sample is the query that records `P₀`, and the post-invalidation re-run that records `P₁` is a **third measured query**, the `refresh` sample (§7.2). Step 5's reset-and-re-confirm query is correctness-only and remains **unmeasured**. No other R-case and no S-case has a third measured query.
5. **Two runtime configurations.** Every R-case and S4 runs under (a) the historical configuration (`--single-process --no-zygote`, for continuity with M1–M3's archived numbers) and (b) a **representative normal multi-process Chromium** with those two flags removed. Both are reported; **(b) is authoritative for every worker-related conclusion and for every §7.2 target evaluation.**
6. **Repetitions and counterbalancing.** Every R-case is run **5 repetitions per state**. Two orderings are counterbalanced by a fixed, recorded schedule: the `'tlas'` / `'linear'` arm order alternates by repetition parity, and the **case order** rotates by repetition index (repetition `r` starts the case list at position `r mod |cases|`). Report **median, min, max, and all five raw values** — never a mean alone.
7. **Observer boundaries, and the two distinct windows they define.** Every observer (CDP trace, rAF recorder, span recorder, diagnostic-event recorder, input probe) is started and reset immediately before each individual measured query, bracketed by `performance.mark` pairs naming the tuple. No observer spans two measured queries.

   **The `performance.mark` pair is the *query window*, and it is unchanged**: it is what §6.2's X-2 duty cycle and §7.3's `Rᵢ`/`Hᵢ` are computed over, and nothing here alters it.

   **Observers stop at the end of a longer *observation envelope*, not at the closing mark.** Stopping at the closing mark cannot see the very stall the target exists to catch: a query that blocks the renderer for 500 ms prevents every scheduled rAF callback and every queued input handler from running *until after* the query ends, so the frame interval spanning the freeze and the true delay of the events queued behind it both fall outside a window that closes with the query. The envelope therefore opens with a **pre-query anchor** — one observed rAF callback and one completed input-probe round-trip before the opening mark — and closes only when **all** of: the closing mark has passed; **at least one post-query rAF callback has fired**; and every dispatched input probe has either had its handler run or has exceeded §7.2's T-c threshold. **The envelope's own limit is `max(2 × the query window's own duration, 5 s)` measured from the closing mark**, after which the envelope closes regardless; that bound exists so a hung renderer, a lost frame callback, or an unhandled probe cannot stall the gate indefinitely, and reaching it is recorded on the tuple. Everything the envelope observes after the closing mark is attributed to T-b1/T-b2/T-c **only** — never to X-2's duty cycle, never to `Rᵢ`/`Hᵢ`, and never to T-a, all of which remain strictly inside the query window.
8. **Reporting statistics.** For any *population*: `count, min, p50, p95, p99, max, mean, sum`, plus counts and fractions over 8 ms, 24.8 ms, and 50 ms. For any *scalar*: median of repetitions plus the raw set. **`Math.max(...[])` is `-Infinity`** — every population summary carries an explicit empty-set guard and reports `NOT EXERCISED`, never a verdict computed from an unpopulated set. **Maxima are never compared across differently-sized populations** (§7.6.3); comparisons use like-for-like percentiles with both counts stated.

### 6.2 The three axes, and how each is actually obtained

The most important methodological section, and the one where the obvious browser APIs do **not** work.

#### X-1 — Viewer responsiveness (decides necessity)

- **Main-thread task timeline.** From a **Chromium DevTools Protocol trace**, via a Playwright CDP session on the measured page, capturing the renderer's complete task timeline within the `performance.mark`-delimited query window. **Long Tasks and Long Animation Frames are cross-checks only, never the source**: `longtask` entries exist only for tasks above ~50 ms, so they can neither enumerate all tasks nor produce a duty cycle, and their *absence* proves nothing. Reported: the full task-duration distribution, and counts over 8 ms, 24.8 ms, 50 ms, and 100 ms.

  **What counts as a "main-thread task", and on what clock — fixed here, because `Rᵢ` and `Hᵢ` are computed against it.** §7.3 assumes recorder-callback timestamps and trace tasks share a clock and that "main-thread task" is unambiguous; neither is true of a raw Chromium trace, and two harnesses reading it differently would produce different verdicts from identical runs. This paragraph supplies the definitions §7.3 consumes and **changes no formula, no attribution, and no boundary's stage ownership**:

  - **Trace configuration, pinned to the tested build.** Tracing is started over CDP `Tracing.start` with the **JSON** transfer format and the categories `toplevel`, `devtools.timeline`, `blink.user_timing`, and `disabled-by-default-devtools.timeline` — recorded verbatim in the report along with the exact Chromium version, since event naming is version-dependent and is pinned to the build actually tested. The measured renderer's **process and thread ids** are identified from the `TracingStartedInBrowser` / `thread_name` metadata events for the page under test, never guessed from ordering. **If the trace reports `dataLossOccurred`, or either anchor mark is absent from it, the tuple is invalid** — reported as such and excluded, never used to compute a duty cycle, `Rᵢ`, `Hᵢ`, or T-a from partial events.
  - **Task selection.** A *task* is a **top-level** `toplevel`-category task event on the measured renderer's main thread (`RunTask`, and the build's equivalent top-level task name recorded verbatim from the pinned version), identified by that renderer's process and thread ids. Nested events inside it — function calls, timers, user-timing marks, GC, parse/compile — are **never** counted as tasks in their own right; they are attributions *within* their enclosing task. Summing any nested layer, or mixing layers, double-counts and is forbidden.
  - **Nesting and de-duplication.** Where trace events overlap, only the outermost `toplevel` event contributes a task interval, and each instant on the timeline belongs to exactly one task. This is the same "innermost classified stage contributes once" discipline §7.3's residual already applies to *stages*, applied here to *tasks*.
  - **Clock domain and conversion, by paired samples rather than by assumption.** Trace timestamps are monotonic **microseconds** in the tracing clock's own origin; `performance.now()` is **milliseconds** from the renderer's time origin. The CDP Tracing contract does **not** guarantee that a user-timing trace event carries both representations, so the mapping is not read off one event. Instead the harness emits, immediately before the opening mark and immediately after the closing mark, a **paired clock sample**: an in-page `performance.mark` whose `performance.now()` value is also returned to Node in the same evaluation. Each pair gives one (trace-µs, `performance.now()`-ms) correspondence at a known instant; the offset is taken from the two pairs and the residual drift between them is **recorded per query window**, exactly as §6.2's input-probe calibration already records its own offset and drift. Unit conversion is explicit (µs ÷ 1000). Comparing raw trace microseconds against `performance.now()` milliseconds without this conversion is a defect, not a variant reading; and if either paired sample is missing from the trace, the tuple is invalid under the data-loss rule above.
  - **Boundary-crossing tasks.** A task that begins before the opening mark or ends after the closing mark contributes only its **intersection** with the window, never its full duration. This is the same intersection rule §7.3 already applies to `Hᵢ`'s sub-marks, stated once here for tasks.
  - **Stage intervals, and the yield-splitting rule that makes the reconstructed form safe.** Stage boundaries are taken from the harness's own `performance.mark`/`measure` pairs wherever it emits them, in preference to reconstructing `[end − ms, end]` from a recorder callback's receipt time; the reconstructed form remains permitted only for stages reported solely through the `(label, ms)` span hook, and the report states which form each stage used. **A reconstructed interval is never assumed contiguous.** §3.2 already establishes that a recorded span can absorb another port's *yielded* wall clock, so treating `[end − ms, end]` as one uninterrupted synchronous segment would let renderer, timer, input, or unrelated collision work inside that span be subtracted from a main-thread task as though it were transferable stage time — which would shrink `Rᵢ` and could qualify a boundary that does not deserve it. **The rule:** §16.4's yield instrumentation already records every real yield with its resume latency, on the same window and clock; any reconstructed interval that overlaps a recorded yield is **split at that yield's boundaries**, and only the resulting sub-segments are treated as stage-attributed time. The yielded gap belongs to no stage and is never subtracted. **This uses only instrumentation §16.4 already enumerates and adds nothing to that closed list.** Where a stage's span overlaps a yield whose own boundaries were not recorded, that stage contributes no attributed interval and the report says so, rather than contributing an interval that may be wrong.
  - **Worker-response delivery-task correlation, for `Hᵢ`'s receipt/deserialization component (§7.3 condition 4(b), §17).** A structured-clone message's deserialization is performed by the browser **before** the page's `message` event handler runs, so a `performance.mark` placed inside `onmessage` cannot bracket it — the clone cost has already elapsed by the time any in-handler mark executes, and starting `Hᵢ`'s receipt component at the first mark inside the handler would silently omit it. Neither §7.3 nor §17 brackets receipt/deserialization with a sub-mark at all; this rule supplies it instead, mechanically. The harness places one `performance.mark` as the **first statement** of the worker arm's `onmessage` handler — the **correlation mark** — for the sole purpose of **locating** which CDP main-thread task received the message, never as a timing boundary in its own right. Correlated to the trace by the same paired-clock-sample method defined above, the correlation mark's trace timestamp falls inside exactly one CDP top-level task (the task-selection rule above); that task is the **delivery task**. Because S7′ runs one worker call at a time with no concurrent in-flight request (§17), the delivery task following a given repetition's `postMessage` send is unambiguously that repetition's response — no `requestId` disambiguation is needed. The delivery task's contribution is its full interval from its own start **up to whichever comes first: the task's own end/yield, or the arm's closing `performance.mark`** — never merely from the correlation mark onward, and **never extended past the closing mark even where the same physical browser task keeps executing after it**. Structured-clone deserialization, event dispatch, the `onmessage` handler, and the result-mapping continuation up to the closing mark are what this component measures; §17's own sequencing rule places stage-scoped validation, §15's memory sampling, and disposal strictly **after** the closing mark — which is drawn immediately once the response is mapped to the stub result, before any of that later work runs — so crediting time past it to `Hᵢ` would pull harness-only validation/sampling cost into a verdict-bearing figure, exactly what §17 already forbids for the measured comparison generally and what §6.1.7 already requires of `Rᵢ`/`Hᵢ` specifically (both "remain strictly inside the query window"). **If the trace does not place the correlation mark inside exactly one top-level task** — a missing mark, a `dataLossOccurred` trace, or a mark that cannot be uniquely assigned to one task — **the delivery task is unidentifiable, and `Hᵢ(w,τ)` is UNEVALUABLE at that repetition** (§7.3's existing UNEVALUABLE disposition), never estimated from the mark's own elapsed time or any other proxy.
- **Frame production.** An in-page `requestAnimationFrame` cadence recorder: frame count, inter-frame intervals, p95/max interval, and counts of intervals above 32 ms and 100 ms. **Measured over §6.1.7's observation envelope**, so the interval that *spans* the query — from the last pre-query frame to the first post-query frame — is always observed and is always included; that interval is the single most important one T-b2 exists to catch, and a recorder stopped at the closing mark would never see it. A repetition in which no post-query frame was observed before the envelope's own limit is reported **INDETERMINATE**, never as a pass.
- **Input responsiveness.** Input must be **trusted and externally generated**: dispatched from Node through Playwright (`page.mouse.move` / `page.keyboard.press`) at a fixed recorded cadence, with the **intended dispatch timestamp taken in Node, outside the blocked renderer**, and the handler-entry timestamp taken in-page. An in-page `dispatchEvent` is **forbidden** as the primary measure — synthetic events are untrusted, are excluded from Event Timing, and `dispatchEvent` invokes handlers synchronously, so it measures nothing about queue delay. The protocol fixes: event type (`mousemove` over the canvas), cadence (one every 100 ms, from the pre-query anchor through the observation envelope — see the sampling and disposition rules below), target element, clock correlation (a calibration exchange measured immediately before and after each query window, with offset and drift recorded), and **missed-event handling**, defined precisely below. Event Timing entries are recorded as a cross-check where the browser produces trusted ones.

  **Missed-event handling — restated, because the earlier rule could pass a total freeze.** An event dispatched shortly before the closing mark whose handler had not yet run was previously censored at "≥ the query's remaining duration", a lower bound that can sit far below T-c's 100 ms threshold even when the true delay is hundreds of milliseconds — so a 500 ms freeze could be recorded as a set of small, threshold-satisfying lower bounds. The rule is therefore: every probe event is followed until its handler runs **or** until §6.1.7's envelope closes. An event whose handler runs — whenever it runs, including after the closing mark — contributes its **full measured delay**, dispatch-to-handler. Only an event still unhandled when the envelope closes is censored, at its **elapsed** delay to that point. A censored observation whose lower bound already **exceeds** the threshold is a **failure**. A censored observation whose lower bound is **below** the threshold with no observed completion is **INDETERMINATE** and may never be reported as satisfying T-c — a correctly implemented envelope makes this case rare, because it only arises when the envelope's own limit is reached with events still queued.

  **Percentile algorithm and minimum observation count, fixed so two harnesses agree.** p95 (and every other percentile in §6.1.8) is the **nearest-rank** percentile on the sorted sample: the value at 1-based index `⌈p·N⌉`, with censored observations ordered by their lower bound. **Probe dispatch, correlation, and coalescing — fixed, because `page.mouse.move` alone does not settle them.** Probes are dispatched over CDP **`Input.dispatchMouseEvent`**, which accepts an explicit event timestamp, rather than left to `page.mouse.move`'s own dispatch semantics. Each probe moves to a **unique coordinate** drawn from a fixed, recorded sequence over the canvas, and the in-page handler records that coordinate, so every handler entry is attributable to exactly one dispatch and browser **input coalescing** is detectable rather than silent: a probe whose coordinate never appears was coalesced away and is **censored**, per the schedule rule below, never recorded as a zero-delay observation. Probes are issued **one per scheduled slot, in order**, never as a concurrent burst whose queue order is unknown; the Node-side intended-dispatch timestamps therefore form an ordered series.

**The cadence stays 100 ms, and the minimum-count disposition is `INDETERMINATE` — which is never a pass, and therefore never permits what §7.3's Verdict A forbids.** The cadence is **not** derived from any earlier query's duration: cold is the longest query in a tuple, so a cadence scaled to it under-samples a much shorter warm query — a 2.2 s cold would give a 100 ms cadence and leave a 250 ms warm query with two probes, and re-running at that same cadence would fail identically every time. Nor is the floor simply declared satisfied: at a 100 ms cadence a query shorter than ~500 ms genuinely **cannot** yield five in-window observations, and §3.1's ~520 ms warm case sits right at that boundary, so short warm tuples can legitimately fall below it.

The disposition is therefore fixed here rather than wished away. A repetition with **fewer than 5** in-window observations, or whose censored observations leave the percentile undetermined, is reported **`INDETERMINATE` for T-c**. `INDETERMINATE` is **never reported as satisfying T-c**. Because §7.3's Verdict A requires every verdict-bearing tuple to *meet* T-a, T-b1, T-b2, **and** T-c, a tuple whose T-c is `INDETERMINATE` has not met it, and **A is not available on that tuple** — by §7.3's existing rule, not by any new one. **This adds no §7.5 mandatory-D condition and changes no verdict predicate**; it only fixes which of the existing outcomes an under-sampled measurement maps to, so two harnesses cannot read the same data as A and as not-A. The tuple, the metric, the observation count, and the query duration that produced it are all named in the report.

Only **in-window dispatches count toward T-c**; probes continue through the envelope's tail so their handlers can be observed, but a probe issued after the closing mark measures an already-unblocked main thread and would flatter the statistic. The count is **always** reported alongside the percentile, per §6.1.8.

**The schedule never waits on the renderer, and skipped or coalesced probes are censored rather than discarded.** Dispatches are placed on a **fixed wall-clock timeline computed in advance**; a mechanism that awaits renderer acknowledgement before issuing the next probe cannot hold a cadence precisely when the renderer is blocked, which is the condition being measured. A slot whose dispatch could not be issued on time, and a probe whose unique coordinate never reaches a handler, are both recorded as **censored observations at the elapsed delay to the envelope's close** — **not** as "not dispatched", and never silently dropped, because a probe disappearing under renderer overload is *evidence of* the stall T-c exists to detect, not an absence of evidence. Their disposition follows the censoring rules above: a lower bound over the threshold is a failure; a lower bound under it with no observed completion is `INDETERMINATE`. **The floor is 5, not a larger number, because a larger one would make T-c unevaluable on exactly the tuples that matter most.** At the fixed 100 ms cadence a warm query of §3.1's measured ~520 ms yields only about five probe events, so a floor of, say, 20 would report `NOT EXERCISED` for T-c on every warm tuple and would remove T-c from the warm evidence entirely — silently narrowing what verdict **A** is affirmed on. At `N = 5` the nearest-rank p95 is the sample **maximum**; that degeneracy is stated here rather than hidden, and it is acceptable because §7.2 already medians T-c across the tuple's five repetitions and separately forbids any single repetition above 1.5× the threshold. Cold queries (~2.2 s) yield roughly twenty observations and are unaffected.

#### X-2 — Main-thread consumption (explains interference)

Duty cycle = Σ(task durations from the **CDP trace** within the marked window) ÷ window duration. **Not** a sum of the library's own spans (§3.2), and **not** derived from Long Tasks. The library's own span totals are reported alongside as a cross-check, and any disagreement is reported rather than reconciled silently.

#### X-3 — Query makespan (what the user waits on)

End-to-end elapsed time, in every measured state the case has (cold and warm, plus `refresh` for R6 — §6.1.4, §7.2), *including* yield delay and (for any worker measurement) worker startup, transfers, and result publication. Yield count and cumulative yield delay are **measured directly** (§16.4.1), never estimated.

#### Scheduler conformance (retained, but not a verdict axis)

The maximum inter-checkpoint span **across every checkpoint label** — not one primitive, which is what let M3 report 6.10 ms where the same runs' worst bracketed span was 12.2 ms. Direct-bracket spans (`weld`, `connectivity`, `bvh-construction`, `capacity-admission-commit`, `tlas-build`, `clearance-distance-query`) are reported **alongside** as nested attributions, never unioned into the same maximum and never summed with the bracketed ones.

Reporting only X-3 is forbidden: it hides where the cost is. Deciding on the conformance metric alone is forbidden: **a query can consume hundreds of conforming 8 ms tasks, pass the span gate, and still starve Viewer rendering** — precisely what the M3-era "6.1 ms vs 8 ms" framing cannot see.

### 6.4 The canonical correctness comparator

One comparator, used for (a) the gate's **TLAS-vs-linear** parity comparison and (b) any **full-result** worker arm — an arm that reproduces the complete query pipeline and therefore emits final pair sets, distances, witnesses, statistics, and diagnostics. It does **not** govern a **stage-scoped spike**, which by §17's construction genuinely computes only the one stage it moves and carries a stub result mapping for everything downstream of it; that case is covered by the stage-scoped rule below. Defined once here and referenced by §19.

| Field | Rule |
|---|---|
| Pair set | The full sorted set of `(sourceModelTag, sourceDbId, targetModelTag, targetDbId, type)` tuples must be equal. Counts alone are never sufficient. |
| `distance` | **Bit-identical** for the TLAS-vs-linear comparison — both paths hand the identical operand pair to the identical `clearanceQuery`, and `run-gate-m3.mjs` already measures a max delta of exactly `0` over all shared keys, so anything else is a regression. For a **worker arm only**, an absolute tolerance of `1e-9` is permitted and must be reported as an explicitly relaxed comparison, justified by possible float-operation reordering across the boundary. |
| `witness` | Shape equality (`{sourcePoint,targetPoint}` for `clearance`, `{kind,point}` for `volume-overlap`), and each coordinate equal within `1e-9 × max(sourceWorldDiagonal, targetWorldDiagonal)` — a scale-relative absolute tolerance, whose numeric value for the fixture actually used is computed and printed in the report. |
| `statistics` | `clearanceExactAabbSurvivors`, `narrowPhasePairs`, `clearanceOverlapPrechecksRun`, `clearanceHardClashExclusions`, `clearanceDistanceQueriesRun`, and `clearanceHits` must be equal. Timing fields are excluded. |
| `diagnostics` | **Multiset** equality over the complete public payload of each entry: `reason`, `scope`, `role` (present on fragment-scoped entries, `CollisionWorld.js:97-107`), and every applicable fragment reference expanded to `(modelTag, dbId, fragId)` — `fragment` for fragment-scoped entries, `sourceFragment` and `targetFragment` for pair-scoped ones. A key omitting `role` and the singular `fragment` would treat a source-side and a target-side `clearance-anisotropic-scale-unsupported` as identical and let a provenance regression pass. `modelTag` is used rather than `modelId`, which is documented as reused-under-collision-prone. |

A run is **invalid** — `FAILED_VALIDATION`, non-zero exit — if any field above differs. A performance verdict never fails the process; a correctness violation always does.

**Stage-scoped validity — the rule for a spike that genuinely reproduces only one stage's outputs.** Such a spike is compared to the synchronous path **only on the outputs it actually reproduces**, over the *identical* inputs the synchronous path was given. Everything downstream of its stub result mapping is a timing artifact by construction (§17) and is **never** compared. For **S7′**'s precheck vertical (§17) the criterion is: over the identical candidate list, the worker-side precheck's per-pair `conclusive` verdicts, its `inconclusiveCauses` distribution, and its excluded-pair set must match the synchronous path's. For **S7′**'s geometry-preparation vertical (§17) the criterion is: over the identical geometry set, (i) the welded `position` / `index` buffers are **element-wise equal**; (ii) connectivity matches as a **partition** — `componentCount` equal and `componentOf` inducing the identical grouping of triangles up to relabelling, with `closedManifold` element-wise equal under that relabelling; and (iii) the returned serialized BVH's `roots`, `index`, and `indirectBuffer` are **byte-identical** to the main thread's, which is well-defined because both sides run the same pinned `three-mesh-bvh@0.9.14` build over identical input, so a difference is a real defect rather than a tolerance question. A mismatch fails **that spike** — recorded as such, with the spike's evidence unusable for §7.3's conditions — and does **not** invalidate the gate run or fail the process. A stage-scoped spike is never asked for the fields above that it does not produce.

## 7. The responsiveness target, decision rules, and thresholds (Required Decision 3)

### 7.1 What is inherited, and what it does and does not mean

`frameBudgetMs = 8` and M1's derived **24.8 ms** ceiling are shipped conventions (§4), reused unchanged. **They are scheduler-conformance checks, not user-experience thresholds.** Passing them says the library yields as designed; it says nothing about whether the Viewer stayed usable. Bands for the worst bracketed span across all labels: `> 24.8 ms` = **NONCONFORMANT** · `> 8 ms` but `≤ 24.8 ms` = **CAUTION** · `≤ 8 ms` = **CONFORMANT**.

### 7.2 The responsiveness target — precommitted, provisional, statistically defined

There is **no product-approved responsiveness target for this operation today**, and none can be derived from the repository. This spec declares a provisional one — anchored to named external conventions rather than a number chosen here — *and* makes its confirmation a mandatory-D prerequisite (§7.5.1).

**Provisional target, evaluated on the representative multi-process runtime (§6.1.5b), for each verdict-bearing R-case:**

- **T-a** — no main-thread task in the query window exceeds **50 ms** (the Long Tasks definition; measured from the CDP trace, not from `longtask` entries).
- **T-b1** — the p95 inter-frame interval is at most **32 ms** (two frames at 60 Hz).
- **T-b2** — no inter-frame gap exceeds **100 ms** (the RAIL model's Response budget, itself derived from Nielsen's 0.1 s "feels instantaneous" limit). T-b's two clauses are split because they are thresholds of different kinds — a percentile and a hard maximum — and §7.2's aggregation rules treat those differently.
- **T-c** — p95 measured input-handler delay is at most **100 ms** (the same RAIL Response budget), over the trusted externally-generated input series of §6.2, with censored observations counted at their lower bound.

**Aggregation unit — fixed, so two implementations cannot disagree:**

- **T-a and T-b2 are hard maxima and require 5/5 repetitions to pass.** A single repetition containing a >50 ms task fails T-a; a single repetition containing an inter-frame gap >100 ms fails T-b2. Hard maxima are not medianed and are not subject to the 1.5× clause below; a rare 61 ms task, or a single 149 ms frame gap, is exactly the event the target exists to catch.
- **T-b1 and T-c are percentile statistics.** Each is computed **within** each repetition; the case passes only if (i) the **median across the five repetition values** is within the threshold **and** (ii) **no single repetition exceeds 1.5× the threshold**. Clause (ii) stops a median hiding one badly-degraded run.
- Every evaluation is per `(runtime, case, broadPhase, state)`, where `state ∈ {cold, warm}` — or `{cold, warm, refresh}` for **R6**, §6.1.4's one declared exception — are the measured queries §6.1.4 defines for each fresh world. **Every state a case has is independently verdict-bearing**: each is evaluated on its own query window, against the same thresholds, by the same aggregation rules, and a case passes only if it passes in **every** state it has under **both** broad-phase arms it can execute. Cold is not excluded, and states are never pooled into one window — the cold path is where §3.1's ~1.4 s of unattributed cost lives and where §8.2's cold-only boundaries (WB-1a/WB-1b) would apply, so a cold-state failure must be able to fail a case (§7.3 condition 2, §17's S7′ variant selection). Where a case is declared warm-only (S4, §5.6), only the warm state exists and only it is evaluated. Where a case declares the third `refresh` state — **R6 only** (§5.2.1's post-invalidation re-run recording `P₁`); no other R-case and no S-case has one — it is evaluated on its own query window by these same rules, and a **target** failure there (T-a, T-b1, T-b2, or T-c) fails that tuple **exactly as** a cold or warm failure does, and can satisfy §7.3 B condition 1 on its own. Correctness at that query — a stale or incorrect result, a parity mismatch against the linear oracle, or a lifecycle error — is governed by §6.4 and §19.1 exactly as it is at cold and warm: it invalidates the **run** (`FAILED_VALIDATION`, non-zero exit). It is never a target failure and is never evidence for B condition 1, which is a responsiveness condition only.

**Secondary, reported but not target-bearing:** X-3 makespan against Nielsen's 1 s "keeps the user's flow of thought seamless" limit (Nielsen 1993, the source RAIL's Response budget derives from — cited for the 1 s figure specifically, which is *not* a RAIL budget), and against the **accepted status quo**: M2 and M3 both shipped and were reviewed with a warm single-element federated query at ~440–520 ms wall time. Evidence of what this project has already accepted, not a claim that it is comfortable.

**T-a, T-b1, T-b2, and T-c are all provisional** and must be restated once confirmed, exactly as `maxSyncTriangleCount` and `maxCollisionInstancesPerEpoch` stayed provisional until their own gates measured them.

### 7.3 The evidence → verdict mapping

Read mechanically. Narrative judgement may not override a missing prerequisite. Recall §1.2: B and C are *justification* verdicts; parity is an adoption prerequisite (§19.2), not a verdict condition.

**Precedence, stated once and mechanically.** Evaluate in this fixed order: **mandatory D** first (any §7.5 condition or §1.1 cause, checked before anything else); then **A**, when the synchronous baseline meets every target at every verdict-bearing tuple; then **B**, when at least one applicable §8.2 **B-class** boundary is mechanically **SUFFICIENT** at the relevant tuple; then **C**, only when *every* applicable B-class boundary is mechanically **INSUFFICIENT** and a named §8.2 **C-class** boundary is mechanically **SUFFICIENT**; otherwise **D**. This is not an arbitrary tie-break: C's own predicate (below) requires B's insufficiency as one of its conditions, so B and C cannot both hold at the same tuple — the smaller, sufficient architecture is what a run reports, and C is never reached while a B-class boundary already suffices.

**Verdict A — stay synchronous.** Permitted **only** when *every* verdict-bearing R-case, on the representative multi-process runtime, under every broad-phase arm it can execute and in **every** measured state it has (§7.2's `(runtime, case, broadPhase, state)` unit — cold and warm, plus `refresh` for R6), meets T-a, T-b1, T-b2, and T-c by §7.2's aggregation rules. A failing S-case does not by itself block A, but §7.5.4 governs when an S-case is nonetheless decision-driving. Simplicity is a benefit; **migration difficulty is not evidence of adequacy.**

**Verdict B — a targeted worker boundary is sufficient.** A named §8.2 boundary `w` has, at a verdict-bearing tuple `τ`, a mechanical disposition only where it is **applicable** there — a boundary that is not applicable at `τ` has no disposition at all and counts toward neither B's nor C's requirements at `τ`, distinct from UNEVALUABLE below.

**Applicability, defined mechanically, so "which boundary is even a candidate here" is never left implicit:**
- `w` is applicable at `τ` only if `τ` is a verdict-bearing tuple where **T-a is among the failing metrics** (condition 1's own scope).
- a **B-class** `w` (WB-1a, WB-1b, WB-2p, WB-3) is applicable at `τ` iff §17's family/substage selection rule (median-across-repetitions, strict winner, §17) selects `w`'s own family at `τ` — and, where the narrow-phase family wins, `w`'s own substage specifically. A B-class boundary whose family or substage does not win at `τ` is simply **not applicable** there; this is the mechanical answer to "is WB-3 applicable at a tuple where precheck, not distance, carries the cost" — it is not, and it therefore never becomes UNEVALUABLE or INSUFFICIENT at that tuple, it is simply absent from consideration.
- a **C-class** `w` (WB-2, WB-4) is applicable at `τ` iff the **narrow-phase family** wins at `τ` (§17) **and** the failure at `τ` is located in the **warm narrow phase** (Verdict C's own location clause, below). A C-class boundary is never applicable where the geometry-preparation family wins, or where the failure is not warm-narrow-phase.

**Given applicability, `w`'s disposition at `τ` is exactly one of three — checked in this fixed order, so no boundary is ever both, and so missing evidence always resolves before conditions 6–8 are even consulted:**

1. **UNEVALUABLE**, checked first — required evidence for `w`'s own threshold check is missing: for a **B-class** `w`, no matching §17 vertical ran at `τ`; for a **C-class** `w`, its own derived-evidence package (Verdict C's evidence clause, below — never a §17 vertical, since §17 builds none for WB-2/WB-4) cannot be conservatively assembled from existing S6′/S7′/§6.3 operands at `τ`. **UNEVALUABLE is not INSUFFICIENT and asserts nothing about `w`'s merits**, and it is checked *before* conditions 6–8 — a boundary missing its primary threshold evidence is UNEVALUABLE regardless of what a condition 6–8 input would otherwise show. An UNEVALUABLE boundary may never be used to help satisfy B, and may never be counted toward Verdict C's requirement (below) that every applicable B-class boundary be INSUFFICIENT.
2. **INSUFFICIENT** — evidence is present (`w` is not UNEVALUABLE) and either its own threshold check fails at some repetition — `Rᵢ(w,τ) + Hᵢ(w,τ) > 50 ms` for a B-class `w` (condition 4(b)), or the identical check on `w`'s derived bound for a C-class `w` (Verdict C, below) — or `w` fails a named condition 6–8 with evidence present.
3. **SUFFICIENT** — evidence is present, `w`'s threshold check holds at **every** one of `τ`'s five repetitions, and conditions 6–8 all hold.

A tuple left with an applicable boundary UNEVALUABLE, or with every applicable boundary of both classes INSUFFICIENT, and no other boundary settling it, falls to D under §7.5's tenth condition — never silently to C, and never silently to B.

**Multi-tuple aggregation.** §7.3's conditions are evaluated independently at every verdict-bearing tuple where T-a is among the failing metrics; **the same "any unsettled tuple forces D" principle condition 1 already establishes for §7.5.9-shaped tuples applies identically here.** If every such tuple has some boundary SUFFICIENT, the overall verdict names every distinct SUFFICIENT boundary needed to settle all of them: **B** if every one of those boundaries is B-class (a cold tuple settled by WB-1b and a separate warm tuple settled by WB-2p both name B-class boundaries and the overall verdict is still B, naming both — this does not blur what "one bounded stage" means in §1.1, since each named boundary still moves exactly one stage); **C** if settling at least one tuple required a C-class boundary, regardless of whether other tuples were separately, and sufficiently, settled by a B-class one. If any verdict-bearing tuple in scope has **no** boundary SUFFICIENT of either class, the overall verdict is **D** (§7.5.10), even where every other tuple is fully settled — mirroring condition 1's existing rule rather than inventing a new one.

Verdict B requires, for each tuple it settles, **all** of:
1. the synchronous baseline **fails** T-a, T-b1, T-b2, or T-c at one or more verdict-bearing R-cases, in **any** measured state that case has — cold, warm, or, for R6, `refresh` (§7.2).

   **A failing tuple's disposition depends on *which* target(s) it fails, and that is decided here rather than left implicit.** If **T-a is among the failing metrics** at a failing `(case, broadPhase, state)` tuple, that tuple is eligible for the stage-level evidence path below: condition 3's screen and condition 4(b)'s `Rᵢ + Hᵢ ≤ 50 ms` check are both *defined* there, and together they are genuine, mechanical evidence bearing on T-a specifically. If the tuple's **only** failing metrics are **T-b1, T-b2, and/or T-c** — T-a passes there — then **M4 has no pre-registered evidence path for that tuple at all**: condition 4(b)'s formula is tied to T-a's own 50 ms threshold and has no defined application where T-a does not fail, condition 3's screen is likewise T-a-only and is defined only in a failing window, and S7′'s evidence is stage-scoped (§17) and structurally cannot establish end-to-end frame-cadence or input-latency sufficiency. Such a tuple is **not** decided by B or C. It is decided by §1.1's ***no-full-query-evidence*** cause, restated as the mandatory-D condition **§7.5.9** — an **evidence-scope limitation finding about M4's method, explicitly not a finding that no boundary would help**, and kept visibly distinct from §1.1's *no-boundary* cause, which is a decisive negative about the architecture.

   **Because §7.5's conditions are mandatory whenever *any* of them holds, a single verdict-bearing T-b1/T-b2/T-c-only failing tuple forces the overall verdict to D**, even where other failing tuples would otherwise support B or C. That consequence is deliberate: it is what stops a B or C verdict from being read as a claim about a failure mode M4 cannot measure. The B/C-supporting evidence gathered at the T-a-failing tuples is still reported in full, and it is what §19.2's adoption measurement starts from;
2. **at least one** applicable §8.2 **B-class** boundary — **WB-1a**, **WB-1b**, **WB-2p**, or **WB-3** (§8.2's classification) — is **SUFFICIENT** at the tuple, per the disposition rule above. Each B-class boundary has at most one evidence path: §17's S7′ vertical is selected by the §6.3 stage attribution of the failing cost, to match the boundary being evaluated — the precheck vertical for **WB-2p**, selected whose failing cost §6.3's attribution places in the Hard-Clash precheck substage specifically; the extra-copy geometry-preparation vertical for a cold-only **WB-1a**/**WB-1b**. Two substage caveats apply symmetrically, both from §17: the geometry-preparation arm proves **WB-1b** SUFFICIENT (never WB-1a) unless the worker-side BVH-construction sub-stage is also reported in isolation, in which case **WB-1a** may be evaluated on that isolated figure; and if a *different* narrow-phase substage carries the failing cost, §17's tie rule decides which case applies — if the **clearance distance query** is the **strict winner** among the three narrow-phase substages, that is **WB-3**'s own substage, no matching vertical exists for it, and **WB-3 is UNEVALUABLE** at that tuple; if the **exact-query stage** (crossing / containment / surface intersection) wins strictly, **or ties** the clearance distance query, **no B-class boundary is applicable for it at all** — §8.2 names none, and the tie is resolved conservatively against crediting WB-3. Either way the actually-dominant substage is reported by name, no new vertical or boundary is invented for it, and (per §7.3's applicability rule) **C-class boundaries remain evaluable regardless**, since C's own applicability depends only on the narrow-phase family winning and the failure's warm-narrow-phase location, not on which substage within that family dominates;
3. §6.3's partition passing the **main-only remainder** screen at **every failing `(case, broadPhase, state)` tuple where T-a is among the failing metrics** — the tuples condition 1 makes eligible for this evidence path. The screen has **no defined application** at a T-b1/T-b2/T-c-only failing tuple (§7.5.9 governs those), and it is never evaluated at a *passing* tuple such as R1 or R2 where those pass, because the residual it computes is defined only inside a failing query window. At each tuple in scope, the largest **main-only-attributed task residual** in that tuple's failing query window must be at most the **50 ms** T-a threshold. This is the **boundary-independent** residual, notated **`Rᵢ(all,τ)`** — the permissive no-boundary screen only. It is distinct from the **per-boundary** `Rᵢ(w,τ)` condition 4(b) evaluates for a specific named boundary `w` (defined there); the two notations are never substituted for each other. **The residual is computed exactly as follows, so two harnesses cannot disagree.** The harness timestamps each recorder callback at receipt with `performance.now()` (harness-side only — no library change, no addition to §16.4), giving every reported stage the interval `[end − ms, end]` on the same clock the query's `performance.mark` pair anchors to the CDP trace. For each CDP main-thread task interval inside the marked window, subtract the portions of that task covered by stages classified **transferable** under the fixed rule immediately below; what remains is a set of uncovered (main-only) sub-intervals of that task. That task's main-only-attributed residual is the **longest contiguous uncovered interval** among them — explicitly **not** the sum of all uncovered intervals in that task. **Overlapping stages are counted once**: only the innermost classified stage covering an instant contributes, so a nested direct-bracket span inside a checkpoint-bracketed one is never subtracted twice (§6.2's rule that nested and bracketed spans are never unioned or summed). The screen value is the **maximum of that per-task longest-contiguous-interval figure, over all tasks in the window and over all five repetitions**, evaluated as a hard maximum exactly like T-a — a pass requires all five repetitions to pass. **Contiguity is required because it is what models actual uninterrupted main-thread blocking after the boundary is built:** a worker `await` genuinely *ends* the task at the point the offloaded stage is removed, so main-only work lying on both sides of a transferable stage inside one of today's tasks would post-boundary occupy two separate, shorter tasks, each judged against T-a on its own. Only a truly contiguous main-only span — one that would survive as a single uninterrupted task even after the boundary is built — is valid evidence that no boundary can close the gap; summing the pieces would understate how the task topology actually changes and could force a decisive no-boundary **D** on a window every §8.2 boundary would in fact split into passing tasks.

   **The transferable classification this screen uses is fixed and pre-registered, so it never depends on the verdict it helps determine.** Two of §6.3's rows carry no single fixed class — `compactAndWeld` is "main-only as written; movable only via the extra-copy variant (§8.2) … classify per variant", and per-pair geometry resolution is "main-only on first touch, transferable when warm". **For the purposes of this screen only**, any stage §6.3 marks as movable under *any* §8.2 variant counts as **transferable**: `compactAndWeld` counts as transferable (it moves under WB-1b's extra-copy variant), and per-pair geometry resolution counts as transferable (it moves once warm). This classification is read straight off §6.3's static table and is **independent of which §8.2 boundary a later B verdict would name and of which vertical §17 selects** — which is what removes the circularity that would otherwise arise, since §17's variant selection consumes this very screen's partition. **The consequence is deliberate and is stated here rather than left implicit:** this is the most *permissive* classification available — it credits every stage that is movable under some variant as fully removable — so a screen that still fails under it is a genuinely conservative finding that **no** §8.2 boundary, not merely the one that would eventually be named, can close the gap. That is exactly what licenses the *no-boundary* **D**. The actual stage-level cost and overhead of whichever variant is later selected is not this screen's business; it comes from S7′ under condition 4. **Condition 4(b) does not reuse `Rᵢ(all,τ)` directly**: it recomputes the identical longest-contiguous-residual rule with the covered set restricted to the boundary `w` under evaluation (defined there). `Rᵢ(all,τ)` remains this screen's own quantity, used only to decide the *no-boundary* D cause below.

   **The same permissiveness bounds what a *pass* means, and that limit is stated here rather than left to be inferred.** This is a **permissive no-boundary exclusion screen**: it proves only that **no** §8.2 boundary can help when it *fails*. A pass does **not** establish that the specific boundary a B verdict eventually names meets T-a on its own real, integrated implementation — the screen has already credited the removal of every stage movable under *any* variant, including stages the named boundary does not move (a B naming WB-1a is credited here with the weld and with warm per-pair geometry resolution, neither of which WB-1a touches). Named-boundary, full-query T-a sufficiency is therefore established exactly as T-b1, T-b2, and T-c sufficiency is: by the adoption milestone's end-to-end measurement on the real (non-stub) integrated worker path (§19.2), not by M4.

   **This screen is T-a-only, deliberately.** Removing transferable time from a *real* trace bounds the main-only task residual, but it cannot reconstruct the frame cadence or input latency a *hypothetical* main-only execution would have — moving work also changes task boundaries, message handling, yield placement, and frame opportunities. **T-b1, T-b2, and T-c sufficiency for the hypothetical post-boundary configuration is therefore not established by M4 at all.** Observing it would require a real integrated worker path executing complete queries end to end, which §17 forbids M4 from building, and S7′'s evidence is stage-scoped (§17) and cannot supply it. That sufficiency is instead an **adoption prerequisite** for the implementation milestone (§19.2), on exactly the same footing as full correctness parity already is there — consistent with §1.2, under which B and C are *justification* verdicts that a named boundary is worth building and measuring end to end, not claims that the post-boundary configuration has been shown responsive. If the screen fails, no boundary in §8.2 can solve it: B **and** C are both excluded (C requires this same condition), and the verdict is **D** under §1.1's *no-boundary* cause. **That is a different D from §7.5.9's**, and the report must say which it is naming: the *no-boundary* D is a decisive negative about the architecture, reached by evaluating this screen at a tuple where T-a *does* fail; §7.5.9's *no-full-query-evidence* D is reached where T-a does **not** fail, this screen is therefore never evaluated, and the finding is about what M4 is permitted to measure rather than about any boundary's prospects;
4. spike S7′ evidence, in the two distinct roles below. **Neither role invokes §7.4.2's effect rule, and no "improvement" test is applied to S7′ evidence anywhere in this spec.** S7′ is stage-scoped by construction (§17); three successive attempts to define an operand on which a stage-scoped spike could prove a full-window improvement each failed for a different reason (§7.4.2 records them), and the attempt is abandoned rather than repaired. **S7′ supplies stage-level feasibility and overhead evidence only.** That evidence can justify that a named boundary is worth building and measuring end to end — which is exactly what a *justification* verdict claims (§1.2) — and it can never on its own establish full-query responsiveness sufficiency.

   **(a) Report-only stage cost.** At **every failing `(case, broadPhase, state)` tuple where T-a is among the failing metrics**, plus **R1 and R2**, plus **the largest verdict-bearing workload**, S7′ reports the named boundary's own stage-level cost — the input snapshot and any extra copy, the transfer and its serialization, the worker-side execution, the `await`, and the response's receipt and deserialization — as both main-thread-occupancy figures and the arm's real **elapsed** bracket duration (X-3), alongside the synchronous arm's figures over the same stage and identical inputs (§17). **This clause carries no pass/fail claim of any kind and asserts no improvement.** Its purpose is transparency: the boundary's true price is on the record, at both ends of the workload range (condition 5), before B or C is reached. A clause-(a) figure can never on its own fail condition 4, and INCONCLUSIVE is not a possible outcome here because no statistical comparison is being tested.

   **(b) The added-occupancy bound — the *entire* mechanical evidence a B or C verdict rests on.** Evaluated **per named boundary `w` (either class)** as pass/fail at **every failing `(case, broadPhase, state)` tuple where T-a is among the failing metrics, and nowhere else.** **The scope test is a property of the tuple, never of why the tuple is in S7′'s case set.** R1, R2, and the largest verdict-bearing workload appear in clause (a)'s and condition 5's case set as **report-only overhead coverage**, and *that* inclusion never brings them under this check; but if such a tuple **independently qualifies** — it is itself a failing tuple with T-a among its failing metrics — it is in clause (b)'s scope on that basis, exactly like any other qualifying tuple. What is excluded is a tuple that **passes** the target: `Rᵢ(w,τ)` is defined only inside a failing query window (condition 3's construction), so it has no value there, and asking a passing tuple to satisfy a pass/fail bound would let a tuple where nothing was wrong force D.

   **`Rᵢ(w,τ)` is boundary-specific, not condition 3's shared `Rᵢ(all,τ)`.** For each of the five paired repetitions `i`, `Rᵢ(w,τ)` is computed by condition 3's identical per-task rule — subtract covered portions from each CDP main-thread task in the failing window; take the **longest contiguous** uncovered interval per task; count an overlapping stage once — **except the covered ("transferable") set is restricted to the stage(s) `w` itself owns** (§8.2's row for `w`), never the union of every §8.2-movable stage that condition 3's screen credits. Consequently `Rᵢ(w,τ)` is never smaller than `Rᵢ(all,τ)` at the same task — `w` owns a subset of what that permissive screen removes — and a boundary owning **more** stages has a **smaller** `Rᵢ(w,τ)`, because more of the task's work is credited as removed by `w` itself. **This is the mechanical channel through which a broader (C-class) boundary can be evaluated where a narrower one sharing the same messaging shape could not**: `w`'s added occupancy `Hᵢ(w,τ)` does not shrink with scope (a boundary returning more result data pays at least as much serialization/deserialization, never less), but `Rᵢ(w,τ)` does, because a boundary owning the exact-query and distance-query stages in addition to the precheck stage removes strictly more main-only-attributed work from the residual than one owning the precheck stage alone. Let `Hᵢ(w,τ)` be the **boundary-attributable** largest main-thread occupancy `w`'s own crossing adds at repetition `i`, defined precisely in the next paragraph. Clause (b) passes for `w` only if `Rᵢ(w,τ) + Hᵢ(w,τ) ≤ 50 ms` for **all five** repetitions, evaluated as a hard maximum exactly like T-a and like condition 3's own screen. The sum is deliberately conservative — it charges the largest added task against the largest residual task even where the two could not occupy the same task — so its errors fall toward **D**, which is the safe direction under §7.5. Where `w`'s `Rᵢ(w,τ)` or `Hᵢ(w,τ)` has no measured or conservatively-bounded value at `τ` — no matching §17 vertical for `w`, or a wire-contract component (e.g. **WB-2**'s or **WB-4**'s own, larger result payload, which no S7′ vertical directly builds, §17) that cannot be bounded from existing operands — `w` is **UNEVALUABLE** at `τ`, never INSUFFICIENT, and settles nothing for B or C at that tuple (§7.5's tenth condition).

   **`Hᵢ(w,τ)` is computed by per-task intersection with `w`'s own boundary-owned sub-marks, never by a whole-task filter.** §17's worker-arm bracket deliberately contains the `await`, and the main thread is **not** idle across it: §6.1.7 keeps every observer running for the query's duration, §6.2 dispatches a trusted `mousemove` every 100 ms, and the loaded federated model's Viewer rAF loop and renderer keep producing main-thread tasks. None of that is work the boundary adds, and much of it runs precisely *because* the boundary freed the main thread — so counting it would charge the boundary's own benefit against it, asymmetrically and perversely, pushing clause (b) toward `Rᵢ(w,τ) + Hᵢ(w,τ) > 50 ms` the more successfully the boundary worked. S7′'s worker arm therefore emits **sub-marks around `w`'s boundary-owned main-thread chunks it can bracket in JavaScript**: (i) the input snapshot and any extra copy, and (ii) serialization plus the `postMessage` call. **The third component — the response's receipt and its structured-clone deserialization — cannot be bracketed by a sub-mark at all**, because deserialization is performed by the browser before the `onmessage` handler runs, so no in-handler mark can start before it has already happened; §6.2's delivery-task correlation rule supplies it instead. For each CDP main-thread task in the arm's bracketed window, take the **summed duration of that task's intersections with `w`'s sub-mark intervals** from (i) and (ii) **plus, for whichever task §6.2's correlation rule identifies as the delivery task, that task's own interval from its start up to whichever comes first — the task's own end/yield, or the arm's closing `performance.mark` (never past the closing mark, even if the same task keeps executing after it — §6.2's rule states why)** — never the whole task for any *other* reason, whether or not it also contains other, non-boundary-owned work; a task that neither intersects a sub-mark nor is the identified delivery task contributes zero, and a task straddling a sub-mark and other work contributes only the overlapping portion. **`Hᵢ(w,τ)` is the maximum of that per-task figure over every task in the window at repetition `i`.** This deliberately **sums** a task's boundary-owned contributions rather than taking the longest contiguous one — the opposite of `Rᵢ(w,τ)`'s contiguity rule, and deliberately so: `Rᵢ` models how a task *splits* once a stage is genuinely removed, so only an uninterrupted remaining span counts against it, while `Hᵢ` models occupancy the boundary *adds* to a task that still exists, so two boundary-owned chunks inside one uninterrupted task both lengthen it and both count — and the delivery task's full interval is exactly one such chunk, credited whole because §6.2's rule establishes it is a single uninterrupted browser task performing nothing but that message's receipt, deserialization, dispatch, and handling. Ambient tasks — Viewer rendering, the rAF cadence recorder, the input-probe handlers — that run during the `await` while the main thread is otherwise free remain **excluded** by this same rule, since they neither overlap a sub-mark nor are the delivery task, and contribute zero; no separate exclusion clause is needed. Worker-side execution and the `await` itself occupy no main-thread task and contribute nothing by construction, which is also why a total-elapsed figure may **not** be substituted for `Hᵢ(w,τ)`. **Where §6.2's correlation rule cannot identify a single delivery task at a repetition, `Hᵢ(w,τ)` has no value there and `w` is UNEVALUABLE at that repetition** — the same disposition this condition already gives a boundary missing its primary threshold evidence — never a mark-only estimate substituted in its place. These sub-marks, and the delivery-task correlation mark, are **harness-side `performance.mark` calls in the spike's own code**: they add nothing to §16.4's closed instrumentation list and require no library change.

   **What clause (b) does and does not establish, stated plainly so it cannot be over-read.** Clause (b) is the whole of the mechanical evidence B and C rest on. It is a direct, peak-based threshold check computed from real measured quantities — `w`'s own main-only residual plus `w`'s own measured added main-thread cost — against **the same quantity T-a is a threshold on**, namely a bound on the largest post-boundary main-thread task. It establishes that and nothing else. It uses the **boundary-specific** `Rᵢ(w,τ)`, not condition 3's boundary-independent `Rᵢ(all,τ)` — a tighter bound than condition 3's permissive union, restricted to exactly the stages `w` owns — but it is still not a demonstration that `w` meets T-a on its own real, integrated implementation: the S7′ figures it consumes are themselves stage-scoped and paid fresh every repetition (§17), never measured against a persistent-cache steady state, so full real-integrated T-a sufficiency for the *adopted* boundary remains an adoption prerequisite (§19.2), exactly as before. It does **not**, and structurally cannot, establish **T-b1 / T-b2 / T-c** sufficiency: that would require a real integrated worker path executing complete queries, which §17 forbids M4 from building, so it too stays an adoption prerequisite (§19.2), unchanged. And where **T-a is not among a tuple's failing metrics**, clause (b) has **no defined application there at all**; that tuple is governed by §1.1's *no-full-query-evidence* cause and §7.5.9, never by B or C;
5. S7′ overhead measured at **both** the smallest queries (R1/R2) and the largest verdict-bearing workload — a design winning only at a stress case must not silently become the default. **This is report-only overhead coverage, exactly as condition 4(a) says, and is never itself a pass/fail gate**: being in this set does not bring R1, R2, or the largest verdict-bearing workload under condition 4(b), since `Rᵢ` is undefined wherever no failing query window exists. Any of them that **independently qualifies** as a failing tuple with T-a among its failing metrics is nonetheless in 4(b)'s scope on that basis, per condition 4(b)'s scope rule;
6. §15's memory budget met on §15.3's controlling metric, measured cold/warm/peak/retained, with the multipliers confirmed (§7.5.7);
7. §10 and §11's lifecycle, stale-result, and disposal requirements demonstrated by S4′ (and S5′ where the topology requires it);
8. no structural blocker outstanding — in particular §8.6's module-resolution precondition, resolved by S1′ under this explicit, mechanical three-case rule: **(a)** an as-served module worker resolves its imports with no change ⇒ condition **met**; **(b)** it does not, but S1′ demonstrates a permitted variant is feasible — a relative-path-only entry, or a recorded build/rewrite step, never a blob-URL or request-interception substitute (§17) — and records the required change ⇒ condition **met**, with that change carried forward as a named adoption prerequisite in §19.2; **(c)** no permitted variant demonstrates a feasible route ⇒ condition **unmet**, D, naming module resolution as the blocker. Reading a required-but-undemonstrated build step as an outstanding blocker (case (c)) is never conflated with a resolved one that merely defers implementation (case (b)).

**Verdict C — a broader ownership boundary is required.** Requires B's conditions 1 and 3–8 **as revised above, evaluated for a C-class boundary** — which means in particular that C is reachable only where **T-a is among the failing metrics** at the relevant tuple, since conditions 3 and 4(b) have no defined application anywhere else. Plus **all** of:

- evidence that the failure is in the **warm narrow phase**;
- **every applicable §8.2 B-class boundary is mechanically INSUFFICIENT at the tuple** (per the disposition rule and applicability definition above). An UNEVALUABLE B-class boundary settles nothing here: it does not count as insufficiency, and a tuple with an applicable-but-UNEVALUABLE B-class boundary falls to D (§7.5's tenth condition), never to C by default. **Where no B-class boundary is applicable at the tuple at all** — the exact-query-substage case, where §17 names no B-class vertical and §8.2 names no candidate boundary — this clause is **vacuously satisfied** (there is no applicable boundary to be insufficient), which is the intended, not an accidental, reading: C requires the *absence of a working targeted alternative*, and "no targeted alternative was even nameable" is as strong a case for that absence as "the one nameable alternative measurably failed";
- **a named §8.2 C-class boundary (WB-2 or WB-4) is mechanically SUFFICIENT at the tuple** — condition 4(b)'s `Rᵢ(w,τ) + Hᵢ(w,τ) ≤ 50 ms` holds for that boundary at every one of the tuple's five repetitions, computed exactly as condition 4(b) defines for any named boundary, with `Hᵢ(w,τ)` for a C-class `w` bounded conservatively from existing operands — the population-push occupancy from the B-class vertical that shares `w`'s resident-data footprint (e.g. **WB-2**'s population figure is bounded by **WB-2p**'s precheck-vertical population sub-mark, since both snapshot the same operand set, §17), the compact-query-send occupancy from that same vertical's send sub-mark, and the response-receive occupancy from §6.3/§12.4's direct measurement of `w`'s own, broader response shape (pair verdicts, distances, witnesses) wherever the gate times deserialization of that payload shape. **If any of these three cannot be conservatively bounded from an operand M4 already measures, `w` is UNEVALUABLE, not SUFFICIENT, and the tuple falls to D** (§7.5's tenth condition) — no new spike or instrumentation is added to remove that gap;
- **the mechanical difference between the rejected B-class boundary and the satisfying C-class boundary is named**, not asserted by narrative. For each B-class boundary found INSUFFICIENT, the report names the specific stage(s) the satisfying C-class boundary owns that the B-class boundary did not — read directly off §6.3/§12.4's per-substage attribution, which is what shrinks `Rᵢ(w,τ)` for the broader boundary (condition 4(b)'s note above) — or, where message/transfer cost is the discriminator rather than stage ownership, the specific measured figure showing the broader boundary's crossing removes or amortizes a cost the narrower one pays repeatedly;
- **S6′ as explanatory evidence, never as C's discriminator.** S6′ measures the per-pair, non-resident topology's own `postMessage` overhead directly at the observed candidate volume, result-message volume included (§17). It explains *why* a per-pair topology is disfavored relative to the one-way-population topology both WB-2p's and WB-2's/WB-4's verticals actually use, and it is one input to the conservative `Hᵢ(w,τ)` bound above where a wire-contract component needs it — it never independently decides C on its own, and "C1 refuted by S6′" is retired as a standalone clause (§18's C1 row is updated to match).

**What this does and does not establish.** C is a mechanical justification that a broader class of boundary is the only evaluated class capable of satisfying the stage-level T-a model at the tuple — it is **not** proof of full-query responsiveness, exactly as B is not (condition 4(b)'s closing paragraph, above). Population cost is charged to the state/repetition in which it actually occurs; only *cumulative* cost may be amortized across §7.4.1's declared horizon, and amortization is never used to shrink a *peak*-based `Hᵢ(w,τ)` figure — T-a bounds the largest individual task, and dividing a one-time population cost across many queries does not make that task itself smaller. Full-query sufficiency for the adopted boundary remains an adoption prerequisite under §19.2, on the same footing as B's. **C is never reached by narrative argument from figures that do not mechanically decide it**; where the evidence above does not settle every one of C's clauses, the outcome is D, which is the same safe direction condition 4(b)'s conservative sum already errs toward (§7.5).

**C's reachability is not defended here, and on the spec's own carried-forward evidence it is expected to be narrow.** C's defining failure is in the **warm narrow phase**, and §3.1's evidence there — a largest checkpoint-bracketed span of 6.0 ms warm, and a worst `clearance-distance-query` span of 6.10 ms with **zero** samples over `frameBudgetMs` — makes a warm **T-a** failure unlikely and a T-b1/T-b2/T-c-only warm failure the expected shape, which §7.5.9 routes to **D**. If that is what the measurements show, **D is the correct verdict and is reported as such**: an evidence-scope finding that M4 cannot resolve C's own question with the evidence it is permitted to gather — **not** a finding that a worker-resident architecture would not help, and not a defect to be repaired by loosening some other condition.

**Verdict D — blocked.** §7.5's **ten** mandatory conditions — including **§7.5.9's *no-full-query-evidence* cause**, which fires at any verdict-bearing tuple whose only failing metrics are T-b1, T-b2, and/or T-c; and **§7.5.10's *no-settled-boundary* cause** (new), which fires whenever a tuple is left with no B-class boundary SUFFICIENT, at least one applicable boundary of either class UNEVALUABLE or evaluated-and-INSUFFICIENT with no other boundary settling the tuple, or C's evidence not mechanically satisfied — plus §1.1's *no-boundary* cause when condition 3's screen fails at a T-a-failing tuple and A, B, and C are therefore all excluded. Where more than one applies, each is named separately, and no two of these causes are ever reported as if they were the same finding.

### 7.4 Topology, amortization, and the effect rule

#### 7.4.1 Topology and amortization must be fixed before any overhead figure means anything

- **Worker topology must be named**: one long-lived worker vs. per-query worker vs. pool; persistent worker-resident cache vs. per-query population. §18 enumerates the options; a proposal picks one, and every overhead number is reported against it.
- **The amortization horizon is declared, not open-ended.** A one-time population cost may be amortized over **the queries actually executed in the measured scenario sequence, and over nothing else.** Amortizing over unspecified "future queries" is a named loophole (§7.6.4).
- **Overhead is compared at both ends of the workload range** (B condition 5), never only where it looks best.

The comparison M4 then makes is simply: *does §7.3 condition 4(b)'s* **`Rᵢ(w,τ) + Hᵢ(w,τ) ≤ 50 ms`** *hold for the named boundary `w`, per §7.3 conditions 3–4, at every failing tuple where* **T-a is among the failing metrics**? — the boundary's own main-only residual (restricted to the stage(s) `w` owns, never condition 3's boundary-independent union) plus the main-thread occupancy `w` **adds back**, which is the input snapshot and any extra copy, serialization plus `postMessage`, and the response's receipt and deserialization. Full stop. It is not a ratio test against an invented "small fraction," and it is **not an improvement test**: no M4 verdict condition asks S7′ to demonstrate an improvement, and §7.4.2's effect rule is not invoked on S7′ evidence anywhere (§7.4.2). The boundary's stage-level cost — its occupancy figures and its real **elapsed** bracket duration alike — is measured and reported alongside (§17, §7.3 condition 4(a)) so its true price is on the record, and it gates nothing. M4 deliberately does **not** compare a proposal against T-b1/T-b2/T-c end to end: that comparison requires an integrated worker path executing complete queries, which §17 forbids M4 from building, and it is therefore an adoption prerequisite (§19.2) rather than a verdict condition — which is also why a tuple failing **only** T-b1/T-b2/T-c admits no M4 determination at all and is decided by §7.5.9.

#### 7.4.2 The precommitted effect rule (what "beyond measurement noise" means)

For a paired comparison between two arms — both run for the same 5 repetitions under §6.1.6's schedule, both measured over the **same scope covering the same work**, and both submitting the **same explicitly named per-repetition scalar operand** — an improvement counts **only if both** hold:

1. the difference of the two arms' **medians** exceeds the **interquartile range of the noisier arm** across its five repetition values (a non-parametric spread bound requiring no distributional assumption at n = 5); **and**
2. the improvement's **direction is consistent in at least 4 of the 5 paired repetitions** (a sign test at n = 5; 4/5 or 5/5 is the strongest statement 5 pairs support).

Failing either, the effect is **INCONCLUSIVE**, which under §7.5.5 forces D rather than permitting B or C.

**No M4 verdict condition currently invokes this rule, and none may be read as invoking it implicitly. In particular, S7′ evidence is never subject to it.** Earlier drafts routed §7.3 condition 4 through this rule, which required a stage-scoped spike to demonstrate an "improvement" on some operand. Three successive operand definitions were tried and each failed for a different reason: a **full-query window** needed a code seam that does not exist; **elapsed time** makes B and C unreachable by construction, because the worker arm's bracket necessarily contains the synchronous work *plus* the snapshot, the transfer, the serialization, and the `await`; and a **peak main-thread task duration** is insensitive to the T-b1/T-b2/T-c-only failure shape that §3.1's carried-forward evidence — 6–12 ms checkpoint-bracketed spans — says is the expected one. The correction adopted is an **evidence-scope correction, not a fourth operand**: §7.3 condition 4 no longer asks S7′ for an improvement at all. Its clause (a) is report-only stage cost, and its clause (b) is a direct `Rᵢ + Hᵢ ≤ 50 ms` threshold check that was never routed through this rule and remains sound. **No fourth operand may be invented for S7′**, and S7′ evidence may not be used to support any improvement claim.

**The rule is retained rather than deleted, and is deliberately handed forward.** It is a legitimate, well-specified, distribution-free method for one specific situation: a paired comparison of two arms measuring the same work on the same named operand at n = 5. That situation is exactly what the **adoption milestone's** own end-to-end sufficiency comparison is (§19.2) — the real, integrated (non-stub) worker path against the synchronous oracle, over complete queries, on **T-a / T-b1 / T-b2 / T-c**. Keeping the rule specified here means that milestone inherits a precommitted "beyond measurement noise" definition instead of re-deriving one after its numbers are in. Any future condition invoking it must name the quantity it is applied to explicitly, and must state the scope both arms cover; **an elapsed wall-clock operand (X-3) is never valid for a stage-scoped comparison**, for the reason given above.

### 7.5 When D is mandatory

Verdict **D** is required — not merely permitted — if **any** of the following holds. Each D verdict names which apply and exactly what would resolve them.

1. **No confirmed responsiveness target.** §7.2's target is still provisional and unconfirmed.
2. **No representative runtime.** §6.1.5b could not be run, or produced results materially different from the historical configuration with no explanation.
3. **Capacity censoring.** The workloads the decision turns on could not be executed because a shipped constant rejected them (§4).
4. **Workload validity.** The scenario a proposal depends on is not established as a real collision-core requirement — including §5.5's condition (an unconfirmed ~10-instance workload driving the decision) and S3 (whole-model source, post-M4 scope).
5. **Insufficient statistical confidence.** A comparison the verdict depends on is **INCONCLUSIVE** under §7.4.2. **No M4 verdict condition currently invokes §7.4.2's effect rule** (§7.4.2), so this condition is at present vacuous; it is retained, not deleted, so that any condition ever added that *does* invoke the rule is automatically wired to mandatory D rather than silently ungated.
6. **Missing causal attribution.** §6.3's partition is incomplete — in particular while the ~1.4 s unattributed cold cost, the direct Hard-Clash-precheck duration, or the inconclusive-cause breakdown remain unmeasured.
7. **Unconfirmed memory multipliers.** §15.3's 1.0×/2.0× budgets are still provisional and a B/C verdict depends on them.
8. **Undetermined device/browser scope, or undetermined concurrency expectations where the proposal depends on them.** The target was evaluated on a machine class not established as representative — this condition applies to **A, B, and C alike**, because a target met only on one development machine is not a met target; **or** the proposal's topology is a worker **pool** (§18's C5) while concurrent-`findClashes` usage expectations remain unspecified (§8.8). A single-worker topology is not blocked by the concurrency half.
9. **No full-query evidence path for the observed failure shape — §1.1's *no-full-query-evidence* cause.** A verdict-bearing `(case, broadPhase, state)` tuple fails the target on **T-b1, T-b2, and/or T-c only**, with **T-a passing** at that tuple. §7.3 condition 4(b)'s `Rᵢ + Hᵢ ≤ 50 ms` check — the entire mechanical evidence B and C rest on — is tied to T-a's own 50 ms threshold and has **no defined application** where T-a does not fail; condition 3's screen is likewise T-a-only and is defined only inside a failing window; and S7′'s evidence is **stage-scoped** (§17) and structurally cannot establish end-to-end frame-cadence or input-latency sufficiency. M4 therefore has **no pre-registered evidence path capable of deciding A vs. B vs. C for that tuple**, and D is required (§7.3 condition 1). **What would resolve it:** the adoption milestone's end-to-end **T-a / T-b1 / T-b2 / T-c** sufficiency measurement on a real, integrated (non-stub) worker path executing complete queries (§19.2) — the same measurement that already resolves full correctness parity there, and which §17 forbids M4 from building. **This is an evidence-scope limitation of M4's own method and nothing more.** It is emphatically **not** §1.1's *no-boundary* cause: it makes no claim that a worker boundary would fail to help, it names no main-only stage as responsible, and it must never be reported as if it did. Where this condition and the *no-boundary* cause both apply at different tuples, the report names both, separately, with the tuples each arises from.
10. **No settled boundary of either class — §7.5.10's *no-settled-boundary* cause.** At a verdict-bearing tuple where §7.5.9 does not apply (T-a is among the failing metrics) and condition 3's screen (§7.3) does not itself force the *no-boundary* cause, D is nonetheless required whenever the tuple ends with **no boundary of either class SUFFICIENT there** — the single condition, covering every way that can happen: no **B-class** boundary is even applicable at the tuple (§7.3's applicability rule — the exact-query-substage case, where §8.2 names no B-class row, though a C-class boundary may still be separately applicable and settle the tuple there) **and** no C-class boundary is applicable either or none applicable is SUFFICIENT; an applicable boundary is **UNEVALUABLE** (no matching §17 vertical for a B-class boundary, or an unboundable derived-evidence package for a C-class one); or every applicable boundary of both classes is evaluated and found **INSUFFICIENT**. **This is not a claim about the architecture's prospects**, unlike the *no-boundary* cause, and it is not §7.5.9's evidence-scope limitation either: it names the specific boundary(ies) — or their absence — left unsettled at that tuple, and what would resolve it: typically a matching §17 vertical, a conservatively-bounded wire-contract figure, or (for the no-applicable-boundary case) naming the dominant substage that has no candidate boundary at all. Never reported as if it were §7.5.9's or §1.1's cause; where more than one of the three applies at different tuples, each is named separately.

### 7.6 Named loopholes

1. **Cherry-picking high-count but spatially sparse sources** (or dense ones) — defeated by §5.1's mandatory covariates, §5.4's stratification on **per-instance** `density` rather than raw `proximity`, and §5.4's per-level achieved-separation reporting with its `DENSITY_UNSTRATIFIED` label. **Determinism alone is not the defence** and must not be cited as one: a deterministic algorithm forecloses *discretionary* cherry-picking, but it does not by itself guarantee that the cohorts it produces represent distinct densities — which is exactly why the achieved separation is measured and labelled rather than assumed.
2. **One cold and one warm sample** — defeated by §6.1.6's five counterbalanced repetitions and §7.2's aggregation rules.
3. **Comparing a maximum from one sample count against a maximum from another** — §6.1.8 requires like-for-like percentiles with both counts stated.
4. **Amortizing worker transfer over an unspecified number of future queries** — defeated by §7.4.1's declared horizon.
5. **Ignoring result-message volume** — a worker returning thousands of pair results pays serialization and main-thread deserialization cost; §6.3 requires it attributed and §8.4 names it.
6. **Treating a capacity rejection as a fast pass** — defeated by §4's `CAPACITY_REJECTED` requirement.
7. **Deciding on the scheduler-conformance metric alone**, which can be fully conformant while the UI starves — defeated by §6.2 and §7.2.
8. **Reporting only the historical `--single-process` runtime** — defeated by §6.1.5.
9. **Measuring input latency with in-page `dispatchEvent`**, which measures nothing — explicitly forbidden by §6.2.
10. **Deriving duty cycle from Long Tasks**, which cannot see tasks under ~50 ms — explicitly forbidden by §6.2.

**Transfer detaches.** Transferring an `ArrayBuffer` neuters it on the sender. The main thread still needs the welded geometry for the `'linear'` oracle and for `ContainmentQuery.anyComponentInside`'s direct `.attributes.position` / `.index.array` reads. So a transfer-based design either **copies** (memory duplication) or **loses** the main-thread copy (the oracle stops working — forbidden by §14). Every proposal states which and accepts the consequence.

### 8.2 The candidate boundaries — with the payoff stated correctly

"The easy worker stage is worth ~316 ms" is **wrong**:

- The vendor's `GenerateMeshBVHWorker` moves **only `MeshBVH` construction** — it transfers position/index buffers away temporarily and returns them; it does not move this repository's weld or connectivity phases (`node_modules/three-mesh-bvh/src/workers/GenerateMeshBVHWorker.js:7`). On the M3 fixture that is **~43 ms**, not 316 ms.
- `compactAndWeld` (~176 ms) must run in the same synchronous span as proxy resolution *until collision-owned copies exist*. It can move only under an **extra-copy variant**: the main thread first `slice()`-copies the raw Viewer position/index views, then hands those copies to a worker that welds. Whether that wins is a measurement; §6.3 requires the extra copy's cost attributed.
- Connectivity (~96 ms) reads only the welded index and is **freely transferable**.

| Option | Class | Boundary | What actually moves | Payoff on current evidence | Principal cost |
|---|---|---|---|---|---|
| **WB-0** | — | none | — | — | status quo |
| **WB-1a** | **B** | BVH construction only (vendor-supported) | `new MeshBVH(...)` per distinct geometry | **~43 ms cold**, zero warm | buffers out and back per geometry |
| **WB-1b** | **B** | full geometry preparation, extra-copy variant | copy → weld → connectivity → BVH in the worker | up to **~316 ms cold**, zero warm, minus the added copy | one extra main-thread copy per geometry; larger transfer |
| **WB-2p** | **B** | Hard-Clash precheck only | `volumeOverlapQuery` over the candidate list | measured by §17's precheck vertical | both operands' geometry + BVH + connectivity worker-resident **for this stage only** — a worker-owned cache scoped to precheck inputs, not per-pair transfer |
| **WB-2** | **C** | narrow-phase pair evaluation | precheck + exact queries + distance query | the dominant **warm** cost (~450–518 ms of ~518 ms warm narrow phase, one source instance) | both operands' geometry + BVH + connectivity worker-resident ⇒ a worker-owned cache serving the **whole** narrow-phase region, not per-pair transfer |
| **WB-3** | **B** | clearance distance primitive only | `closestPointToGeometry` | ~11% of warm narrow phase | WB-2's data requirement for a tenth of the benefit — the cache exists to serve this one primitive alone. Re-measured, not assumed. |
| **WB-4** | **C** | whole query below extraction | broad + narrow phase + per-pair aggregation | everything except main-only stages | entire instance population and all geometry worker-resident |
| **WB-5** | — | extraction | — | — | **structurally impossible**, §8.5 |

**Class is decided by scope of execution ownership, never by whether a worker-resident cache exists.** A **B-class** boundary (WB-1a, WB-1b, WB-2p, WB-3) moves exactly one bounded, named stage; the main thread still issues and orchestrates the surrounding query, including any other narrow-phase substage the boundary does not name. Where a B-class boundary needs data resident in the worker across a query's own candidate set (WB-2p, WB-3), that residency exists solely to serve the one named stage and does not broaden the boundary's class — this is why **WB-3 stays B-class** despite needing the same resident dataset WB-2 needs (§8.3): it executes only `closestPointToGeometry` over that data and never takes ownership of the precheck or exact-query stages. A **C-class** boundary (WB-2, WB-4) moves a broader query-execution region spanning multiple narrow-phase substages, or the whole query below extraction; its worker-resident cache exists to serve that broader region. §7.3 depends on this classification to keep B and C mechanically distinct, and to give the narrow-phase B branch — previously nameless (WB-2 strictly contains the precheck vertical's evidence and so could not honestly be named on it) — a boundary it is permitted to name: **WB-2p**.

**WB-1a and WB-1b are cold-only** — the geometry cache already amortizes them to zero warm — while **WB-2p/WB-2/WB-3/WB-4 are where the warm cost is.** A verdict of B or C must say which named boundary, and of which class.

### 8.3 The tension M4 must resolve with evidence

The warm narrow phase is hard to move **because of ownership and lifecycle, not because its data is fundamentally non-transferable**. Once copied out of Viewer state, positions, indices, connectivity arrays, matrices, BVH buffers, epochs, and revisions are all representable as worker data (§8.1), and a *persistent worker-owned cache* avoids per-query duplication. **Needing a worker-resident cache is not, on its own, evidence for C** (§7.3, §8.2's classification rule) — WB-2p and WB-3 need one too, and stay B-class. What actually separates the shapes is *how much of the narrow phase's own execution* the boundary takes over. The honest framing:

> the **whole** narrow-phase region (WB-2) is movable only under a persistent worker-resident cache serving every one of its substages, and only becomes the named verdict once every applicable single-stage (B-class) boundary is shown insufficient (§7.3); the cold-only geometry stages (WB-1a/WB-1b) are already amortized to zero warm and need no such argument; and a single warm substage moved alone (WB-2p, WB-3) may need the same resident data but takes ownership of only that one stage — cache residency is a shared prerequisite across all four, not a discriminator between them.

A hypothesis, not a finding — and it does **not** support A on its own.

### 8.4 What a WB-2 message would contain — and why WB-4 cannot share it

**These are two different contracts, and conflating them would credit WB-4 with work it never moved.** The per-query message below carries an already-computed `pairs` candidate list. **Producing that list is the broad phase.** That is exactly right for **WB-2**, whose §8.2 boundary is narrow-phase pair evaluation and which correctly leaves broad phase on the main thread. It is wrong for **WB-4**, whose §8.2 boundary is the *whole query below extraction* — "broad + narrow phase + per-pair aggregation." A worker handed a finished pair list has not run broad phase; the main thread has. Measuring WB-4 against this contract would attribute a narrower boundary's cost to it, and — because a boundary's residual `Rᵢ(w,τ)` is computed over the stages `w` itself owns (§7.3 condition 4(b)) — would credit WB-4 with removing broad-phase work its measured topology never removed. **§8.2's class and boundary definitions are unchanged by this section; only the wire contracts are separated.**

#### 8.4.1 WB-2's contract

Per `(epoch, geometryIndex)`, pushed **once** as a one-way population, not per pair:

```
{ epoch, geometryIndex,
  position: Float32Array, index: Uint32Array,            // copied first — the oracle needs its own
  bvh: { version, roots: ArrayBuffer[], index, indirectBuffer },   // MeshBVH.serialize output
  connectivity: { componentCount, componentOf: Int32Array, closedManifold: Uint8Array },
  localDiagonal, aspectRatio, aspectRatioExceeded }
```

Per query, a compact repeated message:

```
{ requestId, worldGeneration, mode, clearance?,
  epochs: [{ epoch, placementRevision, revisionArmed: boolean }],   // §10; arming mirrors §2.2's path rule
  pairs: [{ sourceEpoch, sourceFragmentId, sourceGeometryIndex, sourceMatrix: Float64Array(16),
            targetEpoch, targetFragmentId, targetGeometryIndex, targetMatrix: Float64Array(16) }] }
```

Response:

```
{ requestId, epochs: [{ epoch, placementRevision }],     // echoed for revalidation, never an authority
  results: [{ sourceFragmentId, targetFragmentId, verdict, conclusive, inconclusiveCauses?, distance?, witness?, ... }],
  diagnostics: [...], statistics: { ... } }
```

Absent by design: no `Model`, no `modelId`, no `dbId` (§9). **Response volume is itself a measured cost** (§7.6.5).

#### 8.4.2 What WB-4's contract would additionally require

WB-4 owns broad phase, so it cannot be sent candidate pairs; it must be sent the population and scope from which it derives them itself. Beyond §8.4.1's per-geometry population, WB-4's contract must define, at minimum:

- how the **complete `PlacedInstance` population** per target epoch reaches the worker and is kept current — the `worldMatrix` / `worldBounds` / `ownerDbId` records broad phase actually scans (§2.4), not just the geometries the narrow phase consumes;
- how **source and target membership and scope** are expressed per query, replacing the pair list;
- whether **TLAS ownership and rebuilding** are worker-resident, and if so how a rebuild is triggered and counted;
- how a **placement revision** updates resident records, preserving §2.2's path-specific arming scope and §10's settlement matrix;
- which response and population operands supply WB-4's own `Hᵢ(w,τ)` bound.

**No new spike or instrumentation is added to obtain this** (§16.4's list is closed, §17 builds no WB-4 vertical). Where these components cannot be conservatively bounded from operands M4 already measures, **WB-4 is UNEVALUABLE at that tuple** — which is precisely what §7.3's Verdict C evidence clause already prescribes for a C-class boundary whose derived-evidence package cannot be assembled, and that tuple falls to D under §7.5's tenth condition. This section adds no verdict rule; it only makes clear that WB-4's package is a *different* package from WB-2's and may not be assembled from §8.4.1's pair-list topology.

### 8.5 Why extraction cannot move (settled by structure)

`viewer.impl.getRenderProxy`, `model.getInstanceTree()`, `enumNodeFragments`, and `fragList.getWorldMatrix`/`getWorldBounds` are live main-thread Viewer objects backed by the Viewer's own GPU/DOM state, and `adaptViewerGeometry` returns references into those buffers valid only within one synchronous span. **WB-5 is ruled out on structure.** If the ~1.4 s of unattributed cold cost lives here, it is a permanent main-thread floor capping every other option — which is why §6.3 makes attributing it mandatory and §7.5.6 makes leaving it unattributed a mandatory-D condition.

### 8.6 Module resolution — a precondition, not a detail

The app has **no bundler**. `server.js` serves `wwwroot/` statically and mounts `collision/` at `/collision`; `wwwroot/index.html:47-53` declares an import map mapping `three`, `three-mesh-bvh`, and `three/addons/utils/BufferGeometryUtils.js` to vendored paths. Every module under `collision/` imports `three` and `three-mesh-bvh` by **bare specifier**, and so does the vendor's own `src/workers/generateMeshBVH.worker.js`.

An import map is scoped to the realm of the document that declares it, and there is no shipped browser mechanism for applying it to a dedicated worker's realm. If that holds here, **no module worker built from the current source tree can resolve its imports**, and every worker option — including reusing the vendor's `GenerateMeshBVHWorker` — acquires a prerequisite: a worker-specific build/rewrite step, worker entry modules using relative paths only, or a classic worker over a pre-bundled script. Any CSP affecting `worker-src` must be checked at the same time.

This spec does **not** assert the outcome; spike **S1′** settles it empirically, and §17 constrains how — a blob-URL or intercepted-request worker would answer a *different* question (different base URL, different origin inheritance) than a same-origin served module worker.

### 8.7 `SharedArrayBuffer` is unavailable today

SAB — and therefore `ParallelMeshBVHWorker`/`WorkerPool`, zero-copy shared geometry, and any `Atomics`-based cancellation flag — requires cross-origin isolation (`COOP: same-origin` + `COEP: require-corp`). `server.js` sets no such headers, and the page loads cross-origin Viewer assets (`developer.api.autodesk.com`, `cdn.autodesk.io`) that COEP would block without per-resource CORP or a credentialless mode. Enabling isolation is not a local change and risks breaking Viewer asset loading.

**Adopted position:** SAB designs are out of scope for M4's verdict. If only a SAB design could meet the target, the correct verdict is **D**, with cross-origin isolation named as the blocker — never an unvalidated recommendation to change server headers.

### 8.8 Concurrency posture

Without SAB, N workers means N copies. M4's default is **one long-lived worker** unless measured evidence shows a single worker is the bottleneck; a pool is a memory multiplier before a throughput multiplier, and §15's budget applies per worker. Whether concurrent `findClashes` calls are an expected *usage* pattern is unspecified (§23 open question 5) — note that concurrent calls are demonstrably *supported* today (`CollisionWorld.js:2591-2599` handles interference between different concurrent calls), which is a correctness constraint on §10 regardless of frequency. A pool topology is blocked on the usage question by §7.5.8; a single-worker topology is not.

## 9. Runtime identity implications (Required Decision 6)

1. **The main thread is the sole identity authority.** `_modelLifecycle`, `_liveEpochs`, `_modelByEpoch`, `_placementRevisionByEpoch`, lease validity, and `ownerDbId` resolution stay main-thread, unchanged.
2. **The worker receives opaque numeric tokens only** — `loadEpoch`, `placementRevision`, `geometryIndex`, `fragmentId`, `requestId`, `worldGeneration`. Never a `Model` (structurally impossible), never `modelId` (diagnostic-only, collision-prone).
3. **The worker never learns dbIds.** dbId aggregation, `groupBy:'dbId'` semantics, and source/target provenance are computed main-thread from `PlacedInstance.ownerDbId` after results return, so `ClashPair.source.model` / `.target.model` remain real `Model` references resolved by the identity authority.
4. **`loadEpoch`'s global monotonic never-reused property is what makes token revalidation sound.** A stale epoch token is simply absent from `_liveEpochs`.
5. **Geometry identity remains `(loadEpoch, geometryIndex)`**, so a worker-side cache is keyed identically and an epoch release invalidates both by the same key.
6. **Fragment identity remains `fragmentId` within an epoch**; the first-discovery-wins `_representativeFragmentByGeometry` election stays main-thread.
7. **No worker result may introduce an identity the main thread did not already hold.** A response naming an unknown epoch or fragmentId is discarded, not resolved.

Deliberately compatible with the future durable-identity layer: nothing persists a `Model` reference or `modelId` as if durable, and nothing requires the worker to hold identity state a future durable identity would have to reconcile.

## 10. Lifecycle / stale-result correctness (Required Decision 7)

A worker introduces one new hazard class: **a result computed from state that is no longer valid, arriving after the fact.** Any proposal must carry this design, and S4′ must prove it.

### 10.1 Request state is per-call, never global

**`requestId` is a routing and duplicate-response key, not a supersession signal.** The main thread holds a `Map<requestId, RequestState>` where `RequestState = {settle, reject, epochs: [{epoch, placementRevision, revisionArmed}], worldGeneration, issuedAt}`. **Every concurrent `findClashes` call has its own entry and settles independently.**

This is a correctness requirement, not a preference: concurrent calls are an existing, handled scenario — `_getTlasEntryForEpoch` reasons explicitly about interference from "a DIFFERENT concurrent call" and resolves it by retrying with fresh state, never by cancelling either call (`CollisionWorld.js:2591-2599`). **A world-global "current in-flight id" would silently convert supported independent concurrent calls into latest-call-wins and would leave the superseded call's promise permanently pending.** M4 must not introduce that; if latest-call-wins were ever wanted it would be an explicit public contract change under roadmap §8, not a silent side effect of a worker.

Each request also carries a snapshot taken at true query entry — the same point `createCompositeCheckpointPort` snapshots `expectedRevisionByEpoch` (`CollisionWorld.js:1107`) — and `revisionArmed` mirrors §2.2's path-specific arming exactly.

### 10.2 The acceptance predicate and the complete settlement matrix

**Validation is split in two, and only the *routing* half runs before the matrix — the lifecycle precedence below is unchanged.** The rows key on `requestId`, `worldGeneration`, and `epochs`, but a malformed message may carry none of them, so *some* validation must precede them; putting *all* of it first would wrongly let a malformed payload outrank a disposed world and would contradict the stated `disposed → evicted → placement-revision` precedence. The order is therefore exactly:

**Request identity must survive worker replacement, which the recovery rule above makes a real case.** `worldGeneration` does not change when a crashed or protocol-faulted worker is replaced, so without further identity a late response from the *replaced* worker could be attributed to a *new* request that happens to reuse an id. Two rules close this, and both are cheap: **`requestId` is monotonically increasing and never reused for the lifetime of a world**; and a monotonic **`workerGeneration`** is stamped into `RequestState` at dispatch and echoed on every message. A response whose `workerGeneration` is not the current worker's is **discarded silently** — its own request was already rejected when that worker was discarded, so nothing is left to settle — and it can never be mistaken for an answer to a later request. This adds no §10.4 scenario: it is what makes the existing scenario (h), worker crash mid-request, settle correctly once recovery is permitted.

1. **Routing-envelope validation — attribution only.** Can this message be attributed to a pending request at all? A message yielding a usable `requestId` is routed and proceeds to step 2. A message with **no usable `requestId`** is unattributable by construction and is **protocol-fatal**: the main thread rejects **every** entry in the map with an error naming the protocol fault, clears the map, and discards the worker — the same settlement shape the crash row prescribes, for the same reason. This step inspects nothing but the routing identity.
2. **The lifecycle matrix below, in its existing precedence** — disposed → generation → evicted → armed-epoch placement revision. **Lifecycle state outranks payload validity**: a malformed response arriving for a disposed world rejects with `WorldDisposedError`, not a `TypeError`, so the errors a caller can observe stay exactly today's set. **Every lifecycle check is evaluated against the epoch set captured in `RequestState` at dispatch, never against the epoch list the response names.** A response is not an authority on its own scope (§8.4.1 already says its echoed tokens are "echoed for revalidation, never an authority"), so "any named epoch absent from `_liveEpochs`" means *any epoch this request was issued against* — otherwise a worker that simply omits the epoch which became stale would evade both the eviction and the placement-revision rows and publish a result derived from it. The response's echoed `worldGeneration` and epoch set must additionally **match the captured set exactly** — same generation, same epochs, no omissions, no extras, no duplicates, and matching captured revisions and arming flags — and any mismatch is a request-local malformed failure under step 3.
3. **Payload validation.** Only for a routed message that survived step 2: a malformed or schema-invalid payload is a **request-local** failure, rejecting that one entry with a `TypeError`-class error naming the request and leaving every other in-flight request untouched. **A response naming an unknown epoch or an unknown fragment id is one of these schema failures.** §9's rule that such a reference is "discarded, not resolved" governs the *reference*, and this step settles the *request*: the response is rejected as schema-invalid and the promise settles exactly once, rather than the unknown reference being dropped while the rest of the payload is published. Discarding only the offending entry and resolving the remainder is **forbidden** — it would publish a partial result the caller could not distinguish from a complete one. This is the existing §10.4 scenario (g), not a new one.

**Disposal rejects synchronously, before the worker is terminated**, so the termination path that follows finds an empty request map and cannot re-reject an already-settled promise with a second, different error.

This is an ordering and sub-shape clarification of the existing malformed-response case, **not a ninth scenario**: §10.4's scenario (g) covers both sub-shapes, and the count of eight is unchanged.

On receiving a message, the main thread looks up `requestId` in the map. **Every** outcome settles the owning promise exactly once:

| Condition at receipt | Outcome |
|---|---|
| `requestId` not in the map | **Discard silently** — a duplicate or late response for an already-settled call. Counted in statistics; settles nothing, because nothing is pending. |
| world disposed | reject with `WorldDisposedError` |
| `worldGeneration` mismatch | reject with `WorldDisposedError` (the world this result belongs to no longer exists) |
| any named epoch absent from `_liveEpochs` | reject with `ModelEvictedError` |
| an **armed** epoch's current `_placementRevisionByEpoch` ≠ its captured value | reject with `ModelPlacementChangedError` |
| response malformed / schema-invalid | reject with a `TypeError`-class error naming the request; never a silent drop |
| worker `onerror`, crash, or `terminate()` while requests are in flight | reject **every** entry in the map with an error naming the cause, then clear the map |
| otherwise | resolve with the mapped result |

Precedence follows the existing convention — **disposed → evicted → placement-revision** — so the **lifecycle** rejections reproduce today's error set exactly: `WorldDisposedError`, `ModelEvictedError`, `ModelPlacementChangedError`, with today's precedence and today's meanings.

**The compatibility claim is limited to those, and deliberately not extended to transport faults.** A worker introduces failure modes the synchronous path structurally cannot have — a malformed or unattributable response, a worker crash, an explicit `terminate()` — and the rows above reject on all three. Those are **new ways a valid `findClashes` call can reject**, and saying otherwise would mislead a host that today catches exactly the three lifecycle errors: it would meet a generic `Error` on a crash, be unable to tell it from a defect, and not know that the next call is expected to succeed against a replacement worker (the recovery rule below). M4 therefore records this as a **named adoption prerequisite** rather than settling it here: before a worker path is adopted, the implementation milestone must define the exact public mapping for protocol faults, crashes, and termination — a documented stable error type, or a mapping onto an existing documented error with an explicit `cause` — together with whether a retry is safe (§19.2). **M4 adds no public error type**, and no verdict condition depends on which mapping is chosen; what M4 fixes is only that every one of these outcomes settles its promise exactly once.

**The armed-epoch clause must reproduce today's arming scope, not broaden it.** Revalidating placement for *every* epoch on *every* path would introduce aborts that do not exist today for `broadPhase:'linear'` callers — a silent contract change, and therefore forbidden.

**After a protocol-fatal fault or a worker crash, the discarded worker is not reused.** The next `findClashes` call constructs a fresh worker and repopulates its cache by the ordinary one-way population path (§8.4.1, §18) — it neither reuses the dead worker, nor permanently rejects, nor silently falls back to synchronous execution behind the caller's back. Cache repopulation cost after such a fault is ordinary cold cost and is reported as such. Stating this is what makes "no unsettled promise" implementable rather than aspirational: without a defined post-fault policy, a subsequent call has no specified settlement at all.

**No unsettled promise is permitted under any of these conditions.** That property is what S4′ exists to demonstrate.

### 10.3 Interaction with eviction and disposal

- `evictModel(model)` must remain **synchronous and never-throwing**, including on a disposed world — it is called from `BEFORE_MODEL_UNLOAD_EVENT`. A worker design *posts* an eviction message and returns; it never awaits an acknowledgement.
- The worker may transiently hold state for an evicted epoch. Acceptable **only because** §10.2 guarantees no result derived from it is accepted. It is reclaimed on the worker's processing of the message, and `dispose()` terminates the worker outright — which by §10.2's crash/terminate row rejects every in-flight request rather than leaving promises pending.
- `invalidateModelPlacement(model)` bumps the revision main-thread; an in-flight request naming an **armed** epoch is thereby invalidated. A worker must **never** re-read placement itself — it has no Viewer access and no authority to.
- The lazy staged refresh and the TLAS rebuild it forces stay main-thread-authored; refreshed placement is pushed as data.

### 10.4 What S4′ must prove, not merely design

On a stub worker with no real geometry: rejection **at publication**, with the correct error and **no unsettled promise**, for **all** of —

(a) `dispose()` mid-flight; (b) `evictModel` mid-flight; (c) model reload producing a **new epoch** while a result for the old one is in flight; (d) `invalidateModelPlacement` mid-flight in **both** the armed (TLAS) and unarmed (linear) states — the unarmed case must **not** reject; (e) **two concurrent requests with responses returned out of order**, each settling its own caller correctly and neither cancelling the other; (f) a **duplicate** response for an already-settled `requestId`, discarded without disturbing anything; (g) a malformed response; (h) worker `onerror` / `terminate()` mid-request, rejecting every in-flight request. Proving that a token survives structured cloning is *not* sufficient.

## 11. Cancellation / abort compatibility (Required Decision 8)

### 11.1 The honest starting point

No caller-facing cancellation; two internal deferred-rejection signals that stop *waiting* without preempting work; a poll-on-checkpoint validator. **Abort granularity today is already one atomic unit** — one pair, one build phase, one traversal. A worker does not make that worse; this is parity, not a worker cost.

### 11.2 What M4 must evaluate

- **Signal path.** Without SAB (§8.7) a worker cannot poll a shared flag, and `postMessage` cannot interrupt a synchronous `closestPointToGeometry` or `bvhcast` inside the worker. Cooperative abort in a worker has *exactly* the granularity the main thread has today: between pairs, not within one.
- **Graceful abort vs. termination.** A between-pairs cooperative check driven by a queued message; and `worker.terminate()`, immediate and unconditional but destroying all worker-resident cache — making the next query cold and, per §10.2, rejecting every in-flight request.
- **Partial work disposal.** §10.2 guarantees no partial result is accepted; what must additionally be established is that the *memory* is reclaimed.
- **Cleanup of transferred/rebuilt state.** A design that transfers must state how the main thread recovers, or must copy.

### 11.3 What M4 must decide, and what it must not

**Decide:** does collision core need a per-request cancellation token at all, or is per-call stale-result rejection (§10) plus disposal sufficient for its own obligations?

**Do not:** introduce a cancellation API shape constraining how the future result layer expresses reject / partial / discard. No `AbortSignal` is added.

**S5′ is conditional** on the selected topology disposing by terminating a dedicated worker; if so, it becomes required.

## 15. Memory and duplication budget (Required Decision 14)

### 15.1 Two metrics, because one is not reproducible

**`estimateMemoryInBytes(bvh)` covers only the BVH** — not geometry buffers, connectivity arrays, pending messages, duplicated buffers, or abandoned caches. And a byte-array lower bound cannot be compared mechanically with a heap total. M4 therefore defines **two metrics** and says which controls.

**Metric M — typed-buffer lower bound (deterministic, controlling).**

```
M(scope) = Σ_geometry [ position.byteLength + index.byteLength
                      + Σᵢ bvh._roots[i].byteLength + (bvh._indirectBuffer?.byteLength ?? 0)
                      + connectivity.componentOf.byteLength + connectivity.closedManifold.length ]
         + Σ_epoch    [ tlas.primitiveBuffer.byteLength + tlasRecordCount × recordBytes ]
         + Σ_epoch    [ placementCount × (16×8 + 6×8 + 16) ]      // Float64Array(16) + two 3-arrays + scalars
         + Σ_epoch    [ instanceCount × instanceBytes ]
         + Σ_inflight [ Σ payload backing buffers (de-duplicated)  // observable payload residency only;
                      + payloadMetadataBytes ]                    // NOT the browser's internal clone buffer
```

**The in-flight term is a *payload-residency* bound, and only over values a harness can actually read.** §15.2 already requires pending-message bytes and peak-during-transfer to be reported, and `peakΔ` is decision-bearing under §15.3, so omitting the transient term entirely would leave the largest transient duplication — a sender copy and a receiver copy simultaneously resident during a population push — outside the budget it is most likely to breach. But the term must be defined over **observable** quantities: the request and response of §8.4.1 are ordinary structured-clone **object graphs**, which have **no `byteLength`**, and the browser's internal structured-clone serializer buffer is **not exposed to script at all**. Summing those would force every implementer to invent a serializer model, and two reasonable inventions would land on opposite sides of the 2.0× limit for identical runtime behavior. The term is therefore exactly two things: the **de-duplicated backing buffers actually referenced by the payload** (`ArrayBuffer`/typed-array `byteLength`, which *are* readable), and **`payloadMetadataBytes`**, the same fixed logical size computed for the payload's scalar and object fields by the identical field-list rule used for `recordBytes` / `instanceBytes` above, printed verbatim in the report.

**Ownership and de-duplication:** a buffer is counted **once per physical residency**. A `postMessage` *transfer* detaches the sender's buffer, so it is counted on exactly one side at a time; a *copy* is counted on both. A buffer shared by reference within one realm is counted once, however many objects reference it.

**What this term deliberately does not claim.** It bounds the **payload** the boundary keeps resident, not the browser's true peak during cloning: the internal serializer's own transient copy is unmeasurable from script and is therefore **declared unmeasured**, recorded as a named uncertainty rather than modelled. Metric H's heap sampling around the transfer is what observes it indirectly, and `peakΔ` is sampled at the deterministic instant of maximum **payload** residency — the instant the harness itself controls, because it controls when buffers are handed across (§15.2) — with the chosen instant named in the report. Metric M's name, a typed-buffer **lower bound**, is exactly what this term keeps it.

`recordBytes` and `instanceBytes` are **structural constants, not heap measurements** — this is what keeps Metric M deterministic, and the earlier heap-derived definition did not. Deriving them as `(H_after − H_before) / N` over `N = 10_000` constructed objects would have placed a **Metric H** quantity inside the metric declared deterministic and controlling: `usedJSHeapSize` deltas move with allocation strategy, GC timing, V8 version, pointer compression, hidden-class and backing-store reuse, and unrelated heap activity, so two identical runs could derive different per-object sizes and land on opposite sides of §15.3's `1.0 ×` / `2.0 ×` budgets. Instead each is a **fixed logical size computed from the frozen shape's declared fields**, at **8 bytes per numeric field**, **4 bytes per boolean-or-small-integer field**, and a **fixed 32-byte per-object header allowance**, with the field lists exhaustive and the arithmetic printed verbatim in the report so it can be checked without running anything:

```
instanceBytes = 32 (header) + 8 (fragmentId) + 8 (geometryIdentity.loadEpoch)
                           + 8 (geometryIdentity.geometryIndex) + 32 (nested identity header)  = 88
recordBytes   = 32 (header) + 8 (epoch) + 8 (fragmentId) + 8 (geometryIndex)
                           + 6 × 8 (the record's own min/max bounds triples)                   = 104
```

`instanceBytes` covers `CollisionInstance`'s complete shape (§2.4) and nothing else; `recordBytes` covers one TLAS primitive record. **A shape change invalidates the constant** — if either frozen shape gains or loses a field, the constant is recomputed by this same rule and the change recorded, rather than the old number being carried forward. The figures are a documented **lower bound on logical content**, which is exactly what Metric M claims to be (its name says so), not an estimate of V8's true object footprint.

**Real per-object overhead is reported under Metric H only**, as a cross-check, by the `N = 10_000` construction described above — recorded and compared against the structural constant, with any large divergence itself a reportable finding, exactly as the M-vs-H divergence rule below already requires. It never enters Metric M and therefore never moves a §7.3 condition 6 disposition.

**What Metric M deliberately omits, enumerated — because the omissions are not symmetric between designs.** M counts typed buffers plus the two frozen record shapes above. It does **not** count: per-geometry and per-result JS wrapper objects; `Map` / `Set` entry overhead in the registries and request maps; promise and closure retention; candidate-array and result-array backing stores beyond their typed contents; reconstructed `THREE.BufferGeometry` and `MeshBVH` wrapper objects on the worker side; or engine-level per-object headers beyond the fixed 32-byte allowance. A design that retains tens of thousands of small wrapper objects can therefore stay inside M's ratio while its measured heap does not — the omission favours object-heavy designs specifically. **This is a declared limitation of the controlling metric, not a defect to be resolved by re-weighting it here**: making a heap-derived ceiling independently binding would put a nondeterministic quantity back into a verdict input, which is exactly what this section exists to prevent. The gate must therefore report, alongside every M figure, the corresponding Metric H figure and **this enumeration**, and a large M-vs-H divergence is a **named reportable finding** carrying the omitted-structure list, so the gap is visible to whoever reads the verdict rather than buried in a ratio. Whether an object-overhead ceiling should itself become binding is recorded as a question for the adoption milestone (§19.2), which measures a real integrated path and can observe these structures directly. `estimateMemoryInBytes(bvh)` is reported **alongside** as a structural cross-check on the BVH term only, never substituted for it.

**Metric H — measured heap (cross-check).** `performance.memory.usedJSHeapSize` (Chromium, non-standard, coarse), under a fixed protocol: the harness launches Chromium with `--js-flags=--expose-gc` (it launches its own browser, so nothing about the app changes), then at each sample point calls `gc()` twice separated by two `requestAnimationFrame` turns, waits one further turn, and takes the **median of three** readings. Worker-side heap is measured inside the worker by the identical protocol and reported **separately**, never silently added to the main-thread figure — **subject to feature detection, because a worker realm is not guaranteed to provide what that protocol needs.** `performance.memory` is non-standard, `gc()` exists only under the `--js-flags=--expose-gc` the harness itself passes, and **`requestAnimationFrame` does not exist in a worker realm at all**, so the page-side settling turns cannot simply be re-executed there. The worker protocol is therefore: the **page** drives the settling turns and then sends the worker an explicit sample command, the worker calls `gc()` twice around them if available and returns the median of three `usedJSHeapSize` readings. Where any required API is missing, the worker figure is reported **`UNAVAILABLE`** with the reason named, never silently zero and never quietly replaced by the main-thread number. **Metric H being `UNAVAILABLE` does not alter Metric M's controlling role** (§15.1) — M is deterministic and structural precisely so that the verdict does not depend on H's availability — but the unavailability is recorded, and the M-vs-H divergence check simply cannot be performed for that scope, which is itself reported. `performance.measureUserAgentSpecificMemory()` is **unavailable** — it requires cross-origin isolation this app does not have (§8.7) — and that limitation is recorded rather than papered over.

**Metric M controls the verdict**, being deterministic, reproducible across runtimes, and independent of GC timing. Metric H is reported for every scope, and a large divergence between them is itself a reportable finding.

### 15.2 Required reporting

For **cold, warm, peak, and retained** scopes, separately for main thread and worker: base collision-world memory; per-model geometry-cache memory; TLAS memory; instance/placement memory; worker duplicate/rebuilt structures; **pending-message bytes** (`byteLength` in flight plus serialized result payload size); peak during transfer/build; steady state after. Every figure states which metric produced it.

"Peak" is taken as Metric M at the point of maximum simultaneous residency — deterministically identifiable, since the harness controls when buffers are handed across — with Metric H sampled immediately before and after that point.

### 15.3 The budget

```
base   = M(main thread, steady state, no worker)
delta  = M(main thread, steady state, with worker) + M(worker, steady state) − base
peakΔ  = M(peak, both sides) − base
```

Steady-state `delta ≤ 1.0 × base`; `peakΔ ≤ 2.0 × base`. Both **provisional**; §7.5.7 makes an unconfirmed multiplier a mandatory-D condition when a B/C verdict depends on it.

Rationale, so these are not bare numbers: without SAB, a non-transferring worker duplicates by construction, so *some* doubling is unavoidable and a budget below 1.0× would reject every option a priori. Above 1.0× means duplication plus additional rebuilt structure. **"Proportionate" is not left to judgement, and no effect-rule carve-out applies here**: §7.4.2's rule is invoked by no M4 verdict condition (§7.4.2), so a proposal exceeding either bound simply **fails §7.3 condition 6**, which is the boundary's disposition for that tuple — INSUFFICIENT if a matching vertical measured the excess, UNEVALUABLE if it did not — and the outcome is D (§7.5), the safe direction. Whether the multiplier a user sees is worse than `delta` suggests depends on what the main thread already holds independent of any worker proposal — and §2.5's corrected accounting is the reference for that: the welded `position`/`index` buffers are held **once**, wrapped by reference rather than duplicated by `BufferGeometry`, with the BVH's own internal structures, the connectivity array, and wrapper-object overhead as the genuine *additional* memory beyond that one welded copy. There is no independent ~2× baseline duplication to add on top of `delta`.

## 16. Benchmark harness design (Required Decision 15)

### 16.1 Adopted shape: one standalone new gate, no shared module

**A new, standalone `test/performance/run-gate-m4.mjs`.** `run-gate.mjs`, `run-gate-m2.mjs`, and `run-gate-m3.mjs` are **not modified** — they are the archived evidence artifacts behind M1, M2, and M3's accepted dispositions.

**No shared helper module is extracted.** Lifting the summarizers and fixture sequence into a `gate-harness.mjs` would create an abstraction with one consumer and make historical comparison *harder* (a future edit silently changes what M4 measured relative to M2/M3). Duplicating ~80 lines of behavior-free boilerplate is the lower-risk call and keeps every threshold and disposition readable in one file. Extraction becomes justified only if M4 acquires **multiple real consumers**; if so, extract an **M4-only** module then, still leaving M1–M3 untouched.

### 16.2 Hard requirements

- Real federated fixture for R1–R6 and S1–S3; **S4 is the only fully synthetic case**, constructed in-page, labelled synthetic everywhere. **S2T is *partially* synthetic** — real source, real near-source Architecture cohort, and synthetic distant bystanders injected into one existing target epoch through a test-local model facade that **replaces** the Architecture `Model` identity rather than adding a fourth (§5.3.1) — and is labelled partially synthetic everywhere; it is never mixed into a real-fixture aggregate, and its facade adds nothing to §16.4's closed instrumentation list.
- Both runtime configurations (§6.1.5), the multi-process one marked authoritative.
- Five counterbalanced repetitions per R-case state with the raw set reported (§6.1.6), and one fresh world per `(runtime, case, broadPhase, repetition)` (§6.1.4).
- Machine-readable JSON to `test/performance/results/m4-gate-<timestamp>.json`. Never raw span/diagnostic/event arrays (M1's disposition records an unusable 15 MB / 769K-line dump); always count + per-key breakdown + bounded sample + bounded top-N.
- **Never a verdict from an unexercised criterion.** Explicit empty-set guards; `NOT EXERCISED` reported honestly; every unrunnable case reports `CAPACITY_REJECTED` with the exact limit and observed value.
- **Fail loudly on correctness.** Any §6.4 mismatch ⇒ `disposition: 'FAILED_VALIDATION'`, non-zero exit. Any errored run ⇒ `'FAILED'`. Performance verdicts never fail the process. This applies to §6.4's comparator at its stated scope — the gate's TLAS-vs-linear comparison and any full-result worker arm; a **stage-scoped** spike's §6.4 stage-scoped validity failure fails and disqualifies **that spike**, is recorded as such, and does not set `FAILED_VALIDATION` on the gate run.
- Record provenance: browser version and launch flags, OS and machine class, the cohort dbId lists with their §5.4 profiling covariates (including each cohort's achieved weighted density and any `DENSITY_UNSTRATIFIED` label) and any forced replacement, the constants read from `collision/constants.js`, the counterbalancing schedule, the input-probe clock calibration and drift, the derived `recordBytes`/`instanceBytes`, and console warnings.
- For **S2T** additionally: the facade's construction and the exact Viewer surface it supplies, the synthetic fragment-id and geometry-id ranges with the real model's measured maxima they sit above, the bystander layout verbatim, the requested and achieved admitted-instance count per population level, the counterbalanced level order, and the **per-level result of §5.3.1's level-to-level control rule** — reported as an explicit pass or a named violation, and never omitted, since an S2T result is uninterpretable without it.
- Install and clear the span/event recorders in a `try`/`finally` per measured call, and dispose the `CheckpointRecorder`'s `PerformanceObserver` and the CDP session.
- **Emit the §6.3 main-only / transferable partition as a first-class report section.**

### 16.3 What the harness must not do

Retune a shipped constant; modify `collision/` behavior; **modify `server.js` or add a route to it**; change server headers; leave a recorder installed across runs; or silently trim a selection until it passes a capacity check.

**Serving spike assets does not require changing `server.js`.** The M4 harness may start **its own** express instance, from a file under `test/performance/` or `spike/m4/`, mounting the same `wwwroot/` and `/collision` paths the production server mounts **plus** `spike/m4/`. That is an additional test-only process, not a production route, and it is how S1′ gets a same-origin served worker module (§17).

### 16.4 The instrumentation M4 requires — enumerated and closed

All additive, all no-ops when unused, all in the same class as M1 Task 23's `setSpanRecorder`. This is the **complete** list:

1. **Yield instrumentation** in `collision/scheduler.js`: each real yield's resume latency and a running yield count, through the existing recorder hook. This makes X-3's yield delay a measurement rather than an estimate.
2. **Narrow-phase interior labels and an additive inconclusive-cause enum**: separate geometry resolution from the Hard-Clash precheck and separate the precheck's three sub-terms; and have `volumeOverlapQuery` / `classifyHardClashPrecheck` surface *which* conditions produced `conclusive: false` (crossing budget / containment sample budget / aspect ratio / non-manifold / unresolved containment). **Causes are a set, not a single value, because the source produces them that way.** A negative `volumeOverlapQuery` merges the diagnostics of all three terms — crossing, `aInB`, and `bInA` (`query/VolumeOverlapQuery.js:239-245`) — so one pair can legitimately carry crossing-budget exhaustion *and* unresolved containment *and* a non-manifold operand at once. A singular field would force either an undocumented precedence rule or silent loss of exactly the causal detail §12.4 exists to obtain, and two harnesses picking different survivors would report different dominant causes from identical runs. The field is therefore `inconclusiveCauses`, a **sorted set of bounded enum values**, and the per-cause histogram of item 5's retention rule counts **each cause occurrence**, with the co-occurrence count also reported so the multiset is not mistaken for a partition. **Separately, `precheckNotRunReason`** records the cases that never enter `volumeOverlapQuery` at all and are therefore not inconclusive *causes* — chiefly `classifyHardClashPrecheck`'s `skip-precheck` early return when `aabbMinDistance > 0` (`query/ClearanceHardClashPrecheck.js:19-21`), and geometry unsupported ahead of the call. **Additive**: the existing `{reason: 'clearance-hard-clash-precheck-inconclusive'}` diagnostic string and the existing `conclusive` boolean are unchanged, so no public contract moves — the causes travel only on item 5's event channel, and this remains one instrumentation item, not two.
3. **Two non-overlapping synchronous brackets**, replacing what a single combined timer around the whole span cannot separate: (a) an **extraction bracket** around `_resolveGeometryView` / `adaptViewerGeometry` alone, closing §3.1's ~1.4 s attribution gap; and (b) a bracket around `compactAndWeld` alone, matching what §6.3's table already requires of it as its own, separately classified row. **Both brackets are placed inside the injected `buildWeld(loadEpoch, geometryIndex, ownerModelIdHint)` function's own synchronous body** (`geometry/createGeometryRegistry.js:28`) — never around the `GeometryRegistry._runPhase` wrapper that `await`s it (`geometry/GeometryRegistry.js:202`) — and contiguously: bracket (a) closes at the exact instant `resolveGeometryView(...)` returns, and bracket (b) opens at that same instant. Because `resolveGeometryView` and `compactAndWeld` "MUST run inside the same synchronous span, with no intervening await/yield" (`createGeometryRegistry.js:29-32`'s own invariant), everything between the two calls — the `unsupported` destructuring and early-return branch, and the call to `compactAndWeld` itself — falls **inside bracket (b)**, since it runs after bracket (a) closes and before bracket (b)'s own closing mark at `compactAndWeld`'s return (or at the early `return` for an unsupported geometry, in which case bracket (b) is reported with zero weld work and the `oversized`/`unsupported` outcome named). **Their union therefore covers every line of `buildWeld`'s synchronous body, from entry to its return, with no gap and no overlap** — the mechanical guarantee this section requires. The one thing the union does *not* claim to cover is `_runPhase`'s own wrapper overhead around `await builderFn()` — the sub-millisecond cost of awaiting an already-resolved promise, orders of magnitude below every threshold this spec uses — which is not itself a stage and is reported, when it can be observed as non-zero, as a named residual rather than folded into either bracket. Together the two brackets produce §6.3's partition; a single combined bracket cannot, because §6.3 classifies Viewer extraction and `compactAndWeld` as two independently-attributed rows with different M4 requirements. Where a call path genuinely cannot separate the two (an inlined fast path), the interval is reported **combined** and named as such, and is treated as **main-only** for §7.3 condition 3's screen — the more conservative of the two classifications — rather than assumed transferable.
4. **Read-only diagnostic accessors for memory accounting**: per-epoch geometry-entry count and enumeration of resident geometry entries (welded buffer byte lengths, BVH, connectivity) for Metric M. Precedent: `getEpochCollisionInstanceCount` was added for M1's own gate for exactly this reason, and `run-gate-m2.mjs` currently reaches into privates because the accessor is missing.
5. **One structured, no-op diagnostic-event recorder** — `setDiagnosticEventRecorder(fn)` / `clearDiagnosticEventRecorder()` / `reportDiagnosticEvent(kind, payload)` in `collision/scheduler.js`, alongside the existing span hook and gated by the identical null-check so it costs nothing when unset. The existing `reportSpan(label, ms)` accepts a label and a number and nothing else (`scheduler.js:47-55`), so the per-pair covariates §12.4 and §13 require cannot be expressed through it, and encoding them into label strings would be unbounded and unparseable. **Bounded schema**, fixed here so the channel cannot grow arbitrarily:

   ```
   kind: 'clearance-distance-query' | 'hard-clash-precheck' | 'narrow-phase-pair' | 'geometry-resolve'
   payload: {
     sourceEpoch, sourceFragmentId, targetEpoch, targetFragmentId,      // pair identity (numbers)
     stage,                                                             // short enum string
     ms,                                                                // duration of this stage
     sourceTriangles, targetTriangles,                                  // geometry covariates
     sourceComponents, targetComponents,
     sourceScaleFactor, targetScaleFactor, anchoredOnSource,            // clearance-only
     requestedClearance, anchorLocalMaxThreshold, distance, outcome,    // clearance-only
     conclusive, inconclusiveCauses, precheckNotRunReason,              // precheck-only; causes is a SET
     containmentSamplesUsed                                             // precheck-only
   }
   ```

   **Retention rule, so raw high-volume events never enter the result JSON:** the harness's sink aggregates online — per `kind` and per `stage`, it keeps counts, §6.1.8's full duration summary, per-covariate correlation accumulators (sums, sums of squares, sums of products), a per-`inconclusiveCause` histogram (counting each cause in `inconclusiveCauses`, plus a co-occurrence count) and a per-`precheckNotRunReason` histogram, and a bounded top-N (N = 20) of the slowest individual events. Raw events are discarded after aggregation.

6. **One benchmark-only, disabled-by-default S7′ stage-input capture hook** — `setSpikeInputCapture(fn)` / `clearSpikeInputCapture()`, gated by the identical null-check-when-unset pattern as items 1 and 5, so it costs nothing and changes nothing when unset. **Its sole purpose is to make S7′'s own stage input reproducible**, closing the gap the earlier retention rule left: S7′'s worker arm requires the *exact* real candidate list (precheck vertical) or the *exact* real resolved geometry set (geometry-preparation vertical) for the query under measurement, and neither is returned or retained by `findClashes` today, while item 5's diagnostic-event sink is explicitly aggregate-only and discards raw events. **The two verticals capture differently, because they need different things and production resolves geometry differently from how it finalizes candidates.** For the **precheck vertical**, `fn` is invoked **once per query**, at the point the broad-phase candidate list is finalized, with the complete real candidate list. For the **geometry-preparation vertical**, geometry is *not* resolved once per query: `_runNarrowPhasePair` resolves it lazily, per narrow-phase pair, for **both** the source and the target operand (`CollisionWorld.js:2114-2119`), so a query can call `compactAndWeld` zero to many times, for a mix of source- and target-side geometries, interleaved with narrow-phase pair processing — there is no single return representing the query's whole geometry set. The hook therefore **accumulates**: `fn(loadEpoch, geometryIndex, role, weldedGeometry)` is invoked every time `compactAndWeld` produces a result during the measured query, for either role, and the harness — never the library — is responsible for collecting these into one **query-local, bounded set keyed by `(loadEpoch, geometryIndex)`** (first-discovery-wins, since a geometry resolved once is cached and never re-welded within the same epoch); S7′ consumes that accumulated set, covering every distinct geometry — source and target alike — actually resolved for the query, as **one bounded snapshot emitted after the query completes**, never a single per-call value. This is **M4 harness/spike instrumentation only**: it adds no public `collision/` API, is never wired to any worker or production code path, and is referenced by no verdict condition directly — S7′ (§17) is its only caller. **Capture is bounded, transient, and per-repetition**: the harness holds the captured value only for the duration of the one repetition that produced it, discards it before the next repetition begins, and it is never written to the result JSON, never aggregated, and never cached across queries — a disabled-by-default seam with no persistent retention behavior, not a second data path alongside item 5's event channel.
7. **Nothing else.** No worker code, no cancellation API, no progress API, no constant changes, no change to any existing diagnostic reason, statistics field, or public error.

Items 1–3 and 5 are useful to future milestones independently of M4's verdict.

Where it is the **exact-query stage** (strictly, or tied with clearance-distance), **no B-class boundary is applicable for it at all** — §8.2 names none — so the tuple's contribution to D is named accordingly, not attributed to any specific B-class boundary's disposition. **This does not exclude C**: where the narrow-phase family as a whole still wins and the failure is located in the warm narrow phase, WB-2/WB-4 remain applicable and evaluable on their own derived-evidence path (§7.3's Verdict C) regardless of which narrow-phase substage within that family dominates — the absence of a B-class candidate is exactly the case §7.3's vacuous-satisfaction clause exists for. Reporting a precheck-scoped result as evidence for an exact-query or distance-query boundary is forbidden by the same rule that forbids it across verticals.
- **Main-only stages dominate** (extraction, aggregation, publication): no vertical models them — WB-5 is ruled out on structure (§8.5). §7.3 condition 3's screen governs — evaluated, as always, only where **T-a is among that tuple's failing metrics**; where it is not, the screen is never evaluated and §7.5.9's *no-full-query-evidence* cause governs instead. If the screen is evaluated and fails, the verdict is **D** under §1.1's *no-boundary* cause.

**When the two families tie at recorded precision** — the only case in which "does not cleanly separate" now has a fixed meaning — **both variants run**, and each is reported against **only** the boundary it actually models. Reporting a geometry-preparation result as evidence for a narrow-phase boundary, or the reverse, is forbidden.

Both variants carry the **same** bound, the **same** case set (every failing `(case, broadPhase, state)` tuple **where T-a is among the failing metrics**, plus R1 and R2 and the largest verdict-bearing workload as report-only overhead coverage — §7.3 condition 4), the **same** 5 counterbalanced repetitions, the **same** X-1/X-2/X-3 and §15 metrics, the **same** stage-scoped measured scope (below), and the **same** stub-result-mapping restriction below. This selects *which* bounded measurement runs; it adds no spike infrastructure and no new spike.

**S7′'s measured window is the offloaded stage, not a full query.** For every measured tuple, and in **either** variant, S7′ is a **paired, stage-scoped comparison over identical inputs**: one arm executes the named stage **synchronously on the main thread**, exactly as the library does today — that is, through the library's ordinary cooperative checkpoint path, so its measured task topology is today's; the other snapshots that stage's inputs, transfers them once, executes the stage **in the worker**, and awaits and receives the response. Both arms' `performance.mark` pairs bracket the stage and nothing else — from the moment that stage's computation would begin through the moment its result becomes available to the next, stubbed stage; for the worker arm, the snapshot, the transfer, the worker-side execution, the await, and the receipt of the return value are all **inside** the bracket, so nothing the boundary really costs falls outside what is measured. **That one bracket yields distinct quantities, and they are never conflated.** (i) The arm's **main-thread occupancy** figures and (ii) its **elapsed** bracket duration (X-3) — its real wall-clock cost, transfer and serialization overhead included — are both **report-only** stage-cost evidence under §7.3 condition 4(a); neither is subjected to any improvement test, and §7.4.2's effect rule is applied to neither (§7.4.2). (iii) The one quantity that is **verdict-bearing** is the **boundary-attributable** `Hᵢ(w,τ)` of §7.3 condition 4(b), computed by §7.3's exact per-task summed-intersection rule — repeated here rather than re-derived, so the two never drift apart: it is *not* simply the largest task inside the worker arm's bracket, and it is *not* a whole-task filter. The bracket deliberately contains the `await`, across which the main thread is not idle — Viewer rendering, the rAF cadence recorder, and §6.2's 100 ms input probe all run there, precisely *because* the boundary freed the main thread, and none of it is work the boundary adds. **The worker arm therefore emits harness-side sub-marks around the boundary-owned main-thread chunks it can bracket in JavaScript** — the input snapshot and any extra copy; serialization plus `postMessage`. **The response's receipt and its structured-clone deserialization are never bracketed by a sub-mark**, because deserialization happens before `onmessage` runs and no in-handler mark can precede it; §6.2's delivery-task correlation rule supplies that component instead, via one correlation mark placed as the first statement of `onmessage` and used only to locate — never to time — the CDP task that received the message. For each CDP main-thread task in the bracket, take the **summed duration of that task's intersections with the sub-mark intervals above, plus, for the task §6.2's rule identifies as the delivery task, that task's own interval up to whichever comes first — its own end/yield, or the arm's closing `performance.mark`, never past it** (§6.2's rule states why: post-close work is validation/sampling/disposal, never a delivery cost, whichever physical task it happens to run in); `Hᵢ(w,τ)` is the **maximum** of that per-task figure over the window, with a task that neither intersects a sub-mark nor is the delivery task contributing zero — which is how ambient tasks are excluded, with no separate exclusion clause needed. Worker-side execution and the `await` occupy no main-thread task and contribute nothing by construction. **Where the correlation rule cannot identify a single delivery task at a repetition, `Hᵢ(w,τ)` is UNEVALUABLE there**, never estimated from the correlation mark's own elapsed time. These sub-marks, and the correlation mark, are `performance.mark` calls **in the spike's own code**: harness-side only, adding nothing to §16.4's closed instrumentation list and requiring no library change. Both arms run the same 5 counterbalanced repetitions and are measured on X-1/X-2/X-3 and on §15's metrics.

**Everything downstream of the stage is stubbed, in both arms.** The worker's return value is received inside the bracket and then held **inert**: no worker-produced value drives any subsequent query stage, nothing S7′ computes is persisted or published as a result of record, and the arm runs no further query pipeline for measurement purposes. Whatever a downstream stage would have consumed is a **stub result mapping**. S7′ therefore produces **stage-level feasibility and overhead evidence only**.

**What S7′ does not establish, stated so it cannot be over-read.** Because the arms are stage-scoped, their X-1, X-2, and X-3 statistics describe **a stage, never a complete query**, and they cannot be read as the frame cadence or input latency a hypothetical post-boundary configuration would exhibit end to end — moving work also changes task boundaries, message handling, yield placement, and frame opportunities across the *rest* of the query, none of which a stage-scoped measurement observes. **Full-query T-b1/T-b2/T-c sufficiency for the hypothetical post-boundary configuration is not established by M4** — and neither is full-query **T-a** sufficiency for the *named* boundary, since §7.3 condition 3's screen is a permissive exclusion screen over the union of all §8.2 variants rather than a bound on the one boundary a B verdict names. Establishing either would require a real integrated worker path executing complete queries, which the prohibition at the end of this section forbids M4 from building. That sufficiency is an **adoption prerequisite** for the implementation milestone (§19.2), on the same footing as full correctness parity. §7.3 condition 3 records that deferral; §7.3 condition 4 states exactly what S7′ *does* establish — **stage-level feasibility and overhead evidence, and never an "improvement"**: no verdict condition applies §7.4.2's effect rule to S7′ evidence, and none may be added that does (§7.4.2). And where a failing tuple's **only** failing metrics are T-b1, T-b2, and/or T-c, S7′ supplies no usable evidence path at that tuple at all: §7.5.9's *no-full-query-evidence* D cause governs it (§7.3 condition 1), and that is a statement about M4's evidence scope, never about the boundary's prospects.

**§6.4's stage-scoped validation of the worker output runs *after* the closing `performance.mark`, never inside the measured comparison.** The synchronous arm performs no such comparison, and element-wise welded-buffer and byte-identical serialized-BVH equality checks are not cheap; validating inside the bracket would charge the worker arm work the synchronous arm never does and could turn a viable boundary into a false D. The order is therefore: execute, receive, close the mark, then validate, sample §15's metrics, and dispose.

**For §15**, the arm counts the retained worker-produced prepared result as the **one** prepared-result copy a real boundary would retain (a real WB-1b path keeps it — `GeometryRegistry` holds welded geometry and acceleration state as persistent registry state). Any value retained purely to serve as the stub result mapping is **harness-only scaffolding**: excluded from the controlling Metric M budget and reported separately as harness overhead, so the arm's steady-state and peak figures stay representative of the boundary rather than of the measurement rig.

This is what makes §7.3 B condition 4's paired arms a report of **like measured work**: both cover the same stage over the same inputs with the same downstream stub, so the worker arm's reported stage cost is the boundary's real price and not an artifact of a bracket that omits work the synchronous arm's bracket contains. No improvement is inferred from the pairing — condition 4(a) is report-only and condition 4(b) is a threshold check on `Rᵢ + Hᵢ`, not a comparison between the arms.

**Where the failing tuple is R6's `refresh` state**, the arm reproduces §5.2.1's sequence in one world, because the `refresh` query cannot exist without its precursors. Those precursor queries — R6's cold and its warm `P₀` query — are executed as **setup** for the `refresh` measurement and are not themselves S7′ measured samples unless they are independently failing tuples in their own right, in which case they are measured as such under the rules above.

**Deliberately not a spike:** a generic `serialize → postMessage → deserialize` round-trip timing. A persistent worker-cache design is a **one-way population plus repeated compact query messages**, not a round trip per geometry; an artificial round trip would overstate its cost and bias the verdict toward A. S7′ measures the real topology; S6′ measures its repeated-message half.

**Also not permitted for S1′:** a blob-URL worker or a request-interception shim. Both change the worker's base URL and, for blob URLs, its origin inheritance — so they would answer a *different* question than "can this app serve a working module worker," and a pass under either would not license a worker in production. If S1′ fails, the recorded finding is that a build step or relative-path rewrite is a prerequisite, not that a blob worker is an acceptable substitute.

**No spike may build a working worker collision path.** S7′, in **either** variant, is a stage-scoped measurement vertical with a stub result mapping: no worker-produced value ever enters a query, and it produces no result of record. Its entire correctness surface is §6.4's **stage-scoped validity rule**, which compares only the offloaded stage's own outputs over identical inputs. If B or C is reached, building the real path is the *next* milestone's work.

## 18. Cache architecture options (Required Decision 10)

| # | Option | Startup cost | Warm-query cost | Memory | Invalidation / eviction | Complexity |
|---|---|---|---|---|---|---|
| **C1** | Main-thread cache only; transfer/copy both operands' buffers **per pair** | none | one message pair per candidate — at R2's 1,978 candidates per source instance almost certainly fatal; **S6′ measures this topology's own per-message cost directly**, as explanatory evidence (§7.3's Verdict C) for why every B-class and C-class boundary's vertical is instead built as a one-way population rather than per-pair transfer — S6′'s figure is never itself a B/C discriminator | transient only | trivially correct | lowest |
| **C2** | Worker-owned cache; push welded geometry once per `(epoch, geometryIndex)`; the worker builds its own BVH | one transfer + one BVH build per distinct geometry (1,461 here) | none per pair | worker holds geometry + BVH + connectivity | keyed identically to `GeometryRegistry`; epoch release invalidates both by the same key | moderate |
| **C3** | Fully duplicated caches | as C2 | none per pair | ~2× the collision-world geometry footprint — a second full copy (welded buffers, BVH, connectivity) added on the worker side atop the one copy the main thread already holds (§2.5) | same key, same lifetime — coherent by construction | moderate |
| **C4** | Main thread builds; ships the **serialized** BVH | one transfer per geometry; **no second build** | none per pair | as C2/C3 | as C2 | moderate |
| **C5** | Per-worker caches in a pool | N× | none per pair | N× | N× fan-out | highest |

**Evaluation order:** C1 first (measure it — the only option with no memory cost) → C4 (reuses the main-thread build) → C2 (if S6′/S7′ show serialize+transfer is worse than rebuilding) → C3 only if a main-thread copy is genuinely required alongside a worker copy and C4/C2 cannot provide it → **C5 only on measured evidence of a single-worker bottleneck, and only once concurrent-usage expectations are specified** (§7.5.8), never by default.

C2 and C4 both need the main thread to *keep* the welded geometry (for the `'linear'` oracle and `anyComponentInside`'s direct buffer reads), so both imply **copying**, not transferring, and therefore duplication. Only a design abandoning the main-thread copy avoids duplication, and that breaks the oracle, which §14 forbids.

## 19. Correctness gates

### 19.1 Gates M4's own harness enforces

§6.4's canonical comparator is applied to every TLAS-vs-linear pair of runs, plus these case-specific gates:

| Gate | Proof |
|---|---|
| Same final pairs, provenance, distance, witness, statistics, diagnostics | §6.4's comparator in full. Provenance compared by strict `===` `Model` identity, never `modelId`. |
| Same `conclusive` / incomplete-result semantics | The precheck's `excluded` / `proceed` / `inconclusive` / `skip-precheck` distribution must match, and the incompleteness caveat must be computed identically. |
| Same deterministic aggregation | The dbId-level winner (minimum distance, `comparePlacedCanonically` tie-break) must select the same fragment pair, verified by comparing emitted **witness points**, not just the distance. |
| Same placement-change behavior (R6) | `P₁ ≠ P₀` in the specific pre-recorded way §5.2.1's transform was designed to produce, **identically under both broad phases**; a fresh placement read observed; and `P₀` recovered after step 5 restores the **captured** transform `T₀` and invalidates a second time. **`P₁ == P₀` is a failure.** The **TLAS-rebuild clause is arm-specific** (§5.2.1): on the `tlas` arm, `tlasBuilds` delta = 1 per invalidation; on the `linear` arm, `tlasBuilds` = 0 across every R6 query, since a linear call never reaches `_getTlasEntryForEpoch` (`CollisionWorld.js:1691`, `:1781`, `:2636`). ### 19.2 Adoption prerequisites for the implementation milestone (not M4 verdict conditions)

Because §17 forbids M4 from building a working worker collision path, these cannot be proven by M4 and are **not** conditions on a B or C verdict (§1.2). They are the gates the *next* milestone must clear before a worker path is adopted:

- the full §6.4 comparator satisfied between the synchronous oracle and the worker path, across the complete R-case and S-case matrix, with the `1e-9` distance relaxation reported as such;
- **full-query T-a / T-b1 / T-b2 / T-c sufficiency for the adopted boundary**, measured end to end on the real (non-stub) integrated worker path once one exists, across the verdict-bearing R-cases and states that failed the baseline. M4's S7′ evidence is **stage-scoped** (§17) and cannot establish this: reconstructing a hypothetical post-boundary configuration's real frame cadence and input latency requires the integrated path §17 forbids M4 from building. **T-a is on this list too**, and deliberately: §7.3 condition 3's screen is T-a-only, but it is also a *permissive no-boundary exclusion* screen that credits every stage movable under **any** §8.2 variant, so what M4 settles is T-a for the *union* of all variants, never T-a for the one boundary actually adopted. A B or C verdict therefore asserts that a boundary is *worth building and measuring end to end*, never that the post-boundary configuration has already been shown responsive. **This same measurement is also what resolves §7.5.9's *no-full-query-evidence* D cause.** Where M4 returned D because a verdict-bearing tuple's only failing metrics were T-b1, T-b2, and/or T-c — so §7.3 condition 4(b)'s T-a-anchored check had no defined application there and S7′'s stage-scoped evidence could not substitute — this end-to-end comparison on the real integrated path is where that question actually gets answered. It is named here as the resolution path for that D exactly as it is for parity, and it is reached whether the integrated path is built off a B/C verdict elsewhere in the matrix or as the follow-up work such a D itself names;
- lifecycle rejection across all eight §10.4 scenarios in the real path, not a stub;
- the same diagnostics multiset, including the inconclusive-cause field if it is ever promoted from the event channel into a public diagnostic;
- the same deterministic aggregation and placement-change behavior.

**The synchronous implementation remains the oracle throughout**, unless M4's evidence proves a specific defect in it — reported and dispositioned separately, never silently absorbed.

### 19.3 Verdict-reducer correctness (mandatory self-tests, not a benchmark correctness gate)

§7.3's evidence→verdict mapping — precedence, applicability, disposition (UNEVALUABLE / INSUFFICIENT / SUFFICIENT), and multi-tuple aggregation — is implementation code like any other, and neither §19.1's comparator nor a performance figure says anything about whether *that* code is correct: a reducer defect that reads UNEVALUABLE as INSUFFICIENT, applies a hard-maximum aggregation where a percentile one belongs, or silently misorders the mandatory-D/A/B/C precedence can still produce a well-formed report and exit `0`. **The harness must therefore ship the verdict reducer as a pure function over an evidence vector — never entangled with measurement or I/O — and run a fixed suite of synthetic evidence-vector fixtures against it before any real measurement is trusted.** These fixtures are unit tests of the reducer only; they never substitute for, weaken, or replace §19.1's benchmark correctness gates, and a fixture failure is a harness defect, fixed like any other bug, never reported as a performance or D finding.

**The fixture suite must include, at minimum, one synthetic evidence vector engineered to terminate in each of:**

- **Verdict A** — every verdict-bearing tuple passing every target;
- **Verdict B** — a tuple with exactly one applicable B-class boundary SUFFICIENT and every other §7.3/§7.5 condition satisfied;
- **Verdict C** — a warm-narrow-phase tuple with every applicable B-class boundary INSUFFICIENT and a named C-class boundary SUFFICIENT, including its mechanical-difference clause;
- **each of §7.5's ten mandatory-D causes individually, plus §1.1's *no-boundary* cause separately** — one fixture per named cause. The *no-boundary* cause is not itself one of §7.5's ten (§7.5's tenth, *no-settled-boundary*, is a distinct, separately-fixtured cause) — it is forced directly by §7.3 condition 3's screen failing at a T-a-failing tuple, so its dedicated fixture engineers a synthetic tuple where the boundary-independent `Rᵢ(all,τ)` screen fails, asserting the reducer reports the *no-boundary* D specifically and never conflates it with *no-full-query-evidence* or *no-settled-boundary* — so a reducer that conflates two D causes, or drops one, fails a fixture rather than shipping silently;
- **B-over-C precedence** — a tuple engineered so a B-class boundary is SUFFICIENT at the same tuple a C-class boundary would also satisfy, asserting the reducer reports **B**, never C and never both (§7.3's precedence rule);
- **no applicable boundary of either class SUFFICIENT** — asserting the tuple falls to D under §7.5.10, never silently to B or C;
- **mixed cold/warm and multi-tuple aggregation** — one fixture with a cold tuple settled by one B-class boundary and a separate warm tuple settled by a different B-class boundary (asserting the aggregate reports B, naming both), and one fixture where one of several otherwise-settled tuples has no boundary SUFFICIENT (asserting the aggregate reports D even though every other tuple is settled, per §7.3's multi-tuple rule);
- **every UNEVALUABLE path** — one fixture per UNEVALUABLE trigger this spec names: a missing §17 vertical for a B-class boundary, an unboundable derived-evidence package for a C-class boundary, and an unidentifiable delivery task under §6.2's correlation rule for `Hᵢ` — asserting UNEVALUABLE is never scored as INSUFFICIENT and never silently promoted to SUFFICIENT.

Each fixture is a **hand-constructed evidence vector**, not a real measured run — it exercises the reducer's branches directly, is checked into the harness alongside the gate, and runs before any measurement is trusted. **This is a design requirement on the implementation plan, not a benchmark result**: it constrains what the *next* milestone's harness code must ship, and it adds no new verdict condition, no new mandatory-D cause, and no change to §7.3's semantics or precedence.

- **I7 (Medium) — claimed mandatory-D inputs were not wired into §7.5.** *Verified.* *Fixed:* §7.5.8 now covers device/browser scope (applying to A, B, and C alike) and concurrency expectations (scoped to pool topologies, since a single-worker topology does not depend on them); §23's claim is restated to match exactly.

The review's four clarifying questions are answered inline: M4 delivers a *justification* verdict, not a binding adoption decision (§1.2); concurrent `findClashes` calls are supported today and §10.1 preserves that; approval of the target, device matrix, realistic selection size, and memory multipliers is required before a B/C verdict is binding and is enforced by §7.5.1/7.5.4/7.5.7/7.5.8; and R6 measures refresh cost **and** correctness after a real transform (§5.2.1).

No re-review was performed after applying these fixes, per this project's review-loop policy. The verdict below reflects this spec-writer's own judgement that the fixes resolve the findings as stated.

## 23. Final report

### Adopted workload matrix

Six **declared realistic scenarios** (R1–R6) and five **synthetic sweeps** (S1 density, S2 source-count × density × mode, S3 whole-model-scale, S4 pathological single pair, and **S2T** target-population — *partially* synthetic, and characterization-only). R1, R2, and R5 correspond exactly to what ships today and are verdict-bearing unconditionally; R3, R4, and R6 use a ~10-instance source and are verdict-bearing **only if that workload is product-confirmed**, otherwise they are synthetic and, if decision-driving, force D (§5.5). R6 applies a **real, reversible `setPlacementTransform`** before invalidating, because invalidation alone cannot change a verdict (§5.2.1), and is the **only** case with a third measured query — the post-invalidation `refresh` state, verdict-bearing like cold and warm (§6.1.4, §7.2). Source-instance count is a **controlled variable**: cohorts are built by an exactly-specified quantile-band algorithm over a Viewer-only proximity proxy touching no collision narrow phase, stratified on **per-instance `density`** rather than raw `proximity` (which would fold instance count back into the density factor), with band width, tie-break, forced-member replacement, and undersized-band behavior all fixed (§5.4); because the band widens with `k`, every level's **achieved** separation is measured and a level whose cohorts have converged is labelled `DENSITY_UNSTRATIFIED` and reported as a source-count-only arm rather than as three density contrasts. **Target population** is varied only by **S2T**, which holds the source and the exact local workload fixed under a mechanical level-to-level control rule and grows one existing target epoch with distant synthetic bystanders — supplying the `targetCount` factor of §14's claim that S2 structurally cannot, while establishing nothing about BLAS, welding, connectivity, or geometry-cache scaling (far bystanders never reach geometry resolution) and licensing no extrapolation to a larger real federation (§5.3.1, §5.7). Shipped ceilings — `maxClearanceNarrowPhasePairs` at ~10 dense instances, `maxBroadPhaseInstancePairs` at 183 source instances as a **per-target-epoch-group** cap against the 5,435-fragment Architecture group, and `maxCollisionInstancesPerEpoch` at 20,000, which S2T's top level fills exactly — are `CAPACITY_REJECTED` capability boundaries, never trimmed away and never a pass.

### Measurement protocol

`run-gate-m3.mjs`'s reviewed protocol extended by: **two runtime configurations**, with the representative **multi-process** one authoritative; **five counterbalanced repetitions** with both arm order and case order rotated on a recorded schedule; **one fresh world per `(runtime, case, broadPhase, repetition)`** with explicit cold/warm sequencing — plus R6's third, post-invalidation `refresh` query, the one declared exception (§6.1.4) — and per-query observer boundaries; and **three separately-obtained axes** (§6.2) — X-1 responsiveness from a **CDP main-thread task timeline** plus rAF cadence plus **trusted, externally-generated input** with Node-side dispatch timestamps and clock correlation; X-2 duty cycle from that same trace, never from library spans and never from Long Tasks; X-3 makespan with yields measured directly. Scheduler conformance survives as a separate, non-deciding metric taken across *all* checkpoint labels. Thirteen stages are attributed and each classified **main-only vs. transferable** (§6.3) — the gate's cheapest decisive output, produced before any worker spike.

### Decision thresholds

`frameBudgetMs = 8` and M1's **24.8 ms** ceiling are inherited and re-scoped as scheduler conformance. Because **no product-approved responsiveness target exists**, §7.2 declares a provisional one anchored to named conventions — T-a no main-thread task over 50 ms (Long Tasks), T-b1 p95 inter-frame ≤ 32 ms, T-b2 no inter-frame gap over 100 ms, T-c p95 input delay ≤ 100 ms (RAIL Response) — with the **aggregation unit fixed per threshold** (T-a and T-b2 hard maxima requiring 5/5; T-b1/T-c median-across-repetitions with a no-run-above-1.5× clause) and the **evaluation unit** fixed as `(runtime, case, broadPhase, state)` with every state independently verdict-bearing — cold and warm for every case, plus R6's third post-invalidation `refresh` query (§6.1.4, §7.2), reports makespan against Nielsen's 1 s flow limit and the accepted ~440–520 ms status quo, and makes target confirmation a mandatory-D prerequisite. **The one mechanical threshold a B or C verdict rests on is §7.3 condition 4(b)'s `Rᵢ(w,τ) + Hᵢ(w,τ) ≤ 50 ms`, evaluated per named boundary `w`** — `w`'s own per-repetition main-only residual, restricted to the stage(s) `w` owns (never condition 3's boundary-independent union, which serves only the *no-boundary* D screen), plus `w`'s own **boundary-attributable** added main-thread occupancy `Hᵢ(w,τ)`, evaluated as a hard maximum across all five repetitions, and **only at failing tuples where T-a is among the failing metrics**, since the formula is anchored to T-a's own 50 ms definition and `Rᵢ(w,τ)` exists only inside a failing window. A boundary owning more stages has a smaller residual — the mechanical channel through which a broader (C-class) boundary can be evaluated where a narrower (B-class) one sharing the same messaging shape could not (§7.3's Verdict C). `Hᵢ(w,τ)` is measured by summing, per CDP task, that task's intersection with `w`'s own harness-side sub-marks (snapshot/extra copy, serialization + `postMessage`) **plus, for the task correlated as the delivery task, that task's own interval up to the closing mark** (§6.2's correlation rule — receipt and structured-clone deserialization happen before `onmessage` runs and so cannot be bracketed by an in-handler sub-mark at all), taking the maximum such sum across tasks — never a whole-task filter, and never crediting anything past the closing mark — and explicitly excludes ambient Viewer/rAF/input tasks, which neither overlap a sub-mark nor are the delivery task. Each named boundary is **SUFFICIENT**, **INSUFFICIENT**, or **UNEVALUABLE** at a tuple (§7.3); an UNEVALUABLE boundary settles nothing. **S7′ is not subject to any improvement test:** §7.4.2's precommitted non-parametric effect rule is retained as a well-specified general method but **is invoked by no M4 verdict condition**, and is handed forward to §19.2's adoption-milestone end-to-end comparison, which is the paired comparison it actually fits. Memory budgets (1.0×/2.0×) are provisional and their confirmation is likewise a mandatory-D condition.

### Explicit M4 verdict categories

**A**, **B** (which must name a §8.2 **B-class** boundary), **C** (which must name a §8.2 **C-class** boundary), **D**. §1.2 fixes what B/C mean: *justification* verdicts authorizing the next milestone, not proofs of parity — parity is an adoption prerequisite (§19.2), which is what makes B and C reachable from bounded spike evidence at all. §7.3 maps evidence to verdict mechanically, in a **fixed precedence**: mandatory D first, then A, then B (any applicable B-class boundary SUFFICIENT), then C (only where every applicable B-class boundary is INSUFFICIENT and a named C-class boundary is SUFFICIENT), otherwise D — so B and C are mechanically **exclusive**, never a narrative tie-break. The gate is non-leading in both directions: **A** requires every verdict-bearing R-case to meet the target on the representative runtime under every executable arm, and migration difficulty is explicitly not evidence of adequacy.

**B** requires the baseline to *fail*, and at least one B-class boundary (**WB-1a**, **WB-1b**, **WB-2p**, **WB-3**) SUFFICIENT at the tuple — with S7′'s vertical selected to match it (§17, by a fixed median-across-repetitions, strict-winner aggregation with a named tie rule), and, on both the geometry and narrow-phase sides, a substage caveat: the geometry arm proves WB-1b unless worker-side BVH construction is isolated, and the precheck arm proves only **WB-2p**, so if the clearance-distance substage is the strict narrow-phase winner, **WB-3 is UNEVALUABLE** rather than a new vertical being invented, and if the exact-query substage wins or ties it, no **B-class** boundary is even named for it (C-class boundaries remain separately applicable and evaluable there) — the main-only remainder passing a **T-a-only**, boundary-**independent** screen (`Rᵢ(all,τ)`, §7.3 condition 3) whose per-task residual is the **longest contiguous** main-only interval, under a fixed transferable classification crediting every stage movable under *any* §8.2 variant, so a failure there excludes *every* boundary of either class — and **S7′'s stage-level feasibility/overhead evidence**, split cleanly: clause 4(a) is **report-only** stage cost, asserting **no improvement of any kind**, while clause 4(b)'s **`Rᵢ(w,τ) + Hᵢ(w,τ) ≤ 50 ms`**, evaluated **for the specific boundary `w`** using a boundary-**specific** residual restricted to `w`'s own owned stages, is the *entire* mechanical evidence for `w`'s own sufficiency. Plus the memory budget on the controlling metric (with no effect-rule carve-out for an over-budget proposal, §15.3), and the lifecycle and module-resolution prerequisites (the latter now a three-case S1′ rule, §7.3 condition 8).

**C** additionally requires: the failure located in the warm narrow phase; **every** applicable B-class boundary **INSUFFICIENT** (not merely UNEVALUABLE); a named C-class boundary (**WB-2** or **WB-4**) **SUFFICIENT**, evaluated by the identical `Rᵢ(w,τ) + Hᵢ(w,τ) ≤ 50 ms` check with `Hᵢ(w,τ)` conservatively bounded from existing S6′/S7′/§6.3 operands (never a new spike) or else UNEVALUABLE; and a named mechanical difference — the specific stage(s) or message/transfer cost the C-class boundary removes that the rejected B-class boundary did not. **S6′ is explanatory evidence only** (why a per-pair topology is disfavored, feeding the `Hᵢ` bound above) and is never itself C's discriminator — "C1 refuted by S6′" as a standalone clause is retired.

Because condition 3's screen is *permissive* and boundary-independent, a pass there is not a claim about any **named** boundary: full-query responsiveness sufficiency for the post-boundary configuration — **T-a as well as T-b1/T-b2/T-c** — is deliberately **not** an M4 verdict condition for either B or C, but an adoption prerequisite (§19.2), like full correctness parity. **D is mandatory** under **ten** enumerated conditions (§7.5). Three of those D outcomes are named findings rather than missing external inputs, and the report must never conflate them: the **no-boundary** D of §1.1, a decisive negative about the architecture forced when the boundary-independent screen fails at a T-a-failing tuple; the **no-full-query-evidence** D of §1.1 and §7.5.9, forced where a verdict-bearing tuple's *only* failing metrics are **T-b1/T-b2/T-c**, since condition 4(b)'s T-a-anchored check has no defined application there and S7′'s stage-scoped evidence cannot substitute; and the **no-settled-boundary** D of §7.5.10, forced where a tuple ends with no boundary of either class SUFFICIENT — whether because none is applicable there at all, an applicable one is UNEVALUABLE, or every applicable one is INSUFFICIENT — a finding about the evidence gathered for *specific* boundaries (or their absence), never about M4's method (§7.5.9's cause) or about the architecture generally (§1.1's cause). §19.2's end-to-end measurement on a real integrated path is where the first two are ultimately resolved. Ten loopholes are named (§7.6).

### Worker-boundary options considered

WB-0; **B-class**: **WB-1a** BVH construction alone (**~43 ms cold, zero warm** — not the 316 ms a naive reading suggests), **WB-1b** full geometry preparation via an extra-copy variant, **WB-2p** the Hard-Clash precheck alone (new — gives the narrow-phase B branch a boundary it is permitted to name against §17's precheck vertical), **WB-3** the clearance primitive alone (~11% of warm narrow phase); **C-class**: **WB-2** the whole narrow-phase pair evaluation (the dominant *warm* cost, viable only once every applicable B-class boundary is shown insufficient, §7.3), **WB-4** the whole query below extraction; **WB-5** extraction, **ruled out on structure**. Class is decided by scope of execution ownership, not by cache use — WB-2p and WB-3 need the same worker-resident data WB-2 needs, but each takes ownership of only one stage (§8.2, §8.3). §8.1 tabulates what can and cannot cross, including that `MeshBVH.serialize`/`deserialize` are real and ArrayBuffer-based, that `geometry.boundsTree` must be re-attached or `closestPointToGeometry` silently degrades, that transferring detaches the sender's buffer (so keeping the `'linear'` oracle forces copying and hence duplication), that a Viewer `Model` is structurally non-cloneable, that this app has **no bundler** and import maps do not reach a worker realm (§8.6, with blob/interception workarounds explicitly disallowed as substitutes), and that `SharedArrayBuffer` is unavailable without cross-origin isolation the app cannot trivially have (§8.7).

### Lifecycle / identity model

The main thread is the sole identity authority; the worker gets opaque numeric tokens only. **Request state is per-call** — a `Map<requestId, RequestState>` with independent settlement, because concurrent `findClashes` calls are an existing supported scenario the landed code explicitly handles (`CollisionWorld.js:2591-2599`), and a global "current in-flight id" would silently impose latest-call-wins and strand promises. §10.2 gives a complete settlement matrix (dispose, generation mismatch, eviction, armed-epoch placement change, malformed response, duplicate, worker crash/terminate, success) reproducing today's error set and precedence with **no unsettled promise under any condition**, and preserving the **path-specific** placement arming scope so linear callers' behavior is unchanged. §10.4 requires all eight scenarios proven at publication, including concurrent out-of-order responses and worker crash.

### Cancellation / progress feasibility requirements

Today's abort granularity is already one atomic unit, so a worker is parity, not regression; without shared memory a `postMessage` cannot preempt a synchronous traversal in the worker either. M4 decides whether a per-request cancellation token is needed at all, without pre-committing the result layer's policy, and adds no `AbortSignal` and no latest-call-wins. Termination-latency measurement is conditional on the chosen topology. Progress overhead is measured by S8′ — assigned to a named spike precisely because it needs a real worker — with no progress API or UI added. Whether current yielding keeps the UI responsive is **not established by any prior gate** and is answered by X-1.

### Cache / memory evaluation strategy

Five options (§18), cheapest-first, with C5 gated on both a measured single-worker bottleneck and specified concurrency expectations. Memory uses **two metrics**: a deterministic typed-buffer lower bound (Metric M, controlling) with per-record and per-instance sizes fixed as structural constants from the frozen shapes' declared fields (never from a heap delta, which would put a nondeterministic Metric H quantity inside the controlling metric), and a `--expose-gc`-protocol heap measurement (Metric H, cross-check), with worker heap measured separately and `measureUserAgentSpecificMemory()` recorded as unavailable. Pending-message bytes and abandoned caches are accounted explicitly. Budgets 1.0×/2.0×, provisional, with confirmation a mandatory-D condition; no effect-rule carve-out applies to an over-budget proposal — it simply fails §7.3 condition 6 and the outcome is D.

### Benchmark harness plan

One **standalone** `test/performance/run-gate-m4.mjs`; M1/M2/M3 byte-stable; **no shared helper module**. The harness may start its **own** express instance mounting `spike/m4/` alongside the production paths — which is how S1′ gets a same-origin served worker without touching `server.js`. Hard requirements: both runtimes (S2T on the representative multi-process one only, §5.6); five counterbalanced repetitions; fresh world per tuple, with S2T's tuple additionally carrying its population level; real fixture, with S4 the only *fully* synthetic case and S2T *partially* synthetic; summarized JSON with online aggregation and bounded top-N; `CAPACITY_REJECTED` with limit and observed value; loud failure on correctness while performance never fails the process; full provenance including cohort covariates, counterbalancing schedule, input-probe clock calibration, the trace clock-correlation offsets, and the structural per-object byte constants; and the main-only/transferable partition as a first-class section. Exactly six instrumentation additions are permitted and enumerated (§16.4) — yield latency, narrow-phase interior labels plus an additive inconclusive-cause enum, the two non-overlapping extraction/weld brackets, read-only memory accessors, one structured no-op diagnostic-event recorder with a bounded schema and retention rule, and one disabled-by-default S7′ stage-input capture hook — and nothing else.

### Required spikes

Eight, confined to `spike/m4/`, deleted at close unless adopted, and **ordered**: the main-only/transferable partition comes from the *gate* first. **S1′** module resolution and CSP in a worker realm, same-origin served, both runtimes, with blob/interception substitutes forbidden; **S3′** worker cold-start latency; **S4′** per-call stale-result rejection across eight publication-time scenarios; **S5′** (conditional) terminate latency and post-termination rebuild; **S6′** (conditional) per-message overhead including result volume; **S7′** (conditional on the baseline failing) the **batched vertical spike** at every failing R-case tuple **where T-a is among the failing metrics**, plus R1/R2 and the largest verdict-bearing workload as report-only overhead coverage, measured as a **stage-scoped paired comparison** — the named stage run synchronously through the library's ordinary cooperative checkpoint path versus the same stage run in the worker over identical inputs, with a stub result mapping downstream in both arms — so both arms cover like measured work. It yields exactly two things: **report-only stage cost/overhead** (occupancy figures and the arm's real elapsed bracket duration alike, §7.3 condition 4(a)), and the **boundary-attributable** `Hᵢ` that condition 4(b)'s `Rᵢ + Hᵢ ≤ 50 ms` check consumes, measured over harness-side sub-marks on the boundary's own main-thread chunks and excluding ambient tasks that run during the `await`. **S7′ is never asked to demonstrate an improvement, and §7.4.2's effect rule is applied to none of its evidence.** It yields **stage-level feasibility, cost, and overhead evidence only**; full-query T-a/T-b1/T-b2/T-c sufficiency for the *named, adopted* boundary is **not established by M4** and is an adoption prerequisite (§19.2), and a tuple failing only T-b1/T-b2/T-c has no S7′ evidence path at all (§7.5.9). **S8′** (same gate) progress-messaging overhead. A generic serialize→transfer→deserialize round-trip is deliberately *not* a spike. No spike may build a working worker collision path.

### Correctness gates

§6.4's single canonical comparator — pair set, bit-identical distance (with an explicitly-labelled `1e-9` relaxation for a worker arm only), scale-relative witness tolerance, six statistics fields, and a diagnostics multiset keyed on the complete public payload including `role` and every fragment's `(modelTag, dbId, fragId)` — plus case-specific gates for conclusive semantics, deterministic aggregation, and R6's placement-change behavior where `P₁ == P₀` is a failure. §19.2 separately records the adoption prerequisites the *implementation* milestone must clear, which M4 structurally cannot.

### Remaining open questions

1. **Is the provisional responsiveness target (§7.2) acceptable as the decision criterion?** A product decision. Until confirmed, §7.5.1 makes **D mandatory** — the single most important blocker.
2. **What is the ~1.4 s of unattributed cold cost?** (§3.1, §6.3). If it is `getRenderProxy`/`adaptViewerGeometry`, it is a permanent main-thread floor capping every worker option. Answered by §16.4.3 plus a gate run.
3. **Is a ~10-element selection a real workload?** (§5.5). Nothing in the repository establishes it; the shipped UI gates on one dbId. Determines whether R3/R4/R6 are verdict-bearing or force D.
4. **What production device classes and browsers must the target hold on?** (§7.5.8). A target met only on the development machine is not a met target — this binds A as much as B or C.
5. **Are concurrent `findClashes` calls an expected usage pattern?** They are demonstrably *supported* (which §10.1 preserves), but their expected frequency is unspecified and gates any pool topology (§7.5.8, §18's C5).

Answerable only at levels where the cohorts are actually separated: a level §5.4 labels `DENSITY_UNSTRATIFIED` — which `k ≈ 183` is, by construction — yields one source-count arm rather than three density contrasts, and the question is answered for that level only in those terms.

### Which of the four outcomes does this spec land on?

**None, deliberately.** M4's verdict is an output of running the gate. Two provisional readings are recorded, clearly marked as such:

- **On current evidence the defensible provisional outcome is D** — because the decisive measurements are missing (no responsiveness measurement of any kind exists; the precheck's duration is inferred and its inconclusive causes are collapsed into one; ~1.4 s of cold cost is unattributed; every archived number comes from a `--single-process` runtime and a single source instance; and no responsiveness target, device matrix, or realistic-selection-size decision exists) — **not** because worker migration looks difficult. §7.5 turns each gap into a mandatory-D condition rather than a judgement call.
- **The framing that motivated this milestone is probably not where the decision turns.** The "6.1–6.5 ms against 8 ms" story concerns a primitive accounting for ~11% of warm narrow-phase cost, measured on the wrong metric (the worst *bracketed* span in the same runs was 12.2 ms) in a non-representative runtime, and it is a *scheduler-conformance* question, not a responsiveness one.
- **A second, distinct route to D is now explicit, and is expected to be live.** §3.1's carried-forward spans — a largest checkpoint-bracketed span of 12.2 ms cold and 6.0 ms warm, with *zero* distance-query samples over `frameBudgetMs` — make a **T-a** failure unlikely and a **T-b1/T-b2/T-c-only** failure the expected shape. That shape is exactly §7.5.9's *no-full-query-evidence* cause: M4's one mechanical B/C threshold is anchored to T-a's 50 ms definition and has no defined application where T-a passes, and S7′'s stage-scoped evidence cannot substitute. **Verdict C is the most exposed**, since C's defining failure is in the warm narrow phase, which §3.1 shows is composed entirely of sub-8 ms units — so on current evidence C is more likely to be foreclosed by this cause than to be reached. **That is the honest, intended behavior, not a defect**: it says M4's permitted evidence cannot resolve that failure mode, **not** that a worker would not help, and it names §19.2's end-to-end measurement on a real integrated path as where the question is answered. No condition elsewhere in §7.3 is loosened to compensate.

**Verdict: ready for implementation planning.**

The gate is fully specified: realistic scenarios separated from synthetic sweeps with a deterministic cohort algorithm and an explicit workload-validity condition; a protocol with two runtimes, counterbalanced repetitions, fresh-world identity, and three separately-obtained axes using measurement mechanisms that actually work; a mandatory main-only/transferable partition; inherited conventions re-scoped correctly plus a precommitted target with fixed aggregation units, and a single mechanical per-boundary threshold (`Rᵢ(w,τ) + Hᵢ(w,τ) ≤ 50 ms`, scoped to T-a-failing tuples, evaluated separately for every named §8.2 boundary) with no improvement test on stage-scoped evidence anywhere; a B/C classification (§8.2) that makes the two mechanically exclusive by construction; a mechanical evidence→verdict mapping with symmetric anti-bias rules, **ten** mandatory-D conditions — including the *no-full-query-evidence* cause that makes M4's own evidence-scope limit an explicit, named verdict rather than a silent gap, and the *no-settled-boundary* cause that does the same for an UNEVALUABLE or INSUFFICIENT boundary — and ten named loopholes; a corrected worker-boundary analysis with its structural blockers identified; a per-call lifecycle model preserving both concurrent-call independence and path-specific placement arming, with a complete settlement matrix; cancellation and progress requirements that add no API; a two-metric memory strategy with explicit equations and a GC protocol; a standalone harness plan with a closed six-item instrumentation list including one bounded structured event channel and one disabled-by-default, bounded stage-input capture hook for S7′; eight ordered and conditionally-gated spikes; and a single canonical correctness comparator with adoption prerequisites separated from verdict conditions.

Of the nine open questions, four are measurements this harness produces or spikes it specifies. The other five are **external inputs**, each explicitly wired into §7.5 as a mandatory-D condition — so a missing input produces a correct verdict of D rather than an unsound verdict of A, B, or C. An M4 implementation plan can be written directly from this document, and the gate it describes cannot silently reach a conclusion it has not earned.
