## Review findings

The milestone is directionally aligned with the idea, but I would not approve it for implementation until the four P1 issues are resolved.

1. **[P1] Room discovery runs before a model exists and is then cached forever.**
   The spec resolves room dbIds during extension `load()` and caches them for the extension lifetime ([spec:155](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/superpowers/specs/2026-08-06-collision-library-milestone1-design.md:155)). In this app, extensions start with the Viewer ([viewer.js:18](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/wwwroot/viewer.js:18)), while the model is loaded only after later user interaction ([main.js:60](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/wwwroot/main.js:60)). The referenced original extension avoids this by awaiting `viewer.waitForLoadDone()` before building its cache ([original gist](https://gist.github.com/yiskang/c568db634e48c917d258716982eb89ba)). Defer discovery until the model/object tree is ready or the first query, key the cache by model, and invalidate it on model changes.

2. **[P1] The proposed containment test is not a valid `volume-overlap` predicate.**
   After finding no surface intersection, it tests only the element’s bounding-box center against the room ([spec:137](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/superpowers/specs/2026-08-06-collision-library-milestone1-design.md:137)). This is neither symmetric nor guaranteed to sample the element’s volume. It misses a target completely contained off-center inside the source, and can falsely report overlap when the bbox center is inside the target but the source solid is not—for example, a torus surrounding a small target at its center. This contradicts the idea’s symmetric closed-solid definition ([idea:1061](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/ideas/aps-viewer-clash-detection-library-idea.md:1061)). Use geometry-derived sample points and test containment in both directions, accounting for disconnected components, or narrow the API to explicit `source-contained-by-target` semantics.

3. **[P1] Surface contact is incorrectly promoted to positive-volume overlap.**
   Step 1 says any `intersectsGeometry` result means volume overlap ([spec:139](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/superpowers/specs/2026-08-06-collision-library-milestone1-design.md:139)). That API supplies a Boolean mesh-surface intersection; it does not classify proper crossing versus face, edge, or vertex contact ([upstream API](https://github.com/gkjohnson/three-mesh-bvh/blob/master/API.md#intersectsgeometry)). The idea distinguishes overlap from touching and explicitly leaves coplanar semantics to be decided ([idea:1084](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/ideas/aps-viewer-clash-detection-library-idea.md:1084), [idea:1709](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/ideas/aps-viewer-clash-detection-library-idea.md:1709)). Define expected results for face-face, edge-edge, vertex-face, and coplanar contact before using this mode.

4. **[P1] Primitive ranges from the idea’s normalized geometry contract disappeared.**
   The adapter description covers position and index sources but not `drawRange`, legacy `offsets`, groups, or `baseVertex` ([spec:116](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/superpowers/specs/2026-08-06-collision-library-milestone1-design.md:116)). The idea explicitly requires normalized triangle ranges ([idea:198](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/ideas/aps-viewer-clash-detection-library-idea.md:198), [idea:266](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/ideas/aps-viewer-clash-detection-library-idea.md:266)). `MeshBVH` only excludes out-of-range triangles when the private geometry is configured with the correct draw range/groups ([upstream API](https://github.com/gkjohnson/three-mesh-bvh/blob/master/API.md#meshbvh)). Otherwise unused or incorrectly based indices can create false clashes. Add exact normalization rules and fixtures for all three range mechanisms.

5. **[P2] The API appears to allow cross-model queries without defining a shared coordinate convention.**
   `findClashes` accepts independent source and target models ([spec:160](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/superpowers/specs/2026-08-06-collision-library-milestone1-design.md:160)), but the design does not specify how placement transforms, global offsets, units, or large coordinates enter `matrixWorld` and the relative matrix. The idea explicitly requires this decision ([idea:1130](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/ideas/aps-viewer-clash-detection-library-idea.md:1130)). Either reject cross-model pairs in Milestone 1 or define and test canonical Viewer-world normalization.

6. **[P2] `ClashResult` and incomplete-geometry behavior are inconsistent.**
   The spec says it reuses the idea’s types ([spec:202](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/superpowers/specs/2026-08-06-collision-library-milestone1-design.md:202)), where `statistics` is required ([idea:1261](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/ideas/aps-viewer-clash-detection-library-idea.md:1261)), but the empty case returns only `{ pairs: [] }` ([spec:213](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/superpowers/specs/2026-08-06-collision-library-milestone1-design.md:213)). Additionally, unsupported fragments are silently skipped except for a console warning ([spec:207](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/superpowers/specs/2026-08-06-collision-library-milestone1-design.md:207)), making an incomplete result indistinguishable from a verified no-clash result. Require zeroed statistics plus structured skipped-fragment diagnostics, or fail according to an explicit strictness policy.

7. **[P2] Lazy BLAS construction does not address main-thread stalls.**
   The spec deduplicates builds with promises but provides no incremental scheduling ([spec:130](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/superpowers/specs/2026-08-06-collision-library-milestone1-design.md:130)). A promise does not make the synchronous `MeshBVH` constructor non-blocking, so the first context-menu query may build several room BLASes while freezing the Viewer. The idea recommends incremental main-thread construction for its first version ([idea:1033](/Users/kangea/Documents/Workspace/Codes/aps-viewer-clash-detection/docs/ideas/aps-viewer-clash-detection-library-idea.md:1033)). At minimum, schedule between BLAS builds and specify an accepted per-geometry blocking limit.

The deliberate scope reductions—linear broad phase, no workers, no persistence, and no clearance/touching modes—are clearly declared and reasonable for this room-locator milestone. Runtime isolation, model-local deduplication, cloned indices, lazy caching, and fragment-to-dbId aggregation all align well with the idea.
