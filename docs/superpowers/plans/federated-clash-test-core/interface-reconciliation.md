# Cross-phase interface reconciliation — Federated Clash Test core engine

> **Role:** this file is the authority for every cross-phase name in the nine-file implementation plan. It records, for each name, the producing phase's declaration, every consumer's divergent assumption, the decision, and the exact edit applied to the phase files. It also records the duplicate-ownership decisions, a merged spec-issues register, and the items that still need a human/controller decision.
>
> **Governing documents.** Master plan: [`../2026-09-20-federated-clash-test-core-engine-implementation.md`](../2026-09-20-federated-clash-test-core-engine-implementation.md). Spec (frozen): [`../../specs/2026-09-20-federated-clash-test-and-results-design.md`](../../specs/2026-09-20-federated-clash-test-and-results-design.md). Convergence authority: [`../../../reviews/2026-09-20-federated-clash-test-and-results-convergence-review.md`](../../../reviews/2026-09-20-federated-clash-test-and-results-convergence-review.md).
>
> **Standing rules applied.**
> 1. **Producer wins.** Master §2.1 rule 1: the owning phase's *Phase interface summary* is the contract. A consumer's `Assumed` / `Consumes` block that disagrees is the thing that changes — unless the producer is demonstrably wrong or silent (three cases below: **N11**, **N12**, **N19**).
> 2. **The spec is frozen and was NOT edited by this pass**, not even for a genuine correctness contradiction. Where one existed it was marked *PROPOSED SPEC ERRATUM*, always paired with the plan-level workaround that lets implementation proceed meanwhile. No implementation detail is added to the spec, and no full-spec review is started. **All eight such entries were subsequently owner-authorized (2026-09-21) and are APPLIED as spec errata rows A1–A8, joined the same day by a ninth, **A9** (the OPEN-2 `rootOwners`/`cls` schema gap) — see §(iii); none is still proposed.**
> 3. **No tested behavior is deleted.** Wherever a duplicate implementation was removed, the surviving owner's test suite was checked and, where it did not already cover the behavior, the behavior was explicitly moved into the surviving owner's verification list.
> 4. **Markdown only.** No production code, nothing under `clashtest/` or `test/`, no commit.

**Scope:** master + P0…P8 (10 files). **Rows reconciled:** 34 cross-phase names (N1–N34) + 4 duplicate-ownership decisions (D1–D4) + 44 spec-register entries. **Edits applied:** 41 surgical `Edit` calls across 9 files (master 7, P1 6, P2 4, P3 5, P4 3, P5 5, P6 6, P7 8, P8 8). Row ids are the citation keys used inside the phase files.

Four places where two or three phases each planned to implement the same rule. Master §2.1 rule 1 permits exactly one owner per module; a *normative* rule implemented twice is the failure mode §16.3.4's invariant **I-scope** and AC-20(c) exist to prevent.

### D1 — The scope-bracket algorithm: P4.8 vs. P6.6 vs. P3 `materializeUnit`

**The collision.** Three phases each claimed a piece, and two claimed the *same* piece:

- **P3** `materializeUnit(plan, unit).scopeExpect` builds the bracket expectation including the **R20-1** rule (a `kind:'model'` source must bracket its whole population *and* its root subtrees), and `compareScopeExpectation` compares one expectation against one observation.
- **P6.6** planned its **own** `buildScopeExpect(plan, unit)` over `plan.modelsByKey[…].scopeDigests` — re-deriving R20-1 — plus `checkScopeBracket`, both in `run/freshness.js`. P6's open item O2 and P3's open item 5 each independently flagged this as a drift hazard.
- **P4.8** planned to implement "lease gate + bracketed scope digests" itself inside `LocalUnitExecutor` — a **third** copy of the comparison.
- P6's O2 proposed that P4 import both functions from `run/freshness.js`. **That fix is not available:** it makes `execution/` import `run/`, while the master's graph has **P6 depending on P4**. The cycle would block P4 — and the master's "P3 ∥ P4" parallelization — on all of P6.

**ONE owner chosen,** split by what each layer actually knows, so that no sentence of §7.1 or §16.3.2 is contradicted:

| Piece | Owner | Why |
|---|---|---|
| The **expectation**, incl. R20-1 | **P3** `planning/planner.js` :: `materializeUnit(...).scopeExpect` | The planner is the only place that knows a model's selection kind and its planning-time digests. It already produced it. |
| The **comparator** | **P3** `planning/scopeDigest.js` :: `compareScopeExpectation` | Already there. |
| The **re-digest-and-compare half** (`checkScopeBracket`) | **P3** `planning/scopeDigest.js` — **moved here from P6** | Both P4 (per unit) and P6 (read time) need it, and P3 is the only phase both already depend on. It lives beside the comparator it folds. |
| The **per-unit execution** of the bracket (when to call, pre/post, outcome mapping) | **P4** `execution/LocalUnitExecutor.js` (Task P4.8) | §7.1: "the *executor* … runs the pre/post scope-digest checks". It holds the live bindings and lease state at call time. |
| The **read-time** bracket (`getFreshness`) and the run-level consequences of drift | **P6** `run/freshness.js` (Tasks P6.6, P6.7) | §16.3.2, stated in the run's voice: "the engine". |

**Consumers' required change.**
- **P6.6** loses `buildScopeExpect` and `checkScopeBracket` entirely; it consumes `materializeUnit(plan, unit).scopeExpect` and imports `checkScopeBracket` from `planning/scopeDigest.js`. What stays P6's: drift → §16.7 fact mapping (`scope-drift` / `scope-unverifiable`), discarding a drifted unit's results and diagnostics rather than merging them, writing `scopeProof` onto the ledger `UnitRecord`, and placement-change invalidation.
- **P4.8** calls `checkScopeBracket` twice (pre and post) and maps the answers onto `scopeProof` / `failure.code` / `failure.modelKeys`. It implements **no** comparison and builds **no** expectation.
- **P3** gains `checkScopeBracket` in Task P3.2.

**Test safety — no behavior lost.** P6's `run/scopeBracket.test.mjs` held four pure-function cases; all four were **relocated, not deleted**. The `checkScopeBracket` fold cases went to `test/clashtest/planning/scopeDigest.test.mjs`: unchanged root subtrees with a moved population ⇒ `drift` naming the model; `unverifiable` absorbing over `equal` while `drift` dominates both; the all-equal `equal` path; and **grow-and-revert between pre- and post-check still caught**, because both sides compare against the *planning-time* expectation rather than against each other. The three R20-1 `buildScopeExpect` cases went to `test/clashtest/planning/planner.test.mjs`: a `kind:'model'` source emits **both** a roots entry and a population entry; an explicit-list source emits **no** population entry; the list is canonically ordered. Both relocations are written into P3's *Verification / acceptance* list. P6 keeps a run-level suite over the same inputs.

### D2 — The lease gate: executor vs. engine

**The collision.** §7.4 says "the **engine** `admitModel`s every bound model … Before every unit it checks `world.isLeaseValid(lease)`"; §7.1's division-of-responsibility paragraph says "the **executor** … checks leases (§7.4)". P4 put the per-unit check in the executor and flagged it. **P1's cross-phase note independently told P6 to do it.** Two phase files therefore instructed two different components to own one gate — and the likely outcome of leaving it is that *both* implement it, or neither does.

**ONE owner chosen.** **P4's `LocalUnitExecutor`** owns the **per-unit** `world.isLeaseValid(binding.lease)` pre-check: it is the only component holding the live bindings at call time, and §7.1 is the more specific statement. **P6** owns the **run-start `admitModel` sweep** and the run-level `model-evicted` settlement fact.

**Consumers' required change.** P1's cross-phase note corrected — it no longer assigns the check to P6. P6 does **not** re-check leases per unit. P4.8's *Interfaces* block states the ownership explicitly so an implementer reading only P4 sees it.

### D3 — Diagnostic aggregation: P4.9 vs. P5

**The collision.** P4.9 implements `createDiagnosticAggregator` (cross-unit de-duplication, exact accounting, `countsByReason`, `omittedReasonOccurrences`). P5's `deriveRunOutcome` takes `diagnostics` as an input and derives `integrity` from the upper bound, and P5's text references `createDiagnosticAggregator` too. P6 assumed a third, non-existent free-function API (**N20**). The risk was P5 growing its own aggregation to fill the gap P6's phantom API left.

**ONE owner chosen.** **P4 `execution/diagnostics.js`** owns both diagnostic DTOs and *all* aggregation — exactly master §2.1 rule 3 ("two diagnostic DTOs … a projection→aggregation function is the only bridge"). This also absorbs P4's own finding that `maxDistinctReasons` / `omittedReasonOccurrences` must live in the **engine-side aggregator**, not in the closed `UnitOutcome` (register **S-P4-1**). **P5 consumes a finished `DiagnosticsSummary` and aggregates nothing.**

**Consumers' required change.** **P6** drives it: one aggregator per run, `await addUnit(unitId, outcome)` per settled unit, merge the returned `unitTaints` into that unit's ledger record, `snapshot()` once at seal, and inject the `admit(n)` budget oracle built over P3's ledger (**N9**). P6's `RunSpec` pair `aggregateDiagnostics`/`readDiagnostics` collapses to one `diagnosticAggregator`. P5 unchanged.

### D4 — `getPairStatus` / `getElementStatus`: P5 vs. P8

**The collision.** P5 owns `results/status.js` (`getPairStatus`, `getElementStatus`, the normative §12.5 taint rule) and flagged it as an addition to the master map. **P8 independently planned the same two functions plus `createStatusReader` / `buildStatusReaderSteps` in `derive/status.js`, and the sealed-ledger layout reader `readLedger` in `derive/ledgerReader.js`** — a full second implementation of a normative rule that feeds the §8.3 claim predicate. P7's `index.js` re-export list named the two functions without saying which module they came from.

**ONE owner chosen: P5 `clashtest/results/status.js`**, for all five names, because:
1. **P5 pins the sealed ledger's JSON shape** — its `Ledger` / `UnitRecord` typedefs are what `validateResultSet` is written against. The layout and its only reader belong together; P8's `readLedger` would be a second reader of a schema it does not own.
2. The §12.5 taint rule is **normative input to the §8.3 claim predicate**. Two copies is precisely the drift AC-20(c) exists to catch.
3. **P8 is deferrable** (master §1.2; the DoD does not require it) while **AC-17 and AC-20(c) are core acceptance criteria**. A core criterion cannot be satisfied by a module living in a deferrable phase.

**Consumers' required change.** P8 creates **neither** `derive/status.js` nor `derive/ledgerReader.js`. Task P8.1 keeps only its two local fixture builders (deliberately independent of P5 sealing) plus a thin consumer test; `groupBy`/`filter`/`summarize`/`compare` consume P5's `createStatusReader`/`buildStatusReaderSteps`/`readLedger`; Task P8.8 re-exports `getPairStatus`/`getElementStatus` from `derive/index.js` as **re-export lines, not a module**. P7's `index.js` row now names P5 as the source.

**Test safety — no behavior lost.** P5's Task P5.6 and `test/clashtest/results/status.test.mjs` already cover the seven taint-rule clauses, `not-required` for hierarchy-internal and unreachable-only owners, and `undetermined` for a foreign owner. **Two behaviors P8 had pinned and P5 had not were explicitly moved into P5's Gates item 5** so they survive the move: (a) **`required: null` for an `undetermined` pair** — §12.5 declares `required: boolean` and defines no value for `undetermined`, so the reading must be pinned somewhere; (b) **hierarchy-internal detection from the root tables rather than from the bounded first-20 `hierarchyInternal.examples`**, which would otherwise silently under-report element-level caveats. P8's `status.test.mjs` becomes `status.consumer.test.mjs` (import path and shape only). P5 also absorbed P4's handed-over taint-rule-1 resolution as Gates item 6 (register **S-P4-4**).

### OPEN-1 — Does `startRun` throw or reject? (the other half of S-P7-1)

P7 resolved **`rerun`** in favor of rejecting (§18 R21-1 / §13.6 R19-1 / AC-11 over §15.3's "throws"). But **`startRun` returns a `RunHandle`, not a Promise**, so it *must* throw synchronously — and P7's own interface summary, P2's `classifyStartRunArgument` and P5's synchronous `ResultCapacityError` all depend on that. §13.6's "Uniform entry rules (R19-1)" is written generally enough to be read as covering `startRun` too, which would be unimplementable without changing `startRun`'s return type. **This plan assumes R19-1 applies only to Promise-returning entry points.** If the controller reads R19-1 as universal, `startRun`'s signature changes and Tasks P7.4, P2.1 and P5.8 move with it.
**Blocks:** nothing before P7.4. **Recommended:** confirm the narrow reading — it is the only one consistent with §18's own `startRun` sketch.
**CONFIRMED by the milestone owner 2026-09-21 (Option A) — no longer open.** `startRun` stays **synchronous**: it returns a `RunHandle` or **throws synchronously**. Every Promise-returning API, **`rerun` included**, **rejects**. Recorded on master §6 G-PLAN line (c) and in master §8's OPEN-1 row; the companion spec fix for `rerun` is erratum **A8** (register **S-P7-1**). Tasks P7.4, P2.1 and P5.8 are unchanged.

### OPEN-2 — The per-root class marker (`cls`) in the sealed ledger

P8's `getElementStatus` needs, per root, whether that root is in `A ∩ B` (class `C`), to detect hierarchy-internal elements. P8 assumed `ledger.rootTables[].cls`. **P5's pinned `Ledger` shape has `rootOwners: [{modelKey, owners:[{rootDbId, ownerDbIds}]}]` with no class marker**, and P3 carries the class only in the run-scoped, non-durable `tables`. Three options: **(a)** P5 adds `cls` to the persisted `rootOwners` rows — **it is digested, so this changes the ledger digest and is a real schema decision, not an implementation detail**; **(b)** P3 emits a separate persisted class index; **(c)** P8 falls back to the bounded first-20 `hierarchyInternal.examples`, which **under-reports element-level caveats** (the run-level claim block is unaffected, since it reads the `hierarchyInternal` table's non-emptiness, not its examples).
**Originally planned:** (c), with the limitation recorded in P8's implementer item 7 and in P8's ledger-layout note.
**Blocks:** only the completeness of P8's element-level caveats. P8 is deferrable and AC-20(c)'s run-level half is unaffected. **Needed:** a ruling on whether an under-reporting element view is acceptable, or whether the digested schema should carry the marker.
**CONFIRMED by the milestone owner 2026-09-21 (Option A = option (a)) — no longer open.** `cls` is **persisted and digested on each sealed-ledger `rootOwners` row**: P3 emits it (D9), P5 pins, validates (`root-cls-invalid`) and digests it, P8 reads it only through P5's `readLedger` (D4).
